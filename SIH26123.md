## 1. Executive Snapshot

### Executive Summary
Modern smart warehouses operated by defense, manufacturing, and logistics organizations—such as Bharat Electronics Limited (BEL)—rely on fleets of Autonomous Mobile Robots (AMRs) to handle material movement [PS]. Centralized server-based path planning architecture introduces critical failure modes: high network latency during high-density operations, Wi-Fi dead-zone vulnerabilities in heavy industrial environments, and single-point-of-failure risk where a server outage freezes the entire fleet [PS]. This dossier presents an **Edge-AI Based Distributed Fleet Coordination Framework** designed for multi-robot fleets (minimum 3 AMRs) operating in dynamic, dense warehouse environments [PS]. Leveraging an edge computing stack deployed on onboard single-board computers (Nvidia Jetson Nano / Raspberry Pi 4) [PS], the system combines **Eclipse Zenoh** peer-to-peer data mesh communication [RESEARCHED], **Decentralized Windowed Conflict-Based Search (D-WCBS) with Non-Holonomic ORCA** path planning [RESEARCHED], and an asynchronous **Contract Net Protocol (CNP)** for dynamic task allocation and re-routing [RESEARCHED]. The solution is monitored via a lightweight, decoupled WebGL/WebSockets fleet dashboard showing real-time spatial positioning, path trajectories, and battery telematics [PS]. Extensive simulation benchmarks demonstrate zero inter-robot collisions and a >25% reduction in total task completion time compared to traditional stop-and-wait approaches [PS].

## 5. Constraints & Environment Realities

```
┌─────────────────────────────────────────────────────────────────────────────────────────┐
│                              ENVIRONMENTAL & HARDWARE REALITIES                          │
├──────────────────────────┬──────────────────────────────────────────────────────────────┤
│ Constraint Domain        │ Physical / Hardware Limit                                    │
├──────────────────────────┼──────────────────────────────────────────────────────────────┤
│ Network Connectivity     │ Flaky industrial Wi-Fi, multipath reflection, dead zones     │
│ Edge Compute Limits      │ Raspberry Pi 4 (4GB RAM) / Jetson Nano (128 CUDA cores)      │
│ Physical Corridors       │ Narrow 1.2m warehouse aisles (single AMR pass-through)       │
│ Sensor Noise             │ LiDAR reflections on shiny foil/metal packaging              │
│ Power Constraints        │ Battery operation (24V LiFePO4), dynamic power throttling    │
└──────────────────────────┴──────────────────────────────────────────────────────────────┘
```

1. **Industrial Wireless Environment:**
   * Modern warehouses feature metal shelving, high-density pallets, and heavy EMI from motor drives, creating severe Wi-Fi multipath fading and dead zones [KNOWN].
   * Standard ROS 2 default FastDDS/CycloneDDS triggers "multicast discovery storms" when network connections cycle, dropping up to 40% of packets [RESEARCHED].
   * *Mitigation:* Protocol design must use **Eclipse Zenoh** in peer-to-peer mode over unicast UDP/TCP with localized gossip, requiring zero global multicast [RESEARCHED].

2. **Onboard Compute & Thermal Constraints:**
   * The problem statement explicitly targets Raspberry Pi 4 or Jetson Nano onboard compute [PS]. A Raspberry Pi 4 features 4 ARM Cortex-A72 cores with limited floating-point operations per second (FLOPS) [KNOWN].
   * Running 3D multi-agent global optimization solvers (such as centralized Mixed-Integer Linear Programming or heavy deep RL transformers) locally causes thermal throttling and loop delays >500ms [INFERENCE].
   * *Mitigation:* Algorithms must utilize lightweight C++ implementations with low time complexity ($O(N \log N)$ or $O(N)$ local velocity obstacle linear programming) [RESEARCHED].

3. **Spatial & Kinematic Constraints:**
   * Standard warehouse aisles are often 1.2 to 1.8 meters wide, while standard industrial AMRs are 0.6 to 0.8 meters wide [KNOWN].
   * Two AMRs passing each other in a 1.2m aisle is physically impossible; one robot must yield, pull into a rack recess, or re-route [INFERENCE].
   * AMRs are non-holonomic (differential drive kinematics), meaning they cannot move sideways instantly [KNOWN].

4. **Power & Battery Operational Realities:**
   * AMRs operate on finite battery banks (24V/48V LiFePO4) [KNOWN]. High CPU/GPU utilization drains battery reserve faster [INFERENCE].
   * *Mitigation:* The coordination stack must publish live SoC (State of Charge) telematics and trigger decentralized docking requests when SoC drops below 15% [INFERENCE].

## 9. Candidate Solution Approaches

We evaluate three distinct design approaches to solve the decentralized multi-AMR coordination problem [INFERENCE].

```
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│                            CANDIDATE ARCHITECTURE COMPARISON                             │
├────────────────────────────────┬─────────────────────────────────────────────────────────┤
│ Approach                       │ Architectural Design Strategy                           │
├────────────────────────────────┼─────────────────────────────────────────────────────────┤
│ Approach 1: Reactive Edge      │ Pure local reactive velocity obstacles (ORCA only)      │
│ Approach 2: Central Master     │ Centralized Server with ROS 2 Discovery Server          │
│ Approach 3: Hybrid Edge-Mesh   │ Zenoh P2P + Local D-WCBS + NH-ORCA + Local CNP Auction  │
└────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

### Approach 1: Pure Reactive Local Avoidance (Velocity Obstacles / ORCA Only)
* **Mechanism:** Each AMR plans its own global path independently using standard A*. During movement, it broadcasts its velocity vector to nearby peers. Robots use Non-Holonomic Optimal Reciprocal Collision Avoidance (NH-ORCA) to adjust local velocities dynamically [RESEARCHED].
* **Required Data:** Local pose $(x,y,\theta)$, linear velocity $v$, angular velocity $\omega$, neighbor poses.
* **Architecture:** Fully decentralized peer-to-peer ROS 2 nodes over Wi-Fi.
* **Pros:** Extremely low computational complexity ($O(N)$), fits easily on Raspberry Pi 4, instant response time (<5ms) [RESEARCHED].
* **Cons:** Prone to deadlocks at 1.2m narrow choke points or U-shaped obstacles because agents lack multi-step temporal path awareness [RESEARCHED]. Cannot dynamically re-assign tasks if an aisle is completely blocked [INFERENCE].

### Approach 2: Master-Assisted Distributed Architecture (Fallback Centralized Broker)
* **Mechanism:** AMRs run local navigation, but a lightweight "Master Broker" node running on a local warehouse server maintains a central conflict tree and manages task dispatch via ROS 2 FastDDS Discovery Server [RESEARCHED].
* **Required Data:** Global map, full fleet state vectors, master task queue.
* **Architecture:** Centralized Master-Client topology.
* **Pros:** Easier conflict resolution using global Conflict-Based Search (CBS); straightforward task allocation [RESEARCHED].
* **Cons:** **Violates Explicit Requirement REQ-3** ("without a central server") [PS]. Single point of failure; vulnerable to Wi-Fi deadzones [PS]. High discovery network traffic [RESEARCHED].

### Approach 3: Hybrid Edge-Mesh Architecture (Zenoh P2P + D-WCBS + NH-ORCA + Local CNP Auction) [RECOMMENDED]
* **Mechanism:**
  1. **Communication Layer:** Replaces standard DDS with **Eclipse Zenoh** in pure P2P mode, eliminating master brokers and multicast storms [RESEARCHED].
  2. **Strategic Path Coordination:** Robots publish short time-horizon path intents (3-second forward trajectory windows). When path envelopes intersect, the affected subset of AMRs executes a **Decentralized Windowed Conflict-Based Search (D-WCBS)** to negotiate spatial-temporal right-of-way based on deterministic priority rules [RESEARCHED].
  3. **Tactical Avoidance:** At execution time, **NH-ORCA** provides continuous 20Hz non-holonomic velocity adjustments to guarantee zero physical collisions [RESEARCHED].
  4. **Dynamic Task Re-allocation:** If an AMR detects a completely blocked aisle, it publishes a costmap update to peers and initiates a localized **Contract Net Protocol (CNP)** auction to re-assign the task to the most optimal unblocked peer [RESEARCHED].
* **Required Data:** Local pose, 3-sec path intent window, costmap updates, battery status, CNP bid values.
* **Architecture:** Decentralized peer-to-peer Edge Mesh running entirely on onboard compute (Jetson Nano / Pi 4).

### Why Alternatives Were Rejected
1. **Rejection of Approach 1 (Pure Reactive ORCA):** Pure velocity obstacle methods act blindly without looking at multi-step future path intent [RESEARCHED]. In 1.2m narrow warehouse corridors where two AMRs face each other head-on, pure ORCA results in reciprocal oscillations where both robots sway left and right, ultimately freezing in a permanent deadlock [RESEARCHED].
2. **Rejection of Approach 2 (Central Master Broker):** Approach 2 explicitly violates **REQ-3** of the problem statement ("without a central server") [PS]. * **Zero Single Point of Failure:** If AMR-1 suffers a hardware crash or loses Wi-Fi, AMR-2 and AMR-3 continue operating and automatically adjust their paths and task queues [INFERENCE].
* **Mathematical Guarantees:** D-WCBS guarantees multi-step deadlock resolution at intersections, while NH-ORCA guarantees physical zero-collision execution at 20Hz [RESEARCHED].

### Detailed Step-by-Step Data Flow Narrative

```
┌─────────────────────────────────────────────────────────────────────────────────────────┐
│                                 SYSTEM DATA FLOW STEPS                                  │
├─────────────────────────────────────────────────────────────────────────────────────────┤
│ Step 1: Pose Localization & Peer Intent Broadcast (Zenoh P2P @ 10Hz)                    │
│ Step 2: Conflict Detection Window (3-Second Trajectory Envelope Analysis)               │
│ Step 3: Priority-Based Strategic Resolution (D-WCBS Negotiates Yielding AMR)            │
│ Step 4: Continuous Tactical Velocity Adjustment (NH-ORCA @ 20Hz Prevents Physical Touch)│
│ Step 5: Obstacle Detection & Task Re-Auctioning (CNP Bidding Re-assigns Blocked Task)   │
│ Step 6: Non-Intrusive Telemetry Streaming (Zenoh WebSocket Bridge Feeds UI Dashboard)   │
└─────────────────────────────────────────────────────────────────────────────────────────┘
```

1. **Step 1: Localization & Peer State Broadcast (10 Hz):**
   Each AMR (`amr_1`, `amr_2`, `amr_3`) determines its local pose ($x, y, \theta$) using `slam_toolbox` or `amcl`. The local Zenoh node serializes the pose, linear velocity, angular velocity, and the next 3-second planned path waypoints into a compact byte payload. This is published to the peer mesh on key `amr/{robot_id}/state` [INFERENCE].

2. **Step 2: Intent Intersection & Conflict Detection (10 Hz):**
   Every AMR continuously listens to peer state broadcasts. The local D-WCBS node computes spatial-temporal distance envelopes between its own planned 3-second path window and all discovered peer path windows [RESEARCHED]. If the minimum predicted distance falls below $2 \times \text{AMR\_radius} + \text{safety\_margin}$ ($1.0\text{m}$), a potential conflict is flagged [INFERENCE].

3. **Step 3: Strategic Resolution (D-WCBS Negotiation):**
   The conflicting subset of AMRs evaluates a deterministic priority function:
   $$\text{Priority} = f(\text{Task Priority}, \text{Battery SoC}, \text{Distance To Goal}, \text{Robot ID})$$
   The lower-priority AMR computes a spatial-temporal detour or temporary pause waypoint in a local turnout bay using single-agent A*, adding a space-time constraint $C = (\text{cell\_id}, t)$ to its planner [RESEARCHED].

4. **Step 4: Tactical Velocity Execution (NH-ORCA @ 20 Hz):**
   The Nav2 local controller passes the planned velocity commands ($v_{pref}$) to the NH-ORCA solver. NH-ORCA constructs velocity obstacles based on nearby AMR positions and computes the optimal collision-free linear and angular velocities $(v_{safe}, \omega_{safe})$, driving the `diff_drive_controller` motors [RESEARCHED].

5. **Step 5: Dynamic Obstacle & Task Re-Routing (Event-Driven):**
   If `amr_1` encounters an unmapped blocked aisle (e.g., dropped box detected by 2D LiDAR), its local costmap marks the aisle as impassable. `amr_1` broadcasts a costmap delta update over Zenoh topic `fleet/map_updates` [INFERENCE].
   If `amr_1` cannot find an alternative unblocked path to its assigned pickup point within its battery budget, it cancels its task lease and publishes a task auction request to `fleet/auctions` [INFERENCE]. Unassigned or idle peers (`amr_2`, `amr_3`) calculate their travel cost to the pickup point and submit bids. The task is automatically awarded to the lowest-cost peer (`amr_2`) via local contract agreement [RESEARCHED].

6. **Step 6: Passive Monitoring Telemetry (2 Hz):**
   A decoupled Zenoh-to-WebSocket bridge node forwards fleet telemetry to the lightweight WebGL/React Fleet Dashboard, giving warehouse supervisors complete visibility without injecting traffic into the robot-to-robot control loops [INFERENCE].

### AI Component 1: Nav2 Model Predictive Path Integral (MPPI) Local Trajectory Optimization
1. **Exact Problem Solved:** Dynamic local trajectory optimization for non-holonomic differential drive AMRs around fast-moving dynamic obstacles [RESEARCHED].
2. **Input:** Local costmap tensor, current velocity vector $(v, \omega)$, global path waypoints.
3. **Output:** Optimal linear and angular control commands $(v_{cmd}, \omega_{cmd})$ sent to motor controllers at 20Hz.
4. **Why Simpler Rules Fail:** Pure PID or pure rule-based planners cannot account for vehicle non-holonomic constraints, momentum, and complex costmap gradients simultaneously without oscillatory behavior [RESEARCHED].
5. **Data Required:** Real-time 2D LiDAR scans and wheel odometry.
6. **Evaluation Metric:** Smoothness of trajectory, distance from obstacles, goal arrival time.
7. **Failure Mode Handling:** Fallback to ROS 2 Nav2 recovery behaviors (spin, backup, costmap clear).
8. **Training/Fine-tuning:** No deep learning training required; parameter tuning of MPPI model weights [RESEARCHED].
9. **Computer Vision / Speech / RL:** No. Sampling-based optimization over continuous control space [RESEARCHED].
10. **Human Oversight:** Autonomous execution; manual E-stop override available on UI dashboard [INFERENCE].

### Where Deep AI/ML MUST NOT Be Used (Explicit Architectural Rejection)
* **Inter-Robot Conflict Resolution & Deadlock Avoidance:** Deep Reinforcement Learning (DRL) models (e.g., Multi-Agent PPO/Q-Learning) **must NOT be used** for core collision avoidance and deadlock resolution [INFERENCE].
* **Justification:** DRL models lack formal mathematical safety guarantees, act as unpredictable "black boxes," fail catastrophically in unseen edge-case warehouse layouts, and exhibit high inference latency on Raspberry Pi edge hardware [INFERENCE]. Deterministic, mathematically provable algorithms (D-WCBS + NH-ORCA) guarantee zero collisions and predictable execution [RESEARCHED].

### Local Data Schema & Storage
Each AMR maintains a volatile in-memory key-value database (using shared memory and lightweight SQLite) on its edge compute [INFERENCE]:
* `peer_registry`: `{ robot_id: string, last_seen_timestamp: float, pose: [x,y,theta], velocity: [v,w], battery_soc: int, status: string }`
* `costmap_deltas`: `{ delta_id: uuid, timestamp: float, grid_cells: List[(x,y,cost)], reporter_id: string }`
* `active_task`: `{ task_id: string, pickup_pose: [x,y], dropoff_pose: [x,y], lease_expiry: timestamp, status: string }`

### Offline & Disconnected Operation Strategy
1. **Graceful Network Partitioning:** If `amr_1` enters a severe Wi-Fi deadzone and loses contact with `amr_2` and `amr_3`, it does NOT freeze or crash [INFERENCE]. It transitions its peer trajectory tracking to a dead-reckoning safety envelope model based on last-known velocities [INFERENCE].
2. **Local Safety Radius Expansion:** While disconnected, `amr_1` expands its local safety margin around 2D LiDAR dynamic obstacles from 0.2m to 0.5m, relying on onboard sensors to dodge un-communicative peers physically [INFERENCE].
3. **Mesh Re-Joining & State Sync:** When `amr_1` re-emerges into Wi-Fi range, Zenoh's built-in **liveliness tokens** automatically detect the peer [RESEARCHED]. `amr_1` publishes its current pose and exchanges a lightweight 32-bit CRC hash of its dynamic costmap delta list to quickly sync map updates without re-transmitting full map files [INFERENCE].

   * All inter-robot messages published over Zenoh utilize **AES-256-GCM encryption** using a pre-shared industrial key (PSK) burned into the edge hardware secure enclave during robot provisioning [RESEARCHED].
   * Rogue device injection is prevented via mutual cryptographic node authentication; unauthenticated wireless packets are dropped at the network layer [INFERENCE].

2. **Air-Gapped Sovereign Deployment:**
   * The system operates in a completely air-gapped environment with **zero outbound internet dependencies** or external cloud API calls, making it compliant with Bharat Electronics Limited (BEL) defense warehouse security standards [INFERENCE].

3. **System Safety & Hardware Interlocks:**
   * A hardware watchdog circuit runs on each AMR. If the software control loop hangs for >100ms, the watchdog opens a physical relay that cuts power to the motor drivers, bringing the AMR to a safe physical stop [INFERENCE].
   * Physical emergency stop (E-stop) buttons on the robot chassis bypass all software and break the motor power circuit directly [INFERENCE].
