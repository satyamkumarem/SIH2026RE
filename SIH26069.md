## 1. Executive Snapshot

### Executive Summary
The **National Weather Big Data Analytics Platform** is a scalable, real-time intelligence system designed for the **India Meteorological Department (IMD)** under the **Ministry of Earth Sciences (MoES)** [PS]. Severe weather events in India—such as sudden cloudbursts, severe thunderstorms, localized flooding, and heatwaves—often occur faster than traditional ground-station networks can report [INFERENCE]. While citizens extensively post real-time updates and media on social media platforms and public portals [PS], this unstructured data stream suffers from high noise, duplicate uploads, and deliberate or accidental misinformation [INFERENCE]. This project delivers a production-grade big data ingestion and AI verification architecture that collects real-time weather reports from social media (#IMD and weather hashtags), public datasets, APIs, and citizen reports, processes them through an AI pipeline for fake/misleading report detection, deduplication, and automated categorization, and visualizes verified weather events on an interactive Web GIS Dashboard and Admin Panel [PS].

The problem statement has been broken down into atomic, measurable requirements. All explicit requirements from the original statement are preserved without alteration [PS].

### Atomic Requirements Breakdown
*   **Req-1: Multi-Source Real-Time Ingestion** [PS]
    *   *Source Text*: "capable of collecting and processing real-time weather-related information for India from multiple internet-based sources including social media platforms, public datasets, websites, APIs, and citizen reports." [PS]
    *   *Interpretation*: The system must ingest high-velocity data from heterogeneous sources simultaneously.
    *   *Implementation Implication*: Requires decoupled ingestion adapters (REST, Webhooks, Web Scrapers, RSS parsers) feeding a message queue (e.g., Apache Kafka or Redis Streams) [ASSUMPTION].
*   **Req-2: Automated Hashtag & Metadata Harvesting** [PS]
    *   *Source Text*: "automatically collect weather related posts and information tagged with #IMD and other relevant weather hashtags, along with metadata such as date & time, city, state, GPS location, photos, videos, and event category, and store the information in a centralized database." [PS]
    *   *Interpretation*: Automated text extraction, metadata parsing, geospatial normalization, and media attachment extraction.
    *   *Implementation Implication*: NLP metadata parsers, reverse-geocoding service, and object storage (e.g., MinIO/S3) linked to PostGIS [ASSUMPTION].
*   **Req-3: Centralized Big Data Storage & Processing Architecture** [PS]
    *   *Source Text*: "store the information in a centralized database. The system should leverage big data technologies and open-source tools to support large-scale real-time data ingestion, processing, storage, and visualization." [PS]
    *   *Interpretation*: High-throughput streaming and querying capability using open-source tools.
    *   *Implementation Implication*: Open-source big data stack combining PostgreSQL/PostGIS for spatial data, Elasticsearch/OpenSearch for text search, and Apache Spark/Celery for distributed processing [ASSUMPTION].
*   **Req-4: AI-Based Fake & Misleading Detection & Source Verification** [PS]
    *   *Source Text*: "use machine learning and AI-based techniques to identify fake or misleading reports, verify untrusted sources" [PS]
    *   *Interpretation*: Automated trust-scoring system analyzing textual claims, image authenticity (out-of-context or edited media), user account history, and cross-checking against physical station telemetry.
    *   *Implementation Implication*: Multimodal AI classifier combining BERT/RoBERTa for text claim analysis, CLIP/ResNet for visual verification, and spatial cross-validation against nearby IMD Automatic Weather Stations (AWS) [INFERENCE].
*   **Req-5: Automated Deduplication & Multi-Class Event Categorization** [PS]
    *   *Source Text*: "remove duplicate entries, and automatically categorize weather events such as rainfall, thunderstorms, flooding, heatwaves, fog, dust storms, and strong winds." [PS]
    *   *Interpretation*: Clustering spatiotemporal reports within a defined geographical/temporal window and classifying text/media into standard IMD weather event categories.
    *   *Implementation Implication*: Cosine/Vector similarity matching on embeddings + DBSCAN spatial clustering; 7-class text/image classifier [ASSUMPTION].
*   **Req-6: Web Dashboard & Admin Monitoring Panel** [PS]
    *   *Source Text*: "Develop a web-based dashboard and Admin Panel for monitoring and analysing collected data" [PS]
    *   *Interpretation*: Dual-interface web UI: a public/analyst dashboard for weather visualization and an administrative panel for verification override and system management.
    *   *Implementation Implication*: React web application with MapLibre GL / Leaflet for geospatial visualization and role-based access control (RBAC) [ASSUMPTION].
*   **Req-7: Multi-Dimensional Filtering & Verification Tracking** [PS]
    *   *Source Text*: "features including: • Date-wise filtering • Event-wise filtering • Location-wise filtering • Verification status tracking • Real-time visualization and analytics" [PS]
    *   *Interpretation*: Instant spatial (State/District/City/GPS), temporal (Date/Time range), and categorical filtering with visual flags showing verification confidence (Verified, Suspect, Fake, Pending).
    *   *Implementation Implication*: Optimized PostGIS spatial indices and Elasticsearch facets driving API endpoint filters [ASSUMPTION].

## 5. Constraints & Environment Realities

1.  **Social Media API Monetization & Access Restrictions** [KNOWN]
    *   *Reality*: Standard social media platforms (specifically X/Twitter) have eliminated free API access tier for bulk streaming, enforcing strict rate limits and pay-per-use billing models ($0.005 per read) in 2026 [RESEARCHED] [1.3].
    *   *Mitigation*: The platform must rely on a hybrid model: public RSS feeds, news site scrapers, open Mastodon/Bluesky feeds, official webhooks, and direct citizen portal submissions [INFERENCE].
2.  **Geographic & Multi-Lingual Diversity** [KNOWN]
    *   *Reality*: Weather posts across India are written in English, Hindi, Bengali, Tamil, Telugu, Marathi, Gujarati, etc., often mixing languages (Hinglish/Tanglish) [KNOWN].
    *   *Mitigation*: Text classification models must utilize multilingual embeddings (e.g., `xlm-roberta-base` or `IndicBERT`) trained on local regional scripts [ASSUMPTION].
3.  **Low-Bandwidth & Rural Connectivity** [KNOWN]
    *   *Reality*: Severe weather often damages mobile cell towers, causing bandwidth drops or full offline states in rural areas [KNOWN].
    *   *Mitigation*: Citizen mobile interface must support Progressive Web App (PWA) offline queuing (IndexedDB), compressing images on-device before transmission [ASSUMPTION].
4.  **Hardware & Compute Constraints during Hackathon** [ASSUMPTION]
    *   *Reality*: A student team has limited budget for cloud GPUs and large enterprise servers [ASSUMPTION].
    *   *Mitigation*: Use quantized open-source models (ONNX runtime / CPU-optimized PyTorch models) and open-source Dockerized stack on standard cloud/local nodes [ASSUMPTION].

### Approach 1: Monolithic Python Web Architecture (FastAPI + PostgreSQL/PostGIS + Celery)
*   **Mechanism**: A monolithic Python service ingests data periodically via scheduled Celery tasks, runs lightweight AI inference using local PyTorch models, and saves directly to PostGIS.
*   **Pros**: Simple to build, single repository, minimal devops overhead for students.
*   **Cons**: Lacks true big data stream handling; backpressure failures during event spikes; slow AI batch processing.

### Approach 2: Distributed Open-Source Big Data Pipeline (Kafka + Spark Streaming + PostGIS + Vector DB) [RECOMMENDED]
*   **Mechanism**: Decoupled microservices architecture. Ingestion nodes write to **Apache Kafka**. **Apache Spark Streaming** processes incoming feeds in real time, executing AI categorization, reverse-image lookup via **Qdrant Vector DB**, and cross-referencing against IMD AWS data. Results write to **PostgreSQL/PostGIS** and **Elasticsearch**, served via **FastAPI** and **GeoServer** to a **React** frontend.
*   **Pros**: Full compliance with big data problem requirements; horizontally scalable; zero vendor lock-in; handles burst traffic smoothly.
*   **Cons**: Requires multi-container setup (Docker Compose) and higher devops effort during hackathon.

### Approach 3: Cloud-Native Serverless Pipeline (AWS Kinesis + Lambda + DynamoDB + Rekognition)
*   **Mechanism**: Pure cloud-native pipeline utilizing AWS Kinesis for ingestion, Lambda for processing, AWS Rekognition for image analysis, and DynamoDB/Location Service.
*   **Pros**: Zero infrastructure management; high scalability.
*   **Cons**: High operational cost; deep vendor lock-in; unsuitable for offline/air-gapped government deployment; expensive during continuous hackathon testing.

### Detailed Data Flow Narrative
1.  **Ingestion**: Incoming social media feeds (#IMD), citizen submissions via PWA, and scraped weather news are normalized into a unified `RawEvent` JSON payload and pushed to Kafka topic `raw-weather-events` [ASSUMPTION].
2.  **Processing & AI Pipeline**:
    *   *Geo-Parsing*: Extract location names using Named Entity Recognition (NER); resolve lat/long via Nominatim reverse geocoder [ASSUMPTION].
    *   *Categorization*: Multilingual NLP model predicts event class (*Rainfall, Flooding, Heatwave, etc.*) [PS].
    *   *Deduplication*: Image perceptual hash (pHash) and text vector embeddings query Qdrant. If spatial distance < 2 km and time delta < 1 hour, mark as duplicate [ASSUMPTION].
    *   *Fake Detection*: Check image upload date vs historical index. Cross-verify reported rainfall against the nearest IMD AWS station reading [INFERENCE].
3.  **Storage**: Enriched payload is written to PostGIS (`events` table) and indexed in Elasticsearch for fast multi-attribute filtering [ASSUMPTION]. Media is stored in MinIO [ASSUMPTION].
4.  **Visualization**: FastAPI serves filter endpoints and WebSockets to the React frontend, rendering clustered heatmaps and detailed incident cards [ASSUMPTION].

## 13. AI/ML Justification

### 1. Weather Event Categorizer
*   **Purpose**: Classify unstructured text and image reports into 7 explicit weather categories [PS].
*   **Model Type**: Fine-tuned `xlm-roberta-base` (text) + `ResNet-50` (image classifier) [ASSUMPTION].
*   **Input**: Raw post text, image URL [PS].
*   **Output**: Category label (*Rainfall, Thunderstorm, Flooding, Heatwave, Fog, Dust Storm, Strong Winds*) + Confidence Score (0-1.0) [PS].
*   **Data Required**: Labelled text dataset of Indian weather tweets/news + Kaggle weather image dataset [ASSUMPTION].
*   **Why AI**: Rule-based keyword matching fails on multilingual scripts, slang, and context (e.g., "It's raining cats and dogs" vs "No rain today") [INFERENCE].
*   **Evaluation Metric**: Multi-class F1-Score (> 0.88 target) [ASSUMPTION].
*   **Failure Mode**: Ambiguous post marked as "Uncategorized"; sent to Admin review queue [INFERENCE].
*   **Human Oversight**: Admin panel allows 1-click reclassification by meteorologists [INFERENCE].

### 2. Fake & Misleading Report Detector
*   **Purpose**: Identify recycled historical disaster images, fake text claims, or deliberate rumors [PS].
*   **Model Type**: Multimodal CLIP embedding matcher + Proximity Rule Engine [ASSUMPTION].
*   **Input**: Media file, reported GPS location, reported date/time [PS].
*   **Output**: Verification Status (*Verified, Suspect, Fake*) + Verification Score [PS].
*   **Data Required**: Historical flood/disaster image index + IMD AWS telemetry readings [INFERENCE].
*   **Why AI**: Humans cannot manually reverse-search thousands of images per minute during severe weather crises [INFERENCE].
*   **Evaluation Metric**: Precision on Fake Class (> 0.92 to minimize false accusations) [ASSUMPTION].
*   **Failure Mode**: Low-confidence output labeled as "Suspect / Pending Verification" [INFERENCE].
*   **Human Oversight**: Mandatory human review before flagging a citizen account as untrusted [INFERENCE].

### 3. Spatiotemporal Deduplication Engine
*   **Purpose**: Merge multiple social posts referring to the exact same incident (e.g., 50 tweets about one fallen tree in Connaught Place) [PS].
*   **Model Type**: Sentence-BERT embeddings + DBSCAN Spatiotemporal Clustering [ASSUMPTION].
*   **Input**: Text embedding, GPS lat/long, Epoch timestamp [PS].
*   **Output**: Cluster ID + Parent Event Assignment [ASSUMPTION].
*   **Data Required**: Real-time event queue [ASSUMPTION].
*   **Why AI**: Simple spatial matching groups unrelated events; semantic embeddings ensure reports describe the *same visual event* [INFERENCE].
*   **Evaluation Metric**: Adjusted Rand Index (ARI) > 0.85 [ASSUMPTION].
*   **Failure Mode**: Over-clustering distinct nearby events; mitigated by tight spatial radius (< 1 km) [ASSUMPTION].
*   **Human Oversight**: Admin view shows clustered children with un-group option [INFERENCE].

#### Where AI Should NOT Be Used
*   *Do NOT use AI for spatial distance queries*: Use native PostGIS `ST_DWithin` spatial SQL indexing [INFERENCE].
*   *Do NOT use AI for raw date/time filtering*: Use standard database indexing [INFERENCE].
*   *Do NOT use AI for basic user authentication or role management*: Use standard OAuth 2.0 / JWT [INFERENCE].

## 14. Data Architecture & Offline/Low-Network Design

### Database Schema (PostGIS SQL Blueprint)

```sql
-- Core Events Table
CREATE TABLE weather_events (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    source_type VARCHAR(32) NOT NULL, -- 'SOCIAL_MEDIA', 'CITIZEN_PWA', 'NEWS_RSS', 'IMD_AWS'
    external_id VARCHAR(128),
    content_text TEXT,
    language VARCHAR(10) DEFAULT 'en',
    event_category VARCHAR(32) NOT NULL, -- 'RAINFALL', 'FLOODING', 'HEATWAVE', etc.
    verification_status VARCHAR(32) DEFAULT 'PENDING', -- 'VERIFIED', 'SUSPECT', 'FAKE', 'PENDING'
    trust_score FLOAT DEFAULT 0.5,
    location_name VARCHAR(255),
    city VARCHAR(100),
    state VARCHAR(100),
    geom GEOMETRY(Point, 4326) NOT NULL,
    media_urls TEXT[],
    metadata JSONB,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    cluster_id UUID
);

-- Spatial & Filter Indices
CREATE INDEX idx_events_geom ON weather_events USING GIST(geom);
CREATE INDEX idx_events_category ON weather_events(event_category);
CREATE INDEX idx_events_status ON weather_events(verification_status);
CREATE INDEX idx_events_created_at ON weather_events(created_at DESC);
```

### Offline & Low-Network Synchronization (Citizen PWA)
*   **Local Storage**: Browser `IndexedDB` stores report drafts (text, captured GPS, base64 thumbnail) when offline [ASSUMPTION].
*   **Service Worker Queue**: Background Sync API monitors connection state (`navigator.onLine`). When network restores, payloads auto-flush to `/api/v1/citizen-reports` [ASSUMPTION].
*   **Bandwidth Reduction**: On-device HTML5 Canvas resizes images to max 1280x720 JPEG (quality 0.75) prior to upload, reducing payload size by ~85% (from 5MB to ~300KB) [ASSUMPTION].
