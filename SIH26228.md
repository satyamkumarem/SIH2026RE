## 1. Executive Snapshot

This document presents a technical research and architectural dossier for Problem Statement SIH26228, issued by the Directorate General of Information Systems (DGIS), Indian Army under the Ministry of Defence (MoD) [PS]. Operational computer vision (CV) pipelines in defence environments rely on datasets gathered from heterogeneous field sources, third-party pretrained models, and multi-vendor inference modules [PS]. This pipeline structure introduces critical supply-chain vulnerabilities, including poisoned training data, hidden neural backdoors (Trojans), weight tampering, and post-inference log manipulation [PS]. Current cybersecurity controls operate in silos, inspecting individual assets without establishing unified lineage or cross-lifecycle integrity [PS]. The solution defined herein is an air-gapped, extensible, model-agnostic computer vision integrity assurance platform that evaluates training datasets (COCO/YOLO), neural model files (PyTorch/ONNX), and inference outputs [PS]. It provides statistical data sanitization, model Trojan scanning, cryptographic inference binding, environmental shift detection, and an analyst-facing governance dashboard with a tamper-evident audit trail [PS].

## 2. Problem Deconstruction

The explicit problem statement provided in the source JSON is deconstructed into atomic, non-overlapping requirements, maintaining original numbering and structural designations [PS].

### 2.2.1 Training-Data Integrity
* **Requirement**: Identify suspicious or anomalous samples associated with trigger injection, label flipping, systematic mislabelling, near-duplicate flooding, and out-of-distribution insertion [PS]. Where contributor, batch, or source metadata is available, aggregate sample-level evidence into a source-level risk assessment [PS].
* **Source Text**: Section 2.2.1 [PS]
* **Interpretation**: The engine must inspect CV datasets (e.g., image sets with COCO/YOLO annotations) for both label-level corruption and image-level anomalies [INFERENCE]. Instead of flagging isolated images, it must correlate flags across contributors, batches, or cameras to score contributor trustworthiness [INFERENCE].
* **Implementation Implication**: Must implement Spectral Signatures / Activation Clustering for trigger injection [RESEARCHED], Cleanlab Confident Learning for label flipping [RESEARCHED], Perceptual Hashing (pHash) / SSIM for near-duplicate detection [KNOWN], and Mahalanobis / KNN distance metrics for out-of-distribution (OOD) insertion [RESEARCHED]. Metadata aggregation requires hierarchical Bayesian or weighted additive contributor scoring [INFERENCE].
* **Confidence Tag**: [PS]

### 2.2.2 Model Integrity
* **Requirement**: Assess whether a supplied model exhibits anomalous, substituted, or backdoor-like behavior using methods appropriate to the available access level (white-box or black-box) [PS]. Approaches may include behavioral fingerprinting, trigger search/reconstruction, parameter or activation statistics, and comparison against a reference battery [PS]. The system must state access assumptions, confidence, and limitations [PS].
* **Source Text**: Section 2.2.2 [PS]
* **Interpretation**: The framework cannot assume full model internal visibility [PS]. Under white-box access, it can inspect weights and activations; under black-box access, it can only query input-output pairs [INFERENCE].
* **Implementation Implication**: For white-box PyTorch/ONNX models, perform weight distribution analysis, layer-wise activation statistics, and gradient-based trigger reverse-engineering (e.g., Neural Cleanse / ABS) [RESEARCHED]. For black-box models, deploy query-based behavioral fingerprinting and synthetic reference dataset batteries [RESEARCHED]. Output must explicitly state access tier and confidence bounds [PS].
* **Confidence Tag**: [PS]

### 2.2.3 Inference Provenance and Output Integrity
* **Requirement**: Create a verifiable cryptographic binding among input image, model identifier/weight digest, preprocessing/inference configuration, and resulting output [PS]. Post-hoc alteration, substitution, or replay of protected records must be detectable via hashes, signatures, and sequence/timestamp/nonce controls [PS].
* **Source Text**: Section 2.2.3 [PS]
* **Interpretation**: Every inference decision generated by an operational model must be non-repudiable and linked to the exact input and model state [INFERENCE].
* **Implementation Implication**: Compute SHA-256 weight digests of model files, SHA-256 hashes of input raw tensors and pre-processing parameters, and combine them with bounding box predictions into a canonical JSON payload [INFERENCE]. Sign the payload using Ed25519 digital signatures and append to a local Merkle Tree with monotonic sequence numbers and nonces [RESEARCHED].
* **Confidence Tag**: [PS]

### 2.2.4 Distribution-Shift and Anomaly Assessment
* **Requirement**: Detect material deviation from a declared reference distribution caused by terrain, season, sensor, illumination, or acquisition conditions [PS]. Characterize observed shift, provide calibrated risk/confidence scores, and distinguish operational drift from suspicious manipulation [PS].
* **Source Text**: Section 2.2.4 [PS]
* **Interpretation**: Field CV models deployed on drones or ground systems degrade when operational environments change (e.g., summer to winter, day to night, camera sensor swap) [INFERENCE]. The system must tell the operator whether poor performance is due to natural environmental changes or malicious data corruption [INFERENCE].
* **Implementation Implication**: Extract intermediate feature representations using an unpoisoned feature extractor (e.g., standard ResNet/ViT backbone) [RESEARCHED]. Compute Fréchet Distance or Maximum Mean Discrepancy (MMD) relative to the baseline training distribution [RESEARCHED]. Use spatial correlation and noise uniformity analysis to separate environmental lighting/weather shifts from spatial trigger perturbations [INFERENCE].
* **Confidence Tag**: [PS]

### 2.2.5 Analyst-Facing Assurance and Governance
* **Requirement**: Every flag must include a human-readable reason, supporting evidence, confidence/severity score, affected asset, and recommended disposition (accept, review, quarantine) [PS]. Maintain a tamper-evident audit trail and declare unsupported attack classes [PS].
* **Source Text**: Section 2.2.5 [PS]
* **Interpretation**: Military analysts need clear, actionable explanations without technical jargon, along with a secure audit record [INFERENCE].
* **Implementation Implication**: Build a Web UI dashboard displaying visual evidence (e.g., heatmap of reconstructed trigger, bounding box mismatches, feature space cluster plots) [INFERENCE]. Store audit logs in an append-only SQLite engine backed by SHA-256 hash chains [INFERENCE]. Maintain a structured "Capabilities & Limitations" matrix in the report [PS].
* **Confidence Tag**: [PS]

### 2.2.6 Operational Constraints
* **Requirement**: Operates completely offline and air-gapped without cloud services or external APIs [PS]. Ingest COCO and YOLO dataset formats [PS]. Support ONNX and PyTorch/TorchScript model formats [PS]. Baseline integrity assessment must not require retraining (retraining is optional for remediation) [PS]. Fall back gracefully when white-box access is unavailable [PS].
* **Source Text**: Section 2.2.6 [PS]
* **Interpretation**: All software libraries, model weights, dependencies, and evaluation routines must be packaged for local execution on isolated workstations [INFERENCE].
* **Implementation Implication**: Deliver system as a self-contained local application (e.g., PyInstaller binary or offline Docker bundle) with bundled pre-built Python wheels [ASSUMPTION]. Ensure parsing drivers support COCO JSON and YOLO TXT structures [KNOWN]. Provide automatic fallback logic from white-box inspection to black-box behavioral querying when weight inspection fails [INFERENCE].
* **Confidence Tag**: [PS]

## 5. Constraints & Environment Realities

* **Connectivity**: Must operate in strict air-gapped military networks with no internet or cloud access [PS]. System installers must package all dependencies (Python runtime, wheels, UI assets) offline [INFERENCE].
* **Hardware Availability**: Deployment target ranges from tactical rugged laptops (e.g., Intel i7/i9, 32GB RAM, integrated/entry-level GPU) to field server racks [INFERENCE]. The baseline evaluation engine must execute reasonably on CPU-only or modest GPU setups without multi-GPU cluster requirements [INFERENCE].
* **Geographical & Environmental Conditions**: Indian Army operational environments span high-altitude cold deserts (Ladakhi terrain), dusty plains (Thar desert), and dense vegetation (Northeast) [KNOWN]. Vision inputs encounter severe seasonal, weather, and illumination variations that trigger distribution drift [INFERENCE].
* **Dataset Formats**: Must natively ingest COCO (JSON format with image annotations/categories) and YOLO (TXT format per image with class normalized coordinates) datasets without manual reformatting [PS].
* **Model Formats**: Native support required for ONNX (.onnx) computational graphs and PyTorch/TorchScript (.pt, .pth) model serialization formats [PS].
* **Zero Retraining Constraint**: Core integrity checks must evaluate models in a single forward/inspection pass without executing full retraining cycles [PS].

## 6. Research Questions

1. How can backdoor trigger injection be detected in training datasets without knowing the trigger shape, size, or target class?
2. What statistical methods distinguish global environmental shift (e.g., snow on terrain) from localized backdoor trigger insertion in image space?
3. How can white-box model scanning (weight/activation inspection) fall back gracefully when provided with an encrypted or compiled black-box executable?
4. What cryptographic architecture ensures tamper-evident inference records without introducing latency bottlenecks into live computer vision pipelines?
5. How can contributor-level trust scores be computed accurately when dataset contributors submit varying batch sizes?

## 10. Recommended Approach & Why

### Selection
**Approach 3: Hybrid Statistical, Inversion & Cryptographic Assurance Framework** is selected [INFERENCE].

### Justification
1. **Fulfills All Explicit PS Requirements**: Integrates data cleaning (2.2.1), model scanning (2.2.2), cryptographic binding (2.2.3), shift detection (2.2.4), and governance UI (2.2.5) [PS].
2. **Model-Agnostic & Access-Aware**: Operates seamlessly across PyTorch and ONNX models, automatically falling back from white-box weight inspection to black-box query probing [PS].
3. **No Retraining Required**: Audits models in a single inspection pass, respecting constraint 2.2.6 [PS].
4. **Air-Gap Ready**: Runs entirely on local CPU/GPU hardware without cloud dependencies [PS].

### Why Alternatives Were Rejected
* **Approach 1 (Static Rules)** was rejected because simple checksums and static rules cannot detect neural backdoors, trigger-based data poisoning, or environmental distribution drift [INFERENCE].
* **Approach 2 (Deep Meta-Model)** was rejected because training a meta-classifier requires thousands of pre-trained Trojan models, which is computationally infeasible for standard offline hardware and provides poor explainability to military analysts [INFERENCE].

1. **Ingestion Step**: The user inputs a dataset directory (COCO/YOLO) and a model file (ONNX/PyTorch) via the local UI [PS].
2. **Data Integrity Scanning**: The system parses image-label pairs, extracts CNN/ViT features, and executes Spectral Signatures SVD and Cleanlab noise checks [RESEARCHED].
3. **Model Integrity Audit**: The system checks model access rights. If white-box access is available, it analyzes weight layer statistics and performs trigger inversion [RESEARCHED]. If black-box, it runs synthetic query batteries [PS].
4. **Shift Characterization**: Input sample features are compared against a stored reference distribution using Mahalanobis distance and MMD [RESEARCHED].
5. **Inference & Cryptographic Seal**: On model execution, the engine hashes the input image and model weights, packages the predicted bounding boxes, signs the record using an offline Ed25519 key, and logs it to a local Merkle tree [RESEARCHED].
6. **Analyst Presentation**: All findings compile into a structured governance dashboard with clear visual evidence and disposition recommendations [PS].
