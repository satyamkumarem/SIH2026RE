# SIH 2026 Solution Research & Technical Architecture Dossier

## 1. Executive Snapshot

### Executive Summary
The Smart India Hackathon (SIH) Problem Statement `SIH26206` focuses on "Student Innovation in Disaster Management," requiring a comprehensive software solution that addresses risk mitigation, planning, and management across all three critical phases of the disaster lifecycle: before (prevention/preparedness), during (emergency response/rescue), and after (recovery/relief allocation) [PS]. Existing disaster management tools in India—such as NDMA's SACHET early warning portal [RESEARCHED] and ISRO's Bhuvan National Database for Emergency Management (NDEM) [RESEARCHED]—provide essential centralized alerts and macro-level spatial intelligence. However, significant gaps persist at the grass-roots operational level: fragile cellular connectivity during disasters isolates field responders, localized damage assessment takes days to compile, and relief allocation suffers from severe information asymmetry [INFERENCE]. To solve this, we propose **"ResilNet" (Aapda-Sathi)**: an offline-first, edge-intelligent, multi-phase disaster lifecycle management ecosystem [ASSUMPTION]. ResilNet integrates hyper-local AI risk zonation (Pre-Disaster), peer-to-peer Bluetooth Mesh/PouchDB offline emergency communications and AI distress message triaging (During-Disaster), and CV-assisted satellite/drone damage quantification with dynamic resource matching (Post-Disaster) [INFERENCE].

## 5. Constraints & Environment Realities

1. **Cellular Network Failure (Grid Collapse):**
   - *Reality:* Cyclones, earthquakes, and flash floods routinely destroy base transceiver stations (BTS) and power grids, creating zero-connectivity zones for hours or days [KNOWN].
   - *Design Response:* The application must function **offline-first**. Local data must persist in IndexedDB / SQLite, and phone-to-phone peer-to-peer mesh networking (BLE/Wi-Fi Direct) must bridge communication to operational cells [INFERENCE].

2. **Hardware Constraints of Mass End-Users:**
   - *Reality:* Citizens and Aapda Mitra volunteers in rural India predominantly use low-cost Android smartphones (2GB–4GB RAM, entry-level SoC) [KNOWN].
   - *Design Response:* Mobile client software must be lightweight (<25MB download size), optimize background battery usage during mesh operations, and run edge ML models using quantized formats (TFLite / ONNX Runtime Mobile) [ASSUMPTION].

3. **Linguistic Diversity & Digital Literacy:**
   - *Reality:* Rural communities across Indian states operate in local regional languages and may have limited textual literacy [KNOWN].
   - *Design Response:* User Interfaces must rely heavily on standardized universal icons (pictograms), audio voice assistance, and support at least 12 major Indian languages (Hindi, Bengali, Tamil, Telugu, Marathi, Gujarati, etc.) in alignment with the NDMA SACHET protocol [RESEARCHED].

4. **Power Infrastructure Loss:**
   - *Reality:* Disaster-affected zones experience prolonged electrical grid outages [KNOWN].
   - *Design Response:* Software UI must support low-power OLED Dark Mode and energy-efficient background polling cycles to extend device battery endurance [ASSUMPTION].

## 10. Recommended Approach & Why

### Selected Solution
**Approach 3: ResilNet - Hybrid Edge-First Multi-Phase Disaster Lifecycle Ecosystem** [ASSUMPTION].

### Why Alternatives Were Rejected
1. **Rejection of Approach 1 (Monolithic Cloud Portal):** Relies 100% on continuous cloud connectivity. In real Indian disaster events (e.g., severe cyclones or floods), cellular towers lose power within 2 hours [KNOWN]. A purely online portal becomes completely useless to field rescue workers and victims exactly when needed most [INFERENCE].
2. **Rejection of Approach 2 (Cloud-Centric Deep Learning / LLM System):** Unviable due to high operational latency, expensive GPU infrastructure requirements, LLM hallucination risks in life-critical emergency contexts, and total dependence on active internet backhauls [INFERENCE].

### Architectural Superiority of ResilNet
ResilNet solves the central paradox of disaster software: **How to provide intelligent decision-making when central systems are cut off.** By putting light ML models (ONNX Runtime) and P2P communication protocols (Bluetooth Low Energy / Wi-Fi Direct mesh) onto citizen and responder mobile devices, ResilNet forms an ad-hoc local emergency network [INFERENCE]. When any single phone in the mesh touches an edge node with internet (e.g., a satellite-linked command vehicle or restored tower), it automatically uploads the entire local crisis registry to the central DDMA Command Portal [INFERENCE].

### Detailed Data-Flow Narrative

1. **Pre-Disaster Flow (Mitigation & Zonation):**
   - Central backend periodically pulls weather alerts (IMD RSS/CAP) [RESEARCHED] and river levels (CWC) [RESEARCHED].
   - PostGIS spatial engine overlays hazard data onto elevation (SRTM) and ward boundary maps to compute a 1–10 Risk Zonation Index [INFERENCE].
   - Pre-computed risk polygons and nearby emergency shelter coordinates are pushed to citizen mobile devices as lightweight MBTiles vector basemaps during normal network operations [INFERENCE].

2. **During-Disaster Flow (Offline SOS & Mesh Dispatch):**
   - User triggers an emergency distress signal (SOS) without cellular connection [INFERENCE].
   - On-device edge NLP model (quantized DistilBERT ONNX) categorizes the alert (e.g., "Medical Emergency", "Trapped in Water", "Food Need") and assigns a priority score (P1–P4) [INFERENCE].
   - Mobile app broadcasts payload via BLE & Wi-Fi Direct advertising packets. Nearby phones running the app receive, store, and re-broadcast the packet using a Store-and-Forward Mesh Algorithm [INFERENCE].
   - As soon as any responder or citizen in the mesh enters range of an active network gateway (e.g., NDRF Satellite Vehicle or working tower), all queued SOS packets are synced to the PostGIS Cloud Database via WebSockets [INFERENCE].
   - Command Dashboard updates instantly, displaying color-coded SOS clusters prioritized by severity and victim vulnerability [INFERENCE].

3. **Post-Disaster Flow (Damage Assessment & Relief):**
   - Reconnaissance drone imagery is uploaded to the Command Dashboard.
   - YOLOv8-Seg Computer Vision model processes the images, outlining damaged structures and estimating destruction percentages [INFERENCE].
   - Relief camp managers enter stock requirements into their mobile app in offline mode. PouchDB syncs inventory state with central PostgreSQL, matching camp demands against IDRN-cataloged regional supplies [INFERENCE].

## 13. AI/ML Justification

### AI Component 1: Multi-Lingual SOS Distress Triaging (Edge NLP)
1. **Exact Problem Solved:** Automatically categorizing raw victim distress messages/transcripts into standardized emergency types (Medical, Trapped, Structural Collapse, Food/Water) and prioritizing urgency [INFERENCE].
2. **Input:** Raw text string or speech audio transcript in English, Hindi, or regional languages [INFERENCE].
3. **Output:** Category Label (e.g., `CRITICAL_MEDICAL`) + Priority Score (1–5) + Extracted Medical Entities [INFERENCE].
4. **Why Rule System Fails:** Keywords like "water" could mean "I need drinking water" (Low Urgency) or "Water level is rising to roof, cannot breathe" (Extreme Critical Urgency). NLP understands semantic context [INFERENCE].
5. **Data Required:** Multi-lingual disaster intent dataset (annotated synthetic SMS/tweet dataset based on crisis taxonomies) [ASSUMPTION].
6. **Evaluation Metric:** Macro F1-Score (Target >0.88) and Critical Class Recall (Target >0.95 to avoid missing life-threatening calls) [INFERENCE].
7. **Failure Mitigation:** If NLP confidence score is <0.60, system defaults packet to "Priority 2 - Unclassified Manual Review" [INFERENCE].
8. **Training/Fine-Tuning:** Fine-tuning a lightweight `mBERT` or `DistilBERT` model, exported to quantized 8-bit ONNX format (~25MB) [ASSUMPTION].

### Database Schema (Core Tables - PostgreSQL / PostGIS)

```sql
-- Emergency SOS Distress Signals Table
CREATE TABLE emergency_sos (
    sos_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    device_fingerprint VARCHAR(64) NOT NULL,
    victim_name VARCHAR(100),
    contact_phone VARCHAR(15),
    category VARCHAR(30) CHECK (category IN ('MEDICAL', 'TRAPPED', 'FOOD_WATER', 'EVACUATION', 'UNKNOWN')),
    priority_level INT CHECK (priority_level BETWEEN 1 AND 5),
    raw_message TEXT NOT NULL,
    location GEOMETRY(Point, 4326) NOT NULL,
    mesh_hop_count INT DEFAULT 0,
    sync_status VARCHAR(20) DEFAULT 'PENDING' CHECK (sync_status IN ('PENDING', 'RELAYED', 'SYNCED_CLOUD')),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- Resource Inventory Table (IDRN Aligned)
CREATE TABLE resource_inventory (
    resource_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    warehouse_name VARCHAR(100) NOT NULL,
    item_category VARCHAR(50) NOT NULL, -- e.g., 'Inflatable Boat', 'Life Jacket', 'De-watering Pump'
    quantity_available INT NOT NULL CHECK (quantity_available >= 0),
    district_code VARCHAR(10) NOT NULL,
    location GEOMETRY(Point, 4326) NOT NULL,
    last_updated_by VARCHAR(50),
    sync_version BIGINT NOT NULL DEFAULT 1
);

-- Spatial Indices
CREATE INDEX idx_sos_location ON emergency_sos USING GIST(location);
CREATE INDEX idx_sos_priority ON emergency_sos(priority_level, sync_status);
CREATE INDEX idx_resource_location ON resource_inventory USING GIST(location);
```

### Offline & Sync Architecture Strategy
1. **Local Storage Engine:** The mobile client utilizes `RxDB` backed by `SQLite` on mobile native (via React Native Async Storage / SQLite plugin) and `IndexedDB` on web browsers [ASSUMPTION].
2. **Synchronization Protocol:** Uses CouchDB Conflict-Free Replicated Data Types (CRDT) delta synchronization [INFERENCE]. Changes are tracked via incremental `sync_version` sequence numbers.
3. **Conflict Resolution Policy:**
   - *SOS Messages:* Append-only design pattern. SOS records from different devices are immutable and uniquely identified by UUID; conflicts cannot occur [INFERENCE].
   - *Inventory Adjustments:* Last-Write-Wins (LWW) based on verified authority timestamps, backed by an audit transactional ledger [INFERENCE].
4. **Bandwidth Minimization:**
   - Vector maps pre-packaged as `.mbtiles` files per district (~15MB per district) [INFERENCE].
   - SOS payloads serialized using Protocol Buffers (Protobuf) or ultra-compact JSON (<200 bytes per packet) to fit inside BLE advertisement payload windows [INFERENCE].
