# SIH Solution Research & Technical Dossier: AI-Based Automated Urban Parcel Mapping and Cadastral Feature Extraction System

## 1. Executive Snapshot

### Summary
Urban land record management in India faces severe bottlenecks due to manual digitization of drone imagery, complex dense urban morphology, and manual ground-truthing (GT) processes [PS]. The proposed solution is **CadastraiAI**, an enterprise-grade GeoAI and Web-GIS platform designed to automate urban cadastral feature extraction from high-resolution Orthorectified Imagery (ORI), Digital Surface Models (DSM), Digital Terrain Models (DTM), and existing legacy cadastral layers [PS]. By combining multi-modal deep learning models (SAM 2 fine-tuned with Mask R-CNN and ResNet-101 backbones) [INFERENCE] with an automated topological graph solver and GNSS/CORS spatial anchoring [KNOWN], **CadastraiAI** automatically extracts parcel boundaries, building footprints, road networks, and land-use classifications [PS]. The platform accelerates cadastral surveys by up to 80% [INFERENCE], automatically flags geometric anomalies and overlaps [PS], and provides a Web-GIS editing interface alongside an offline mobile app for field verification [PS].

## 2. Problem Deconstruction

The problem description provided by DoLR [PS] is deconstructed into atomic functional and non-functional requirements below:

### Explicit Requirements

#### A. Core Extraction Capabilities
* **Req-a [PS]:** Automatic extraction of parcel boundaries from drone imagery and spatial data.
  * *Interpretation:* System must generate closed, vector polygon boundaries representing individual land plots.
  * *Implementation Implication:* Requires edge detection, semantic/instance segmentation, and polygonization algorithms.
* **Req-b [PS]:** Identification and delineation of building footprints.
  * *Interpretation:* System must segment building roofs, separate adjoining structures, and output clean 2D vector polygons.
  * *Implementation Implication:* Needs elevation-aware deep learning (utilizing DSM minus DTM Normalized Digital Surface Models - nDSM) to isolate elevated structures from ground level.
* **Req-c [PS]:** Detection of roads, pathways, and access corridors.
  * *Interpretation:* System must delineate transportation networks, narrow alleys, and public access rights-of-way.
  * *Implementation Implication:* Linear feature extraction using road vectorization algorithms or deep learning segmentation (e.g., D-LinkNet).
* **Req-d [PS]:** Classification of land-use features in urban areas.
  * *Interpretation:* System must categorize segmented polygons into land-use types (e.g., Residential, Commercial, Industrial, Vacant, Transport, Open Space).
  * *Implementation Implication:* Multi-class semantic classification model leveraging texture, spectral bands, and structure height.

#### B. Input Data Utilization Requirements
* **Req-Input-1 [PS]:** Utilize High-resolution Drone Imagery (UAV imagery).
* **Req-Input-2 [PS]:** Utilize Orthorectified Imagery (ORI) with true spatial scale.
* **Req-Input-3 [PS]:** Utilize Digital Surface Models (DSM) and Digital Terrain Models (DTM).
* **Req-Input-4 [PS]:** Ingest and overlay Existing GIS Parcel layers (legacy vector or scanned geo-referenced maps).
* **Req-Input-5 [PS]:** Integrate Ground Truthing (GT) datasets collected during field surveys.
* **Req-Input-6 [PS]:** Incorporate GNSS / CORS (Continuous Operating Reference Stations) enabled survey data for centimetre-level georeferencing [KNOWN].

#### C. Platform Architectural & Algorithmic Modules
* **Req-Platform-1 [PS]:** AI-based image segmentation models for parcel delineation.
* **Req-Platform-2 [PS]:** Deep learning techniques for feature extraction and object detection.
* **Req-Platform-3 [PS]:** Automated topology generation and parcel polygon creation (cleaning gaps, dangles, and duplicate lines).
* **Req-Platform-4 [PS]:** Detection of overlapping or inconsistent parcel geometries (anomaly and conflict detection engine).
* **Req-Platform-5 [PS]:** Web-GIS visualization and editing interface (interactive vector editing, attribute editing, layer toggling).

#### D. Core Output & Outcome Deliverables
* **Req-Output-1 [PS]:** Automatically generate preliminary urban parcel maps.
* **Req-Output-2 [PS]:** GIS-ready cadastral outputs (standard formats: GeoJSON, Shapefile, GeoTIFF, GeoPackage).
* **Req-Output-3 [PS]:** Web-based visualization dashboard with role-based access.
* **Req-Output-4 [PS]:** Automated topology validation module flagging spatial violations.
* **Req-Outcome-1 [PS]:** Improve speed and efficiency of cadastral surveys and reduce manual digitization efforts.
* **Req-Outcome-2 [PS]:** Enhance accuracy of parcel boundary extraction and support GT/field verification activities.

## 5. Constraints & Environment Realities

1. **Urban Settlement Morphological Complexity:** Dense urban centers (e.g., old city areas in Indian municipalities) feature sharing walls, overhanging balconies, narrow alleys (<2m), and continuous roof covers [PS] [INFERENCE].
2. **Spectral & Physical Ambiguity:** Shadowing from multi-story buildings obscuring ground roads, identical roofing material across adjacent plots, and temporary shed structures [PS] [INFERENCE].
3. **Connectivity & Field Realities:** Field GT staff operates in dense urban pockets with unpredictable 4G/5G mobile connectivity, requiring zero-latency offline mobile GIS caching [INFERENCE].
4. **Geodetic Accuracy Standards:** Cadastral mapping requires Survey of India (SoI) alignment, WGS84 / UTM projection (Zone 43N/44N for India), and sub-decimetre precision via CORS GNSS network integration [KNOWN] [RESEARCHED].
5. **Hardware Compute Limitations:** District survey offices possess standard office PCs without high-end GPUs; heavy deep learning inference must run on cloud/edge servers, while web visualization must remain lightweight [INFERENCE].
6. **Digital Literacy of Survey Personnel:** Field revenue clerks require simplified multi-touch interfaces in regional languages rather than complex desktop GIS software like QGIS/ArcGIS [INFERENCE].

## 9. Candidate Solution Approaches

### Approach 1: Rule-Based Computer Vision & Photogrammetric Thresholding
* **Mechanism:** Uses classical edge detection (Canny, Sobel), Watershed segmentation, and fixed height-thresholding from nDSM.
* **Pros:** Highly explainable, fast CPU execution, no training data required.
* **Cons:** Fragile in dense urban areas; fails under varying roof textures, shadows, and narrow alleys. Poor parcel delineation accuracy (<55% IoU).
* **Feasibility:** High for hackathon, Low for real-world production.

### Approach 2: Pure End-to-End Deep Learning (Mask R-CNN / Swin UNet)
* **Mechanism:** Fine-tunes deep neural networks directly on RGB drone imagery to output building and land-use polygons.
* **Pros:** High pixel accuracy on trained building roofs; robust to visual variations.
* **Cons:** Ignores topological rules (outputs overlapping polygons and gaps between parcels); treats roof overhangs as true ground boundaries; computationally heavy.
* **Feasibility:** Medium for hackathon, Medium for production.

### Approach 3 (RECOMMENDED): Hybrid GeoAI Pipeline (Multi-Modal Segmentation + nDSM Height Fusion + Topological Graph Solver + GNSS Spatial Anchoring)
* **Mechanism:** Fuses RGB drone imagery with nDSM elevation rasters into a 4-channel input feed to SAM 2 / Mask R-CNN. Raw AI mask outputs are converted into vector line strings, snapped using a spatial Graph Solver enforcing planar graph topology (no overlaps, zero gaps), and anchored against legacy GIS / GNSS CORS control points.
* **Pros:** Achieves sub-decimetre legal geometry compliance, handles dense urban structures, automatically resolves topology errors, provides human-in-the-loop editing interface.
* **Cons:** Requires multi-stage engineering pipeline (AI + GIS topology engine).
* **Feasibility:** High for hackathon MVP (using lightweight ONNX models), Exceptional for production deployment.

---

## 10. Recommended Approach & Why

### Selection
**Approach 3: Hybrid GeoAI + Topological Graph Solver Pipeline** is selected.

### Justification
Cadastral parcel mapping is fundamentally a **spatial-legal problem**, not merely an image processing exercise [INFERENCE]. A pure deep learning model (Approach 2) will output visually appealing masks that violate core cadastral rules—such as overlapping parcel boundaries or unmapped gaps between adjacent properties [INFERENCE]. Conversely, rule-based systems (Approach 1) collapse in dense, heterogenous Indian urban environments [INFERENCE].

Approach 3 wins because:
1. **Elevation-Awareness:** Fusing nDSM (DSM minus DTM) prevents roof eaves from distorting ground parcel boundaries [INFERENCE].
2. **Topological Integrity:** The post-processing Graph Solver guarantees planar topology compliance (OGC standards) [KNOWN].
3. **Legacy & GNSS Hybridization:** It respects existing revenue records and CORS survey points as rigid spatial anchors [RESEARCHED].

### Data-Flow Narrative

1. **Ingestion & Preprocessing:** The user uploads high-resolution GeoTIFF files (ORI, DSM, DTM) and legacy GIS layers via the Web-GIS interface. The server computes `nDSM = DSM - DTM` and tiles the imagery into $512 \times 512$ spatial chunks [INFERENCE].
2. **GeoAI Inference:** Raster tiles are routed through the multi-modal segmentation model. The model predicts binary semantic masks for parcel candidates, building footprints, roads, and land-use classes [INFERENCE].
3. **Vectorization & Graph Topology Cleaning:** Raw pixel masks are vectorized via GDAL/Potrace. The Topological Graph Solver applies simplification (Douglas-Peucker), snaps adjacent edges within tolerance ($<10\text{ cm}$), removes dangles, and enforces zero-overlap planar polygon geometries [INFERENCE].
4. **Conflict Detection:** The system compares newly generated polygons against legacy parcel vectors and flags geometry collisions (overlaps, missing boundaries) as visual anomaly overlays [PS].
5. **Human-in-the-Loop Web-GIS Review:** Surveyors inspect the preliminary parcel map, refine boundary vertices using MapLibre GL JS drawing tools, and confirm classifications [PS].
6. **Field Ground Truthing (GT) Sync:** Flagged disputes are pushed to the Mobile GT App. Field staff conduct physical ground checks, record RTK GNSS coordinates, and sync corrections back to PostGIS [PS] [INFERENCE].
7. **Cadastral Export & ULPIN Generation:** Validated maps are assigned 14-digit ULPIN codes based on parcel centroid coordinates and exported as standard GeoJSON / Shapefiles [RESEARCHED].

## 13. AI/ML Justification

### AI Component 1: Building Footprint & Roof Boundary Segmenter
* **Purpose:** Delineate distinct structure contours from drone imagery [PS].
* **Model Type:** SAM 2 (Segment Anything Model 2) fine-tuned on aerial datasets [RESEARCHED].
* **Input:** 4-channel composite tensor (RGB + nDSM height raster).
* **Output:** Binary instance segmentation masks for building structures.
* **Data Required:** Annotated aerial building datasets (e.g., SpaceNet 7, AIRS).
* **Why AI:** Visual variations in roof colors, shadows, and materials make rule-based extraction fail [INFERENCE].
* **Evaluation:** IoU (Intersection over Union) $>0.85$, mAP $>0.80$.
* **Failure Mode:** False boundary merges in continuous dense roofs.
* **Human Oversight:** Surveyor manually draws split lines in Web-GIS editor.

### AI Component 2: Parcel Boundary Fine-Edge Extractor
* **Purpose:** Extract visible ground parcel boundaries (fences, walls, hedges, plot dividers) [PS].
* **Model Type:** DeepLabV3+ with ResNet-101 backbone / BDCN Edge Detector [RESEARCHED].
* **Input:** High-resolution RGB Orthorectified Imagery (ORI).
* **Output:** Probabilistic boundary edge map.
* **Data Required:** Georeferenced cadastral map training pairs.
* **Why AI:** Boundary lines in urban India vary visually (stone walls, boundary hedges, drainage ditches) [INFERENCE].
* **Evaluation:** Precision $>0.80$, Recall $>0.88$, F1 Score $>0.84$.
* **Failure Mode:** Ineffective when boundaries are completely obscured by dense tree canopy.
* **Human Oversight:** Field GT surveyor collects physical GNSS coordinates.

### AI Component 3: Land-Use Multi-Class Classifier
* **Purpose:** Categorize segmented urban land regions into tax/governance categories [PS].
* **Model Type:** EfficientNet-B4 Convolutional Classifier.
* **Input:** Cropped polygon RGB image patch + spatial context features.
* **Output:** Land-use class (Residential, Commercial, Transport, Vacant, Water, Vegetation).
* **Data Required:** Urban land-use ground truth patches.
* **Why AI:** Land-use classification requires context and visual texture analysis.
* **Evaluation:** Categorical Accuracy $>0.90$.
* **Failure Mode:** Misclassifying mixed-use buildings (e.g., ground floor commercial, upper floor residential).
* **Human Oversight:** Dropdown attribute override in Web-GIS interface.

### Where AI Should NOT Be Used
* **Topology Enforcement:** Use deterministic planar graph algorithms (Shapely/PostGIS `ST_Union`, `ST_Polygonize`) [INFERENCE].
* **Area Calculation:** Use exact geodetic mathematical formulas (`ST_Area(geography)`) [KNOWN].
* **ULPIN / Bhu-Aadhaar Assignment:** Use deterministic geohash/coordinate encoding standard algorithms [RESEARCHED].

## 14. Data Architecture & Offline/Low-Network Design

### Database Schema (PostGIS)

```sql
-- Cadastral Parcels Layer
CREATE TABLE parcels (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    ulpin VARCHAR(14) UNIQUE,
    geometry GEOMETRY(Polygon, 4326),
    land_use VARCHAR(50),
    confidence_score FLOAT,
    status VARCHAR(20) DEFAULT 'PRELIMINARY', -- PRELIMINARY, GT_VERIFIED, APPROVED
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Building Footprints Layer
CREATE TABLE buildings (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    parcel_id UUID REFERENCES parcels(id),
    geometry GEOMETRY(Polygon, 4326),
    height_ndsm FLOAT,
    building_type VARCHAR(50),
    confidence_score FLOAT
);

-- Roads and Access Corridors
CREATE TABLE roads (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name VARCHAR(100),
    width_meters FLOAT,
    geometry GEOMETRY(MultiPolygon, 4326),
    road_class VARCHAR(30) -- HIGHWAY, ACCESS_CORRIDOR, ALLEY
);

-- Spatial Anomaly & Topology Error Log
CREATE TABLE topology_errors (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    error_type VARCHAR(50), -- OVERLAP, GAP, UNCLOSED_POLYGON, DISCREPANCY
    geometry GEOMETRY(Geometry, 4326),
    severity VARCHAR(10), -- HIGH, MEDIUM, LOW
    resolved BOOLEAN DEFAULT FALSE
);
```

1. **Local Caching:** Mobile GT app pre-downloads PMTiles vector map packages for the assigned survey ward [INFERENCE].

3. **Delta Sync & Conflict Resolution:** Upon reconnecting to network, local edits push to `/api/v1/sync`. If two surveyors edit the same boundary, the system uses Last-Write-Wins with manual flag escalation for supervisor review [INFERENCE].

## 15. Security, Privacy & Governance

1. **Sensitive Data Protection:** Drone imagery and high-precision spatial records are classified as sensitive geospatial data under Survey of India's Geospatial Data Guidelines 2021 [RESEARCHED]. All rasters are encrypted at rest using AES-256.
2. **Role-Based Access Control (RBAC):**
   * *Field Surveyor:* View assigned ward, edit field GT points, flag anomalies.
   * *District Survey Officer (Tehsildar):* Review AI boundaries, resolve topology disputes, approve final cadastral maps.
