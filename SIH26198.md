# SIH 2026 Solution Dossier & Architectural Blueprint

## 1. Executive Snapshot

### Summary
This dossier presents **"SwasthyaDrishti AI"**, an ABDM-native [RESEARCHED], offline-first multi-modal screening and intelligent clinical decision support platform designed for primary healthcare centers in India [INFERENCE]. Developed in response to Problem Statement **SIH26198** under the AICTE MIC Student Innovation track [PS], the solution targets the challenge of rural healthcare delivery caused by extreme specialist shortages (79.9% specialist deficit in Community Health Centres) [RESEARCHED] and long travel distances for primary care patients [KNOWN]. SwasthyaDrishti AI equips Community Health Officers (CHOs) and Accredited Social Health Activists (ASHAs) at Ayushman Arogya Mandirs (AAMs) [RESEARCHED] with lightweight, explainable edge-AI diagnostic triage tools (Chest X-ray thoracic screening, retinal fundus diabetic retinopathy screening, and respiratory cough audio analysis) [INFERENCE]. The platform operates entirely offline with dynamic CouchDB/RxDB PWA syncing [ASSUMPTION], automatically creates and links 14-digit Ayushman Bharat Health Accounts (ABHA) [RESEARCHED], formats clinical findings as HL7 FHIR R4 bundles [RESEARCHED], and bridges seamlessly with eSanjeevani tele-consultation hubs [RESEARCHED] in compliance with the ICMR 2023 AI Ethical Guidelines [RESEARCHED].

## 5. Constraints & Environment Realities

### Operational & Environmental Analysis
* **Geography & Connectivity**: Rural Ayushman Arogya Mandirs (AAMs) in hilly, tribal, or remote districts frequently suffer 2G/3G connectivity or complete multi-day network blackouts [RESEARCHED].
  * *Design Constraint*: Zero dependence on real-time API calls for diagnostic inference. Cloud APIs used solely for background synchronization and remote teleconsultations [INFERENCE].
* **Hardware Availability**: CHOs and ASHAs operate low-cost Android tablets (2GB-4GB RAM, MediaTek/Snapdragon processors) or budget laptops supplied under National Health Mission (NHM) programs [RESEARCHED].
  * *Design Constraint*: AI models must be heavily quantized (INT8/FP16) and optimized via ONNX Runtime Web / TFLite, capping memory usage under 150MB per model [ASSUMPTION].
* **Power Supply**: Frequent load shedding and grid instability in rural PHCs [KNOWN].
  * *Design Constraint*: Mobile PWA must feature extreme battery-saver mode, local SQLite/IndexedDB persistence, and graceful recovery from sudden shutdown [INFERENCE].
* **Digital Literacy & Language Diversity**: ASHAs have varying degrees of technical literacy; patients speak diverse regional dialects (Hindi, Marathi, Tamil, Bengali, Telugu, etc.) [RESEARCHED].
  * *Design Constraint*: High-contrast UI, icon-driven workflows, multi-lingual audio guidance via Bhashini API, and minimal manual text typing [RESEARCHED].
* **Regulatory Compliance**: Indian Council of Medical Research (ICMR) 2023 Ethical Guidelines for AI in Healthcare mandate that AI cannot act as an autonomous decision-maker; human oversight by a certified medical practitioner (CHO/Doctor) is legally mandatory [RESEARCHED].
  * *Design Constraint*: System functions strictly as a "Decision Support & Screening Tool" with explicit disclaimer flags and mandatory CHO sign-off prior to referral [INFERENCE].

### Approach 1: Pure Cloud Deep Learning & Web Telemedicine Platform
* **Mechanism**: A central cloud server (AWS/GCP) hosting heavy PyTorch ResNet/DenseNet models exposed via REST APIs. Frontline workers upload images/audio over cellular network and receive diagnostic reports `[INFERENCE]`.
* **Pros**: Simple frontend architecture; high model precision using uncompressed 32-bit floating point neural networks `[INFERENCE]`.
* **Cons**: Fails completely in rural connectivity shadow zones; high cloud bandwidth and compute costs; violates offline operational realities of AAMs `[INFERENCE]`.
* **Hackathon Feasibility**: High | **Production Feasibility**: Low (Rural Deployment Failure) `[INFERENCE]`.

### Approach 2: Native Android Mobile Application with On-Device ML
* **Mechanism**: A standalone Kotlin/Android application packaging TensorFlow Lite models for local inference, storing data locally on SQLite `[INFERENCE]`.
* **Pros**: Complete offline functionality; fast local execution `[INFERENCE]`.
* **Cons**: Restricted to Android platform (fails on Windows laptops used by CHOs); difficult to manage distributed web updates; high app binary size (>200MB) `[INFERENCE]`.
* **Hackathon Feasibility**: Medium | **Production Feasibility**: Medium `[INFERENCE]`.

### Approach 3 (RECOMMENDED): ABDM-Native Edge-Cloud Multi-Modal AI Triage & Tele-Referral Architecture ("SwasthyaDrishti AI")
* **Mechanism**: A Progressive Web Application (PWA) built on Next.js/React Native Web. Runs compressed ONNX models client-side inside the browser/WASM runtime for offline multi-modal triage. Stores records in local RxDB/IndexedDB and syncs bidirectionally with a Node.js/PostgreSQL/CouchDB backend when online. Generates ABDM-compliant ABHA V3 identity tokens and HL7 FHIR R4 bundles `[INFERENCE]`.
* **Pros**: Platform agnostic (works on Android tablets, iOS, Windows/Linux laptops); 100% offline diagnostic capability; seamless ABDM/eSanjeevani integration; zero cloud latency for triage `[INFERENCE]`.
* **Cons**: Requires sophisticated local database synchronization handling (CRDTs/vector clocks) `[ASSUMPTION]`.
* **Hackathon Feasibility**: High | **Production Feasibility**: Very High `[INFERENCE]`.

### Justification & Rejection of Alternatives `[INFERENCE]`
1. **Why Approach 1 Was Rejected**: Cloud-only inference renders the platform unusable in primary health sub-centers across rural India where cellular coverage drops frequently `[RESEARCHED]`. Uploading 15MB digital X-rays or uncompressed retinal scans over 2G network causes application timeouts `[INFERENCE]`.
2. **Why Approach 2 Was Rejected**: Native Kotlin limits the software to specific Android versions and prevents usage on web browser consoles and Windows laptops deployed at CHCs/PHCs `[RESEARCHED]`.
3. **Why Approach 3 Wins**:
   * **Robust Offline Capability**: Frontline workers can conduct 50+ patient screenings in deep offline rural areas; diagnostic ONNX inference executes locally in under 120ms `[ASSUMPTION]`.
   * **Cross-Platform PWA**: Deploys instantly across tablets, phones, and desktop browser terminals without requiring app store installation `[INFERENCE]`.
   * **ABDM Interoperability**: Generates standardized FHIR R4 JSON bundles locally, maintaining full alignment with National Health Authority (NHA) digital public infrastructure `[RESEARCHED]`.
   * **Ethical AI Alignment**: Generates local visual heatmaps (Grad-CAM) that empower CHOs to explain AI predictions to patients, satisfying ICMR 2023 ethical mandates `[RESEARCHED]`.

### Detailed Data Flow Narrative `[INFERENCE]`

```
[Patient Arrival] ──> [ASHA/CHO Scans/Creates ABHA ID] ──> [Conducts Edge Screening]
                                                                   │
                                                                   ▼
[eSanjeevani Tele-Referral] <── [Sync to Cloud / ABDM FHIR] <── [ONNX Edge Inference]
```

1. **Step 1: Patient Intake & ABHA Verification**: A patient arrives at an Ayushman Arogya Mandir. The CHO scans the patient's existing ABHA QR code or creates a new 14-digit ABHA ID using Aadhaar OTP / Demographics via ABDM V3 APIs `[RESEARCHED]`.
2. **Step 2: Multi-Modal Screening & Local Edge Inference**:
   * *Chest X-Ray*: Digital X-ray image is captured/loaded. The local ONNX DenseNet-121 model scans the image locally in browser memory, predicting probabilities for Pneumonia, Tuberculosis, and Effusion in <100ms `[INFERENCE]`.
   * *Retinal Fundus*: Fundus camera photo is loaded. The ONNX EfficientNet-B0 model grades Diabetic Retinopathy from Stage 0 (No DR) to Stage 4 (Proliferative DR) `[INFERENCE]`.

## 14. Data Architecture & Offline/Low-Network Design

### Core Schema Definitions (PostgreSQL / RxDB JSON Schema)

```sql
-- PostgreSQL Core Schema for SwasthyaDrishti AI

CREATE TABLE patients (
    patient_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    abha_number VARCHAR(17) UNIQUE, -- e.g. "12-3456-7890-1234"
    abha_address VARCHAR(50) UNIQUE, -- e.g. "name@abdm"
    full_name VARCHAR(100) NOT NULL,
    gender VARCHAR(10) NOT NULL,
    date_of_birth DATE NOT NULL,
    mobile_number VARCHAR(15),
    address_json JSONB,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE clinical_encounters (
    encounter_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    patient_id UUID REFERENCES patients(patient_id),
    facility_hfr_id VARCHAR(50) NOT NULL,
    cho_hpr_id VARCHAR(50) NOT NULL,
    cbac_risk_score INT, -- NCD Screening Risk Score
    vitals_json JSONB, -- {bp_systolic, bp_diastolic, spo2, pulse, temp}
    encounter_timestamp TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    sync_status VARCHAR(20) DEFAULT 'PENDING' -- PENDING, SYNCED, CONFLICT
);

CREATE TABLE ai_triages (
    triage_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    encounter_id UUID REFERENCES clinical_encounters(encounter_id),
    modality VARCHAR(20) NOT NULL, -- CHEST_XRAY, RETINA, COUGH_AUDIO
    model_version VARCHAR(30) NOT NULL,
    findings_json JSONB NOT NULL, -- {pred_class, confidence, probabilities}
    gradcam_image_path TEXT,
    cho_confirmation VARCHAR(20) DEFAULT 'UNREVIEWED', -- CONFIRMED, OVERRIDDEN
    cho_notes TEXT,
    fhir_bundle_json JSONB NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);
```

### Local Storage, Caching & Sync Design `[ASSUMPTION]`
* **Client-Side Cache**: RxDB wraps IndexedDB on the PWA client, reserving up to 500MB of local storage for local patient records, pending triage events, and model weights `[ASSUMPTION]`.
* **Synchronization Strategy**:
  * Uses CouchDB bidirectional replication protocol over WebSockets / HTTPS `[ASSUMPTION]`.
  * Every offline record is appended with a vector clock `(device_id, counter, timestamp)` `[ASSUMPTION]`.
  * **Conflict Handling**: Last-Write-Wins (LWW) based on CHO verified timestamp. Patient identity records are merged using ABHA ID as immutable key `[ASSUMPTION]`.
  * **Retry Strategy**: Exponential backoff (2s, 4s, 8s, 16s, max 60s) with automatic network listening via `navigator.onLine` browser events `[INFERENCE]`.
  * **Bandwidth Reduction**: Images are compressed on client using WebP (80% quality lossy compression) before upload; ONNX feature vectors are synced prior to full binary upload `[INFERENCE]`.
