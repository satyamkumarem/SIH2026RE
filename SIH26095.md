## 1. Executive Snapshot

### Summary
The Ministry of Social Justice and Empowerment (MoSJE), through the Department of Social Justice and Empowerment (DoSJE), funds thousands of Non-Governmental Organizations (NGOs), residential schools, old age homes, and rehabilitation centers under flagship schemes such as NAPDDR, NAPSrC (AVYAY), SHRESHTA, PM-AJAY, and SMILE [RESEARCHED]. A key challenge in Grant-in-Aid (GIA) governance is ensuring that funded facilities exist, maintain required physical infrastructure, host enrolled beneficiaries, and deliver actual services without fake reporting or proxy functioning [PS]. To solve this, this dossier presents an end-to-end technical blueprint for a **Smart Real-Time Monitoring & Inspection Mobile Application and Central Governance Portal**. The proposed system integrates real-time CCTV stream ingestion via RTSP/WebRTC protocols [RESEARCHED], automated random inspection assignment using spatial-temporal constraint algorithms [INFERENCE], live WebRTC video conferencing for instant unannounced beneficiary verification [RESEARCHED], geo-tagged offline-first inspection modules [INFERENCE], and computer vision AI analytics for attendance and facility anomaly detection [INFERENCE]. This solution turns field monitoring from a slow, paper-heavy, predictable exercise into a real-time, evidence-based, tamper-resistant digital pipeline [INFERENCE].

## 5. Constraints & Environment Realities

1. **Connectivity & Network Variability**: Many DoSJE-funded facilities (e.g., residential schools in tribal belts, rural senior citizen homes) operate on 2G/3G or intermittent 4G networks [KNOWN]. The system cannot assume continuous high-speed broadband for continuous live CCTV streaming or real-time inspection form upload [INFERENCE].
2. **Hardware Constraints on Field Mobile Devices**: PMU inspectors use standard Android smartphones with varying camera quality, RAM (3GB–6GB), and battery capacities [KNOWN]. Heavy edge AI model execution on the mobile phone will cause overheating and rapid battery drain [INFERENCE].
3. **Physical CCTV Infrastructure at Facilities**: Grantee NGOs often deploy inexpensive IP cameras or DVR/NVR systems that expose dynamic IP addresses behind CGNAT firewalls [KNOWN]. Standard RTSP direct connection across WAN will fail without TURN servers or reverse-tunneling proxies [RESEARCHED].
4. **Digital Literacy & User Resistance**: Staff at rural NGOs may have basic digital literacy. Interfaces must be multilingual (Hindi, English, regional languages) and feature simple 1-tap actions [INFERENCE].
5. **Anti-Collusion & Field Conditions**: Field inspectors face potential local influence or bribes. predictable inspection routes allow NGOs to temporarily hire "proxy" beneficiaries. The system must enforce unannounced, short-notice assignments [INFERENCE].
6. **Privacy Regulations for Vulnerable Groups**: Facilities host minors (SHRESHTA schools), substance abuse recovering patients (NAPDDR centers), and elderly individuals [RESEARCHED]. Video surveillance and photo capture must strictly respect privacy laws, enforce face blurring on public dashboards, and comply with DPDP Act 2023 [KNOWN].

## 10. Recommended Approach & Why

### Selection: Hybrid Edge-Cloud Automated Platform (Approach 1)
Approach 1 is selected as the winning architecture because it directly resolves the core engineering challenge of the problem statement: **scalable live CCTV streaming without astronomical cloud server costs**, coupled with **tamper-evident field inspection workflows** [INFERENCE].

#### Why Alternatives Were Rejected
- **Approach 2 (Monolithic Cloud Polling)** was rejected because continuously pulling 5,000+ CCTV RTSP feeds into a cloud server 24/7 requires immense network ingress/egress bandwidth and heavy server GPU decoding, even when no official is watching [RESEARCHED]. Furthermore, static scheduled inspections fail to prevent proxy functioning because facilities prepare in advance [INFERENCE].
- **Approach 3 (Pure P2P Mobile Tool)** was rejected because direct P2P WebRTC connection between an official's smartphone and an IP camera fails in 80%+ of real-world cases due to Symmetric NAT/Firewall blocking at both NGO sites and cellular networks, without TURN/SFU relays [RESEARCHED]. Additionally, it lacks central AI analytics and automated duty dispatching [INFERENCE].

### Detailed Data-Flow Narrative

1. **CCTV Stream Ingestion & Playback**:
   - An official opens the Web Portal and selects an NGO facility to view [INFERENCE].
   - The Web Portal sends a request to the MediaMTX Media Gateway with the target facility ID [RESEARCHED].
   - MediaMTX initiates an **On-Demand RTSP Pull** to the camera's RTSP URL (e.g., `rtsp://ngo-cam.domain.org:554/stream1`) [RESEARCHED].
   - MediaMTX transcodes the RTSP stream into sub-second WebRTC (WHEP) and serves it directly to the browser or mobile app, preventing idle bandwidth consumption [RESEARCHED].

2. **Automated Random Inspection Assignment**:
   - The Automated Assignment Scheduler runs periodically (or on demand by central authorities) [INFERENCE].
   - It queries PostgreSQL PostGIS for pending facility audits, NGO risk weighting scores, and PMU inspector real-time GPS locations [INFERENCE].
   - The Google OR-Tools Engine calculates optimal, randomized inspector-to-facility pairings using spatial-temporal constraints [INFERENCE].
   - Assigned inspectors receive a push notification on their Mobile App containing encrypted inspection details unlocked only upon reaching the physical geo-fence [INFERENCE].

3. **Field Evidence Capture & Sync**:
   - The inspector arrives at the facility; the Mobile App verifies physical presence via high-accuracy GPS (<15m radius) and hardware sensors [INFERENCE].
   - Photos/videos are captured using the custom in-app camera plugin, embedding EXIF geotags, timestamps, device orientation, and SHA-256 cryptographic hashes [INFERENCE].
   - If offline, evidence and form submissions are saved locally in SQLite/Hive [INFERENCE]. Once network connectivity is restored, the Background Sync Engine syncs payloads to the cloud using exponential backoff retries [INFERENCE].

4. **AI Anomaly Processing**:
   - Sampled video frames from active CCTV feeds or uploaded field photos are pushed to the PyTorch/YOLOv11 Inference Worker [RESEARCHED].
   - The worker runs headcount detection, flags blacked-out or tampered camera feeds, and performs facial verification against registered beneficiary lists [RESEARCHED].
   - Any anomaly (e.g., "Sanctioned Capacity: 50, Detected Headcount: 4") triggers an instant high-priority alert on the Central Dashboard [INFERENCE].

## 13. AI/ML Justification

### AI Component Analysis

#### 1. Automated Random Inspection Assignment Engine
1. **Exact Problem Solved**: Eliminates manual human bias, inspector bribery, and collusion by algorithmically assigning inspection tasks [INFERENCE].
2. **Input**: List of PMU inspectors (locations, shift schedules, past visit histories), list of NGO facilities (GPS locations, scheme risk scores, last inspection dates) [INFERENCE].
3. **Output**: Weekly/daily matrix of inspection assignments paired with time windows and route itineraries [INFERENCE].
4. **Why Simpler System Fails**: Simple random sampling ignores geographical feasibility (assigning an inspector to a site 500 km away) or creates unbalanced workloads [INFERENCE].
5. **Data Required**: Geographical matrix (distances/travel times), historical visit logs, NGO risk categories [INFERENCE].
6. **Evaluation Metric**: Constraint satisfaction rate (100%), average inspector travel distance, unannounced randomness entropy score [INFERENCE].
7. **Failure Mode Handling**: Fallback to nearest-available inspector allocation with mandatory manual override approval by DoSJE Joint Secretary [INFERENCE].
8. **Training/Fine-Tuning**: No ML training required; uses Constraint Programming / Mixed-Integer Linear Programming (Google OR-Tools) [INFERENCE].

#### 2. CCTV Occupancy & Anomaly Detection Engine
1. **Exact Problem Solved**: Detects ghost facilities (empty rooms claiming 100% capacity), offline/covered cameras, or severe headcount deficits [INFERENCE].
2. **Input**: Sampled H.264/WebRTC video frames (1 frame every 5 seconds per camera) [RESEARCHED].
3. **Output**: Bounding box counts (headcount), Camera Status (`Normal`, `Tampered/Covered`, `Blackout`, `Frozen Stream`) [RESEARCHED].
4. **Why Simpler System Fails**: Simple motion detection triggers false alarms on moving curtains, shadows, or animals [INFERENCE].
5. **Data Required**: COCO-pretrained weights fine-tuned on surveillance camera datasets (VisDrone / COCO-Person) [RESEARCHED].
6. **Evaluation Metric**: Mean Average Precision (mAP@0.5 > 0.85), Frame processing latency (<100ms) [RESEARCHED].
7. **Failure Mode Handling**: Alerts flagged as "Needs Human Verification"; central official reviews 10-second video clip before taking action [INFERENCE].
8. **Training/Fine-Tuning**: Fine-tuned YOLOv11 nano/small on overhead surveillance footage [RESEARCHED].

#### 3. Biometric Anti-Proxy Attendance Verification
1. **Exact Problem Solved**: Verifies that enrolled beneficiaries registered under GIA schemes are physically present during site visits [INFERENCE].
2. **Input**: Geo-tagged photo captured by inspector vs. registered beneficiary template photo [INFERENCE].

```sql
    last_ping TIMESTAMP

CREATE TABLE inspectors (
    inspector_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    full_name VARCHAR(150) NOT NULL,
    email VARCHAR(150) UNIQUE NOT NULL,
    phone VARCHAR(20) NOT NULL,
    assigned_zone VARCHAR(100) NOT NULL,
    current_location GEOGRAPHY(POINT, 4326),
    is_active BOOLEAN DEFAULT TRUE
);

-- Inspection Assignments
CREATE TABLE inspection_assignments (
    assignment_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    facility_id UUID REFERENCES facilities(facility_id),
    inspector_id UUID REFERENCES inspectors(inspector_id),
    assigned_date DATE NOT NULL,
    due_date DATE NOT NULL,
    status VARCHAR(30) DEFAULT 'PENDING', -- PENDING, IN_PROGRESS, COMPLETED, EXPIRED
    assignment_hash VARCHAR(64) -- Cryptographic integrity proof
);

-- Inspection Reports
CREATE TABLE inspection_reports (
    report_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    assignment_id UUID REFERENCES inspection_assignments(assignment_id),
    inspector_id UUID REFERENCES inspectors(inspector_id),
    check_in_time TIMESTAMP NOT NULL,
    check_out_time TIMESTAMP,
    check_in_location GEOGRAPHY(POINT, 4326) NOT NULL,
    verified_headcount INT NOT NULL,
    observations TEXT,
    compliance_score INT CHECK (compliance_score BETWEEN 1 AND 100),
    is_synced BOOLEAN DEFAULT TRUE,
    report_hash VARCHAR(64) NOT NULL
);

-- Geo-Tagged Evidence Files
CREATE TABLE evidence_files (
    evidence_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    report_id UUID REFERENCES inspection_reports(report_id) ON DELETE CASCADE,
    file_type VARCHAR(20) NOT NULL, -- PHOTO, VIDEO, AUDIO
    file_path TEXT NOT NULL,
    latitude NUMERIC(10,8) NOT NULL,
    longitude NUMERIC(11,8) NOT NULL,
    capture_timestamp TIMESTAMP NOT NULL,
    sha256_hash VARCHAR(64) NOT NULL
);
```

### Offline Synchronization & Low-Network Strategy

```
  +-----------------------------------------------------------------------+
  |                        PMU MOBILE APP (OFFLINE)                       |
  |                                                                       |
  |  +------------------+     +------------------+     +---------------+  |
  |  | Inspection Form  | --> | Hive/SQLite DB   | --> | Encrypted Queue| |
  |  | Input + Camera   |     | (Local Storage)  |     | (Pending Sync)|  |
  |  +------------------+     +------------------+     +---------------+  |
  +------------------------------------------------------------|----------+
                                                               |
                                            Connectivity Check | (Ping / Network Listener)
                                                               v
  +-----------------------------------------------------------------------+
  |                         SYNC ENGINE (ONLINE)                          |
  |                                                                       |
  |  +------------------+     +------------------+     +---------------+  |
  |  | Delta Queue Sync | --> | Chunked Multipart| --> | PostgreSQL +  |  |
  |  | (Conflict-Free)  |     | Upload (Resumable|     | MinIO Storage |  |
  |  +------------------+     +------------------+     +---------------+  |
  +-----------------------------------------------------------------------+
```

1. **Local Offline Storage**: The Flutter mobile app uses Hive/SQLite for fast, transactional local state storage [INFERENCE]. Complete inspection form templates, facility master details, and assignment logs are cached locally during network availability [INFERENCE].
2. **Cryptographic Proof of Offline Timestamp**: When an inspector captures evidence offline, the app records device system time alongside hardware GPS coordinates and signs the payload with a device-bound RSA private key [INFERENCE].
3. **Resumable Chunked Evidence Uploads**: Media evidence (photos/videos) is compressed on-device (JPEG compression at 80% quality, H.264 video encoding at 720p) and uploaded using resumable HTTP multipart chunking [INFERENCE].
4. **Conflict Resolution Strategy**: Inspection submissions use immutable write-once append logs (`report_id` UUID primary key) [INFERENCE]. Server-side timestamp ordering resolves any duplicate submission syncs [INFERENCE].
5. **Bandwidth Optimization**: Mobile app interactions default to text and compressed thumbnails on 2G/3G connections, fetching high-resolution evidence only when connected to Wi-Fi/4G [INFERENCE].
