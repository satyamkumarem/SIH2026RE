## 1. Executive Snapshot

The National Technical Research Organisation (NTRO) requires an autonomous threat intelligence and de-anonymization platform to identify, correlate, and track malicious actors operating across Tor hidden services, underground marketplaces, and darknet forums [PS]. Dark web threat actors routinely exploit anonymity networks to trade illicit goods, stolen data, hacking tools, and conduct cyber extortion while concealing their real-world identities [PS]. Existing manual investigation methods struggle against frequent actor rebranding, infrastructure rotation, and multi-alias identities [INFERENCE]. To address this bottleneck, the proposed platform—code-named **AegisDark**—combines autonomous Tor infrastructure misconfiguration scanning (detecting exposed `/server-status` pages, SSL certificate leaks, service banners, and descriptor anomalies), multi-source identity graph correlation (mapping handles, PGP fingerprints, crypto wallets, and trust networks), and AI-driven stylometric and behavioral profiling [INFERENCE]. The system surfaces actor attribution confidence, timeline queries, and actionable report exports (CSV, JSON, PDF/Executive summary) for cyber intelligence analysts [PS].

## 2. Problem Deconstruction

The problem statement provided by NTRO decomposes into atomic functional, technical, and operational requirements [PS]:

*   **Requirement A (Autonomous Multi-Source Gathering):**
    *   *Source Text:* "continuously gathering their footprints from a range of sources (marketplaces, forums, deep web etc.) and linking them to the identifying information available on those sources." [PS]
    *   *Interpretation:* The platform must ingest data from heterogeneous onion services, forums, and leak repositories without manual intervention [INFERENCE].
    *   *Implementation Implication:* Distributed Tor crawlers with socks5 proxy rotation, rate-limiting bypass, HTML parsing, and structured data extraction [INFERENCE].
    *   *Confidence:* [PS]

*   **Requirement B (Tor Infrastructure Misconfiguration & Origin Detection):**
    *   *Source Text:* "finding misconfigurations in Tor hidden services-such as exposed server-status pages, SSL certificates tied to clearnet domains, default service banners, descriptor inconsistencies, etc and matching them with clearnet infrastructure to point to the likely origin servers." [PS]
    *   *Interpretation:* Passive and active network probing of `.onion` endpoints to extract infrastructure fingerprints that match clearnet IP addresses or domains [INFERENCE].
    *   *Implementation Implication:* Automated HTTP scanner checking `/server-status`, `/phpinfo`, TLS certificate Subject Alternative Names (SANs), SSH host keys, Favicon hashes (MMH3), and shodan/censys cross-referencing [INFERENCE].
    *   *Confidence:* [PS]

*   **Requirement C (Heterogeneous Relationship Graph Mapping):**
    *   *Source Text:* "mapping threat actors across multiple marketplaces into a single relationship graph of handles, PGP keys, wallets and trust links." [PS]
    *   *Interpretation:* Link aliases across disparate sites by unifying PGP public key fingerprints, cryptocurrency deposit/payout addresses, handle overlaps, and forum vouching networks [INFERENCE].
    *   *Implementation Implication:* Property Graph Database (Neo4j) with entity resolution logic and deterministic/probabilistic linkage rules [INFERENCE].
    *   *Confidence:* [PS]

*   **Requirement D (AI Stylometric Persona Identification & Behavioral Profiling):**
    *   *Source Text:* "using AI-based analysis, including stylometric persona identification and behavioural profiling, to link rebranded or migrated personas to known threat actors." [PS]
    *   *Interpretation:* When actors abandon old handles or PGP keys (rebranding), the system must match writing style and activity timing to link the new persona to the legacy profile [INFERENCE].
    *   *Implementation Implication:* NLP pipeline combining character/word n-gram TF-IDF vectors, functional word frequencies, syntactic parse trees, Transformer style embeddings (Sentence-BERT), and posting schedule distributions [INFERENCE].
    *   *Confidence:* [PS]

*   **Requirement E (Analytical Front-End & Timeline Queries):**
    *   *Source Text:* "provide an analytical front end to query the database across a chosen timeline and shall work in an autonomous mode, drawing on available sources of good quality and reliability." [PS]
    *   *Interpretation:* Interactive GUI for cyber analysts to search actors, visualize graph connections, track activity timelines, and inspect source evidence [INFERENCE].
    *   *Implementation Implication:* React/Next.js dashboard with graph visualization (Cytoscape.js/D3.js), filterable timelines, score indicators, and source reliability filtering [INFERENCE].
    *   *Confidence:* [PS]

*   **Requirement F (Data Storage, Attribution & Export Capabilities):**
    *   *Source Text:* "collection, storage, contextualization and querying (through GUI/dashboards) of dark web threat actor intelligence-covering actor profiles, identifiers (handles, PGP keys, wallets etc.), hidden service infrastructure indicators, persona linkages, attribution confidence, category, last scan date and source. The system shall also provide the facility to export the result set in CSV, JSON and report formats." [PS]
    *   *Interpretation:* Robust database schema storing comprehensive metadata and an export module generating machine-readable (JSON/CSV) and human-readable intelligence dossiers [INFERENCE].
    *   *Implementation Implication:* PostgreSQL for relational/structured intel, Neo4j for relationship graphs, and automated PDF/JSON/CSV report generation engine [INFERENCE].
    *   *Confidence:* [PS]

## 5. Constraints & Environment Realities

*   **Tor Anonymity & Architectural Isolation:** Onion routing explicitly encrypts traffic in 3 hops (Guard, Middle, Exit/Rendezvous) [KNOWN]. De-anonymization cannot rely on breaking Tor's cryptography; it must rely on operational security (OPSEC) failures by server operators or threat actors [RESEARCHED].
*   **Tor Network Latency & Rate Limits:** Tor connections experience high latency (500ms – 3000ms) and low throughput compared to clearnet [KNOWN]. Crawlers must handle timeouts gracefully and use concurrency without overloading Tor circuits [INFERENCE].
*   **Anti-Scraping Mechanisms:** Underground forums heavily employ custom CAPTCHAs, Cloudflare/DDoS-Guard protection, invite-only login walls, and session timeouts [KNOWN].
*   **Data Ephemerality & Dynamic Infrastructure:** Dark web marketplaces and forums frequently exit-scam, get seized, or shift `.onion` V3 domains [KNOWN]. Data ingestion must capture full DOM snapshots and raw headers before endpoints disappear [INFERENCE].
*   **Computational Hardware Constraints:** Large Language Models (LLMs) and massive graph analytics require GPU acceleration and substantial RAM [KNOWN]. The hackathon prototype must run efficiently on accessible hardware (e.g., single NVIDIA RTX GPU or CPU-optimized lightweight models like FastText/DistilBERT) [ASSUMPTION].

## 9. Candidate Solution Approaches

### Approach 1: Rules-Based Heuristic Aggregator
*   *Mechanism:* Regular expressions and exact-match deterministic rules to parse handles, PGP keys, BTC wallets, and IP addresses. Matches `/server-status` IP strings directly against clearnet databases [INFERENCE].
*   *Problem Fit:* Solves direct OPSEC leaks well [INFERENCE].
*   *Accuracy Potential:* 100% precision for exact matches (PGP, IP), 0% recall for rebranded personas or modified handles [INFERENCE].
*   *Data Requirements:* Raw text and HTTP response headers [INFERENCE].
*   *Complexity:* Low [INFERENCE].
*   *Explainability:* Perfect (100% rule-based) [INFERENCE].
*   *Cost:* Very Low [INFERENCE].
*   *Scalability:* High [INFERENCE].
*   *Hackathon Feasibility:* Excellent [INFERENCE].
*   *Production Feasibility:* Poor (Easily bypassed when threat actors change handles or use basic OPSEC) [INFERENCE].

### Approach 2: Deep Learning & Heavy LLM Agent Pipeline
*   *Mechanism:* Fine-tuned Llama-3 / Mistral LLMs for content extraction, agentic web crawling, and deep transformer-based stylometric embeddings for every post [INFERENCE].
*   *Problem Fit:* High semantic understanding of forum posts [INFERENCE].
*   *Accuracy Potential:* High stylometric nuance [INFERENCE].
*   *Data Requirements:* Massive labeled text datasets for LLM fine-tuning [INFERENCE].
*   *Complexity:* Very High [INFERENCE].
*   *Explainability:* Low (Black-box neural network embeddings) [INFERENCE].
*   *Cost:* High (Requires expensive GPU cluster for real-time inference) [INFERENCE].
*   *Scalability:* Poor without heavy infrastructure funding [INFERENCE].
*   *Hackathon Feasibility:* Very Low (Prone to latency, API timeouts, and hardware limits) [INFERENCE].
*   *Production Feasibility:* Moderate [INFERENCE].

### Approach 3: Hybrid Architecture (Multi-Layered Heuristic Graph + Feature-Based AI Stylometry)
*   *Mechanism:*
    1.  *Layer 1 (Deterministic Graph):* Exact matching on PGP fingerprints, wallet clusters (Common Input Heuristic), SSH host keys, and SSL cert serials in Neo4j [INFERENCE].
    2.  *Layer 2 (Infrastructure Probing):* Automated Tor HTTP engine extracting headers, `/server-status` IPs, Favicon MMH3 hashes, and cross-matching with Censys/Shodan APIs [INFERENCE].
    3.  *Layer 3 (AI Stylometry):* Dual-headed NLP pipeline combining fast character n-gram TF-IDF + Support Vector Machines (SVM) with Sentence-BERT embeddings to produce an Attribution Confidence Score (0–100%) [RESEARCHED].

*   *Complexity:* Moderate [INFERENCE].
*   *Explainability:* High (Provides specific evidence trails: e.g., "PGP Match: 100%, Stylometric Score: 84%") [INFERENCE].

*   *Scalability:* Very High [INFERENCE].

## 10. Recommended Approach & Why

**Selected Approach:** **Approach 3 (Hybrid Architecture: Multi-Layered Heuristic Graph + Feature-Based AI Stylometry)** [INFERENCE].

### Justification & Rejection of Alternatives
*   *Why Approach 1 was rejected:* Pure heuristic rules completely fail when a threat actor rebrands (e.g., switching from Handle `AlphaDemon` to `ShadowZero` without re-using PGP keys) [INFERENCE]. It fails Requirement D [PS].
*   *Why Approach 2 was rejected:* Relying purely on end-to-end heavy LLMs is cost-prohibitive, introduces hallucination risks into criminal investigations, lacks explainability, and cannot run efficiently within a 36-hour hackathon environment [INFERENCE].
*   *Why Approach 3 Wins:* The hybrid approach cleanly separates **deterministic evidence** (PGP keys, wallet addresses, SSL certificates) from **probabilistic evidence** (stylometry, posting schedules) [INFERENCE]. An analyst can see *why* two personas are linked (e.g., "Shared BTC Wallet + 88% Stylometric Match") [INFERENCE]. It fully satisfies all explicit requirements of SIH26151 while remaining implementable by a 4-6 student team [INFERENCE].

### Data-Flow Narrative
1.  **Ingestion:** The `Tor Scraping Engine` fetches target onion marketplace and forum pages via SOCKS5 Tor proxies [INFERENCE].
2.  **Infrastructure Probing:** Concurrently, the `InfraScanner` issues HTTP HEAD/GET requests to target `.onion` domains checking for exposed `/server-status`, `/phpinfo`, TLS certificate Subject Alternative Names (SANs), and Favicon hashes [INFERENCE].
3.  **Entity & Feature Extraction:** Raw HTML and text are pushed to `Celery` workers. RegEx and SpaCy NER identify PGP public keys, cryptocurrency wallets (BTC, ETH, XMR), handles, and contact aliases [INFERENCE].
4.  **Clearnet Cross-Matching:** Leaked IP addresses, TLS fingerprints, or Favicon hashes are cross-referenced via `Shodan/Censys` APIs to identify clearnet origin servers [INFERENCE].
5.  **Stylometric Comparison:** New textual posts are processed by the `NLP Stylometry Pipeline`, comparing TF-IDF character n-grams and Sentence-BERT vector cosine similarity against existing actor profiles in PostgreSQL [RESEARCHED].
6.  **Graph Linkage & Scoring:** `Neo4j` inserts/updates nodes and directed edges [INFERENCE]. An overall *Attribution Confidence Score* ($S$) is calculated:
    $$S = w_1 \cdot \text{DeterministicMatch} + w_2 \cdot \text{StylometricScore} + w_3 \cdot \text{InfraMatch}$$
7.  **Visualization & Export:** Cyber analysts query the Next.js GUI across time windows, inspect the graph topology, examine origin IP evidence, and export comprehensive CSV, JSON, or PDF reports [PS].

## 13. AI/ML Justification

### AI Component 1: Stylometric Persona Identification Engine
*   **Purpose:** Link rebranded or alt-account personas across darknet forums to known threat actors when no shared PGP keys or handles exist [PS].
*   **Model Type:** Hybrid Ensemble (Character N-Gram TF-IDF + Support Vector Classifier + Sentence-BERT Vector Cosine Similarity) [RESEARCHED].
*   **Input:** Raw text corpus (forum posts, pastebins, marketplace listings) min 100 words [INFERENCE].
*   **Output:** Cosine similarity score (0.00 to 1.00) and candidate actor rank list with confidence percentage [INFERENCE].
*   **Data Required:** Labeled forum post datasets (e.g., synthetic dark web forum corpus) [INFERENCE].
*   **Why AI is Preferable:** Human writing style contains subconscious idiosyncratic patterns (punctuation usage, vocabulary richness, structural n-grams) that cannot be captured by simple keyword matching [RESEARCHED].
*   **Evaluation:** Precision@K, Recall, F1-score on held-out author attribution verification sets [INFERENCE].
*   **Failure Mode:** False positive attribution if actors intentionally mask writing style (adversarial stylometry) or use generative AI [RESEARCHED].
*   **Human Oversight:** High. AI output provides a probabilistic score; analyst must manually verify before taking operational/legal action [INFERENCE].

### AI Component 2: Named Entity Recognition (NER) for Threat Intel
*   **Purpose:** Automatically parse handles, crypto wallets, Jabber IDs, and PGP fingerprints from unformatted HTML/text [INFERENCE].
*   **Model Type:** SpaCy Custom Transformer NER pipeline combined with Regex fallback rules [INFERENCE].
*   **Input:** Raw scraped Web page text [INFERENCE].
*   **Output:** Structured JSON entities (`HANDLE`, `BITCOIN_ADDRESS`, `PGP_FINGERPRINT`, `ONION_URL`, `IP_ADDRESS`) [INFERENCE].
*   **Data Required:** Annotated cybersecurity and darkweb forum text samples [INFERENCE].
*   **Why AI is Preferable:** RegEx handles known formats (e.g. BTC addresses), but custom NER is required to distinguish actor handles from generic forum vocabulary in unstructured text [INFERENCE].
*   **Evaluation:** Entity extraction Precision and Recall [INFERENCE].
*   **Failure Mode:** Missed entities (false negatives) or misclassifying generic words as handles [INFERENCE].
*   **Human Oversight:** Medium. Extracted entities can be manually edited in the analytical dashboard [INFERENCE].

### Where AI Should NOT Be Used
*   *Infrastructure Matching:* Origin IP extraction from `/server-status` or SSL certificate Subject Alternative Names (SANs) must rely 100% on deterministic string and cryptographic hash matching [INFERENCE]. AI must never hallucinate IP addresses or TLS fingerprints [INFERENCE].

## 14. Data Architecture & Offline/Low-Network Design

### Database Schema Design

#### Relational Schema (PostgreSQL)
```sql
CREATE TABLE threat_actors (
    actor_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    canonical_name VARCHAR(100) NOT NULL,
    category VARCHAR(50) NOT NULL, -- e.g., Ransomware, Financial Fraud, Initial Access
    attribution_confidence NUMERIC(5,2) NOT NULL, -- 0.00 to 100.00%
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE actor_identifiers (
    identifier_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    actor_id UUID REFERENCES threat_actors(actor_id),
    type VARCHAR(30) NOT NULL, -- HANDLE, PGP_KEY, BTC_WALLET, ETH_WALLET, EMAIL
    value TEXT NOT NULL,
    source_url TEXT NOT NULL,
    first_seen TIMESTAMP WITH TIME ZONE,
    last_seen TIMESTAMP WITH TIME ZONE
);

CREATE TABLE onion_infrastructure (
    infra_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    onion_address VARCHAR(255) NOT NULL,
    server_banner TEXT,
    ssl_cert_fingerprint VARCHAR(128),
    leaked_origin_ip VARCHAR(45),
    mod_status_exposed BOOLEAN DEFAULT FALSE,
    favicon_mmh3_hash VARCHAR(64),
    last_scan_date TIMESTAMP WITH TIME ZONE,
    source_reliability_score NUMERIC(3,2)
);
```

#### Graph Schema (Neo4j Cypher Data Model)
*   **Nodes:**
    *   `(:Actor {id, canonical_name, confidence})`
    *   `(:Handle {name, platform})`
    *   `(:PGPKey {fingerprint, key_id})`
    *   `(:Wallet {address, coin_type})`
    *   `(:OnionService {url, status})`
    *   `(:ClearnetIP {ip_address, country, isp})`
*   **Relationships:**
    *   `(:Actor)-[:USES_HANDLE]->(:Handle)`
    *   `(:Handle)-[:SIGNED_WITH]->(:PGPKey)`
    *   `(:Handle)-[:RECEIVES_FUNDS]->(:Wallet)`
    *   `(:OnionService)-[:EXPOSES_ORIGIN]->(:ClearnetIP)`
    *   `(:Actor)-[:STYLOGRAPHIC_MATCH {score: 0.88}]->(:Actor)`

### Offline / Low-Network Optimization

*   **Batch Scanning Queue:** Crawling tasks are queued locally in Redis and executed in adaptive batches to prevent clogging Tor circuits or triggering target IP bans [INFERENCE].
