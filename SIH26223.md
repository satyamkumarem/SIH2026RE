## 1. Executive Snapshot

### One-Paragraph Summary
Problem statement SIH26223, under the AICTE MIC-Student Innovation vertical, addresses the critical need for innovative hardware-driven solutions for disaster management spanning pre-disaster risk mitigation and planning, in-disaster real-time response, and post-disaster relief management [PS]. In India, severe natural hazards—such as floods, landslides, cyclones, and cloudbursts—frequently cause catastrophic loss of life and infrastructure due to the failure of conventional grid power and cellular communication networks during extreme events [KNOWN]. To bridge this vulnerability, we propose **"ResiliNet-IoT"**: a solar-powered, dual-frequency (865–867 MHz LoRaWAN / ESP-NOW Mesh) hardware node network integrated with edge AI anomaly detection, offline-first GIS mapping, and C-DOT Common Alerting Protocol (CAP) compliance [INFERENCE]. The system provides autonomous early warning thresholds, offline peer-to-peer SOS emergency messaging when cellular towers collapse, and real-time situational awareness dashboards for first responders [INFERENCE]. Designed for a 4–6 student team, the hackathon MVP combines physical hardware sensor pods, a local gateway node, a mobile emergency mesh application, and simulated multi-hazard telemetry [ASSUMPTION].

## 5. Constraints & Environment Realities

*   **Geography & Terrain:** India’s high-risk regions range from hilly Himalayan terrains (landslide/cloudburst prone) to coastal belts (cyclone/storm surge prone) and river basins (flood prone) [KNOWN]. Hardware enclosures must resist high humidity, heavy rain, and extreme temperature variations [INFERENCE].
*   **Connectivity Interruption:** During Category 3+ cyclones or severe floods, cellular base transceiver stations (BTS) suffer physical damage, power loss, or backhaul fiber cuts [KNOWN]. The hardware MUST NOT depend on continuous 4G/5G/WiFi cloud connections [INFERENCE].
*   **Power Supply:** Grid power outages during natural calamities last anywhere from 12 hours to 10 days [KNOWN]. Hardware nodes must be self-sustaining using solar panels and low-self-discharge LiFePO4 batteries [INFERENCE].
*   **Regulatory & RF Spectrum:** In India, wireless equipment in the 865–867 MHz band is license-exempt under Wireless Planning & Coordination (WPC) guidelines, provided Effective Isotropic Radiated Power (EIRP) stays within 1 Watt (30 dBm) [RESEARCHED].
*   **Digital Literacy & Language:** Local village populations require simple visual (flashing red/yellow LEDs) and high-decibel acoustic (siren/buzzer) warnings alongside multi-lingual text/voice alerts (supporting local languages) [INFERENCE].
*   **Hardware Availability & Cost:** Equipment must be buildable using readily available components in India (e.g., SX1276/SX1262 LoRa modules, ESP32 microcontrollers, standard industrial sensors) to ensure affordability for mass deployment by local bodies [ASSUMPTION].

## 9. Candidate Solution Approaches

### Approach 1: High-Cost Cellular / Satellite Fixed IoT Gateway Network
*   **Mechanism:** Deploy high-spec sensor stations equipped with 4G/5G modems and satellite backup (IRNSS/NavIC or Iridium) directly uploading data to AWS/GCP cloud platforms [INFERENCE].
*   **Pros:** High bandwidth, easy cloud integration, standard RESTful architecture [INFERENCE].
*   **Cons:** Expensive hardware per node (>₹50,000); total failure during extended cellular outage if satellite module is omitted due to cost; high operational expenditure [INFERENCE].
*   **Hackathon Feasibility:** Low (Requires expensive satellite hardware modems and active cellular SIM subscriptions) [INFERENCE].

### Approach 2: Solar-Powered LoRaWAN / LoRa Mesh Sensor Array + Off-Grid WiFi SOS Gateway (Selected Core)
*   **Mechanism:** Deploy distributed sub-GHz (865–867 MHz) LoRa sensor nodes running on solar + battery power. Nodes evaluate micro-environmental data locally (TinyML edge rule evaluation). If thresholds are crossed, nodes send multi-hop RF alerts across the mesh to a master Gateway node. The Gateway node broadcasts local sirens/flashing lights AND spins up a local WiFi SoftAP where nearby trapped citizens can log in via mobile browser (Captive Portal) to post distress requests and GPS locations without internet [INFERENCE].
*   **Pros:** 100% off-grid capability, low component cost (~₹2,500–₹4,000 per node), license-free RF spectrum in India, multi-hop mesh resiliency, extremely low power draw [RESEARCHED].
*   **Cons:** Low data bandwidth (restricted to short sensor readings and text payloads; no high-res video) [KNOWN].
*   **Hackathon Feasibility:** Very High (Can be built and physically demonstrated using ESP32 + SX1276 modules) [INFERENCE].

### Approach 3: Autonomous Swarm UAV Drone Reconnaissance Network
*   **Mechanism:** Deploy custom autonomous quadcopter drones equipped with computer vision cameras and thermal imaging to search disaster zones and relay communication [INFERENCE].
*   **Pros:** Excellent spatial coverage, airborne aerial mapping, thermal body detection [RESEARCHED].
*   **Cons:** Flight time limited to 20–30 minutes per battery; highly vulnerable to heavy storm winds and severe rain; expensive flight controllers and airframes [KNOWN].
*   **Hackathon Feasibility:** Medium-Low (Hardware assembly and indoors flight demo in hackathon venue is risky and limited) [INFERENCE].

### Data Flow Narrative
1.  **Sensing & Edge Check:** Every 10 seconds, the ESP32 microcontroller wakes from light sleep, powers on sensors, and reads environmental parameters (water level distance, tilt acceleration, rainfall accumulation) [INFERENCE].
2.  **Edge Evaluation:** The microcontroller checks values against baseline safety windows. If an anomalous surge is detected (e.g., water level rising > 5cm/min or tilt angle changing > 15 degrees), the edge node instantly triggers its local piezo siren and optical strobe light [INFERENCE].
3.  **Mesh Transmission:** The node serializes the sensor data into a compact 24-byte binary packet containing `[Node_ID, Timestamp, Battery_Volts, Sensor_Flags, Water_Level, Tilt_Angle]` and broadcasts it via its SX1276 LoRa transceiver at 865.5 MHz [INFERENCE].
4.  **Multi-Hop Routing:** Intermediate LoRa pods receive the packet, check the hop count, and re-transmit if necessary to reach the Master Gateway node located up to several kilometers away [INFERENCE].
5.  **Offline SOS Ingestion:** Concurrently, at the Gateway node, trapped citizens in the immediate area connect their mobile phones to the hardware node's broadcast WiFi network ("EMERGENCY_SOS"). The gateway automatically serves an offline captive portal allowing citizens to submit their name, number of people trapped, medical urgency, and auto-captured GPS coordinates. The gateway injects these distress packets directly into the LoRa mesh queue [INFERENCE].
6.  **Central System Upload & CAP Dispatch:** Whenever internet connectivity (cellular/satellite/WAN) is restored at the Gateway, all buffered sensor telemetry and citizen SOS packets synchronize with the Central Command Cloud Platform. The platform updates the PostGIS map display and formats critical warnings into standardized C-DOT CAP XML alerts for broadcast to regional emergency response teams [RESEARCHED].

## 13. AI/ML Justification

### Proposed AI Component 1: Edge-Based Multi-Sensor Landslide & Flood Anomaly Detection
*   **1. Purpose:** Detect multi-parameter anomaly patterns (e.g., simultaneous soil moisture saturation + micro-vibration + heavy rain) that precede landslides or flash floods, reducing false alarms from isolated sensor spikes [INFERENCE].
*   **2. Model Type:** Lightweight Decision Tree / Random Forest Quantized C-Code (generated via Edge Impulse or MicroTVM) executing directly on ESP32 microcontrollers [INFERENCE].
*   **3. Input:** Rolling 1-minute window of 4 sensor features: `[soil_moisture_%, vibration_rms_g, tilt_angle_deg, rainfall_rate_mm_hr]` [INFERENCE].
*   **4. Output:** Risk Score (0–100%) and Alert Class (`NORMAL`, `WATCH`, `WARNING`, `CRITICAL`) [INFERENCE].
*   **5. Data Required:** Synthetic and historical sensor log datasets representing steady state vs. slope failure / rapid inundation [ASSUMPTION].
*   **6. Why AI is Preferable:** Simple fixed threshold rules fail when a single sensor degrades or experiences noise. Machine learning evaluates feature interactions simultaneously [INFERENCE].
*   **7. Evaluation Metric:** Precision (>95%) and Recall (>98%) on validated hazard datasets; zero false negatives on critical slope shifts [INFERENCE].
*   **8. Failure Mode:** If edge AI model execution fails, system automatically falls back to deterministic hard-coded safety threshold checks [INFERENCE].
*   **9. Human Oversight:** Automated alerts sent to DDMA control room require human operator confirmation before issuing mass evacuation sirens [INFERENCE].

### Explicit Exclusion of AI
*   **Deterministic Safety Triggers MUST NOT Use AI:** Absolute flash flood water level thresholds (e.g., "Water height > 3.0 meters above bridge deck") MUST trigger immediate local sirens using hard-coded IF-ELSE rules. Relying on an AI model for critical threshold triggers introduces unacceptable non-deterministic failure risks [INFERENCE].

## 14. Data Architecture & Offline/Low-Network Design

### Database Schema (PostGIS Spatial Model)

```sql

CREATE TABLE sensor_nodes (
    node_id VARCHAR(32) PRIMARY KEY,
    hardware_version VARCHAR(16),

CREATE TABLE node_telemetry (
    telemetry_id BIGSERIAL PRIMARY KEY,
    node_id VARCHAR(32) REFERENCES sensor_nodes(node_id),
    recorded_at TIMESTAMP NOT NULL,
    water_level_cm NUMERIC(6, 2),
    tilt_x NUMERIC(5, 2),
    tilt_y NUMERIC(5, 2),
    rainfall_mm NUMERIC(5, 2),
    battery_v NUMERIC(3, 2),
    raw_rssi INT,
    raw_snr NUMERIC(4, 1)

-- Offline Citizen SOS Messages
CREATE TABLE citizen_sos (
    sos_id VARCHAR(64) PRIMARY KEY,
    gateway_id VARCHAR(32),
    citizen_name VARCHAR(100),
    contact_phone VARCHAR(15),
    trapped_count INT,

    synced_to_cloud BOOLEAN DEFAULT FALSE

```

### Offline Synchronization Strategy
1.  **Store-and-Forward Queue:** When internet/cellular backhaul is down at the Master Gateway, incoming mesh messages and citizen SOS records are written directly to local non-volatile LittleFS flash storage or SQLite on the Gateway node [INFERENCE].
2.  **Backhaul Polling & Ping:** A background daemon on the Gateway pings cloud health endpoints every 30 seconds [INFERENCE].
3.  **Chunked Payload Sync:** Upon establishing a valid HTTP/MQTT connection, the Gateway transmits buffered JSON payloads in compressed batches of 50 records [INFERENCE].
