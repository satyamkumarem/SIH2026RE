## 1. Executive Snapshot

The **Enterprise Cryptographic Discovery & Analysis Tool (ECDAT)** is a specialized security and risk governance framework designed for the National Technical Research Organisation (NTRO) [PS]. Its core purpose is to systematically scan, discover, inventory, and analyze cryptographic primitives across enterprise software repositories, compiled binaries, third-party libraries, container images, hardware security modules (HSMs), and cloud service configurations [PS]. By cataloging cryptographic assets into a standardized **OWASP CycloneDX 1.6 Cryptographic Bill of Materials (CBOM)** [RESEARCHED], ECDAT calculates quantum vulnerability exposure using **Mosca’s Theorem** ($x + y > z$) [PS] and maps quantum-vulnerable algorithms (e.g., RSA, ECC, Diffie-Hellman) [KNOWN] to NIST-standardized Post-Quantum Cryptography (PQC) alternatives (FIPS 203 ML-KEM, FIPS 204 ML-DSA, FIPS 205 SLH-DSA) [RESEARCHED]. The system provides an interactive web-based visualization dashboard and automated report generation engine to enable strategic, prioritized PQC migration for defense and critical national infrastructure [INFERENCE].

The explicit problem statement provided by NTRO decomposes into the following explicit and derived atomic requirements:

*   **Explicit Requirement (i) - Multi-Layer Cryptographic Artefact Discovery & Cataloging:** [PS]
    *   *Source Text:* "Identify and catalogue all cryptographic artefacts (algorithms, keys, certificates, protocols, libraries, hardware modules, cloud services) across internal and external facing applications, products and infrastructure."
    *   *Interpretation:* Scanner must inspect source code, compiled binaries, shared libraries (`.so`, `.dll`), container manifests, TLS/X.509 certificates, cloud service configs (AWS KMS, Azure Key Vault), and HSM parameters [INFERENCE].
    *   *Implementation Implication:* Requires multi-engine parsing: Abstract Syntax Tree (AST) scanning for source code, symbol table and string extraction for compiled binaries, X.509 ASN.1 parsing for certificates, and API adapters for cloud key management [INFERENCE].
    *   *Confidence Tag:* [PS]

*   **Explicit Requirement (ii) - Quantum Risk Assessment & Threat Highlighting:** [PS]
    *   *Source Text:* "The tool should perform a comprehensive quantum risk assessment and identify systems prone to potential quantum attacks, and highlight risks to sensitive data."
    *   *Interpretation:* Must evaluate asymmetric encryption (RSA, ECC, ECDSA, DH) as highly vulnerable to Shor's Algorithm [KNOWN], symmetric ciphers (AES-128 vs AES-256) under Grover's Algorithm [KNOWN], and highlight "Harvest Now, Decrypt Later" (HNDL) exposure [RESEARCHED].
    *   *Implementation Implication:* Build a rules engine mapping each primitive/key size to a quantum risk score (Vulnerable, Deprecated, Safe) and data exposure threat level [INFERENCE].
    *   *Confidence Tag:* [PS]

*   **Explicit Requirement (iii) - Asset Classification & Mosca Framework Application:** [PS]
    *   *Source Text:* "Classify all the artefacts by type, lifetime and business criticality. Apply structured frameworks such as Mosca’s algorithm (compare data lifetime plus migration time against expected arrival of cryptographic relevant quantum computer) to identify and categorize risks."
    *   *Interpretation:* Implement Mosca's inequality $x + y > z$, where $x$ = data shelf-life requirement, $y$ = system migration duration, and $z$ = estimated time to Cryptographically Relevant Quantum Computer (CRQC) [RESEARCHED].

    *   *Interpretation:* Provide specific replacement recommendations (e.g., replace RSA-3072 with FIPS 203 ML-KEM-768 or ML-KEM-1024, or hybrid ECDH + ML-KEM) accounting for performance overheads like key size expansion and execution latency [RESEARCHED].

## 5. Constraints & Environment Realities

Because NTRO is a national technical intelligence agency, the operational environment introduces strict non-functional constraints:

*   **Air-Gapped & Restricted Networks:** Defense and intelligence infrastructure operates in isolated environments [INFERENCE]. The tool cannot rely on external SaaS APIs, internet-based LLMs, or cloud-hosted database lookups [INFERENCE]. All scanning, AST parsing, and vulnerability databases must function 100% offline [INFERENCE].
*   **Heterogeneous Target Architecture:** Target systems range from modern cloud-native microservices (Go, Rust, Python, Node.js) to legacy defense C/C++ embedded binaries (x86_64, ARM64, MIPS) [INFERENCE]. The scanner must handle both high-level source code and low-level binary artifacts [PS].
*   **Performance & Memory Limits:** Enterprise codebases and container images can exceed several gigabytes [KNOWN]. The scanner must utilize streaming AST parsers, regex optimization, and multi-threaded file indexing to prevent out-of-memory (OOM) crashes on standard developer workstations [INFERENCE].
*   **Zero Code Execution Policy:** Scanning must be non-intrusive (static analysis) [INFERENCE]. Executing untrusted target binaries or container scripts during scanning presents severe malware/security risks [KNOWN].
*   **Multi-Language & Custom Crypto:** Systems often combine standard libraries (OpenSSL, BouncyCastle, PyCryptodome) with custom, wrapped, or in-house cryptographic implementations [RESEARCHED].

## 9. Candidate Solution Approaches

### Approach 1: Lightweight Regex & Shell Script Rule Engine
*   **Mechanism:** CLI tool using optimized regular expressions (ripgrep / grep rules) to search source code files and binary text strings for cryptographic keywords (e.g., `RSA_generate_key`, `AES_cbc_encrypt`, `SHA1_Init`).
*   **Required Data:** JSON file containing ~200 regex rules for crypto functions.
*   **Architecture:** Scriptable Python CLI producing static HTML reports.
*   **Evaluation:**
    *   *Problem Fit:* Low. Misses semantic context, leading to massive false positives (e.g., comments, variable names, non-crypto functions) [INFERENCE].
    *   *Complexity:* Very Low.
    *   *Cost:* Zero.
    *   *Hackathon Feasibility:* High (Can be built in 1 day).
    *   *Production Feasibility:* Poor (Cannot handle complex enterprise binaries, container layers, or structured ASTs).

### Approach 2: Multi-Engine Static Analyzer + CBOM Builder + Mosca Engine + Web Dashboard (RECOMMENDED)
*   **Mechanism:** Combined static analyzer using **Tree-Sitter AST parsing** for source code, **PE/ELF/Mach-O symbol & string extraction** for binaries, **Docker layer unpacking** for containers, and an offline **Mosca Risk & PQC Optimization Engine**.
*   **Required Data:** AST tree patterns for 6 major languages, binary symbol signatures (OpenSSL, Libsodium, CNG), NIST PQC lookup table, CycloneDX 1.6 schema.
*   **Architecture:**
    1. Modular Core Engine in Rust/Go or Python (multi-threaded file crawler & AST analyzer).
    2. Analytical Risk Layer applying Mosca's Equation ($x + y > z$) and NIST PQC mapping.
    3. Export Layer producing OWASP CycloneDX 1.6 JSON & PDF reports.
    4. Frontend GUI in React/Next.js with interactive dependency graphs and risk heatmaps.
*   **Evaluation:**
    *   *Problem Fit:* Excellent. Fully satisfies requirements (i), (ii), (iii), (iv), and deliverables A, B, C [PS].
    *   *Complexity:* Medium-High.
    *   *Cost:* Low (Open-source stack).
    *   *Hackathon Feasibility:* High for a 4-6 student team dividing backend/frontend responsibilities.
    *   *Production Feasibility:* Excellent (Scalable, air-gappable, deterministic).

### Approach 3: Deep LLM Code Analysis + Dynamic Runtime Agent Sniffing
*   **Mechanism:** Embeds a local Large Language Model (e.g., Llama-3-8B) to read source code lines and infer cryptographic usage, combined with eBPF runtime tracing on live Linux containers.
*   **Required Data:** Massive fine-tuning dataset of code snippets and eBPF kernel probes.
*   **Architecture:** Heavy Python backend requiring high-end GPU hardware (e.g., NVIDIA RTX 4090 / A100) for local LLM inference.
*   **Evaluation:**
    *   *Problem Fit:* Moderate, but overly complex and non-deterministic [INFERENCE].
    *   *Complexity:* Extremely High.
    *   *Cost:* High (Requires expensive GPU hardware for offline execution).
    *   *Hackathon Feasibility:* Very Low (LLM fine-tuning and eBPF kernel instrumentation are unreliable in short hackathons).
    *   *Production Feasibility:* Poor (High latency, high memory requirement, risk of LLM hallucinations in security reports) [INFERENCE].

## 10. Recommended Approach & Why

We select **Approach 2 (Multi-Engine Static AST/Binary Scanner + CycloneDX 1.6 CBOM + Mosca Risk Engine + Interactive GUI Dashboard)**.

### Why Alternatives Were Rejected:
*   *Approach 1 (Regex Scripting)* was rejected because simple pattern matching produces high false-positive rates (flagging comments, dead code, test mocks) and cannot parse container image layers or structured AST semantics [INFERENCE].
*   *Approach 3 (LLM + eBPF)* was rejected because defense agencies require **100% deterministic, auditable, and reproducible static scanning** [INFERENCE]. LLMs introduce non-deterministic hallucination risks (e.g., misidentifying key lengths or inventing non-existent algorithms) [INFERENCE]. Furthermore, dynamic eBPF tracing requires active code execution, violating the zero-execution safety constraint for untrusted binaries [INFERENCE].

### Data-Flow Narrative
1. **Target Ingestion:** The user submits a target via the GUI or CLI (e.g., local directory path, Git repository URL, container `.tar` file, or `.so`/`.dll` binary).
2. **Multi-Artifact Discovery:**
   * *Source Code:* The Tree-Sitter AST engine parses syntax trees for function calls (e.g., `RSA_public_encrypt`, `Cipher.getInstance("AES/CBC/PKCS5Padding")`).
   * *Binaries:* `pyelftools`/`pefile` inspect import tables, dynamic symbol tables, and embedded string constants for cryptographic signatures.
   * *Containers:* Unpacks OCI/Docker filesystem layers in memory, running binary and certificate extractors on contained binaries.
   * *Certificates:* Parses X.509 ASN.1 structure to extract public key type, key size, signature algorithm, and expiration date.
3. **Normalization & Metadata Enrichment:** Scanned findings are converted into a standardized `CryptoAsset` object containing primitive type, implementation library, file location, key length, and operational context.
4. **Mosca Risk Assessment Engine:** Computes $U = (x + y) - z$.
   * $x$ (Data Lifetime): Extracted from metadata tags or default policy (e.g., Top Secret = 25 years).
   * $y$ (Migration Time): Calculated based on system complexity score (e.g., 3 years).
   * $z$ (Time to CRQC): Fixed baseline standard estimate (e.g., 10 years / ~2035) [ASSUMPTION].
5. **PQC Recommendation Matrix Engine:** Maps vulnerable primitives to FIPS 203 (ML-KEM), FIPS 204 (ML-DSA), or FIPS 205 (SLH-DSA). Evaluates latency and key size trade-offs.
6. **Output Generation:** Formats the dataset into OWASP CycloneDX 1.6 CBOM JSON schema [RESEARCHED], generates executive PDF summaries, and streams data to the React GUI.

## 13. AI/ML Justification

### Deterministic Rule Engine vs. AI/ML Analysis

*   **Core Scanning & CBOM Generation (NO AI NEEDED):**  
    Deterministic AST parsing and binary symbol matching **MUST NOT** use LLMs or machine learning models [INFERENCE]. Static regex/AST rule evaluation is 100% accurate, fast, deterministic, and leaves zero room for model hallucinations [INFERENCE].

*   **Where Machine Learning / Heuristics ADD VALUE (OPTIONAL ENHANCEMENT):**  
    1. *Contextual Custom Crypto Classifier:* A lightweight Random Forest or Naive Bayes classifier trained on code N-grams to detect custom/wrapped cryptographic routines in un-annotated C/C++ source files (e.g., custom bit-shift XOR schedules or proprietary mathematical loops) [INFERENCE].
    2. *PQC Multi-Criteria Decision Optimizer:* A linear programming / fuzzy decision matrix algorithm that ranks alternative PQC algorithms based on application constraints (minimizing key size expansion vs. minimizing signing latency) [INFERENCE].

### Detailed AI Component Evaluation (Custom Crypto Classifier)

1. **Purpose:** Identify custom/proprietary cryptographic implementations that do not invoke standard library APIs [INFERENCE].
2. **Model Type:** Scikit-Learn TF-IDF + Random Forest Classifier (offline execution) [ASSUMPTION].
3. **Input:** Source code token sequences (function blocks).
4. **Output:** Probability score that the function contains custom cryptographic math ($0.0 - 1.0$).
5. **Data Required:** Open-source code samples of standard math vs cryptographic math implementations.
6. **Why AI is Preferable:** Hand-written rules struggle to catch obfuscated or non-standard custom arithmetic loops [INFERENCE].
7. **Evaluation:** Precision, Recall, and F1-score on benchmark cryptographic implementations.
8. **Failure Mode Handling:** If probability is between $0.4$ and $0.7$, tag as "Potential Custom Crypto - Requires Manual Verification" [INFERENCE].
9. **Human Oversight:** Security analyst must manually review flagged custom crypto instances [PS].
