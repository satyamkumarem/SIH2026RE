## 1. Executive Snapshot

Non-Automatic Weighing Instruments (NAWIs)—such as retail electronic scales, platform scales, and heavy weighbridges—form the backbone of trade, agriculture, healthcare, and industrial commerce in India [PS]. Under the Legal Metrology Act, 2009 and the Legal Metrology (General) Rules, 2011, all NAWIs must undergo rigorous type evaluation and model approval by designated testing laboratories (such as Regional Reference Standard Laboratories [RRSLs] and NPL India) prior to commercial deployment [PS, KNOWN]. Currently, laboratory metrologists evaluate NAWIs against the international standard **OIML R 76** using manual spreadsheets or Word templates [PS]. This manual process leads to high calculation error rates, lack of standardized reporting formats, long processing backlogs, and risk of data tampering [PS, INFERENCE]. This dossier presents **MetroSpec-R76**, an offline-first, web-and-desktop application designed to digitize, automate, and streamline NAWI type evaluation, compliance calculation, report generation, and archival for the Department of Consumer Affairs (DoCA) [INFERENCE, ASSUMPTION].

## 2. Problem Deconstruction

## 5. Constraints & Environment Realities

1. **Laboratory & Field Testing Conditions:**
   - *Physical Constraints:* NAWI testing takes place in specialized reference laboratories (RRSLs) or field sites (e.g., heavy industrial weighbridges, granaries, mining sites) [KNOWN].
   - *Connectivity:* Testing pits and heavy industrial sites frequently lack mobile network coverage or Wi-Fi [INFERENCE].
   - *Operating System & Hardware:* Testing labs utilize standard Windows desktop PCs, laptops, or rugged field tablets [KNOWN]. Systems must not require high-end GPUs or massive RAM [INFERENCE].

2. **Metrological & Legal Rigor:**
   - *Zero Margin for Math Error:* Metrological conformity assessment is legally binding [KNOWN]. Floating-point roundoff errors inherent in basic JavaScript/Python floats ($0.1 + 0.2 = 0.30000000000000004$) are strictly unacceptable [INFERENCE].
   - *Non-Repudiation:* Test reports used for Model Approval are legal certificates [KNOWN]. Once approved, data must be immutable and verifiable against tampering [INFERENCE].

3. **User Literacy & Operational Reality:**
   - Metrologists are domain experts in physics and metrology, not software engineers [INFERENCE]. UX must feature clear metrological terminology (e.g., $e$, $d$, MPE, $\Delta L$, Tare), zero cluttered UI, and intuitive step-by-step navigation corresponding to OIML R 76 test sequence [INFERENCE].

## 9. Candidate Solution Approaches

### Approach 1: Monolithic Desktop Application (Electron + SQLite)
- **Mechanism:** Standalone desktop app packaged via Electron/React or Python PyQT, storing evaluation reports in a local SQLite database [ASSUMPTION].
- **Pros:** Completely offline operation; native file system access for local Word/PDF export; responsive UI [INFERENCE].
- **Cons:** Central dashboard requires manual export/import files; difficult to manage software updates across multiple regional labs; no centralized DoCA repository [INFERENCE].
- **Hackathon Feasibility:** High | **Production Feasibility:** Medium.

### Approach 2: Pure Cloud-Native Web Application (React + FastAPI + PostgreSQL)
- **Mechanism:** Web portal hosted on cloud server (e.g., NIC Cloud / AWS), requiring active internet connection for all testing operations [ASSUMPTION].
- **Pros:** Instant centralized repository; real-time DoCA dashboard; simple software updates; seamless eMaap portal integration [INFERENCE].
- **Cons:** Fails completely when metrologists conduct tests in air-gapped labs or offline field locations (weighbridges) without active internet [INFERENCE].
- **Hackathon Feasibility:** High | **Production Feasibility:** Low (due to offline field constraint).

### Approach 3: Hybrid Offline-First Progressive Web App (PWA) with Desktop Wrapper & Central Sync (RECOMMENDED)
- **Mechanism:** Modern Web / PWA frontend (React + TypeScript) compiled for web browser access and packaged via Electron/Tauri for desktop deployment. Utilizes local IndexedDB (via RxDB/PouchDB) for full offline data entry, calculations, and local PDF/Word generation. Automatically synchronizes with a central PostgreSQL cloud backend whenever network connectivity is detected [INFERENCE, ASSUMPTION].
- **Pros:** Uncompromised offline field testing capability; immediate local report generation; centralized DoCA repository and analytics on cloud sync; zero vendor lock-in [INFERENCE].
- **Cons:** Slightly higher technical complexity in implementing conflict-free offline synchronization logic [INFERENCE].
- **Hackathon Feasibility:** High | **Production Feasibility:** High.

## 10. Recommended Approach & Why

**Selected Solution:** **Approach 3 (Hybrid Offline-First PWA with Centralized Cloud Synchronization)** [INFERENCE, ASSUMPTION].

**Why Alternatives Were Rejected:**
- *Monolithic Desktop Application (Approach 1)* was rejected because it creates isolated data silos in each testing laboratory. It fails Requirement R8 and R11 by preventing central DoCA supervisors from monitoring national testing pipelines and maintaining an integrated search repository without manual batch file transfers [PS, INFERENCE].
- *Pure Cloud Web Application (Approach 2)* was rejected because legal metrology testing frequently occurs in shielded laboratory environments or underground weighbridge pits where internet connectivity is non-existent [KNOWN, INFERENCE]. Requiring an active connection would cause app crashes and data loss during 5-hour testing procedures [INFERENCE].

Approach 3 wins because it satisfies every explicit requirement in the SIH PS: local offline operation for metrologists, deterministic automated calculations, instant PDF/Word generation, role-based access, and centralized repository/dashboard sync for DoCA administrators [PS, INFERENCE].

### Detailed Data Flow Narrative

1. **Initialization & Setup:**
   - Metrologist logs into MetroSpec-R76 using JWT authentication [INFERENCE].
   - The application fetches the active OIML Rule Set (`OIML_R76_2006.json`) and caches it locally in IndexedDB [INFERENCE].

2. **Instrument & Environmental Data Entry:**
   - Metrologist creates a new evaluation job, entering manufacturer details and instrument technical specs (Max, Min, $e$, $d$, Class) [PS].
   - The client-side validation logic immediately calculates $n = \text{Max}/e$ and validates whether the instrument parameters comply with OIML R 76 Class boundaries (e.g., verifying Class III $n$ is between 100 and 10,000) [PS, KNOWN].
   - Ambient temperature, humidity, and mains voltage are logged [PS].

3. **Test Observation Recording & Deterministic Calculation:**
   - For each test procedure (e.g., Weighing Performance Test), the metrologist enters applied load $L$, indication $I$, and change-point weight $\Delta L$ [PS, KNOWN].
   - The embedded deterministic math engine immediately computes:
     $$P = I + 0.5e - \Delta L$$
     $$E = P - L$$
     $$E_c = E - E_0$$
   - The engine queries the local rule schema to find the MPE threshold for load $L$ (e.g., $\pm 0.5e$ for $0 \le L \le 500e$; $\pm 1.0e$ for $500e < L \le 2000e$; $\pm 1.5e$ for $2000e < L \le 10000e$ for Class III) [KNOWN].
   - Compliance status (`PASS` / `FAIL`) for that load step is updated on-screen in real time [PS].

4. **Document Generation & Storage:**
   - Upon completion of all test suites, the overall evaluation result is derived [PS].
   - The system triggers the Report Generation Engine, rendering a standardized PDF document (matching OIML R 76-2 layout) and an editable Word DOCX file [PS, RESEARCHED].
   - Photographs of instrument seals and load cells are compressed and embedded into the report [PS].

5. **Approval Workflow & Synchronization:**

## 13. AI/ML Justification

### Critical Metrology Rule:
**Core OIML R 76 MPE and Pass/Fail compliance calculations MUST NOT use Generative AI, Machine Learning, or Fuzzy Logic [INFERENCE].** Legal metrology requires 100% deterministic, mathematically exact, and legally defensible logic [KNOWN]. Using a neural network or LLM to determine if a weighing scale passes error tolerances would introduce hallucination risks and fail legal audit standards [INFERENCE].

### Approved Non-Core AI Application 1: OCR Data Entry Assistant
- **Purpose:** Automatically transcribe physical printed readings from legacy weighing scale indicator thermal receipts or handwritten laboratory test sheets into digital forms [ASSUMPTION].
- **Model Type:** Tesseract OCR / Lightweight Vision Transformer (TrOCR) [ASSUMPTION].
- **Input:** Image or scanned PDF of scale indicator receipt or lab worksheet [ASSUMPTION].
- **Output:** Extracted numeric values for Load ($L$), Indication ($I$), and Temperature ($T$) [ASSUMPTION].
- **Data Required:** 200 sample images of indicator receipts and lab log sheets [ASSUMPTION].
- **Why AI:** Eliminates manual typing fatigue and reduces manual data transcription errors [INFERENCE].
- **Evaluation Metric:** Character Error Rate (CER) $< 1\%$ and Precision $> 99\%$ [ASSUMPTION].
- **Failure Mode:** Misinterpretation of digits (e.g., reading `8` as `3` due to thermal print blur).
- **Human Oversight:** Mandatory side-by-side human verification step where the metrologist must confirm extracted numbers before committing them to the report [INFERENCE].

### Approved Non-Core AI Application 2: Metrological Anomaly & Typo Detection
- **Purpose:** Flag suspect data entry anomalies before report generation (e.g., detecting if a metrologist accidentally entered an indication $I = 100.0\text{ kg}$ for a load $L = 10.0\text{ kg}$) [INFERENCE].
- **Model Type:** Isolation Forest / Rule-Based Heuristic Boundary Classifier [INFERENCE].
- **Input:** Array of test observations across load steps [INFERENCE].
- **Output:** Warning flags pointing to specific out-of-trend data rows [INFERENCE].
- **Why AI/Heuristics:** Detects accidental keystroke errors early, saving time before final report sign-off [INFERENCE].
- **Human Oversight:** Alerts are advisory only; the metrologist retains full authority to override warnings [INFERENCE].
