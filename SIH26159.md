## 1. Executive Snapshot

### Summary
**SecureMailScope** is an AI-assisted passive network forensic framework designed to automatically assess the cryptographic security posture of enterprise email infrastructures from captured network traffic (PCAP files) `[PS]`. Operating passively without interrupting live mail flows `[INFERENCE]`, the system reconstructs TCP streams across SMTP, IMAP, and POP3 communications `[PS]`, detects cleartext-to-TLS elevations via STARTTLS negotiation `[PS]`, parses TLS handshakes `[PS]`, extracts and validates X.509 digital certificates `[PS]`, evaluates Forward Secrecy `[PS]`, and identifies deprecated protocol versions, weak cipher suites, and invalid certificate chains `[PS]`. A hybrid engine combines deterministic RFC compliance checks with machine learning models (Isolation Forest and XGBoost) `[INFERENCE]` to calculate cryptographic posture scores, detect anomalous TLS sessions (such as downgrade attacks or fingerprint anomalies) `[PS]`, prioritize threat remediation `[PS]`, and deliver interactive SOC visualization dashboards alongside exportable PDF, JSON, and HTML forensic reports `[PS]`.

## 2. Problem Deconstruction

The problem statement explicitly requires an offline/passive forensic framework to analyze email protocol traffic in PCAP files `[PS]`. Below is the complete atomic requirement breakdown preserving all explicit directives:

### Explicit Atomic Requirements
* **REQ-01 (Protocol Identification)**: Passive automatic identification of application-layer email protocols: SMTP (ports 25, 587, 465), IMAP (ports 143, 993), and POP3 (ports 110, 995) from packet dumps `[PS]`.
* **REQ-02 (STARTTLS Elevation Detection)**: Detection of in-band `STARTTLS` negotiation and encrypted session upgrades across plain-text initial connections `[PS]`.
* **REQ-03 (TCP Stream Reconstruction)**: Reconstruction of complete TCP communication streams from raw, out-of-order, or retransmitted packets `[PS]`.
* **REQ-04 (TLS Handshake Parsing)**: Reconstruction and parsing of TLS handshakes, including Client Hello, Server Hello, Certificate, Key Exchange, and Cipher Spec frames `[PS]`.
* **REQ-05 (TLS Parameter Extraction)**: Identification of negotiated TLS versions (SSLv3, TLS 1.0, 1.1, 1.2, 1.3), negotiated cipher suites, and key exchange mechanisms (e.g., ECDHE, DHE, RSA) `[PS]`.
* **REQ-06 (X.509 Certificate Extraction)**: Extraction of X.509 certificate binaries and parsing of certificate attributes `[PS]`.
* **REQ-07 (Certificate Chain Validation)**: Validation of certificate chains against trusted Root Certificate Authorities (CAs) and hostname matching `[PS]`.
* **REQ-08 (Certificate Attribute & Expiry Analysis)**: Extraction and analysis of public key algorithms, key lengths (e.g., RSA 1024 vs 2048/4096, ECC curves), digital signature algorithms (e.g., SHA-1, SHA-256), and expiration dates `[PS]`.
* **REQ-09 (Cryptographic Vulnerability & Deprecation Detection)**: Detection of deprecated protocols (SSLv3, TLS 1.0, TLS 1.1), weak cipher suites (e.g., RC4, 3DES, EXPORT, NULL), weak hashing algorithms (MD5, SHA-1), and insecure protocol configurations `[PS]`.
* **REQ-10 (Forward Secrecy Assessment)**: Evaluation of whether negotiated cipher suites support Perfect Forward Secrecy (PFS) (e.g., Ephemeral Diffie-Hellman ECDHE/DHE vs static RSA) `[PS]`.
* **REQ-11 (AI Feature Extraction)**: Extraction of numerical and categorical cryptographic features (JA3/JA3S fingerprints, extension distributions, handshake timing, cipher strengths) for intelligent analysis `[PS]`.
* **REQ-12 (AI Cryptographic Risk Classification & Posture Scoring)**: AI/ML-driven classification of security risks and calculation of overall cryptographic posture scores `[PS]`.
* **REQ-13 (AI Anomaly Detection)**: Machine learning techniques to detect anomalous or suspicious TLS behavior (e.g., unexpected client fingerprints, version downgrade attempts, unexpected extension profiles) `[PS]`.
* **REQ-14 (Threat Prioritization & Mitigation)**: Automated prioritization of identified vulnerabilities with actionable mitigation recommendations for administrators `[PS]`.
* **REQ-15 (Forensic Reporting & Dashboards)**: Generation of exportable forensic reports in JSON, PDF, and HTML formats, alongside an interactive web dashboard for security monitoring and visualization `[PS]`.

## 5. Constraints & Environment Realities

* **Air-Gapped & Passive Processing**: SOC and defense environments (such as NTRO) operate in isolated networks without outbound internet connectivity `[KNOWN]`. Active network probing, live OCSP stapling queries to public CAs, or calling public cloud LLM APIs (e.g., OpenAI API) are strictly infeasible `[INFERENCE]`.
* **Payload Encryption Boundary**: Once TLS negotiation completes, payload data (email body, credentials, headers) is encrypted `[KNOWN]`. Passive forensic analysis MUST rely exclusively on metadata in cleartext protocol frames (e.g., SMTP EHLO, STARTTLS response) and cleartext TLS Handshake records (Client Hello, Server Hello, Certificate) `[INFERENCE]`.
* **High PCAP File Volume**: Enterprise packet captures can range from hundreds of megabytes to several gigabytes `[KNOWN]`. Parsing speed and memory efficiency require streaming PCAP processing rather than loading entire PCAPs into RAM `[INFERENCE]`.
* **Local Trust Store Management**: Root certificate chain validation must rely on a locally bundlable trust store (e.g., Mozilla CA Certificate bundle) since public CRL/OCSP endpoints cannot be reached offline `[INFERENCE]`.

## 6. Research Questions

1. **How can in-band STARTTLS transitions be reliably detected across non-standard TCP ports?**  
   *Answer*: Perform deep packet inspection (DPI) for protocol-specific ASCII keywords (`220 ... STARTTLS` in SMTP, `CAPABILITY ... STARTTLS` in IMAP, `+OK STLS` in POP3) regardless of destination port `[RESEARCHED]`.
2. **What features best identify TLS downgrade attacks without decrypting payload traffic?**  
   *Answer*: Differences between client supported cipher list in Client Hello and negotiated cipher suite in Server Hello, presence of TLS fallback SCSV (`TLS_FALLBACK_SCSV`), mismatch between JA3 hash and normal client profiles, and version mismatches `[RESEARCHED]`.
3. **What standard defines modern cryptographic compliance for email infrastructure?**  
   *Answer*: NIST SP 800-52 Rev. 2 (mandating TLS 1.2/1.3, minimum 2048-bit RSA / 256-bit ECC, forbidding SSLv2/v3, TLS 1.0/1.1, RC4, 3DES, MD5, SHA-1 signatures) `[RESEARCHED]`. RFC 8314 deprecates cleartext email access/submission and STARTTLS in favor of Implicit TLS `[RESEARCHED]`.

## 10. Recommended Approach & Why

The **Hybrid Modular Engine (Approach 3)** is selected `[INFERENCE]`.

### Why Alternatives Were Rejected
1. **Approach 1 (Pure Rule-Based)** was rejected because deterministic rules alone cannot detect subtle behavioral anomalies, such as rare MUA fingerprint variations, version downgrade patterns across session clusters, or client impersonation attacks `[INFERENCE]`.
2. **Approach 2 (Deep Learning on Raw Bytes)** was rejected because cryptographic handshake auditing requires exact, deterministic verification of version numbers, key bit-lengths, and certificate validity dates `[INFERENCE]`. Deep learning models cannot guarantee 100% deterministic precision on binary fields and introduce black-box explainability issues unsuitable for forensic incident reporting `[INFERENCE]`.

### Advantage of the Selected Hybrid Approach
Approach 3 splits the workload into two specialized layers:
1. **Deterministic Layer**: Handles TCP reassembly, STARTTLS decoding, TLS handshake parsing, and X.509 certificate validation with 100% mathematical precision `[INFERENCE]`.
2. **Machine Learning Layer**: Uses lightweight, explainable models (Isolation Forest for anomaly detection and XGBoost for risk score weighting) on extracted handshake metadata (JA3/JA3S, extension lengths, cipher ordering) `[INFERENCE]`.

### Data Flow Narrative
1. **Ingestion**: The user uploads a `.pcap` or `.pcapng` file through the Web Dashboard or REST API endpoint `[INFERENCE]`.
2. **Stream Reassembly & Protocol Parsing**: The backend invokes the PCAP Engine. PyShark/TShark processes raw packet frames, grouping packets into 5-tuple TCP streams (Src IP, Src Port, Dst IP, Dst Port, Protocol) `[INFERENCE]`. The protocol dissector identifies cleartext commands (`EHLO`, `STARTTLS`, `1 CAPABILITY`, `STLS`) `[INFERENCE]`.
3. **TLS Handshake Dissection**: Upon detecting `STARTTLS` elevation or direct implicit TLS connections (ports 465, 993, 995), the TLS parser decodes Client Hello and Server Hello records, extracting the client-offered ciphers, negotiated cipher suite, TLS version, and extension arrays `[INFERENCE]`.
4. **Certificate Audit**: X.509 certificates embedded in the TLS Handshake are extracted. The certificate parser computes SHA-256 fingerprints, validates Subject Alternative Names (SAN), checks validity windows against current time, evaluates RSA/ECC key bit-lengths, signature algorithms (SHA-1 vs SHA-256), and validates the issuer chain against the local CA trust bundle `[INFERENCE]`.
5. **Deterministic Rule Benchmarking**: Extracted parameters are benchmarked against NIST SP 800-52 Rev 2 and RFC guidelines. Flaws (e.g., TLS 1.0, RC4, MD5 signature, expired cert, missing PFS) trigger deterministic risk flags `[INFERENCE]`.
6. **AI Feature Extraction & Anomaly Scoring**: Handshake parameters are converted into a feature vector (JA3 hash, cipher suite count, extension length, version ID). The Isolation Forest model calculates an anomaly score for the session, while the XGBoost model outputs a normalized Posture Score (0–100) `[INFERENCE]`.
7. **Storage & Dashboard Rendering**: Processed results are written to an analytical DuckDB/SQLite database and transmitted to the React frontend for real-time SOC dashboard rendering and report generation (PDF, JSON, HTML) `[INFERENCE]`.

## 13. AI/ML Justification

### Component 1: Cryptographic Posture Risk Classification & Prioritization
* **Purpose**: Map high-dimensional session flags (version, cipher, cert flags, PFS status) into a normalized security risk score (Low, Medium, High, Critical) and posture rating `[PS]`.
* **Model Type**: XGBoost / Random Forest Classifier `[INFERENCE]`.
* **Input**: Numerical vector: `[tls_version_id, cipher_security_bits, is_pfs, cert_days_to_expire, key_length, sig_algorithm_id, starttls_enforced]` `[INFERENCE]`.
* **Output**: Posture Score (0–100) and Severity Category (Critical, High, Medium, Low) `[INFERENCE]`.
* **Data Required**: Labeled synthetic dataset of 500+ sessions mapped to CVSS-like vulnerability scores `[INFERENCE]`.
* **Why AI is Preferable**: Provides nonlinear weighting of combined weak parameters (e.g., TLS 1.2 with RSA key exchange and 1024-bit cert is higher risk than TLS 1.2 with ECDHE and 1024-bit cert) `[INFERENCE]`.
* **Evaluation**: F1-Score, Precision, and Recall on synthetic test splits `[INFERENCE]`.
* **Failure Mode**: Model misclassifies a weak session as safe. *Mitigation*: Hard rules override ML predictions for known prohibited ciphers (e.g., RC4 always forces Critical risk) `[INFERENCE]`.
* **Human Oversight**: SOC analyst can view feature importance SHAP plots explaining the score `[INFERENCE]`.

### Component 2: TLS Anomaly Detection
* **Purpose**: Identify suspicious, non-standard, or spoofed TLS sessions (e.g., unknown MUA JA3 hashes, version downgrade attempts, malformed extensions) `[PS]`.
* **Model Type**: Isolation Forest (Unsupervised Anomaly Detection) `[INFERENCE]`.
* **Input**: Feature vector: `[JA3_hash_frequency, num_extensions, cipher_list_length, SNI_length, handshake_duration_ms]` `[INFERENCE]`.
* **Output**: Anomaly Flag (Boolean) and Anomaly Confidence Score (-1.0 to +1.0) `[INFERENCE]`.
* **Data Required**: Baseline capture of normal enterprise email client traffic `[INFERENCE]`.
* **Why AI is Preferable**: Detects unknown zero-day TLS client modifications or unexpected client behavior without explicit signatures `[INFERENCE]`.
* **Evaluation**: Receiver Operating Characteristic - Area Under Curve (ROC-AUC) on anomalous test PCAPs `[INFERENCE]`.
* **Failure Mode**: False positive anomaly alert for legitimate non-standard email client. *Mitigation*: Allow analyst to whitelist approved JA3 fingerprints in dashboard `[INFERENCE]`.

### Where AI MUST NOT Be Used
AI **MUST NOT** be used for deterministic validation tasks `[INFERENCE]`:
1. Parsing TLS Version, Cipher Suite Hex IDs, and Certificate Expiry Dates `[INFERENCE]`.
2. Checking RSA Key Length (e.g., 1024 vs 2048 bits) `[INFERENCE]`.
3. Verifying X.509 Digital Signature validity `[INFERENCE]`.
*Reason*: Deterministic code must perform exact parsing; using probabilistic AI models for standard binary parsing risks hallucinated compliance statuses `[INFERENCE]`.

## 14. Data Architecture & Offline/Low-Network Design

### Schema Architecture (DuckDB / SQLite)

```sql
-- Table 1: Ingested PCAP Files
CREATE TABLE pcap_files (
    pcap_id VARCHAR PRIMARY KEY,
    filename VARCHAR NOT NULL,
    upload_timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    total_packets INT,
    total_sessions INT,
    overall_posture_score FLOAT
);

-- Table 2: Reconstructed Email Protocol Sessions
CREATE TABLE email_sessions (
    session_id VARCHAR PRIMARY KEY,
    pcap_id VARCHAR REFERENCES pcap_files(pcap_id),
    src_ip VARCHAR,
    src_port INT,
    dst_ip VARCHAR,
    dst_port INT,
    protocol VARCHAR, -- 'SMTP', 'IMAP', 'POP3'
    starttls_detected BOOLEAN,
    starttls_successful BOOLEAN,
    implicit_tls BOOLEAN
);

-- Table 3: TLS Handshake & Cryptographic Metadata
CREATE TABLE tls_handshakes (
    handshake_id VARCHAR PRIMARY KEY,
    session_id VARCHAR REFERENCES email_sessions(session_id),
    tls_version VARCHAR, -- 'TLS 1.0', 'TLS 1.2', 'TLS 1.3'
    cipher_suite_hex VARCHAR,
    cipher_suite_name VARCHAR,
    key_exchange_algo VARCHAR,
    has_forward_secrecy BOOLEAN,
    ja3_fingerprint VARCHAR,
    ja3s_fingerprint VARCHAR
);

-- Table 4: Extracted X.509 Digital Certificates
CREATE TABLE certificates (
    cert_id VARCHAR PRIMARY KEY,
    session_id VARCHAR REFERENCES email_sessions(session_id),
    subject_cn VARCHAR,
    issuer_cn VARCHAR,
    valid_from TIMESTAMP,
    valid_until TIMESTAMP,
    is_expired BOOLEAN,
    key_algorithm VARCHAR, -- 'RSA', 'EC'
    key_length INT, -- 1024, 2048, 4096
    signature_algorithm VARCHAR, -- 'sha1WithRSAEncryption', 'sha256WithRSA'
    is_chain_valid BOOLEAN
);

-- Table 5: Cryptographic Vulnerabilities & AI Findings
CREATE TABLE security_findings (
    finding_id VARCHAR PRIMARY KEY,
    session_id VARCHAR REFERENCES email_sessions(session_id),
    rule_id VARCHAR,
    severity VARCHAR, -- 'CRITICAL', 'HIGH', 'MEDIUM', 'LOW'
    title VARCHAR,
    description TEXT,
    remediation_guidance TEXT,
    is_ai_anomaly BOOLEAN
);
```

### Offline / Air-Gapped Operations
* **Zero External Dependencies**: All static assets (React bundle, Tailwind CSS, Google Fonts, Recharts) are compiled into self-contained frontend builds served directly by FastAPI `[INFERENCE]`.
* **Embedded Trust Store**: Certificate chain validation uses an embedded `cacert.pem` trust bundle shipped within the application container `[INFERENCE]`.
* **Local Report Engine**: PDF reports are generated using `WeasyPrint` locally, requiring no external cloud printing or web services `[INFERENCE]`.
