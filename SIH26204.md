YatraDrishti bridges independent hospitality providers, local travel operators, and tourists through dynamic pricing & inventory management for SME hotels, multi-modal itinerary optimization, localized Multilingual AI Concierge, and offline-first mobile safety & navigation features [ASSUMPTION].

## 5. Constraints & Environment Realities

* **Geography & Remote Terrain:** Major Indian tourist circuits include high-altitude regions (Ladakh, Himachal Pradesh, Uttarakhand) and forest/coastal belts where 4G/5G mobile connectivity is spotty or non-existent `[KNOWN]`.
* **Device Landscape:** Small hotel operators and local tour guides often rely on budget Android smartphones (2GB–4GB RAM, Android 10+) rather than high-end devices or desktop PCs `[KNOWN]`.
* **Language Diversity:** India has 22 officially recognized languages. Tourists and local vendors in rural hubs (e.g. Hampi, Khajuraho, Mawlynnong) frequently communicate in regional dialects (Kannada, Hindi, Khasi) rather than English `[KNOWN]`.
* **Digital Literacy & Payment Habits:** While UPI adoption is universal in urban areas, micro-operators in deep rural circuits still require simplified, multi-lingual UI with voice prompts and WhatsApp-based notification workflows `[INFERENCE]`.
* **Field Operating Power:** Smartphones used by travelers during day-long excursions suffer battery drain when continuously running GPS/data-heavy maps; vector tile offline caching is essential `[INFERENCE]`.

## 9. Candidate Solution Approaches

### Approach 1: Monolithic OTA Aggregator Web Portal
* **Mechanism:** A traditional web platform connecting hotel listings and travel packages with an online payment gateway.
* **Required Data:** Hotel listings database, static travel packages JSON.
* **Architecture:** Node.js/Express monolithic server with PostgreSQL and React frontend.
* **Complexity:** Low.
* **Cost:** Very Low.
* **Explainability:** 100%.
* **Scalability:** Medium.
* **Hackathon Feasibility:** High (3-4 days build).
* **Production Feasibility:** Low (Redundant; cannot compete with established OTAs).
* **Risks:** Fails to differentiate from existing OTAs; no incentive for SME hotels to switch.

### Approach 2: AI Chatbot-First Concierge Application
* **Mechanism:** A conversational LLM interface (WhatsApp Bot + Web Widget) that answers tourist queries, suggests hotels, and links to external booking pages.
* **Required Data:** RAG vector store containing destination guides and hotel contact info.
* **Architecture:** Python FastAPI + LangChain + OpenAI/Llama-3 + WhatsApp Business API.
* **Complexity:** Medium.
* **Cost:** Medium (LLM token costs).
* **Explainability:** Low to Medium (LLM hallucinations possible).
* **Scalability:** High.
* **Hackathon Feasibility:** Very High.
* **Production Feasibility:** Low to Medium (Chatbots alone do not solve inventory management or transaction flows for hotel owners).
* **Risks:** High API cost; dynamic inventory updates are hard to enforce via text chat alone.

### Approach 3 (Recommended): YatraDrishti - Unified Open Tourism Intelligence & Hospitality Operating System
* **Mechanism:** A multi-sided system combining three core modules:
  1. *Hospitality Cloud (SME PMS):* Zero-commission direct booking engine, AI dynamic room rate recommender, and automated guest onboarding (NIDHI 2.0 / Form C helper).
  2. *Smart Travel Router:* Multi-modal transit generator (trains, buses, local taxis) paired with an offline-first PWA for tourists.
  3. *Hyper-Local Experience Marketplace:* Directly connects verified local guides, cultural performers, and artisans to tourists via location-based discovery.
* **Required Data:** NIDHI 2.0 mock schema, OpenStreetMap GeoJSON, GTFS route data, weather API, hotel booking transactions database.
* **Architecture:** Microservices/Modular Monolith (Node.js/FastAPI) + PostgreSQL/PostGIS + Redis + Vector DB (Qdrant/FAISS) + React Native / PWA frontend.
* **Complexity:** High.
* **Cost:** Low to Medium.
* **Explainability:** High (Hybrid deterministic logic + bounded LLM RAG).
* **Scalability:** High.
* **Hackathon Feasibility:** Realistic MVP obtainable within student hackathon timeframe by focusing on core prototype flows.
* **Production Feasibility:** Exceptional (Solves structural pain points across all three legs: Hotels, Travel, Others).
* **Risks:** Multi-stakeholder UI complexity; requires robust demo simulation data.

### Data-Flow Narrative

1. **Merchant Onboarding & Inventory Listing:**
   * A budget hotel owner accesses the Merchant Portal, fills basic property details, and enters room categories and base rates.
   * The *Hospitality Service* stores property data in PostgreSQL and assigns a unique QR/WhatsApp link for direct guest bookings.
2. **AI Dynamic Price Suggestion:**
   * Nightly, the *AI Intelligence Engine* evaluates local weather forecasts, local festival calendars, nearby competing hotel prices, and historic booking velocity.
   * The model calculates an optimal recommended rate and alerts the hotel manager via SMS/WhatsApp to accept or adjust with 1-click `[INFERENCE]`.
3. **Tourist Itinerary Generation:**
   * A traveler opens the Tourist PWA, selects budget, travel dates, interest tags (e.g., heritage, adventure), and starting location.
   * The *Smart Travel Router* queries PostGIS spatial indices to locate optimal destinations, fetches multi-modal transit legs, and queries the *Hospitality Service* for verified room availability.
   * The response is compiled into a chronologically sequenced itinerary with estimated costs and interactive maps `[INFERENCE]`.
4. **Offline Synchronization:**
   * When the tourist clicks "Save Trip Offline", the PWA downloads Vector Map tiles (MBTiles format), accommodation details, contact info, and step-by-step route directions into IndexedDB via Service Workers.
   * If network connection drops in remote zones, the PWA continues displaying live GPS position over pre-cached vector tiles `[INFERENCE]`.

## 13. AI/ML Justification

### Component 1: Hotel Dynamic Pricing Engine

* **Purpose:** Recommend daily optimal room rates for budget hotels to maximize yield based on demand indicators.
* **Model Type:** LightGBM / Ridge Regression model trained on seasonality, day-of-week, local events, weather, and current occupancy velocity.
* **Input:** `[hotel_id, date, base_rate, local_event_score, weather_forecast_code, current_occupancy_pct, competitor_avg_rate]`
* **Output:** Recommended rate (INR) + upper/lower confidence bounds.
* **Data Required:** Historical pricing dataset + simulated festival calendar data.
* **Why AI is Preferable:** Static pricing leaves revenue on the table during peak festivals and causes high vacancy during off-peak periods. Rule-based matrices become unmanageable with multiple variables `[INFERENCE]`.
* **Evaluation Metric:** Mean Absolute Percentage Error (MAPE) < 8% on room yield predictions.
* **Failure Mode:** If model predicts an unrealistic rate (e.g. 5x base rate), a strict safety guardrail caps pricing changes to between -30% and +80% of base rate.
* **Human Oversight:** The hotel manager receives a alert and must confirm rate changes before they publish `[INFERENCE]`.

### Component 2: Multilingual Travel RAG Assistant

* **Purpose:** Answer tourist queries about travel rules, local customs, heritage facts, and safety guidelines in regional Indian languages.
* **Model Type:** Llama-3-8B / Gemini-Flash with Qdrant Vector Retrieval-Augmented Generation (RAG).
* **Input:** User natural language query (Text/Voice) + User location coordinates + Language preference.
* **Output:** Structured natural language response + source references + actionable links.
* **Data Required:** Verified tourism text repository (scraped from Incredible India, ASI documentation, local travel guides).
* **Why AI is Preferable:** Static FAQ pages cannot handle natural conversational queries in mixed Hindi/English or regional dialects.
* **Evaluation Metric:** Faithfulness and Answer Relevance score > 0.85 (Ragas framework).
* **Failure Mode:** Fallback to structured search results and direct emergency helpline contacts if confidence score is low.
* **Human Oversight:** AI responses include official source disclaimer tags `[INFERENCE]`.

### Where AI Should NOT Be Used
* **Booking Ledger & Inventory Allocation:** Must strictly use ACID-compliant SQL transactions with database row locks. AI should never make dynamic decisions on room allocation or payment processing `[INFERENCE]`.
* **Emergency Dispatch / Helplines:** Must directly route to hardcoded SOS phone numbers and local police authority registries `[INFERENCE]`.

## 14. Data Architecture & Offline/Low-Network Design

### Core Relational Database Schema (PostgreSQL)

```sql
-- SME Hotel Properties
CREATE TABLE properties (
    property_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    owner_id UUID NOT NULL,
    title VARCHAR(255) NOT NULL,
    category VARCHAR(50) CHECK (category IN ('hotel', 'homestay', 'resort', 'bed_and_breakfast')),
    nidhi_id VARCHAR(100), -- NIDHI 2.0 registration reference
    address TEXT NOT NULL,
    location GEOMETRY(Point, 4326) NOT NULL,
    base_rate_inr NUMERIC(10,2) NOT NULL,
    is_active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- Property Rooms & Inventory
CREATE TABLE room_inventory (
    inventory_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    property_id UUID REFERENCES properties(property_id) ON DELETE CASCADE,
    room_type VARCHAR(100) NOT NULL,
    total_rooms INT NOT NULL,
    available_rooms INT NOT NULL,
    date DATE NOT NULL,
    current_rate_inr NUMERIC(10,2) NOT NULL,
    CONSTRAINT unique_property_date_room UNIQUE(property_id, room_type, date)
);

-- Bookings Ledger
CREATE TABLE bookings (
    booking_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    property_id UUID REFERENCES properties(property_id),
    tourist_id UUID NOT NULL,
    check_in DATE NOT NULL,
    check_out DATE NOT NULL,
    total_amount_inr NUMERIC(10,2) NOT NULL,
    status VARCHAR(30) DEFAULT 'confirmed' CHECK (status IN ('pending', 'confirmed', 'cancelled', 'completed')),
    payment_tx_id VARCHAR(100),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- Local Experience Providers ("Others")
CREATE TABLE local_experiences (
    experience_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    provider_name VARCHAR(255) NOT NULL,
    service_type VARCHAR(50) CHECK (service_type IN ('guide', 'artisan_workshop', 'taxi', 'cultural_show')),
    location GEOMETRY(Point, 4326) NOT NULL,
    hourly_rate_inr NUMERIC(10,2) NOT NULL,
    contact_phone VARCHAR(20) NOT NULL,
    rating NUMERIC(2,1) DEFAULT 5.0
);
```

### Offline-First Architecture & Synchronization Flow

```
[ PWA Client (Browser) ]
       |
       +---> Detects Network Disconnection (navigator.onLine == false)
       |
       +---> Swaps Map Renderer to Leaflet IndexedDB Tile Cache
       |
       +---> Queues Offline Actions (Bookings, Favorite Spots) in IndexedDB Queue
       |
       v (Network Restored)
[ Service Worker Sync ] ---> Posts Queued JSON Payloads to Gateway (/api/v1/sync)
       |
       v
[ Backend Sync Controller ]
       |
       +---> Resolves Idempotent Booking Requests (UUID check)
       +---> Handles Conflicts (If room sold out: Flags 'Pending Manual Confirmation')
       +---> Returns Sync Response -> Clears IndexedDB Queue
```

* **Bandwidth Reduction:** API payloads use compressed JSON arrays; map graphics use lightweight Vector Mapbox Tiles (.pbf) compressed via Gzip/Brotli.
* **Conflict Resolution:** Last-Write-Wins rule for preference updates; optimistic locking with database version tags for room bookings.

## 15. Security, Privacy & Governance

* **Personal Identifiable Information (PII):** Guest phone numbers, government identification details (Aadhaar/Passport for Form C compliance) are encrypted at rest using AES-256 and in transit via TLS 1.3 `[KNOWN]`.
* **Location Privacy:** Tourist GPS coordinates are processed transiently in memory for route generation and emergency alerts; precise location traces are never sold or stored permanently in unhashed form `[INFERENCE]`.
* **Authentication & Authorization:** Role-Based Access Control (RBAC) enforced via JWT tokens separating `Tourist`, `Merchant_Hotel`, `Local_Provider`, and `System_Admin` `[ASSUMPTION]`.
* **Regulatory Compliance:** Designed in alignment with India's Digital Personal Data Protection (DPDP) Act 2023—providing explicit consent toggles, purpose limitation, and a "Right to Data Erasure" endpoint `[RESEARCHED]`.
* **System Misuse Mitigation:** Fake review prevention via verified booking key validation; direct provider phone masking using virtual cloud telephony simulation `[INFERENCE]`.
