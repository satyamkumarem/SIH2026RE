## 1. Executive Snapshot

### Summary
The WeatherGPT project aims to solve the problem of fragmented meteorological information dissemination across India [PS]. Currently, weather data is scattered across multiple portals, bulletins, satellite feeds, and forecast systems, making it difficult for citizens, farmers, researchers, and disaster managers to obtain timely, actionable insights [PS]. WeatherGPT will serve as a multi-channel, voice-enabled conversational AI platform that ingests real-time meteorological datasets, numerical weather prediction (NWP) model outputs (such as GFS/WRF), and disaster warning feeds [PS]. It delivers location-specific weather updates, early disaster warnings, agromet advisories, aviation briefings, and historical climate trend analyses in multiple Indian languages via natural language querying and voice interaction [PS].

## 5. Constraints & Environment Realities

1. **Connectivity Realities in Rural/Coastal Areas** [KNOWN]
   - *Impact*: Rural agricultural belts and marine offshore zones frequently suffer from intermittent 2G/3G connectivity or packet loss [KNOWN].
   - *Design Response*: Implement an offline-first architecture with local SQLite/IndexedDB caching, lightweight JSON payloads, and audio compression (Opus format) [INFERENCE].

2. **Language & Literacy Barriers** [KNOWN]
   - *Impact*: Over 50% of rural agricultural workers in India rely on spoken local dialects and cannot easily parse written text or complex meteorological terms [KNOWN].
   - *Design Response*: Voice-first interaction model with automatically generated audio responses in regional Indian languages (Hindi, Marathi, Telugu, Tamil, etc.) using lightweight TTS [INFERENCE].

3. **Hardware Constraints on Field Devices** [KNOWN]
   - *Impact*: Target users often operate entry-level smartphones with limited storage (<32 GB) and constrained RAM (<3 GB) [KNOWN].
   - *Design Response*: Avoid heavy client-side AI execution. Keep client bundle size under 15 MB and offload speech recognition / LLM inference to a cloud pipeline [INFERENCE].

4. **Heterogeneous Meteorological Data Formats** [RESEARCHED]
   - *Impact*: Weather data exists in diverse formats including GRIB2 (GFS/WRF forecasts), NetCDF (historical gridded data), CAP XML (alerts), GeoTIFF (satellite/radar), and JSON/REST APIs (station observations) [RESEARCHED].
   - *Design Response*: Build a unified Data Abstraction Layer that transforms heterogeneous formats into a standardized spatial-temporal schema in PostgreSQL/PostGIS [INFERENCE].

5. **Rate Limits & IP Whitelisting on Government APIs** [RESEARCHED]
   - *Impact*: Official IMD APIs (`api.imd.gov.in`) require static IP whitelisting and enforce strict rate limits during extreme weather events [RESEARCHED].
   - *Design Response*: Implement a backend caching proxy (Redis) with exponential backoff and fallback mock data triggers during hackathon demonstrations [INFERENCE].

## 9. Candidate Solution Approaches

| Evaluation Criteria | Approach 1: Intent-Driven Rule Engine + Rigid Templates | Approach 2: Pure LLM with Web Search / Unstructured RAG | Approach 3: Hybrid Architecture (LLM Query Parser + Deterministic Data Pipeline + Multi-Domain Persona Engine) [RECOMMENDED] |
| :--- | :--- | :--- | :--- |
| **Mechanism** | Regex and intent-slot parsing mapping user query directly to fixed API endpoints and templated responses. | User query fed directly to an LLM (e.g., GPT-4 / Llama 3) with web searching or vector DB search over weather text. | LLM acts strictly as an Intent & Entity Extractor (JSON output). ## 10. Recommended Approach & Why

The recommended architecture is **Approach 3: Hybrid AI Architecture (LLM Intent Extractor & Structured Spatial RAG Engine)** [INFERENCE].

### Why Alternatives Were Rejected
1. **Rejection of Approach 1 (Rule-Based System)**: While fast, pure rule-based systems break whenever users speak in natural, non-standard Indic dialects or phrase complex queries (e.g., "If it rains tomorrow morning in Nashik, should I harvest my grapes today?"). It fails to satisfy the core SIH mandate for an "intelligent conversational platform" [PS].
2. **Rejection of Approach 2 (Pure Unstructured LLM / Web-RAG)**: LLMs inherently struggle with precise spatial-temporal numeric calculations and are known to hallucinate numerical values (e.g., predicting 45°C instead of 35°C or inventing non-existent rain warnings) [KNOWN]. In disaster management and aviation weather, hallucinated numbers can lead to catastrophic consequences [INFERENCE].

### Why Approach 3 Wins
- **Guaranteed Numeric Factual Accuracy**: The LLM *never* generates weather data from its parametric memory. Instead, it converts user text/speech into a structured JSON query payload (Location: "Pune", Time: "Next 24 Hours", Domain: "Agriculture", Parameter: "Precipitation") [INFERENCE].
- **Sub-Second Latency**: Structured database lookups against pre-ingested GFS/IMD caches take <50ms. The LLM is only used for lightweight intent extraction and final natural language voice synthesis [INFERENCE].
- **Safety Guardrails**: If an extreme alert (CAP XML) exists for the user's location, the system overrides normal responses and injects high-priority safety instructions [INFERENCE].

### Detailed Data Flow Narrative
1. **User Request**: A farmer in Nashik presses the voice button on the mobile app and speaks in Marathi: "आज संध्याकाळी पाऊस पडेल का? मला पिकावर औषध फवारायचे आहे." (*"Will it rain this evening? I need to spray pesticide on my crop."*) [INFERENCE].
2. **Audio Ingestion & STT**: The compressed audio (Opus format over WebSocket) reaches the FastAPI backend and is converted to text using an Indic Speech-to-Text engine (Bhashini API or OpenAI Whisper) [INFERENCE].
3. **Intent & Entity Extraction**: The transcribed text is sent to the LLM Query Engine. Using strict JSON function calling, the LLM extracts:
   - `Intent`: `WEATHER_FORECAST_AND_AGRO_ADVISORY`
   - `Location`: `Nashik, Maharashtra`
   - `Time_Range`: `Today Evening (16:00 - 20:00 IST)`
   - `Domain`: `Agriculture` (Sub-category: `Pesticide Spraying`) [INFERENCE].
4. **Spatial Resolution & Querying**: The orchestrator converts "Nashik" into coordinates (lat/long) via PostGIS, fetches real-time hourly GFS/IMD forecast data from Redis/PostgreSQL, and checks the CAP Alert MQTT broker for active severe weather warnings [INFERENCE].
5. **Domain Context Synthesis**: The database returns: `Rain Probability: 85%, Expected Rainfall: 12mm between 17:00-19:00 IST, Wind Speed: 18 km/h`. The Agromet Rule Engine evaluates: *Pesticide spraying not recommended when rain probability > 40% or wind > 15 km/h* [INFERENCE].
6. **Response Generation & TTS**: The synthesized context + raw metrics are passed back to the LLM to format a concise, empathetic response in Marathi. The text is passed to an Indic TTS model, streaming audio back to the mobile app [INFERENCE].

## 13. AI/ML Justification

### AI Component 1: Intent & Entity Extractor (LLM)
- *Purpose*: Extract structured parameters (location, temporal range, weather metric, user persona) from raw unstructured user queries in natural language [INFERENCE].
- *Model Type*: Fine-tuned Llama-3-8B-Instruct or GPT-4o-Mini with JSON schema mode / Function Calling [INFERENCE].
- *Input*: Unstructured text query (e.g., "Will it hail in Shimla over the weekend?") [INFERENCE].
- *Output*: JSON payload `{"location": "Shimla", "start_date": "2026-09-05", "end_date": "2026-09-06", "phenomenon": "hail"}` [INFERENCE].
- *Data Required*: 500+ annotated multi-domain weather queries in English and Indian languages [ASSUMPTION].
- *Why AI is Preferable*: Simple regex or rule parsers fail on complex, dialectal, or multi-intent queries [INFERENCE].
- *Evaluation Metric*: Entity extraction F1-score (>0.92 target) [INFERENCE].
- *Failure Mode*: Unrecognized location -> Prompt user for clarification or fallback to device GPS [INFERENCE].
- *Human Oversight*: High-risk disaster parameters are cross-checked against CAP alert tables before generating response [INFERENCE].

### AI Component 2: Indic Speech Processing (STT / TTS)
- *Purpose*: Convert spoken audio queries into text and synthesize written responses back into clear audio for rural users [PS].
- *Model Type*: Whisper-Medium fine-tuned on Indic speech / AI4Bharat Bhashini Models [RESEARCHED].
- *Input*: Audio stream (Opus/WAV) from mobile device [INFERENCE].
- *Output*: Transcribed Indic text / Audio output byte stream [INFERENCE].
- *Data Required*: Pre-trained Indic speech corpora [RESEARCHED].
- *Why AI is Preferable*: Deterministic algorithms cannot process acoustic human speech variations [KNOWN].
- *Evaluation Metric*: Word Error Rate (WER < 12%) [INFERENCE].
- *Failure Mode*: Noisy audio background -> Return text transcription to screen and request voice repeat [INFERENCE].
- *Human Oversight*: On-screen transcript allows user to visually inspect speech recognition accuracy [INFERENCE].

### Explicit Non-AI Component: Numeric Forecast Calculation
- *Decision*: **DO NOT USE AI / LLMs TO CALCULATE OR PREDICT NUMERIC FORECAST METRICS DIRECTLY** [INFERENCE].
- *Justification*: Weather prediction requires solving complex physical thermodynamic differential equations (run by supercomputers executing WRF/GFS models) [KNOWN]. LLMs predicting future temperature or precipitation values produce dangerous hallucinations [INFERENCE]. All numerical weather metrics MUST come directly from IMD/NOAA database tables [INFERENCE].

## 14. Data Architecture & Offline/Low-Network Design

### Database Schema (Simplified SQL Definition)

```sql
-- Weather Station Current Observations
CREATE TABLE station_observations (
    station_id VARCHAR(50) PRIMARY KEY,
    station_name VARCHAR(100),
    geom GEOMETRY(Point, 4326),
    temp_c NUMERIC(4,1),
    humidity_pct INT,
    wind_speed_kmh NUMERIC(4,1),
    rainfall_24h_mm NUMERIC(5,1),
    recorded_at TIMESTAMPTZ NOT NULL
);

-- NWP Grid Forecasts (GFS / WRF Ingest)
CREATE TABLE nwp_grid_forecasts (
    id BIGSERIAL PRIMARY KEY,
    model_name VARCHAR(20), -- 'GFS' or 'WRF'
    grid_point GEOMETRY(Point, 4326),
    forecast_time TIMESTAMPTZ NOT NULL,
    temp_2m NUMERIC(4,1),
    precip_prob_pct INT,
    precip_amount_mm NUMERIC(5,1),
    wind_u NUMERIC(4,1),
    wind_v NUMERIC(4,1),
    created_at TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_nwp_spatial ON nwp_grid_forecasts USING GIST(grid_point);
CREATE INDEX idx_nwp_time ON nwp_grid_forecasts(forecast_time);

-- CAP Disaster Alerts
CREATE TABLE cap_alerts (
    alert_id VARCHAR(100) PRIMARY KEY,
    headline TEXT,
    severity VARCHAR(20), -- 'Extreme', 'Severe', 'Moderate'
    affected_zone GEOMETRY(Polygon, 4326),
    instruction TEXT,
    effective_from TIMESTAMPTZ,
    expires_at TIMESTAMPTZ
);
```

### Offline & Low-Network Optimization Strategy
1. **Local SQLite / PWA Cache**: The mobile client caches the 7-day forecast for the user's saved location locally [INFERENCE].
2. **Bandwidth Reduction**: Voice streams are compressed using the Opus codec at 16 kbps (reducing data usage by 80% compared to raw PCM WAV) [INFERENCE].
3. **Payload Compression**: All backend REST and WebSocket JSON responses are gzip/brotli compressed [INFERENCE].
4. **Offline Mode UX**: When network connection drops below 2G speeds:
   - The app notifies the user: *"Working Offline. Showing cached forecast from 2 hours ago."* [INFERENCE].
   - Critical safety rules (e.g., standard lightning safety rules) remain locally available on device storage [INFERENCE].
