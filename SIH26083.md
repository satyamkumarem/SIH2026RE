## 1. Executive Snapshot

Rising global temperatures and climate change have severely amplified the frequency, duration, and intensity of heatwaves across India [PS] [KNOWN]. Traditional heatwave alerts released by meteorological departments rely almost exclusively on ambient dry-bulb air temperature thresholds [PS]. This creates a dangerous public health blind spot because standard dry-bulb forecasts ignore the compounding physiological impacts of relative humidity, wind speed, and solar radiation on human thermoregulation [PS]. A temperature of 40°C at 20% relative humidity is survivable with standard hydration, whereas 40°C at 70% relative humidity exceeds the human body's evaporative cooling limit through perspiration and can be fatal [PS] [KNOWN]. Current public health and municipal infrastructure lacks localized, impact-based forecasting that translates atmospheric parameters into physiological risk, human thermal stress indices, and projected health outcomes like hospitalizations and mortality [PS]. 

To bridge this gap, the proposed solution—**HeatShield AI (Hyper-Local Thermal Stress & Mortality Early Warning System)**—is an intelligent, end-to-end impact-based predictive platform [INFERENCE]. It ingests multi-variable numerical weather prediction (NWP) forecasts from the National Centre for Medium Range Weather Forecasting (NCMRWF) and India Meteorological Department (IMD) [INFERENCE], computes multi-metric Human Thermal Stress Indices (Universal Thermal Climate Index [UTCI], Wet-Bulb Globe Temperature [WBGT], and Heat Index [HI]) [PS], maps them to an automated Mortality and Hospitalization Risk Index using statistical epidemiological models calibrated with local demographics [PS] [INFERENCE], displays hyper-local ward-level color-coded risk maps on a dynamic GIS dashboard [PS], and dispatches automated, role-based actionable advisories and SOP triggers via SMS/WhatsApp APIs to city administrators, healthcare systems, and vulnerable citizens 3 to 5 days in advance [PS].

## 5. Constraints & Environment Realities

* **Geographic & Micro-Climate Heterogeneity:** Indian cities exhibit intense Urban Heat Island (UHI) effects where high-density concrete slums experience 3°C to 6°C higher ambient thermal stress than vegetated, affluent zones [RESEARCHED]. The system must account for local land cover (NDVI) and built environment (impervious surface area) [INFERENCE].
* **Weather Data Grid Resolution:** Raw global and regional NWP models (like NCMRWF NCUM or NOAA GFS) operate at 12 km resolution [RESEARCHED]. Wards in major Indian cities average 1 km² to 5 km² [RESEARCHED]. Direct grid-to-ward mapping requires spatial downscaling [INFERENCE].
* **Connectivity & Network Variability:** High-density urban slums and peripheral rural wards suffer from frequent cellular network congestion and bandwidth throttling during emergencies [KNOWN]. The administrative GIS portal must remain lightweight (<2 MB initial payload), and field worker web apps must support Progressive Web App (PWA) offline capabilities [INFERENCE].
* **Hardware Availability in Municipal Bodies:** Municipal ward offices often rely on entry-level desktop PCs or low-cost Android smartphones running older browser versions [KNOWN]. Dashboards must be optimized for standard web browsers (Chrome/Firefox/Edge) without requiring high-end GPUs for vector rendering [INFERENCE].
* **Language & Digital Literacy:** Over 40% of outdoor manual workers in urban centers are migrant laborers with limited formal literacy [RESEARCHED]. Notifications sent via SMS/WhatsApp must support voice-notes or visual iconography/color codes (Green/Yellow/Orange/Red) alongside simple regional text [INFERENCE].
* **Power Grid Reliability:** During peak heatwaves, extreme AC usage leads to localized power grid trippings and blackouts [KNOWN]. Critical alerting infrastructure (SMS gateway workers and backend servers) must run on fault-tolerant cloud environments [INFERENCE].

## 9. Candidate Solution Approaches

When designing a localized heatwave warning and thermal stress platform, three distinct technical architectures can be evaluated:

### Approach 1: Simple Rule-Based & Heat Index Threshold System
* **Mechanism:** Ingest dry-bulb temperature and relative humidity from a public weather API. Calculate NOAA Heat Index using Rothfusz regression equation [RESEARCHED]. Map Heat Index values to static alert categories (e.g., HI > 41°C = Orange Alert). Apply a linear multiplier based on ward density to estimate risk.
* **Architecture:** Monolithic Python Flask web app with SQLite database and basic Leaflet JS map.
* **Evaluation:**
  * *Problem Fit:* Low. Fails to incorporate wind speed and solar radiation required for UTCI/WBGT [PS].
  * *Accuracy:* Poor. Static thresholds ignore lag effects and acclimatization [RESEARCHED].
  * *Complexity:* Very low.
  * *Explainability:* High (Simple lookup tables).
  * *Cost:* Almost zero.
  * *Scalability:* Limited.
  * *Hackathon Feasibility:* 10/10 | *Production Feasibility:* 3/10.

### Approach 2: Classical ML / Statistical Poisson GAM + Multi-Index Engine + Spatial GIS (RECOMMENDED)
* **Mechanism:** Multi-stage pipeline. Ingest 4D forecast variables (T, RH, Wind, Radiation) from NWP/Open-Meteo. Calculate exact UTCI, WBGT (Liljegren model), and Heat Index using physics-based thermodynamic equations via `pythermalcomfort` [RESEARCHED]. Apply an over-dispersed Poisson Generalized Additive Model (GAM) / Log-Linear model calibrated with historical climate-mortality records and ward demographic vulnerability indices to predict excess mortality and hospitalizations 3-5 days in advance [RESEARCHED]. Downscale grid points to ward polygons using land-use/NDVI weighting [INFERENCE]. Trigger role-based advisories via SMS/WhatsApp APIs [PS].
* **Architecture:** Microservices/Modular architecture: FastAPI backend, PostGIS spatial database, Redis queue with Celery for async computations, React/Next.js frontend with Leaflet/Mapbox GL, and Twilio/WhatsApp webhook integration.
* **Evaluation:**
  * *Problem Fit:* Excellent. Fully addresses UTCI, WBGT, HI, mortality risk prediction, ward GIS, and automated advisories [PS].
  * *Accuracy:* High. Physics-based thermal indices combined with epidemiologically validated statistical health models [RESEARCHED].
  * *Complexity:* Moderate. Completely manageable for a 4-6 student hackathon team.
  * *Explainability:* High. Public health officials can inspect health coefficients and thermal index formulas.
  * *Cost:* Low (Open-source stack).
  * *Scalability:* High.
  * *Hackathon Feasibility:* 9/10 | *Production Feasibility:* 9/10.

### Approach 3: Deep Learning (GNN + Physics-Informed Neural Networks - PINN) + Generative Diffusion Downscaling
* **Mechanism:** Map 12 km NCMRWF ensemble forecasts onto a spherical icosahedral grid using Graph Neural Networks (GNN) to calculate atmospheric anomalies. Pipe isolated regions into a Generative Diffusion Model for sub-kilometer downscaling [RESEARCHED]. Use a deep LSTM/Transformer network trained on hospital records to predict mortality.
* **Architecture:** Distributed PyTorch cluster on GPU servers, Complex spatial pipeline, React frontend.
* **Evaluation:**
  * *Problem Fit:* High theoretical capability, but excessive overhead.
  * *Accuracy:* High potential, but susceptible to "black-box" hallucinations and extreme overfitting without massive training data [INFERENCE].
  * *Complexity:* Extremely High. Requires massive GPU infrastructure and deep DL expertise.
  * *Explainability:* Very low (Black-box neural networks rejected by government health authorities).
  * *Cost:* Extremely high (GPU instances required).
  * *Scalability:* Hard to deploy on low-spec municipal infrastructure.
  * *Hackathon Feasibility:* 4/10 | *Production Feasibility:* 4/10.

### Detailed Data-Flow Narrative

1. **Forecast Data Ingestion:** Every 6 hours, the system background worker (Celery/Cron) triggers an ingestion script that fetches 5-day hourly meteorological forecasts (2m Air Temperature, Relative Humidity, 10m Wind Speed, Surface Solar Radiation Downwards) for the target region from numerical weather forecast APIs (NCMRWF/Open-Meteo/GFS) `[INFERENCE]`.
2. **Thermodynamic Index Calculation:** Ingestion workers pass raw weather arrays into the Thermodynamic Engine. Using `pythermalcomfort`, the system calculates hourly UTCI, WBGT, and Heat Index values for every grid point `[RESEARCHED]`.
3. **Spatial Downscaling & Ward Mapping:** The PostGIS spatial engine maps grid-level thermal indices onto municipal ward GeoJSON polygons. A urban heat island spatial weighting factor (derived from ward-level vegetation cover and built-up density) adjusts the ambient UTCI score to reflect hyper-local ward conditions `[INFERENCE]`.
4. **Mortality & Hospitalization Risk Estimation:** For each ward, the adjusted UTCI sequence is fed into the epidemiological Poisson GAM. The model computes the expected percentage increase in all-cause mortality and predicted emergency room hospitalization spikes over the next 3 to 5 days relative to baseline `[RESEARCHED]`.
5. **Vulnerability Weighting & Alert Classification:** The system multiplies health risk by the Ward Social Vulnerability Index (SVI based on elderly density, BPL ratio, and outdoor worker proportion). Wards are categorized into color-coded threat levels: **Green (Comfortable/Low)**, **Yellow (Moderate Stress)**, **Orange (Severe Stress)**, and **Red (Extreme Danger / Fatal)** `[PS]`.
6. **Automated Advisory Generation & Alert Dispatch:** When a ward enters **Orange** or **Red** status 3-5 days in advance, the backend Advisory Engine automatically builds role-specific SOP messages. The Alert Dispatcher pushes WhatsApp/SMS notifications to registered city disaster managers, health officers, and outdoor worker groups `[PS]`.

## 13. AI/ML Justification

### AI Component 1: Epidemiological Mortality & Hospitalization Risk Estimator

1. **What exact problem does AI solve?** Maps multi-day non-linear exposures of human thermal stress (UTCI/WBGT) to daily excess mortality percentage and emergency room hospitalization spikes, accounting for lag effects (0-3 days) [RESEARCHED].
2. **What is the input?** Hourly forecasted UTCI (°C), duration of event (consecutive hours > threshold), historical baseline mean summer temperature, ward demographic vulnerability index (elderly %, BPL %) [RESEARCHED].
3. **What is the output?** Predicted Percentage Increase in Excess Mortality (%) and Predicted Hospitalization Spike Index (0-100 scale) for each ward 3 to 5 days in advance [PS].
4. **Why can a simpler rule/system not solve it?** Human physiological response to heat is non-linear and exhibits a "U-shaped" or "J-shaped" exposure-response curve with distinct local thresholds [RESEARCHED]. A simple linear rule fails to capture compounding lag effects (e.g., 3 consecutive warm nights increase mortality significantly more than a single hot afternoon) [RESEARCHED].
5. **What data is required?** Historical daily temperature/UTCI time series combined with historical daily all-cause mortality and hospital admission logs [RESEARCHED].
6. **How will it be evaluated?** Root Mean Square Error (RMSE), Mean Absolute Error (MAE), and Poisson Deviance on historical test years [RESEARCHED].
7. **What happens when it is wrong?** False Positive: Municipalities over-prepare (minor resource expense). False Negative: Under-alerting during lethal heatwave. Mitigation: System sets conservative confidence bounds and incorporates human-in-the-loop validation for Red Alerts [INFERENCE].
8. **Does it require training?** Yes (fitting Poisson GAM / Log-Linear parameters on historical health-weather data) [RESEARCHED].
9. **Does it require fine-tuning?** Yes, city-specific calibration (e.g., Delhi thresholds differ from coastal Chennai thresholds) [RESEARCHED].
10. **Does it require RAG?** No.
11. **Does it require computer vision?** No.
12. **Does it require speech processing?** No (Optional TTS for voice notifications in future scope).
13. **Does it require forecasting?** Yes (integrates NWP weather forecasts) [PS].
14. **Is human oversight required?** Yes, city disaster management officers review automated Red Alerts before triggering major city-wide shutdowns [INFERENCE].

### Explicit Non-AI Components (Where AI Should NOT Be Used)
* **UTCI, WBGT, and Heat Index Calculations:** Calculating UTCI and WBGT must **NOT** use neural networks or ML regression. They must use exact physics-based thermodynamic algorithms and standard polynomial approximations (e.g., ISO 7243 WBGT standard and UTCI universal thermoregulation code) [RESEARCHED]. ML introduces floating-point errors and non-deterministic behavior into deterministic physical laws `[INFERENCE]`.

## 14. Data Architecture & Offline/Low-Network Design

### Spatial Database Schema (PostgreSQL + PostGIS)

```sql
-- Ward Master & Spatial Boundaries
CREATE TABLE wards (
    ward_id VARCHAR(50) PRIMARY KEY,
    ward_name VARCHAR(100) NOT NULL,
    zone_name VARCHAR(100) NOT NULL,
    city_name VARCHAR(100) NOT NULL,
    population_total INT,
    elderly_pop_density FLOAT, -- demographic vulnerability
    outdoor_worker_ratio FLOAT, -- demographic vulnerability
    svi_score FLOAT, -- Social Vulnerability Index (0.0 to 1.0)
    geom GEOMETRY(MultiPolygon, 4326) -- WGS84 Spatial Polygon
);

-- Time-Series Hourly Forecasts & Computed Indices
CREATE TABLE thermal_forecasts (
    forecast_id BIGSERIAL PRIMARY KEY,
    ward_id VARCHAR(50) REFERENCES wards(ward_id),
    forecast_timestamp TIMESTAMP WITH TIME ZONE NOT NULL,
    lead_time_days INT CHECK (lead_time_days BETWEEN 1 AND 5),
    temp_drybulb FLOAT, -- °C
    relative_humidity FLOAT, -- %
    wind_speed_10m FLOAT, -- m/s
    solar_radiation FLOAT, -- W/m²
    utci_val FLOAT, -- Calculated UTCI °C
    wbgt_val FLOAT, -- Calculated WBGT °C
    heat_index_val FLOAT, -- Calculated HI °C
    risk_level VARCHAR(20) CHECK (risk_level IN ('GREEN', 'YELLOW', 'ORANGE', 'RED')),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Health Impact Projections
CREATE TABLE health_impact_predictions (
    prediction_id BIGSERIAL PRIMARY KEY,
    ward_id VARCHAR(50) REFERENCES wards(ward_id),
    forecast_date DATE NOT NULL,
    predicted_excess_mortality_pct FLOAT,
    predicted_hospital_admissions_spike FLOAT,
    alert_category VARCHAR(20)
);

-- Administrative SOP & Dispatch Logs
CREATE TABLE alert_dispatch_logs (
    log_id BIGSERIAL PRIMARY KEY,
    ward_id VARCHAR(50),
    recipient_role VARCHAR(50), -- 'MUNICIPAL_OFFICER', 'HOSPITAL_ER', 'CITIZEN'
    channel VARCHAR(20), -- 'SMS', 'WHATSAPP'
    message_body TEXT,
    dispatch_status VARCHAR(20),
    sent_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### Offline & Low-Network Resiliency Strategy
* **Service Worker Caching (PWA):** The mobile client web app registers a PWA Service Worker caching the core shell, ward maps, and last-synced alerts into Browser `IndexedDB` [INFERENCE].
* **Bandwidth Optimization:** Vector tiles for ward boundaries are compressed using Mapbox Vector Tile (MVT) binary format, reducing GIS payload from ~5 MB GeoJSON to < 150 KB [INFERENCE].
* **Delta Synchronization:** Mobile clients query sync endpoints passing `last_sync_timestamp`. Backend returns only updated ward risk statuses, minimizing payload to < 5 KB [INFERENCE].
* **Retry Engine & Idempotency:** SMS/WhatsApp dispatch jobs are queued in Redis. Failed dispatches auto-retry with exponential backoff (10s, 30s, 2m) using unique `idempotency_key` (e.g., `WARD102_20260905_RED`) to eliminate duplicate alerts [INFERENCE].
