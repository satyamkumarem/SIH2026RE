# SIH 2026 Problem Analysis & Solution Architecture Dossier

## 1. Executive Snapshot

This dossier provides a solution architecture and strategic blueprint for **SIH26202**, an open-theme Student Innovation problem statement under the All India Council for Technical Education (AICTE) [PS]. The problem addresses the fundamental challenge of intelligent resource management by integrating artificial intelligence with heterogeneous, multi-source data streams to generate actionable insights and transform technology adoption [PS]. 

To fulfill this mandate, we propose **ResourcAI**: an AI-powered Multi-Source Resource Intelligence & Optimization Platform [INFERENCE]. ResourcAI ingests real-time and historical telemetry across critical resource vectors (e.g., electrical power, water distribution, campus/municipal facility utilization, and waste systems) from IoT sensors, public open-data platforms, weather feeds, and satellite imagery [INFERENCE]. Using time-series machine learning models, automated data harmonizers, and an explainable AI insight engine, ResourcAI detects resource leakages, forecasts peak demand, optimizes dynamic allocation, and provides automated decision support for facility managers and municipal administrators [INFERENCE].

## 5. Constraints & Environment Realities

* **Connectivity & Bandwidth:** Rural, semi-urban, or dense campus environments across India frequently suffer from high latency, packet loss, or periodic cellular outages `[KNOWN]`. Continuous cloud dependency for sensor streaming or edge control creates single points of failure `[INFERENCE]`.
* **Hardware Diversity:** Telemetry sensors span multiple generations—from legacy MODBUS energy meters to low-cost ESP32/Raspberry Pi microcontrollers and modern LoRaWAN water flow meters `[KNOWN]`. Interfaces must support REST, MQTT, HTTP POST, and CSV/JSON batch ingest `[INFERENCE]`.
* **Power & Network Instability:** Field gateways and edge devices may lose main AC power during localized load shedding `[KNOWN]`. Edge systems require non-volatile buffering (e.g., local SQLite/S3-compatible buffers) to retain telemetry until restoration `[INFERENCE]`.
* **Language & Digital Literacy:** Field staff and junior maintenance technicians operate primarily in regional languages (e.g., Hindi, Tamil, Marathi) `[KNOWN]`. Complex technical graphs must be augmented with simplified color-coded indicators (Green/Yellow/Red) and local language voice/text summaries `[INFERENCE]`.
* **Budget & Infrastructure Limitations:** Academic institutions and small municipalities operate under strict budget constraints `[KNOWN]`. Recommending proprietary enterprise software (e.g., $50,000/year enterprise licenses) is impractical; the stack must be built entirely on open-source frameworks `[INFERENCE]`.

## 10. Recommended Approach & Why

We select **Approach 3 (Hybrid Architecture)** as the winning strategy [INFERENCE].

### Why Alternatives Were Rejected:
1. **Rejection of Approach 1 (Rule-Based System):** While trivial to implement, it fails to satisfy the problem statement's explicit mandate for *artificial intelligence* [PS]. Static thresholds produce extreme false-positive rates in variable environments (e.g., high water usage during campus sports meets flagged as leaks), undermining user trust [INFERENCE].
2. **Rejection of Approach 2 (Deep Learning / CV Heavy):** Deep neural networks (LSTM / Transformers / Dense CV pipelines) introduce unnecessary compute overhead, high latency, and black-box outputs [INFERENCE]. In resource management, facility managers require *explainable* reasoning (e.g., "Pump #3 flagged due to 35% current draw spike uncorrelated with pressure output") rather than opaque probability scores [INFERENCE]. Furthermore, streaming multiple HD video feeds in hackathon conditions creates unnecessary failure points [INFERENCE].

### Why Approach 3 Wins:
* **Strict Alignment:** Solves all explicit [PS] requirements: intelligent resource optimization, multi-source ingestion (data.gov.in, weather, IoT), AI forecasting, and actionable insight generation [INFERENCE].
* **Demo Reliability:** Tabular ML models (XGBoost, Isolation Forest) train in seconds and infer in milliseconds on standard CPU instances, guaranteeing instantaneous response during live judging [INFERENCE].
* **Explainability:** Incorporates SHAP values and natural language generation, directly fulfilling the "get valuable insights" mandate [PS].
* **Feasibility:** Allows clean division of labor among a 4–6 student team (2 Backend/ML engineers, 2 Frontend/GIS developers, 1 IoT/Data simulator, 1 System Architect) `[INFERENCE]`.

### Detailed Data Flow Narrative

1. **Ingestion Step:** IoT telemetry (simulated via Python/MQTT or physical ESP32 nodes) transmits temperature, voltage, water flow, and pressure readings at 5-second intervals to an EMQX/FastAPI ingestion endpoint [INFERENCE]. Simultaneously, asynchronous background workers pull ambient weather data from OpenWeatherMap and regional baselines from `api.data.gov.in` [RESEARCHED].
2. **Harmonization & Storage Step:** Incoming payloads enter the Schema Harmonizer, which validates data types, injects ISO timestamps, converts units to standard SI (e.g., kWh, Liters/min), and writes to **TimescaleDB** (PostgreSQL time-series extension) [INFERENCE]. Hot sensor state is published to **Redis** for sub-second UI updates via WebSockets [INFERENCE].
3. **AI Inference Loop:** Every 60 seconds (or on event triggers), the ML service pulls the last 60 minutes of sensor telemetry from Redis/TimescaleDB [INFERENCE].
   * **Isolation Forest** evaluates feature vectors (flow rate, delta pressure, hour of day) to calculate anomaly scores [INFERENCE].
   * **XGBoost** predicts expected demand for the next 24 hours based on historical trends, weather forecasts, and calendar events [INFERENCE].
   * If an anomaly score exceeds a dynamic threshold (e.g., > 0.75), the **XAI Insight Synthesizer** combines model feature attribution scores (SHAP) with a rule-augmented template to generate a plain-text advisory (e.g., *"Warning: Pipe Sector B3 shows 42% unexpected nocturnal flow increase, indicating a downstream leak."*) [INFERENCE].
4. **Action & Notification Step:** The FastAPI backend pushes WebSocket alerts to the Operations Web Dashboard and dispatches an automated SMS/Push notification to field maintenance personnel [INFERENCE].
5. **Field Mobile Execution Step:** Field technicians receive the ticket on their PWA. If offline, the ticket details, geospatial pipe maps, and resolution forms are accessed via client-side IndexedDB [INFERENCE]. Upon completing the repair, the technician uploads a photo and status update; sync occurs automatically when network connectivity is restored [INFERENCE].

## 14. Data Architecture & Offline/Low-Network Design

### TimescaleDB Schema (PostgreSQL Extension)

```sql
-- Core Telemetry Hypertable for Time-Series Ingestion
CREATE TABLE sensor_telemetry (
    timestamp TIMESTAMPTZ NOT NULL,
    sensor_id VARCHAR(64) NOT NULL,
    resource_type VARCHAR(32) NOT NULL, -- 'WATER', 'ELECTRICITY', 'SOLAR'
    location_id VARCHAR(64) NOT NULL,
    flow_rate DOUBLE PRECISION, -- Liters/min
    pressure DOUBLE PRECISION,  -- PSI
    voltage DOUBLE PRECISION,    -- Volts
    current_draw DOUBLE PRECISION, -- Amps
    power_kw DOUBLE PRECISION,   -- kW
    raw_payload JSONB
);
SELECT create_hypertable('sensor_telemetry', 'timestamp');

-- Anomaly Log Table
CREATE TABLE anomaly_alerts (
    alert_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    created_at TIMESTAMPTZ DEFAULT NOW(),
    sensor_id VARCHAR(64) REFERENCES sensor_telemetry(sensor_id),
    anomaly_score DOUBLE PRECISION NOT NULL,
    severity VARCHAR(16) NOT NULL, -- 'LOW', 'MEDIUM', 'HIGH', 'CRITICAL'
    xai_explanation TEXT NOT NULL,
    status VARCHAR(32) DEFAULT 'OPEN' -- 'OPEN', 'DISPATCHED', 'RESOLVED'
);
```

### Offline & Synchronization Architecture

```
+-----------------------------------------------------------------------------------+
|                        OFFLINE FIELD TECHNICIAN SYNC FLOW                         |
+-----------------------------------------------------------------------------------+

  [ FIELD MOBILE PWA ]
          |
          +---> Active Internet Connection? 
          |         |
          |         +--- YES ---> Submit Direct via HTTPS REST ---> [ FASTAPI BACKEND ]
          |         |
          |         +--- NO  ---> Write Ticket to Local IndexedDB Cache
          |                           |
          |                           v
          |                     Background Service Worker
          |                     (Listens for 'online' Event)
          |                           |
          |                           v
          |                     Re-establish Connection
          |                           |
          |                           v
          |                     Bulk Push Queued Requests to /api/v1/sync/batch
          |                           |
          v                           v
  [ SERVER DB ] <--- Apply Idempotent Upsert & Resolve Conflicts via Last-Write-Wins
```

* **Local Storage:** Client PWA utilizes **IndexedDB** (via `dexie.js`) to store pending maintenance logs, photo data URLs, and cached geospatial vector tiles [INFERENCE].
* **Conflict Resolution:** Every client transaction generates a local UUID and client timestamp. The server applies **Last-Write-Wins (LWW)** with idempotent processing based on transaction UUIDs [INFERENCE].
* **Bandwidth Reduction:** Telemetry payloads use compact JSON key names and optional GZIP compression. Background polling uses HTTP conditional headers (`If-None-Match` / ETag) to prevent redundant data transfer over cellular links [INFERENCE].
