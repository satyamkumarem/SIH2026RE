# 1. Executive Snapshot

### System Objective
To build an automated, AI-driven, multi-portal compliance verification platform that cross-references submitted bidder documents against authoritative Indian government portals (API Setu, GeM, GSTN, Udyam, MCA21, EPFO/ESIC, CPPP debarment) to generate auditable compliance scores, risk classifications, and discrepancy flags, thereby serving as a robust decision-support tool for CPCL procurement officers `[INFERENCE]`.

### Summary
Public sector procurement at Chennai Petroleum Corporation Limited (CPCL) via the Government e-Marketplace (GeM) requires rigorous verification of bidder credentials across numerous statutory registries, including Udyam, GSTN, Income Tax/PAN, MCA21, EPFO, ESIC, Startup India, NSIC, and central debarment lists `[PS]`. Manual cross-checking of multi-page technical/financial bids against disparate government portals creates significant operational bottlenecks, delays contract awards, and introduces human error `[PS]`. The proposed solution—**GeM-Check AI**—is a dual-engine platform combining an automated Public Digital Infrastructure (PDI) API gateway with a domain-tuned Vision-LLM extraction and compliance scoring engine `[INFERENCE]`. By fetching cryptographically verified entity metadata and extracting un-structured document text (e.g., OEM authorization, local content certificates, past performance), the system detects cross-document inconsistencies, calculates a weighted Compliance Score & Risk Level, and delivers an auditable decision-support dashboard for CPCL Procurement Officers `[INFERENCE]`. The final decision to qualify or disqualify a bidder remains exclusively with the human procurement officer, preserving full administrative accountability `[PS]`.

# 5. Constraints & Environment Realities

*   **Regulatory & Administrative Governance:**
    *   Under General Financial Rules (GFR 2017) and CVC guidelines, an automated system **cannot** legally disqualify a bidder. Final qualification/disqualification authority rests strictly with the designated CPCL Procurement Officer `[KNOWN]`.
    *   *Design Impact:* AI outputs are rendered strictly as advisory alerts and recommendations `[PS]`.
*   **External Portal API Accessibility & Gating:**
    *   Direct production API access to government portals (GSTN, MCA21, EPFO) requires formal government onboarding, IP whitelisting, and MeitY approval through API Setu `[RESEARCHED]`.
    *   *Design Impact:* The architecture must feature an abstraction layer capable of switching seamlessly between live production endpoints and robust mock/sandbox API adapters during development and hackathon demonstrations `[INFERENCE]`.
*   **Document Format Quality & Heterogeneity:**
    *   Bidder uploads on GeM range from digitally signed native PDFs to low-resolution scanned documents, skewed mobile camera photos, and multi-language stamp papers `[RESEARCHED]`.
    *   *Design Impact:* Document ingestion requires pre-processing (deskewing, noise reduction, binarization) prior to OCR and layout-aware extraction `[INFERENCE]`.
*   **Data Privacy & Confidentiality (DPDP Act 2023 Compliance):**
    *   Bids contain sensitive financial figures, proprietary technical details, PAN numbers, and personal details of directors/signatories `[KNOWN]`.
    *   *Design Impact:* Storage must use AES-256 encryption at rest, TLS 1.3 in transit, and strictly enforce Role-Based Access Control (RBAC). Data processing must remain on CPCL premises or MeitY-empaneled sovereign cloud `[INFERENCE]`.
*   **Hardware & Infrastructure Limits at Evaluation Desks:**
    *   CPCL evaluation officers operate on enterprise desktop environments with web browser access, connected to local corporate intranet or secure VPN `[INFERENCE]`.
    *   *Design Impact:* The UI must be lightweight, responsive, web-based (React/Next.js), avoiding heavy client-side rendering or non-standard plugins `[INFERENCE]`.

# 9. Candidate Solution Approaches

### Approach 1: Deterministic Rule-Based API Aggregator
*   **Mechanism:** Direct Python script / REST API gateway that queries statutory APIs (Udyam, GSTN, PAN) using regex-extracted registration numbers from documents. Hardcoded IF-THEN rules evaluate compliance `[INFERENCE]`.
*   **Problem Fit:** Poor for unstructured documents (scanned PDF certificates, OEM authorizations); excellent for structured API lookups `[INFERENCE]`.
*   **Accuracy Potential:** 100% for API cross-checks; low (<40%) for scanned/unstructured document parsing `[INFERENCE]`.
*   **Data Requirements:** Structured JSON inputs, registration numbers `[INFERENCE]`.
*   **Complexity:** Low `[INFERENCE]`.
*   **Explainability:** 100% deterministic `[INFERENCE]`.
*   **Cost:** Very Low `[INFERENCE]`.
*   **Scalability:** High `[INFERENCE]`.
*   **Hackathon Feasibility:** High (1–2 days build) `[INFERENCE]`.
*   **Production Feasibility:** Inadequate (fails on scanned/unstructured bid documents) `[INFERENCE]`.

### Approach 2: End-to-End Vision-LLM Agentic System
*   **Mechanism:** All uploaded bid PDF pages are converted to images and passed into a Large Multimodal Model (e.g., GPT-4o / Claude 3.5 Sonnet / Llama-3.2-Vision) with web-browsing tool calls to search government portals `[INFERENCE]`.
*   **Problem Fit:** High flexibility for unstructured documents; poor for deterministic statutory validation `[INFERENCE]`.
*   **Accuracy Potential:** High document extraction, but subject to LLM hallucinations and non-deterministic scoring `[INFERENCE]`.
*   **Data Requirements:** High token bandwidth, unstructured PDF pages `[INFERENCE]`.
*   **Complexity:** Very High `[INFERENCE]`.
*   **Explainability:** Low (black-box neural network outputs) `[INFERENCE]`.
*   **Cost:** High API operational costs `[INFERENCE]`.
*   **Scalability:** Low (rate limits and high latency per bid page) `[INFERENCE]`.
*   **Hackathon Feasibility:** Moderate `[INFERENCE]`.
*   **Production Feasibility:** Unacceptable for CPSE procurement due to compliance risks, latency, and hallucination concerns `[INFERENCE]`.

### Approach 3: Hybrid Architecture (PDI Gateway + Layout-Aware Vision OCR + Deterministic Scoring Engine) [RECOMMENDED]
*   **Mechanism:** Dual-layer pipeline. 
    1. *Layer A (PDI Gateway):* Direct REST clients query statutory databases (API Setu, GSTN, Udyam, CPPP index) using extracted identifiers `[INFERENCE]`.
    2. *Layer B (Document Extraction Engine):* LayoutLMv3 / PaddleOCR + fine-tuned small LLM (e.g., Llama-3.1-8B-Instruct via vLLM) parses unstructured documents (Make in India, OEM MAF, UDIN) into structured JSON schema `[INFERENCE]`.
    3. *Layer C (Deterministic Rules Engine):* Compares extracted metadata against statutory API responses and tender ATC criteria, computing a mathematical Compliance Score and assigning Risk Levels `[INFERENCE]`.
*   **Problem Fit:** Optimal. Combines 100% accurate API cross-validation with robust AI document extraction and deterministic scoring `[INFERENCE]`.
*   **Accuracy Potential:** >95% extraction accuracy, 100% deterministic scoring accuracy `[INFERENCE]`.
*   **Complexity:** Moderate-High `[INFERENCE]`.
*   **Explainability:** High (every score reduction is tied to an explicit rule and source document page) `[INFERENCE]`.
*   **Cost:** Low-Medium (local open-weight LLM inference) `[INFERENCE]`.
*   **Scalability:** High `[INFERENCE]`.
*   **Hackathon Feasibility:** Highly Feasible within a student hackathon build `[INFERENCE]`.
*   **Production Feasibility:** Enterprise-ready and fully aligned with CVC/CPCL governance standards `[INFERENCE]`.

# 10. Recommended Approach & Why

**Selected Solution:** **Approach 3 (Hybrid Architecture)** `[INFERENCE]`.

### Why Alternatives Were Rejected:
*   *Approach 1 (Pure Rule-Based)* was rejected because public procurement bids heavily depend on unstructured scanned documents (OEM letters, CA certificates, local content declarations). Pure regex and template matching break whenever document layouts vary `[INFERENCE]`.
*   *Approach 2 (Pure LLM Agent)* was rejected because CVC and CPCL audit norms mandate strict explainability, zero hallucination, and deterministic decision logic. Pure LLM scoring is non-deterministic and presents unacceptable legal risks `[INFERENCE]`.

### Strategic Advantages of the Hybrid Approach:
1.  **Strict Explainability & Zero Hallucination:** The AI is restricted to structured JSON extraction; scoring is handled by a deterministic Python/SQL rule engine `[INFERENCE]`.
2.  **Robustness to Poor Scanning:** Layout-aware Vision-OCR (PaddleOCR + LayoutLMv3) accurately handles noisy, rotated, or stamped Indian government documents `[INFERENCE]`.
3.  **Audit-Ready Verification:** Cross-checks extracted text directly against cryptographic PDI endpoints (API Setu / EntityLocker), proving document authenticity `[INFERENCE]`.

### Detailed Data-Flow Narrative:
1.  **Ingestion Phase:** The Procurement Officer selects a GeM Tender ID on the React Dashboard. The FastAPI backend ingests the Tender Specification PDF (ATC) along with submitted Bidder Document Packages `[INFERENCE]`.
2.  **Document Preprocessing & OCR:** Scanned PDFs are split into page images, deskewed using OpenCV, and passed to PaddleOCR to extract bounding boxes and raw text `[INFERENCE]`.
3.  **Information Extraction:** LayoutLMv3 and Llama-3.1-8B (via vLLM) extract structured entity fields (GSTIN, PAN, Udyam URN, Local Content %, UDIN, OEM MAF expiry date) into validated Pydantic models `[INFERENCE]`.
4.  **PDI Portal Verification:** The extracted identifiers are dispatched asynchronously via the PDI Gateway to API Setu, Udyam, GSTN, and EPFO mock/live endpoints to retrieve authoritative entity records `[INFERENCE]`.
5.  **Debarment & Blacklist Screening:** The bidder's legal name, PAN, CIN, and Director DINs are queried against the Elasticsearch/pgvector debarment index containing CPPP and GeM blacklisted entities `[INFERENCE]`.
6.  **Compliance & Risk Scoring:** The Deterministic Engine cross-references extracted document parameters against portal API responses. String similarity (Levenshtein distance & Jaro-Winkler) checks name/address consistency. Rules compute a 0–100 Compliance Score and assign a Risk Level `[INFERENCE]`.
7.  **Audit Trail & Dashboard Display:** Detailed verification results, page-level bounding box coordinates, and API responses are logged to an append-only PostgreSQL database. The UI renders the Compliance Dashboard for officer review `[INFERENCE]`.

# 13. AI/ML Justification

### 1. Vision OCR & Layout Analysis (PaddleOCR + LayoutLMv3)
*   **Purpose:** Extract textual content and structural layout (tables, headers, key-value pairs) from scanned PDF uploads `[INFERENCE]`.
*   **Model Type:** Convolutional Neural Network (CNN) + Transformer-based LayoutLMv3 `[INFERENCE]`.
*   **Input:** Multi-page PDF page images (300 DPI PNG/JPEG) `[INFERENCE]`.
*   **Output:** Bounding boxes, text tokens, layout hierarchy, bounding coordinates `[INFERENCE]`.
*   **Data Required:** Fine-tuned on public Indian document samples (GST certificates, Udyam certificates, letterheads) `[INFERENCE]`.
*   **Why AI:** Standard text parsers (e.g., PyPDF2) fail completely on scanned images or bitmap PDFs `[INFERENCE]`.
*   **Evaluation Metric:** Character Error Rate (CER) < 3%, Word Error Rate (WER) < 5% `[INFERENCE]`.
*   **Failure Mode:** Low resolution (<100 DPI) or heavy watermarks causing character misinterpretation `[INFERENCE]`.
*   **Human Oversight:** Highlighting low-confidence OCR text in red on the UI for officer manual verification `[INFERENCE]`.

### 2. Structured Information Extraction (Llama-3.1-8B-Instruct via vLLM)
*   **Purpose:** Convert OCR text tokens into standardized JSON schemas (e.g., extracting exact Local Content %, UDIN string, Expiry Date) `[INFERENCE]`.
*   **Model Type:** Quantized Open-Weight Large Language Model (8B parameters) `[INFERENCE]`.
*   **Input:** OCR text blocks + JSON schema system prompt `[INFERENCE]`.
*   **Output:** Validated JSON payload matching Pydantic specification `[INFERENCE]`.
*   **Data Required:** Few-shot prompt templates containing statutory document layouts `[INFERENCE]`.
*   **Why AI:** Document formats vary wildly across thousands of OEMs and Chartered Accountants; regex rules break easily `[INFERENCE]`.
*   **Evaluation Metric:** JSON Schema Validation Pass Rate (>98%), Field Accuracy (>95%) `[INFERENCE]`.
*   **Failure Mode:** Hallucinating non-existent dates or numbers if source text is ambiguous `[INFERENCE]`.
*   **Human Oversight:** Every extracted JSON field is hyperlinked to its source bounding box image snippet on the original PDF `[INFERENCE]`.

### Where AI Should NOT Be Used:
*   **Compliance Scoring Computation:** AI must **NOT** calculate final scores or risk levels directly `[INFERENCE]`. A deterministic Python algorithm applies transparent mathematical deduction weights `[INFERENCE]`.
*   **Debarment Matching Logic:** AI must **NOT** perform raw blacklisting decisions `[INFERENCE]`. Deterministic string distance algorithms (Jaro-Winkler, Levenshtein) flag potential name matches for human officer confirmation `[INFERENCE]`.

### Local Caching, Synchronization & Low-Network Strategy
*   **PDI Portal Caching Layer:** Statutory verification responses (e.g., GST registration details, Udyam profiles) are cached in Redis and PostgreSQL for 24 hours to minimize repetitive external API calls and handle portal outages `[INFERENCE]`.

*   **Offline Mode Operations:** In low-bandwidth or offline intranet environments, the platform functions seamlessly using pre-indexed debarment databases and cached statutory records, queuing external API verification calls until network connectivity is restored `[INFERENCE]`.

# 15. Security, Privacy & Governance

*   **Data Encryption & Protection:**
    *   All data in transit is secured using TLS 1.3 `[KNOWN]`.
    *   All stored PDFs, extracted JSON metadata, and database records are encrypted at rest using AES-256 `[KNOWN]`.
*   **Access Control & Authentication:**
    *   Strict Role-Based Access Control (RBAC) separating `Procurement Officer`, `Auditor`, and `System Admin` roles `[INFERENCE]`.
    *   Multi-Factor Authentication (MFA) required for officer login `[INFERENCE]`.
*   **Data Protection & DPDP Act 2023 Compliance:**
    *   PII fields (PAN numbers, Director Aadhaar details, personal mobile numbers) are masked in UI views (e.g., `XXXXX1234X`) unless explicitly unmasked by an authorized officer for verification purposes `[INFERENCE]`.
    *   System log files automatically redact sensitive tokens and credentials `[INFERENCE]`.
*   **Immutable Audit Trail & Administrative Integrity:**
    *   Every evaluation decision, AI recommendation generated, manual override, and comment made by a procurement officer is appended to a cryptographic audit log `[INFERENCE]`.
    *   Each log entry contains a SHA-256 hash chaining to the previous log entry, making retroactive tampering mathematically detectable `[INFERENCE]`.
*   **Regulatory Status Disclaimer:**
    *   The platform operates strictly as an automated decision-support system. Final qualification or disqualification decisions remain the sole administrative and legal responsibility of the Procurement Officer `[PS]`.
