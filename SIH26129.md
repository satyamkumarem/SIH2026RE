## 1. Executive Snapshot

### Summary
The Government of Maharashtra, specifically the Department of Skills, Employment, Entrepreneurship and Innovation (via the Maharashtra State Innovation Society), faces service fragmentation due to siloed government digital platforms, mobile applications, registries, workflow systems, and databases [PS]. The primary challenge is that existing departmental applications operate with divergent data formats, isolated user identity registries, heterogeneous authentication mechanisms, disparate process flows, and lacking API interoperability [PS]. This forces citizens and businesses to re-submit identical personal data and documents across multiple departments, track application progress across disconnected portals, or make physical visits to government offices [PS]. Simultaneously, government officials lack a consolidated, 360-degree view of beneficiaries, applications, approvals, grievances, and service delivery outcomes [PS]. This project designs a non-invasive, standards-based Federated Middleware Architecture and Interoperability Framework (codenamed **MahaSetu / OpenG2G Interop Layer**) that bridges legacy RDBMS portals and modern microservices using low-code API connectors, Master Data Management (MDM), e-Pramaan/MeriPehchaan federated SSO, DPDP Act-compliant consent-based data sharing, and event-driven workflow orchestration without replacing legacy IT infrastructure [PS, INFERENCE].

## 5. Constraints & Environment Realities

1. **Connectivity & Network Variability**: Citizens in tier-3 cities and rural Maharashtra (e.g., Gadchiroli, Nandurbar) face intermittent 2G/3G connectivity [KNOWN]. The citizen frontend must support offline draft saving (IndexedDB) and progressive sync [INFERENCE].
2. **Legacy Infrastructure Diversity**: Departmental systems range from modern Node.js/Python microservices to 15-year-old ASP.NET / Java JSP monoliths running legacy MySQL/Oracle instances without REST APIs [KNOWN]. Middleware cannot assume all endpoints are REST/GraphQL [INFERENCE].
3. **Language & Digital Literacy**: Over 65% of state portal users prefer Marathi [KNOWN]. Interfaces MUST strictly support bilingual Marathi and English inputs with localization, voice assistance, or simplified form flows [INFERENCE].
4. **Regulatory & Compliance Rules**: Maharashtra Right to Public Services Act (RTS Act) mandates strict turnaround times (e.g., 7–15 days for certificates) [RESEARCHED]. Digital Personal Data Protection (DPDP) Act 2023 imposes strict fines for processing personal data without explicit, loggable consent [KNOWN].
5. **No Database Replacement Mandate**: The problem statement explicitly specifies that existing departmental applications cannot be replaced [PS]. The solution MUST operate as an external facade/bus without altering legacy database schemas [INFERENCE].

## 9. Candidate Solution Approaches

### Approach 1: Centralized Data Warehouse & Monolithic Re-Engineering
* **Mechanism**: Extract all departmental databases nightly into a single central state database warehouse and build a monolithic super-portal on top.
* **Required Data**: Full replication of all legacy department tables.
* **Architecture**: ETL Pipelines + Central Database + Monolithic Portal.
* **Complexity**: Extremely High.
* **Cost**: Very High (massive storage, migration costs).
* **Explainability**: Low (complex ETL dependencies).
* **Scalability**: Poor (single point of failure and bottleneck).
* **Hackathon Feasibility**: Unfeasible.
* **Production Feasibility**: Unfeasible (violates constraint: *"without requiring complete replacement of existing systems"* [PS]).
* **Risks**: High risk of data stale-ness, departmental resistance over data ownership.

### Approach 2: Lightweight Point-to-Point REST Middleware API Wrapper
* **Mechanism**: Build direct REST API wrappers around each legacy database and let portals call each other directly via custom API endpoints.
* **Required Data**: Standard database connection strings for legacy systems.
* **Architecture**: ExpressJS / FastAPI wrappers on legacy DBs + central OpenAPI Swagger directory.
* **Complexity**: Low to Medium.
* **Cost**: Low.
* **Explainability**: High.
* **Scalability**: Medium (becomes `O(N^2)` API mesh complexity as departments grow).
* **Hackathon Feasibility**: High.
* **Production Feasibility**: Low (lacks central governance, consent management, MDM, and workflow orchestration).
* **Risks**: Security vulnerabilities, unmanaged API proliferation, lack of unified audit trail.

### Approach 3: Federated Service Mesh & Event-Driven Middleware Architecture (RECOMMENDED)
* **Mechanism**: Deploy a decoupled, event-driven middleware layer comprising an **API Gateway**, **Schema Transformation & MDM Engine**, **Consent Manager (DPDP compliant)**, **BPMN Workflow Orchestrator**, and **Reusable Legacy Connectors** (DB CDC / REST Proxies).
* **Required Data**: Canonical schema mapping rules, event queues, user consent records, mock API endpoints.
* **Architecture**: Federated Architecture (API Gateway + Event Broker + BPMN Orchestrator + Low-Code Connectors + Unified Citizen & Admin Dashboards).
* **Complexity**: Medium-High.
* **Cost**: Low (built on Open Source stack: FastAPI/Node.js, PostgreSQL, RabbitMQ/Kafka, Camunda).
* **Explainability**: High (modular boundaries).
* **Scalability**: Very High (asynchronous microservices).
* **Hackathon Feasibility**: High (core MVP can be built using Node.js/Python, Redis, RabbitMQ, and React).
* **Production Feasibility**: Excellent (aligns strictly with IndEA 2.0 and DPDP Act standards).
* **Risks**: Requires careful schema definition for canonical data models.

## 10. Recommended Approach & Why

### Selection
**Approach 3: Federated Service Mesh & Event-Driven Middleware Architecture** is selected.

### Why Alternatives Were Rejected
* **Approach 1 (Centralized Monolith)** was rejected because it directly violates the explicit constraint in the problem statement: *"without requiring complete replacement of existing systems"* [PS]. It also breaches departmental data ownership autonomy and introduces severe synchronization delays [INFERENCE].
* **Approach 2 (Point-to-Point Wrappers)** was rejected because while easy to prototype, it fails to fulfill key explicit requirements: Master Data Management (MDM), workflow orchestration, consent management, and unified tracking [PS]. It scales poorly (`O(N^2)` integration spaghetti) and creates security audit blind spots [INFERENCE].

### Why Approach 3 Wins
Approach 3 provides a **non-invasive, pluggable, standards-compliant middleware** that sits transparently between existing legacy departmental portals [INFERENCE]. It allows departments to retain their databases and business logic while exposing standardized REST/JSON interfaces through reusable adapters [INFERENCE]. It fulfills 100% of the explicit requirements [PS]—including federated identity, consent management, event-driven notifications, workflow orchestration, and unified tracking—while adhering to India's national IndEA 2.0 e-governance specifications [RESEARCHED].

### Data-Flow Narrative

1. **Authentication**: The citizen accesses the MahaSetu portal and logs in via MeriPehchaan / e-Pramaan SSO (or mock OIDC provider) [RESEARCHED]. The identity gateway issues a signed JWT containing citizen identifiers (`aadhaar_hash`, `mobile_hash`) [INFERENCE].
2. **Service Request & Pre-fill**: The citizen chooses a service (e.g., "Entrepreneurship Grant"). The system checks the **Consent Manager**. Upon citizen approval, MahaSetu queries the **Legacy DB Adapters** for Aaple Sarkar and DigiLocker to pre-fill education and caste details automatically using the canonical MDM schema [INFERENCE].
3. **Submission & Orchestration**: The citizen submits the application. The **Workflow Orchestrator** generates a **Global Application Tracking ID (GAT-ID)** and pushes an `Application_Created` event to the **RabbitMQ Event Bus** [INFERENCE].
4. **Inter-Departmental Processing**: The Orchestrator routes the request to Department A's system via its **REST Proxy Adapter**. Once Department A approves, an event is emitted, triggering Department B's system for background verification [INFERENCE].
5. **Real-time Status Sync**: The **Global Status Indexer** captures status events across all departmental adapters, keeping the citizen portal and officer dashboard updated in real-time [INFERENCE].
6. **Notifications**: The **Notification Dispatcher** listens to the event bus and sends automated SMS/WhatsApp alerts to the citizen upon every stage transition [INFERENCE].

## 13. AI/ML Justification

### AI Component 1: Smart Data Mapper & Schema Translation Assistant
* **Purpose**: Automatically map non-standard, legacy database column names (e.g., `cust_nm`, `dob_val`, `sch_type`) to the canonical IndEA JSON-LD schema during new department onboarding.
* **Model Type**: Sentence-Transformer Embeddings (e.g., `all-MiniLM-L6-v2`) + Cosine Similarity matching.
* **Input**: Legacy DB schema definitions (JSON/DDL dump).
* **Output**: Suggested mapping dictionary with confidence score (`cust_nm` -> `applicant_full_name`: 0.94).
* **Data Required**: Synthetic dictionary of government data terms and IndEA MDDS schema mappings.
* **Why AI is Preferable**: Eliminates days of tedious manual field mapping when onboarding 20+ state portals.
* **Evaluation Metric**: Mapping Accuracy top-1 / top-3 score.
* **Failure Mode**: Incorrect mapping suggestion.
* **Human Oversight**: System presents suggested mapping to IT Admin for mandatory manual review and 1-click confirmation before generating adapter code.

### AI Component 2: Cross-Departmental Duplicate Beneficiary & Anomaly Detector
* **Purpose**: Prevent citizens from fraudulently claiming duplicate grants/subsidies across different department portals for the same scheme objective.
* **Model Type**: Record Linkage / Fuzzy String Matching + Isolation Forest anomaly detection.
* **Input**: Cross-department applicant submissions (`name`, `father_name`, `dob`, `address`, `bank_account_hash`).
* **Output**: Duplicate likelihood score (0.0 - 1.0) and flag (`FLAGGED_POSSIBLE_DUPLICATE`).
* **Data Required**: Synthetic cross-department grant submission logs.
* **Why AI is Preferable**: Deterministic SQL queries fail when names have slight spelling variations or phonetic differences across Marathi/English transliteration.
* **Evaluation Metric**: Precision and Recall on duplicate detection test set.
* **Failure Mode**: False positive flag blocking legitimate applicant.
* **Human Oversight**: High-risk flags are routed to a human Desk Officer queue for manual verification; application is NEVER automatically rejected by AI.

### Explicit Non-AI Statement
AI is **NOT** used for core workflow routing, eligibility approval decisions, or access control [INFERENCE]. Scheme eligibility rules are strictly deterministic and governed by rule-based SQL/BPMN logic to ensure 100% transparency and legal accountability under public service laws [INFERENCE].

### Low-Network & Offline Synchronization Design
1. **Local Offline Draft Store**: The frontend progressive web app (PWA) utilizes **Browser IndexedDB** via `idb-keyval` to persist form inputs locally if connection drops during entry [INFERENCE].
2. **Background Sync API**: Leverages Service Worker `sync` events to push queued submissions automatically once internet connectivity is restored [INFERENCE].
3. **Payload Compression & Bandwidth Reduction**: Gzip/Brotli compression on all REST payloads; payload size minimized by transferring document hashes instead of heavy PDF binary data whenever verified on DigiLocker [INFERENCE].
4. **Idempotent Queueing**: All incoming submission endpoints accept a client-generated UUID (`idempotency_key`) to prevent duplicate records if retry occurs over unstable networks [INFERENCE].

## 15. Security, Privacy & Governance

1. **Digital Personal Data Protection (DPDP) Act 2023 Compliance**:
   * Personal Identifiable Information (PII) is NEVER shared between departments without explicit, time-bound, purpose-bound digital consent logged from the citizen [KNOWN].
   * The **Consent Engine** stores cryptographically signed consent tokens containing `purpose_code`, `valid_until`, and `data_fields_allowed` [INFERENCE].
2. **Data Storage & Encryption**:
   * All PII data at rest is encrypted using AES-256 [KNOWN].
   * Data in transit is enforced via TLS 1.3 encryption [KNOWN].
   * Direct Aadhaar numbers are never saved; only hashed tokens generated via Aadhaar Vault specifications are processed [KNOWN].
3. **Immutable Audit Trails**:
   * Every inter-departmental API call, consent grant, and data access log is written to an append-only audit table with sequential SHA-256 hashing (hash-chaining) to ensure complete non-repudiation [INFERENCE].
4. **Role-Based Access Control (RBAC)**:
   * Desk Officers can only view data fields authorized for their specific department and processing step [INFERENCE].
   * System Administrators have zero access to plain-text citizen PII [INFERENCE].
