## 1. Executive Snapshot

Modern defense, intelligence, and critical infrastructure networks rely on highly heterogeneous multi-vendor hardware, including enterprise firewalls, core routers, switches, cloud security groups, and open disaggregated architectures [PS]. Securing these complex environments requires continuous alignment with rigorous compliance baselines such as CIS Benchmarks, NIST SP 800-53, DISA STIGs, and ISO/IEC 27001 [PS]. Existing compliance auditing tools suffer from severe vendor lock-in, rigid static parsers that break on firmware updates, or high commercial licensing costs [KNOWN]. 

This project proposes **NetSentinel AI**: an air-gapped, AI-augmented, multi-vendor network compliance auditing platform. It combines a deterministic AST/Grammar normalization engine with lightweight NLP/embedding intent classification and a low-code active learning GUI [INFERENCE]. When unseen vendor CLI syntax is ingested, the system presents unparsed lines to the administrator to map into security categories [PS]. The engine updates its internal heuristics dynamically without requiring backend code redeployment [PS], evaluates configurations deterministically against target security baselines [PS], and generates per-device PDF compliance reports with exact remediation CLI scripts [PS].

## 5. Constraints & Environment Realities

1. **Air-Gapped Sovereign Network Constraints**: NTRO operates high-security, classified environments disconnected from the public internet [KNOWN]. The system cannot rely on cloud-hosted LLM APIs (e.g., OpenAI, Anthropic) or real-time internet telemetry [INFERENCE]. All models, dependencies, and rulesets must run 100% locally on standard x86 workstation hardware [ASSUMPTION].
2. **Firmware & Syntax Drift**: Network vendors routinely alter syntax across major OS versions (e.g., Cisco IOS vs IOS-XE vs NX-OS, Palo Alto PAN-OS 9.0 vs 11.0) [KNOWN]. Static regex parsers fail immediately upon encountering minor keyword shifts [PS].
3. **Configuration Complexity & Non-Linear Structures**: Firewalls and switches use deeply nested configuration blocks (e.g., Palo Alto XML/CLI hierarchies, Juniper curly-brace hierarchies, Cisco indentations) [KNOWN]. Flattening configurations without losing context creates parsing errors [INFERENCE].
4. **Hardware & Resource Limits**: Workstations used by field assessors may lack dedicated high-end GPUs [ASSUMPTION]. The AI component must be computationally lightweight (CPU-runnable NLP models like SpaCy, Sentence-Transformers, or regex-heuristic hybrids) rather than multi-billion parameter LLMs [INFERENCE].
5. **Zero Tolerance for Hallucinated Remediation**: In defense networks, applying a wrong CLI remediation command can drop core routing or lock out administrators [KNOWN]. AI *must not* generate non-deterministic remediation commands probabilistically [INFERENCE].

## 6. Research Questions

1. **How can the system parse hierarchical CLI structures without building full formal grammars for every network vendor?**
   * *Investigation*: Modern network configs follow tree-like block structures (indentation-based like Cisco/Arista, bracket-based like Juniper/F5, or XML/JSON like Palo Alto/AWS) [KNOWN]. Generic indentation and delimiter tree builders (e.g., `ciscoconfparse` or custom AST tokenizers) can convert raw text into a generic Tree syntax before mapping values to schema fields [RESEARCHED].
2. **How does the active learning loop persist updated syntax mappings without backend code redeployment?**
   * *Investigation*: The engine uses dynamic JSON Heuristic Mapping Tables stored in SQLite/PostgreSQL [INFERENCE]. When an admin maps a new command in the GUI, the system saves regex/embedding rules to the database, which the parser reloads instantly at runtime without restarting Python processes [INFERENCE].
3. **What standard schema best represents multi-vendor network security baselines?**
   * *Investigation*: OpenConfig YANG models [RESEARCHED] and Batfish internal structures [RESEARCHED] provide vendor-neutral networking representations. A simplified Pydantic-based Security Baseline Model (SBM) covering Authentication, Service Hardening, ACLs, Logging, and Encryption provides optimal flexibility [INFERENCE].

### Approach 1: Legacy Static Regex Engine
* **Mechanism**: Uses hard-coded regular expressions to scan line-by-line through configuration text for specific keywords (e.g., searching for `ip ssh version 2` in Cisco files) [INFERENCE].
* **Pros**: Simple to build; zero machine learning overhead; fast execution [INFERENCE].
* **Cons**: Fails completely on syntactical variations, multi-line blocks, or unknown vendors; zero dynamic learning ability; high maintenance burden [INFERENCE].
* **Verdict**: Rejected. Violates core requirement for dynamic adaptation and vendor-agnostic scalability [PS].

### Approach 2: Pure LLM-Based Direct Auditing
* **Mechanism**: Ingests raw config text directly into a locally hosted Large Language Model (e.g., Ollama / Llama-3 8B) with a prompt asking the LLM to identify non-compliant lines and write remediation commands [INFERENCE].
* **Pros**: Handles arbitrary text formats naturally; requires no formal AST parser creation [INFERENCE].
* **Cons**: Non-deterministic outputs; significant risk of hallucinating non-existent CLI flags or misinterpreting critical firewall rules; heavy VRAM requirements unsuitable for air-gapped field laptops [INFERENCE].
* **Verdict**: Rejected. Inacceptable security risk to rely on probabilistic LLMs for network compliance enforcement and CLI fix script generation [INFERENCE].

### Approach 3: Hybrid Architecture (AST Tree Builder + Lightweight NLP/Embedding Classifier + Interactive Low-Code Active Learning GUI + Deterministic Policy Engine) [RECOMMENDED]
* **Mechanism**: 
  1. A multi-vendor generic tree parser transforms raw nested CLI configurations into an Abstract Syntax Tree (AST) dictionary [INFERENCE].
  2. Syntactic parameters are mapped to a standardized Security Baseline Model (SBM) schema using pre-built heuristic rules and lightweight semantic similarity (TF-IDF / Sentence-Transformers) [INFERENCE].
  3. Unparsed or low-confidence lines trigger an **Interactive Low-Code Active Learning GUI**, presenting the admin with unparsed text to drag-and-drop into standard security categories (e.g., `Timeout Parameter`) [PS].
  4. Mappings are persisted instantly in an active heuristic DB table without code redeployment [PS].
  5. The normalized SBM JSON is evaluated deterministically against policy rulesets (CIS/NIST/STIG), generating verified Pass/Fail results and parameterized CLI remediation scripts [PS].
* **Pros**: 100% deterministic compliance testing; zero hallucination risk; air-gap lightweight execution on standard CPUs; dynamic learning for unparsed vendors [INFERENCE].
* **Cons**: Requires building a clean low-code GUI and normalization schema during the hackathon [INFERENCE].

## 10. Recommended Approach & Why

The **Hybrid AST + Active Learning Architecture (Approach 3)** is selected [INFERENCE]. 

### Rationale for Selection
1. **Compliance Integrity**: Network compliance requires absolute precision [KNOWN]. Approach 3 isolates machine learning to the *parsing and classification* phase, while leaving the *compliance evaluation and remediation generation* 100% deterministic [INFERENCE]. This guarantees zero false passes caused by AI hallucinations [INFERENCE].
2. **True Adaptability**: By providing an intuitive low-code active learning GUI, the system satisfies NTRO's explicit requirement that administrators can teach the engine unknown vendor syntaxes on the fly without backend code redeployment [PS].
3. **Air-Gap Operational Feasibility**: Approach 3 uses lightweight Python dependencies (`spacy`, `scikit-learn`, `pydantic`, `fastapi`, `reportlab`) that execute within seconds on standard dual-core laptop CPUs without requiring expensive Nvidia GPUs [INFERENCE].

### Detailed Data-Flow Narrative
1. **Ingestion Phase**: The user uploads single or bulk configuration files (e.g., `.cfg`, `.txt`, `.json`) via the Web Dashboard [PS]. The file is passed to the FastAPI backend [INFERENCE].
2. **AST Parsing & Tokenization**: The `Generic AST Tokenizer` converts the unstructured CLI text into a hierarchical tree structure based on indentations, curly braces, or XML/JSON tags [INFERENCE].
3. **Normalization & Active Learning Trigger**:
   * The `NLP Heuristic Engine` attempts to map each configuration branch to fields in the `Security Baseline Model (SBM)` (e.g., mapping `exec-timeout 10 0` to `sbm.management.session_timeout = 600`) [INFERENCE].
   * If lines are unrecognized or fall below confidence thresholds, the engine flags the file and sends unparsed lines to the **Active Learning GUI** [PS].
   * The administrator selects the appropriate category and parameters via low-code UI controls and clicks "Save & Apply" [PS].
   * The engine writes the new extraction heuristic rule into the database and immediately re-parses the file without restarting backend services [PS].
4. **Deterministic Compliance Evaluation**: The fully populated SBM JSON is passed to the `Compliance Engine` [PS]. The engine compares normalized values against selected framework rules (e.g., checking if `sbm.ssh.version == 2` for CIS compliance) [PS].
5. **Remediation & PDF Generation**:
   * For every failed check, the `Remediation Engine` fetches the device-specific Jinja2 template and produces exact CLI command sequences [PS].
   * The `ReportLab Engine` compiles device metadata (serial numbers, OS versions), compliance summary scores, detailed violation tables, and CLI fix scripts into an official single PDF report [PS].

## 13. AI/ML Justification

### Component 1: NLP Heuristic Syntax Mapper & Intent Classifier

1. **What exact problem does AI solve?** Maps syntactically diverse, non-standard vendor CLI command lines to standardized security parameters in the Security Baseline Model (SBM) [PS].
2. **What is the input?** Raw CLI command strings (e.g., `set system login idle-timeout 10`, `line vty 0 4 \ exec-timeout 10 0`) [INFERENCE].
3. **What is the output?** Target SBM category (`management_timeout`), parameter key (`session_timeout_seconds`), and extracted value (`600`) with a confidence score [INFERENCE].
4. **Why can a simpler rule/system not solve it?** Vendor CLI syntaxes vary infinitely across vendors and firmware releases [PS]. Static rules fail whenever keywords or ordering change [PS].
5. **What data is required?** Annotated CLI command dictionaries from common vendor OSs [INFERENCE].
6. **How will it be evaluated?** Precision/Recall on syntax parameter extraction across a multi-vendor test dataset [INFERENCE].
7. **What happens when it is wrong?** Low-confidence extractions (<85%) are routed to the **Interactive Active Learning GUI** for human admin confirmation [PS].
8. **Does it require training?** Uses lightweight supervised TF-IDF / Embedding vectorizer trained on baseline CLI dictionaries [INFERENCE].
9. **Does it require fine-tuning?** No deep transformer fine-tuning required [INFERENCE].
10. **Does it require RAG?** No RAG required [INFERENCE].
11. **Does it require computer vision?** No [INFERENCE].
12. **Does it require speech processing?** No [INFERENCE].
13. **Does it require forecasting?** No [INFERENCE].
14. **Is human oversight required?** Yes, via the Interactive Active Learning Module when confidence thresholds are not met [PS].

### Non-AI Declaration (Explicit Exclusion)
* **Compliance Evaluation Engine**: MUST NOT use AI [INFERENCE]. Checking whether `parsed_val == required_val` must remain 100% deterministic Boolean logic [INFERENCE].
* **CLI Remediation Generation**: MUST NOT use generative AI [INFERENCE]. Fix scripts must be generated using verified, deterministic Jinja2 templates to prevent network outages caused by hallucinated CLI syntax [INFERENCE].
