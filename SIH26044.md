# SIH 2026 Problem Statement Analysis & Solution Architecture Dossier

## 1. Executive Snapshot

### Summary
The gap between academic curriculum outcomes and real-world industrial expectations remains a critical bottleneck across higher education, particularly within specialized domains like the AYUSH (Ayurveda, Yoga & Naturopathy, Unani, Siddha, and Homoeopathy) healthcare sector, pharmaceutical industries, bio-tech, and clinical research organizations [INFERENCE]. To bridge this gap, the Ministry of Ayush and the All India Institute of Ayurveda (AIIA) require a unified, secure, scalable, and intelligent Academia–Industry Collaboration Platform [PS]. This platform connects four core entities: Students, Industry Recruiters/Sponsors, Academicians/Faculty, and Institutional Administrators [PS]. The system drives automated skill assessment, competency gap identification, skill mapping against real-time industry demands, direct internship/job recruitment workflows, industry-led learning programs, dedicated faculty development/research consultancy portals, digital portfolio management with verified credentials, and institutional analytics dashboards [PS]. The proposed architecture utilizes a domain-aware skill graph, vector similarity matching, role-based security, and integration with India's digital public infrastructure (DigiLocker, Academic Bank of Credits, Meri Pehchaan SSO, and AYUSH Grid) [RESEARCHED].

## 5. Constraints & Environment Realities

1. **Digital Literacy & Bandwidth in Rural Institutions**: While premier institutes (like AIIA, New Delhi) enjoy high-speed fiber internet, many affiliated AYUSH colleges and Tier-2/3 institutions operate in regions with intermittent mobile connectivity (3G/4G) [RESEARCHED]. The portal must maintain low page weight (<1.5 MB initial load) and support Progressive Web App (PWA) offline queuing for assessment submissions [INFERENCE].
2. **Device Hardware Diversity**: Students primarily access portals via mid-range Android smartphones (screen width 360px–412px), whereas recruiters and institutional admins use desktop browsers [KNOWN]. The mobile interface must be responsive and touch-optimized [INFERENCE].
3. **Multilingual & Domain Specificity**: The Ministry of Ayush ecosystem encompasses domain-specific terminology (e.g., *Dravyaguna*, *Panchakarma*, *Pharmacovigilance*, *Good Manufacturing Practice (GMP)*, *Standardization of Herbal Formulations*) Alongside general technical/soft skills [RESEARCHED]. Assessment questionnaires and skill mapping must accommodate domain-specific skill taxonomies alongside standard software/management skill taxonomies [INFERENCE].
4. **Data Privacy & Regulatory Mandates**: Compliance with India's **Digital Personal Data Protection (DPDP) Act 2023** is mandatory [KNOWN]. Student resumes, academic scores, and contact details cannot be exposed to unverified recruiters without explicit student consent [INFERENCE].
5. **Academic Credit Alignment**: Under the National Education Policy (NEP) 2020 and National Credit Framework (NCrF), internship hours map directly to academic credits (1 credit = 40 hours of work) [RESEARCHED]. The system must record verified start/end dates and completion certificates to feed into the Academic Bank of Credits (ABC) / APAAR framework [RESEARCHED].

## 9. Candidate Solution Approaches

### Approach 1: Monolithic Rule-Based & Keyword-Matching Portal
* **Mechanism**: Relational Database (PostgreSQL) with rigid SQL queries matching exact student skill keywords against job requirement tags. Static HTML questionnaires calculate percentile scores based on standard answer keys.
* **Architecture**: Monolithic Django or Laravel application with server-side rendered views (HTML/HTMX).
* **Evaluation**:
  * *Problem Fit*: Low–Medium. Misses semantic skill equivalence (e.g., fails to equate "Herbal Drug Analysis" with "Phytochemical Profiling") [INFERENCE].
  * *Complexity*: Very Low. Easy to implement during a hackathon [INFERENCE].
  * *Explainability*: 100% Explainable (Exact keyword match) [INFERENCE].
  * *Cost*: Very Low [INFERENCE].
  * *Scalability*: Limited under complex multi-tenant query filters [INFERENCE].
  * *Hackathon Feasibility*: 95/100 [INFERENCE].
  * *Production Feasibility*: 40/100 (Too rigid for modern skill profiling) [INFERENCE].

### Approach 2: LLM Heavy / Generative AI Centric System
* **Mechanism**: Every candidate resume and job description is passed to an External LLM API (e.g., OpenAI GPT-4 / Claude) via RAG (Retrieval-Augmented Generation) to output candidate suitability scores and generate dynamic assessment questions on the fly.
* **Architecture**: Node.js/Python server with Vector DB (Pinecone/Qdrant) and continuous external LLM API calls.
* **Evaluation**:
  * *Problem Fit*: Medium. Highly flexible, but high risk of hallucinations, non-deterministic scoring, rate limiting, and excessive API costs [INFERENCE].
  * *Complexity*: High [INFERENCE].
  * *Explainability*: Poor (Black-box scoring fails recruiter transparency needs) [INFERENCE].
  * *Cost*: High ($\sim$\$0.02–\$0.05 per API call) [INFERENCE].
  * *Scalability*: Poor due to external API latency (2–5 seconds per request) [INFERENCE].
  * *Hackathon Feasibility*: 70/100 [INFERENCE].
  * *Production Feasibility*: 30/100 (Unviable for government deployment without local open-weights model hosting) [INFERENCE].

### Approach 3: Hybrid Domain-Aware Graph + Vector Embeddings with Rule Guardrails (RECOMMENDED)
* **Mechanism**: Standardized Skill Taxonomy stored as a hierarchical Directed Acyclic Graph (DAG) in PostgreSQL/pgvector. Assessments use calibrated item-response questions. Skill gap is computed deterministically ($\text{Gap} = \text{Target Level} - \text{Assessed Level}$). Candidate-to-Job matching uses Sentence-Transformers (`all-MiniLM-L6-v2`) cosine vector similarity combined with hard eligibility SQL filters (CGPA, degree, batch) [INFERENCE].
* **Architecture**: Microservices-ready Modular Monolith using React (TypeScript) + FastAPI / Python + PostgreSQL (pgvector) + Redis [INFERENCE].
* **Evaluation**:
  * *Problem Fit*: Excellent. Combines deterministic mathematical skill gap scoring with semantic job matching [INFERENCE].
  * *Complexity*: Medium [INFERENCE].
  * *Explainability*: High (Clear mathematical breakdown of matching scores) [INFERENCE].
  * *Cost*: Very Low (Runs locally on standard CPU/GPU instances without per-token API charges) [INFERENCE].
  * *Scalability*: High ($\le 50\text{ ms}$ vector similarity query time for 100k candidates using pgvector IVFFlat index) [INFERENCE].
  * *Hackathon Feasibility*: 90/100 [INFERENCE].
  * *Production Feasibility*: 92/100 [INFERENCE].

## 10. Recommended Approach & Why

The **Hybrid Domain-Aware Graph + Vector Embeddings with Rule Guardrails (Approach 3)** is selected as the winning architecture [INFERENCE].

### Justification
1. **Explainable Skill Gap Identification**: Recruiters and students cannot trust black-box LLM ratings. Approach 3 explicitly lists target vs. demonstrated proficiency levels across granular skill nodes (e.g., *HPLC Analysis: Required Level 4, Demonstrated Level 2 $\rightarrow$ Gap: -2*) [INFERENCE].
2. **Determinism in Eligibility**: Placement shortlisting requires strict compliance with cutoff rules (e.g., minimum 60% marks, BAMS 3rd Year). Approach 3 uses relational SQL guardrails to enforce hard criteria before computing vector similarity [INFERENCE].
3. **Zero External API Costs & Offline Reliability**: By running lightweight open-source embeddings locally (`all-MiniLM-L6-v2`), the solution operates independently of internet connectivity to third-party paid APIs, ensuring affordability and reliability during live hackathon judging and government deployment [INFERENCE].
4. **Rejection of Alternatives**: Approach 1 was rejected due to strict keyword limitations that fail semantic matching. Approach 2 was rejected due to non-deterministic scoring, high latency, hallucination risks, and recurring API costs [INFERENCE].

### Step-by-Step Data Flow Narrative
1. **User Onboarding & Authentication**: A student/faculty/recruiter logs into the portal. The Gateway authenticates the request via JWT token (or Meri Pehchaan SSO mock) and checks active RBAC roles [INFERENCE].
2. **Skill Assessment Phase**: The student accesses the Assessment Service. A randomized, domain-tailored questionnaire is fetched from PostgreSQL. As the student submits answers, progress is saved in Redis [INFERENCE].
3. **Skill Gap Computation**: Upon submission, the Scoring Service evaluates accuracy across skill taxonomy nodes. A JSON profile is generated containing demonstrated vs. required scores, outputting a visual radar gap score [INFERENCE].
4. **Vector Embedding Generation**: The student's overall profile (verified skills, assessment results, domain preferences) is converted into a 384-dimensional dense vector embedding using `Sentence-Transformers` and saved into PostgreSQL via `pgvector` [INFERENCE].
5. **Job / Internship Recommendation**: When a recruiter posts a new opportunity with target skill requirements, the job profile is vectorized. The Matching Engine executes an optimized `pgvector` cosine distance query combined with hard SQL filters (e.g., minimum CGPA, active batch), yielding an instant candidate compatibility percentage [INFERENCE].
6. **Application Tracking ATS Workflow**: The student applies with a single click. The recruiter views applicants sorted by compatibility percentage, moves candidates through ATS pipeline stages (Shortlisted, Interviewed, Offered), and triggers email/in-app notifications [INFERENCE].
7. **Faculty R&D & FDP Workflow**: A faculty user navigates to the Academician Portal to explore industry-sponsored FDPs, industrial training, or corporate research consultancy RFPs, submitting proposals directly to industry partners [INFERENCE].
8. **Institutional Reporting**: TPOs and administrators access aggregated analytics dashboards. PostgreSQL aggregate queries compile real-time metrics on placement percentages, cohort skill deficiencies, and recruiter engagement trends [INFERENCE].

## 13. AI/ML Justification

### AI Component 1: Candidate-to-Opportunity Matcher & Upskilling Recommender
* **1. Exact Problem Solved**: Replaces manual resume keyword matching with semantic matching between multi-dimensional candidate profiles and complex industry job descriptions [INFERENCE].
* **2. Input**: Student skill profile vector (demonstrated skill levels, assessment results, domain interests) [INFERENCE].
* **3. Output**: Numerical compatibility match score ($0\%\text{--}100\%$) and ranked list of missing skill bridge courses [INFERENCE].
* **4. Why Simpler System Fails**: Keyword matching fails when terms differ semantically (e.g., candidate knows "Phytochemistry", job requires "Herbal Standardization") [INFERENCE].
* **5. Data Required**: Pre-trained `all-MiniLM-L6-v2` embedding model weights + standardized skill taxonomy [INFERENCE].
* **6. Evaluation**: Cosine similarity score validation against human recruiter rankings (Target $\ge 0.85$ correlation) [INFERENCE].
* **7. What Happens When Wrong**: Candidate receives slightly lower match rank, but hard SQL filters guarantee basic eligibility is never bypassed [INFERENCE].
* **8. Training Required**: None. Uses pre-trained embeddings [INFERENCE].
* **9. Fine-Tuning Required**: No [INFERENCE].
* **10. RAG Required**: No [INFERENCE].
* **11. CV Required**: No [INFERENCE].
* **12. Speech Processing Required**: No [INFERENCE].
* **13. Forecasting Required**: No [INFERENCE].
* **14. Human Oversight Required**: Yes. Recruiters review shortlisted applicants manually before issuing interview calls [INFERENCE].

### AI Component 2: Automated Assessment Scoring & Skill Gap Vector Generator
* **1. Exact Problem Solved**: Computes multi-attribute skill competency matrices from questionnaire response vectors [INFERENCE].
* **2. Input**: Raw questionnaire response choices, time taken per question, question difficulty weights [INFERENCE].
* **3. Output**: Skill proficiency scores ($0.0\text{--}5.0$) across specific taxonomy nodes and identified gap vectors [INFERENCE].
* **4. Why Simpler System Fails**: Simple raw score sums treat easy and advanced questions equally. Weighted item-response logic accurately measures deep technical skill levels [INFERENCE].
* **5. Data Required**: Calibrated question difficulty weight metadata [INFERENCE].
* **6. Evaluation**: Cronbach's Alpha test for internal assessment consistency ($\ge 0.75$) [INFERENCE].
* **7. What Happens When Wrong**: Student re-takes assessment or manually updates self-declared skills subject to recruiter verification [INFERENCE].
* **8. Training / Fine-Tuning / RAG**: Not required [INFERENCE].
* **9-13. CV / Speech / Forecasting**: Not required [INFERENCE].
* **14. Human Oversight Required**: Optional. Students can view detailed answer breakdowns [INFERENCE].

### Explicit Non-AI Exclusions
AI MUST NOT be used for:
* Candidate eligibility cutoffs (CGPA, degree year, discipline checks must be strict deterministic SQL `WHERE` clauses) [INFERENCE].
* Official academic credit assignment or internship hour logs [INFERENCE].
* Document authenticity verification (must use SHA-256 hash checks and official signature validation) [INFERENCE].

## 14. Data Architecture & Offline/Low-Network Design

### Core Database Schema (PostgreSQL)

```sql
-- Standardized Skill Taxonomy Graph
CREATE TABLE skill_taxonomy (
    skill_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    skill_name VARCHAR(150) NOT NULL UNIQUE,
    category VARCHAR(100) NOT NULL, -- e.g., 'Phytochemistry', 'Clinical Research', 'Soft Skills'
    parent_skill_id UUID REFERENCES skill_taxonomy(skill_id),
    description TEXT
);

-- Users Master Table
CREATE TABLE users (
    user_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    role VARCHAR(50) NOT NULL, -- 'STUDENT', 'RECRUITER', 'FACULTY', 'INSTITUTION_ADMIN'
    full_name VARCHAR(200) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- Student Profiles & Vectors
CREATE TABLE student_profiles (
    student_id UUID PRIMARY KEY REFERENCES users(user_id) ON DELETE CASCADE,
    institution_id UUID NOT NULL,
    degree VARCHAR(100) NOT NULL,
    discipline VARCHAR(100) NOT NULL,
    cgpa NUMERIC(3,2) NOT NULL,
    graduation_year INT NOT NULL,
    verified_status BOOLEAN DEFAULT FALSE,
    skill_vector vector(384) -- pgvector embedding for matching
);

-- Skill Gap Matrix per Student
CREATE TABLE student_skill_gap (
    gap_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    student_id UUID REFERENCES users(user_id) ON DELETE CASCADE,
    skill_id UUID REFERENCES skill_taxonomy(skill_id),
    demonstrated_level NUMERIC(3,2) NOT NULL, -- Range 0.00 to 5.00
    target_industry_level NUMERIC(3,2) NOT NULL,
    skill_gap NUMERIC(3,2) GENERATED ALWAYS AS (target_industry_level - demonstrated_level) STORED,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- Job & Internship Listings
CREATE TABLE listings (
    listing_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    recruiter_id UUID REFERENCES users(user_id) ON DELETE CASCADE,
    title VARCHAR(200) NOT NULL,
    type VARCHAR(50) NOT NULL, -- 'INTERNSHIP', 'JOB', 'APPRENTICESHIP', 'FACULTY_TRAINING', 'RND_PROJECT'
    location VARCHAR(100) NOT NULL,
    stipend_amount NUMERIC(10,2),
    min_cgpa NUMERIC(3,2) DEFAULT 0.0,
    required_skill_vector vector(384),
    status VARCHAR(50) DEFAULT 'ACTIVE',
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- Applications ATS
CREATE TABLE applications (
    application_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    listing_id UUID REFERENCES listings(listing_id) ON DELETE CASCADE,
    applicant_id UUID REFERENCES users(user_id) ON DELETE CASCADE,
    compatibility_score NUMERIC(5,2) NOT NULL, -- Percentage 0.00 to 100.00
    status VARCHAR(50) DEFAULT 'APPLIED', -- 'APPLIED', 'SHORTLISTED', 'INTERVIEWED', 'SELECTED', 'REJECTED'
    applied_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);
```

### Low-Network & Offline Architecture
1. **PWA Local Caching**: The frontend app uses Service Workers and `IndexedDB` to cache active assessment questionnaires, current application statuses, and student digital profile cards locally [INFERENCE].
2. **Assessment Draft Auto-Save**: Answers selected during a skill test are immediately stored in browser `localStorage`/`IndexedDB`. If the network drops, the test continues uninterrupted [INFERENCE].
3. **Background Sync Web Workers**: Upon network restoration, an background sync worker flushes pending assessment submission payloads to the FastAPI `/api/v1/assessments/submit` endpoint with exponential backoff retries [INFERENCE].
4. **Optimistic UI Updates**: Application clicks ("Apply Now") update the client UI immediately while queuing HTTP POST requests in the background [INFERENCE].
