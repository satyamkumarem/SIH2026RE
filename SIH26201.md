## 5. Constraints & Environment Realities

Developing drone and robotic rescue software for Indian field conditions introduces distinct operational realities that dictate system architecture:

```
+-----------------------------------------------------------------------------------+
|                            INDIAN FIELD CONSTRAINTS                               |
+-----------------------------------------------------------------------------------+
|  Connectivity : 80% cellular outage in disaster zones (floods, landslides, quakes)|
|  Geography    : High-altitude low air density (Himalayas) vs. Dense jungle canopy |
|  Battery Life : Micro-drones restricted to 20-30 min flight times                 |
|  Regulations  : DGCA Drone Rules 2021, DigitalSky Green/Yellow/Red airspace limits |
|  User Base    : Non-technical field rescue workers requiring simple touch UI      |
+-----------------------------------------------------------------------------------+
```

1.  **Network Degradation & Cellular Breakdown:** In disaster scenarios (e.g., Assam floods, Uttarakhand landslides), cellular infrastructure (4G/5G) is frequently destroyed [KNOWN]. The system *cannot* rely on cloud-hosted backends for real-time flight control or image processing [INFERENCE]. Edge compute and off-grid radio mesh are mandatory [INFERENCE].
2.  **Topographical & Weather Diversity:** High-altitude deployment (e.g., Lahaul-Spiti, Himachal Pradesh) causes thinner air and up to 30% reduction in battery performance and rotor lift [RESEARCHED]. Dense forest canopies (Northeast India) obstruct standard GPS signals [RESEARCHED]. The software must handle GPS-degraded positioning fallback and compute energy-aware battery return margins [INFERENCE].
3.  **Regulatory Compliance (DGCA & DigitalSky):** Indian airspace is governed by the Drone Rules 2021 [RESEARCHED]. Drones under 500kg must comply with DigitalSky airspace classifications [RESEARCHED]:
    *   *Green Zone:* Up to 400 ft AGL, no prior permission required [RESEARCHED].
    *   *Yellow Zone:* Controlled airspace requiring Air Traffic Control (ATC) approval [RESEARCHED].
    *   *Red Zone:* Strictly prohibited (near international borders, airports, military installations) [RESEARCHED].
    *   The software must automatically overlay DigitalSky spatial layers and enforce No-Fly-Zone (NFZ) hard limits [INFERENCE].
4.  **Hardware & Power Limitations:** Tactical field units run on battery power. Ground Control Station laptops and drone edge computers (Nvidia Jetson Orin Nano / Raspberry Pi 5) have finite compute and battery budgets [KNOWN]. Deep learning vision pipelines must be quantized (TensorRT/ONNX INT8) to consume under 15W [INFERENCE].
5.  **User Digital Literacy:** Field rescue personnel under extreme pressure require minimal manual inputs—single-tap mission confirmation, clear visual hazard warnings, and automated alert generation [INFERENCE].

## 10. Recommended Approach & Why

### Selected Architecture: Hybrid Edge-Swarm Node + Tactical Mesh GCS (Approach 3)

The team selects **Approach 3: The Hybrid Distributed Rescue Orchestration Architecture** [INFERENCE].

```
+-----------------------------------------------------------------------------------+
|                           RECOMMENDED SYSTEM HYBRID                               |
+-----------------------------------------------------------------------------------+
|  [ EDGE DRONE COMPUTER ]  ---> TensorRT YOLOv8 Vision + MAVLink Controller        |
|            | (LoRa / Local Wi-Fi Mesh)                                            |
|  [ TACTICAL FIELD GCS  ]  ---> Electron/React Web GIS + PX4 SITL + Mesh Gateway   |
|            | (Cellular / Satcom when available)                                   |
|  [ CLOUD COMMAND DASH  ]  ---> Strategic Overview + DigitalSky Sync + Audit Logs  |
+-----------------------------------------------------------------------------------+
```

#### Why Alternative Approaches Were Rejected

1.  **Rejection of Pure Cloud Web GCS (Approach 1):** In Indian disaster zones (floods in Assam/Uttarakhand, landslides in Himachal Pradesh), cellular towers are routinely disabled or congested [RESEARCHED]. Requiring continuous cloud connectivity to stream video for AI analysis or send flight commands introduces catastrophic single points of failure [INFERENCE].
2.  **Rejection of Monolithic Desktop ROS2 App (Approach 2):** While fully offline, compiling a monolithic C++/Qt application creates high development friction during a hackathon, makes responsive UI design difficult, and prevents field responders on tablets or mobile phones from viewing the map tactical layer [INFERENCE].

#### Core Justification for Approach 3
*   *Modular Separation:* The computational heavy-lifting (YOLO thermal vision) runs directly on the drone's companion computer at the edge [RESEARCHED].
*   *Local Reliability:* The Ground Control Station runs locally on a laptop as a light Node.js/Python server servicing a Web-based React GIS UI, requiring zero external internet [INFERENCE].
*   *Resilient Data Flow:* MAVLink telemetry travels over direct 900MHz/865MHz radio links or local Wi-Fi mesh, ensuring total independence from public telecommunication grids [INFERENCE].

### Detailed Data-Flow Narrative

1.  **Pre-Flight DigitalSky Safety Check:**
    *   The Operator selects a search polygon on the React GIS Map [INFERENCE].
    *   The GCS local backend loads cached DGCA DigitalSky GeoJSON boundaries and performs a 2D spatial intersection check [INFERENCE].
    *   If the search polygon intersects a Red Zone (e.g., airport radius), mission generation is hard-blocked [INFERENCE]. If in a Yellow Zone, a warning requires operator confirmation [INFERENCE].
2.  **Autonomous Search Path Generation & Dispatch:**
    *   The GCS converts the polygon into an optimized lawnmower waypoint path considering altitude, camera Field-of-View (FOV), and overlap percentages [KNOWN].
    *   The path is serialized into standard MAVLink mission items (`MAV_CMD_NAV_WAYPOINT`) and pushed over UDP/Serial to the PX4 flight controller [KNOWN].
3.  **In-Flight Edge Vision & Detection:**
    *   During execution, the drone's thermal camera streams raw frames to the edge companion computer (Jetson/Pi 5) [RESEARCHED].
    *   The TensorRT-optimized YOLOv8 model inspects frames at 30 FPS [RESEARCHED].
    *   Upon detecting a human heat signature above confidence threshold (e.g., >0.85), the edge computer extracts the vehicle's exact GPS coordinates, altitude, and frame thumbnail [INFERENCE].
    *   A high-priority MAVLink STATUSTEXT / custom message is transmitted back to the GCS over the radio link [INFERENCE].
4.  **Medical Dispatch & Drop Execution:**
    *   The Operator verifies the victim detection on the GCS HUD and clicks "Dispatch Medical Aid" [INFERENCE].
    *   The GCS calculates the optimal drop route for a heavy-lift cargo drone, accounting for wind vector and battery budget [INFERENCE].
    *   Upon arriving over the drop target, the drone initiates a precision hover at 5m AGL, verifies surface obstacle clearance via downward LiDAR/Sonar, and triggers the GPIO servo lock to release the insulated medical container [INFERENCE].

## 13. AI/ML Justification

AI should only be applied where traditional deterministic code fails. Below is the strict justification breakdown:

```
+------------------------------------------------------------------------------------+
|                                AI vs. RULE-BASED LOGIC                             |
+------------------------------------------------------------------------------------+
|  USE AI         : Thermal & Optical Survivor Detection (Unstructured video frames)|
|  DO NOT USE AI  : Flight Stability & Motor Control (Deterministic PID Loops)       |
|  DO NOT USE AI  : DigitalSky Airspace Geofencing (Exact 2D/3D Polygon Geometry)   |
|  DO NOT USE AI  : Fail-Safe Return-to-Launch (Hardcoded Altitude & Battery Limits)|
+------------------------------------------------------------------------------------+
```

### Component 1: Thermal & Optical Human Survivor Detection

*   **1. What exact problem does AI solve?** Distinguishing human bodies (alive/emitting heat) from warm debris, solar-heated rocks, animals, or water reflections in unstructured thermal/optical video feeds [INFERENCE].
*   **2. Input:** Raw 1080p / 640x480 thermal infrared video frames (8-bit or 16-bit radiometric array) [KNOWN].
*   **3. Output:** Bounding boxes `[x_min, y_min, x_max, y_max]`, class label (`human_survivor`), and confidence score `[0.0 - 1.0]` [KNOWN].
*   **4. Why can a simpler rule/system not solve it?** Threshold-based thermal blobs fail completely when background ambient ground temperatures reach 37°C or when bodies are partially covered by rubble/foliage [RESEARCHED].

## 14. Data Architecture & Offline/Low-Network Design

### Offline Data Schema (SQLite / Local JSON DB)

```sql
-- Missions Table
CREATE TABLE missions (
    mission_id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    type TEXT CHECK(type IN ('SEARCH_RESCUE', 'MEDICAL_DELIVERY', 'RECON')),
    status TEXT CHECK(status IN ('PLANNED', 'ACTIVE', 'COMPLETED', 'ABORTED')),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    boundary_geojson TEXT NOT NULL
);

-- Vehicles Table
CREATE TABLE vehicles (
    vehicle_id TEXT PRIMARY KEY,
    type TEXT CHECK(type IN ('QUADCOPTER', 'HEAVY_LIFT_HEXA', 'UGV_GROUND_ROBOT')),
    firmware_version TEXT,
    battery_level INTEGER,
    last_known_lat REAL,
    last_known_lon REAL,
    status TEXT CHECK(status IN ('DISCONNECTED', 'ARMED', 'IN_FLIGHT', 'RTL'))
);

-- Survivor Detections Table
CREATE TABLE detections (
    detection_id TEXT PRIMARY KEY,
    mission_id TEXT FOREIGN KEY REFERENCES missions(mission_id),
    vehicle_id TEXT FOREIGN KEY REFERENCES vehicles(vehicle_id),
    latitude REAL NOT NULL,
    longitude REAL NOT NULL,
    altitude_m REAL,
    confidence REAL NOT NULL,
    thermal_snapshot_blob BLOB,
    status TEXT CHECK(status IN ('UNCONFIRMED', 'VERIFIED_VICTIM', 'FALSE_POSITIVE', 'RESCUED'))
);

-- DigitalSky Airspace Cache
CREATE TABLE airspace_zones (
    zone_id TEXT PRIMARY KEY,
    zone_type TEXT CHECK(zone_type IN ('GREEN', 'YELLOW', 'RED')),
    min_altitude_ft REAL,
    max_altitude_ft REAL,
    geometry_geojson TEXT NOT NULL
);
```

If a field operator marks a detection as "False Positive" while the Field Commander marks it as "Verified", the Commander's role cryptographically overrides the field operator's state [INFERENCE].
