# HydroFlow-NTRO: Multi-Physics Hydrodynamic Dam Break & Inundation Analysis Dossier

---

## 1. Executive Snapshot

### Summary
The National Technical Research Organisation (NTRO) requires a generalized software modelling framework and interactive dashboard to simulate dam break and flash flood inundation across Indian river basins `[PS]`. Recent catastrophic incidents—such as the Rishi Ganga rock-ice avalanche flash flood in Uttarakhand (Feb 2021) `[KNOWN]`, the Wapriyang river blockade (Nov 2021) `[PS]`, and the Phuktal river landslide dam in J&K (2015) `[PS]`—highlight the critical need for rapid Humanitarian Assistance and Disaster Relief (HADR) scenario generation `[PS]`.

The proposed solution, **HydroFlow-NTRO**, establishes a multi-scale hydrodynamic simulation architecture. It integrates a 3D Smoothed Particle Hydrodynamics (SPH) engine for near-field, highly non-linear dam breach and turbulent wave surge mechanics with a 2D grid-based Delft3D/SFINCS engine for rapid, regional downstream flood routing `[INFERENCE]`. The platform automatically ingests open-source Digital Elevation Models (Copernicus GLO-30 / SRTM) `[PS]`, ingests Google Earth Engine (GEE) Sentinel-1 C-band SAR imagery for near-real-time observational flood mapping `[PS]`, computes automated exposure and Loss & Damage analytics `[PS]`, and exports standard geospatial formats (`.shp` and `.kml`) `[PS]`.

## 2. Problem Deconstruction

The problem statement explicit requirements are deconstructed into atomic implementation items while preserving exact letter/number identifiers:

### Explicit Requirement i
* **Source Text**: "Creation of generalized modelling framework to predict / simulate dam break/ river blockage analysis providing the necessary inputs on the basis of sudden water surge as well as loss and damage analysis using ‘Smooth Particle Hydrodynamics model and Delf3D model’." `[PS]`
* **Interpretation**: The core framework must support two distinct hydrodynamic computational paradigms: Smoothed Particle Hydrodynamics (SPH) and Delft3D `[PS]`. It must simulate both structural dam failures and natural river blockages (e.g., landslide/glacial lake dams) `[PS]`, model the resulting sudden water surge hydrograph `[PS]`, run both models, compare their output scenarios `[PS]`, and compute exposure and structural/economic loss and damage `[PS]`.
* **Implementation Implication**: Python wrappers around an open-source SPH solver (e.g., PySPH / DualSPHysics CLI) and Delft3D / D-Flow FM / SFINCS kernel `[RESEARCHED]`. Automated post-processing pipelines must cross-compare inundation depths, flow velocities, and arrival times between SPH and Delft3D outputs `[INFERENCE]`.

### Explicit Requirement ii
* **Source Text**: "Building a customized tool/ framework so that it is possible to generate a flood inundation simulation scenario using different input datasets." `[PS]`
* **Interpretation**: The tool must be modular and generalized to handle arbitrary user-provided or auto-fetched geospatial inputs across any river basin in India `[PS]`.
* **Implementation Implication**: Integration with open-source DEM datasets (Copernicus GLO-30, SRTM 30m, ALOS AW3D30) `[RESEARCHED]`, land cover maps (ESA WorldCover, Bhuvan LULC) `[RESEARCHED]`, and user-defined breaching parameters (breach width, failure duration, initial reservoir water level, discharge hydrograph) `[INFERENCE]`.

### Explicit Requirement iii
* **Source Text**: "Developing a Dashboard for providing modelling input and output visualization framework (GUI). The program should support the large volume of data. Output should be converted to .shp or .Kml file." `[PS]`
* **Interpretation**: A high-performance web Graphical User Interface (GUI) must allow users to configure simulation parameters, visualize heavy spatio-temporal raster/vector datasets without lag, and export flood extent maps and damage overlays directly to Shapefile (`.shp`) and Keyhole Markup Language (`.kml`) formats `[PS]`.
* **Implementation Implication**: Frontend using MapLibre GL JS and Deck.gl for WebGL-accelerated rendering of multi-gigabyte spatio-temporal raster layers `[RESEARCHED]`. Backend geospatial exporters using GDAL/OGR and GeoPandas for `.shp` and `.kml` file generation `[RESEARCHED]`.

### Explicit Requirement iv
* **Source Text**: "Additionally, developing a framework for near real time flood analysis through Google Earth Engine with the help of open source data." `[PS]`
* **Interpretation**: A parallel or complementary module that leverages Google Earth Engine (GEE) Python API to ingest cloud-based open-source satellite imagery (specifically Sentinel-1 Synthetic Aperture Radar - SAR) to perform near-real-time (NRT) observed flood mapping `[PS]`.
* **Implementation Implication**: GEE pipeline executing pre-event vs. post-event SAR backscatter change detection (Otsu thresholding / Lee speckle filtering) to delineate actual ground flood extents and validate model-predicted inundation zones `[RESEARCHED]`.

### Explicit Requirement v
* **Source Text**: "Simulation needs to be done by taking the any river and Dam data (open source) of India during the final demonstration of the software." `[PS]`
* **Interpretation**: The live demonstration must show the system running end-to-end on a real Indian river basin and dam using publicly available datasets `[PS]`.
* **Implementation Implication**: Preparation of complete case studies for Indian rivers, such as the Rishi Ganga / Dhauliganga basin (Uttarakhand 2021 disaster site) `[RESEARCHED]` or the Mullaperiyar / Tehri Dam basins using open-source HydroSHEDS, Copernicus DEM, and CWC public data `[RESEARCHED]`.

## 5. Constraints & Environment Realities

1. **Topographic Data Resolution**: Free global DEMs (Copernicus GLO-30, SRTM) have a 30m spatial resolution and vertical errors of 2–5m `[RESEARCHED]`. Narrow Himalayan river valleys (e.g., Rishi Ganga) may suffer from terrain shadowing or cell averaging `[KNOWN]`.
2. **Computational Complexity**: 3D SPH is computationally intensive, scaling with $O(N^2)$ or $O(N \log N)$ particle interactions `[KNOWN]`. Simulating a 50km river stretch with billions of particles in SPH is impossible in real-time on standard hardware `[KNOWN]`. SPH must be restricted to the near-field dam breach domain ($\sim 1\text{--}3\text{ km}$), while Delft3D/SFINCS handles the 2D regional domain ($\sim 10\text{--}100\text{ km}$) `[INFERENCE]`.
3. **Monsoon Cloud Cover**: Optical satellites (Landsat, Sentinel-2) are frequently obstructed by heavy cloud cover during flash flood events `[KNOWN]`. Synthetic Aperture Radar (SAR) from Sentinel-1 (C-band) is necessary because it penetrates clouds and operates day/night `[RESEARCHED]`.
4. **Bandwidth & Field Connectivity**: Disaster response teams operating in remote districts (e.g., Chamoli, Leh) often experience low-bandwidth mobile networks `[KNOWN]`. The dashboard must support lightweight vector tile transfer (`.pbf`) and offline downloadable `.kml` files `[INFERENCE]`.
5. **Hardware Constraints in Hackathon**: Student teams do not have access to supercomputer clusters. The system must run within free-tier cloud resources (Google Colab / AWS Free Tier / local NVIDIA GPU) during evaluation `[ASSUMPTION]`.

## 9. Candidate Solution Approaches

### Approach A: Standalone 2D Grid Hydrodynamic Architecture (Delft3D / SFINCS Only)
* **Mechanism**: Uses Deltares HydroMT to automatically fetch DEM and land cover data, build a Delft3D/SFINCS 2D shallow water model, and simulate flood propagation downstream of a dam given an empirical parametric breach hydrograph (Froehlich equation) `[RESEARCHED]`.
* **Pros**: Highly scalable, computationally fast (runs in 2–5 minutes for a 50km river stretch), established open-source python integrations `[RESEARCHED]`.
* **Cons**: Fails Explicit Requirement i, which mandates 'Smooth Particle Hydrodynamics' modeling `[PS]`. Parametric hydrographs simplify 3D dam breach mechanics and fluid-structure dynamics `[KNOWN]`.

### Approach B: Pure 3D Meshless Particle Architecture (DualSPHysics / PySPH Only)
* **Mechanism**: Models the entire reservoir, dam structure, and downstream river channel using 3D SPH particle formulations (Weakly Compressible SPH / Incompressible SPH) `[RESEARCHED]`.
* **Pros**: Exquisitely models 3D fluid motion, dam wall erosion, wave splashing, and initial surge impact `[RESEARCHED]`.
* **Cons**: Computationally impossible for regional scales (requires trillions of particles for a 50km basin, taking days/weeks on supercomputers) `[KNOWN]`. Fails Delft3D integration requirement `[PS]`.

### Approach C: Hybrid Dual-Engine Architecture (3D SPH Near-Field + 2D Delft3D Far-Field + GEE SAR) [RECOMMENDED]
* **Mechanism**:
  1. **Near-Field (0–2 km)**: PySPH / DualSPHysics simulates 3D dam breach mechanics, wave surge generation, and structural collapse dynamics to extract a physically realistic discharge hydrograph $Q(t)$ at the dam outlet `[INFERENCE]`.
  2. **Far-Field (2–50 km)**: Delft3D / SFINCS ingests $Q(t)$ from the SPH engine and routes the 2D shallow water flood wave downstream over Copernicus GLO-30 DEM terrain `[INFERENCE]`.
  3. **Empirical Validation**: Google Earth Engine Python API ingests Sentinel-1 SAR imagery to map actual inundation extents for historical calibration `[INFERENCE]`.
  4. **Analytics**: Automated Loss & Damage engine overlays modeled inundation depth with OSM/WorldPop layers `[INFERENCE]`.
* **Pros**: Fulfills ALL explicit requirements (SPH, Delft3D, GEE SAR, Loss/Damage, `.shp`/`.kml` export) `[PS]`. Solves the computational bottleneck by restricting SPH to near-field physics and using Delft3D for regional routing `[INFERENCE]`.

## 10. Recommended Approach & Why

**Selected Approach**: **Approach C (Hybrid Dual-Engine Architecture)** `[INFERENCE]`.

### Justification
1. **Explicit Requirement Compliance**: The problem statement explicitly demands both 'Smooth Particle Hydrodynamics' and 'Delft3D' models, comparing their scenarios `[PS]`. Neither Approach A nor Approach B alone can fulfill this explicit requirement `[INFERENCE]`.
2. **Physical & Computational Realism**: 3D SPH excels at simulating complex, multi-phase fluid dynamics, violent free-surface splash, and structural breaching in the immediate vicinity of the dam (near-field) `[RESEARCHED]`. However, grid-based shallow water equations (Delft3D / SFINCS) are orders of magnitude faster for routing water through long river valleys (far-field) `[RESEARCHED]`. Coupling them provides both physical fidelity at the dam breach and computational feasibility across a 50km river basin `[INFERENCE]`.
3. **Multi-Source Validation**: Integrating GEE Sentinel-1 SAR imagery provides empirical ground-truth verification, enabling disaster managers to compare predictive hydrodynamic models against satellite observations `[INFERENCE]`.

### Why Alternatives Were Rejected
* **Approach A Rejected**: Omits Smoothed Particle Hydrodynamics (SPH), directly violating Requirement i `[PS]`.
* **Approach B Rejected**: Running SPH over a 50km basin requires excessive compute (millions of GPU-hours), rendering it impossible for real-time HADR scenario generation or hackathon demonstration `[KNOWN]`.

### Data-Flow Narrative
1. **User Input & Configuration**: The user opens the web dashboard, selects an Indian river basin (e.g., Rishi Ganga River), selects a dam/river blockage location on the interactive MapLibre map, and defines breaching parameters (water level, failure mode, breach width) `[INFERENCE]`.
2. **Data Ingestion**: FastAPI triggers asynchronous background workers via Celery `[INFERENCE]`. The system automatically queries OpenTopography/GEE for the 30m Copernicus GLO-30 DEM tile, fetches OSM river network geometries, and retrieves ESA WorldCover land use layers `[RESEARCHED]`.
3. **3D SPH Near-Field Execution**: The backend invokes the PySPH / DualSPHysics engine for a localized $1\text{--}2\text{ km}$ bounding box around the dam site `[INFERENCE]`. SPH particle equations compute 3D structural breach dynamics, generating a time-series mass flow rate $Q(t)$ hydrograph at the breach threshold `[INFERENCE]`.
4. **2D Delft3D / SFINCS Far-Field Routing**: The output hydrograph $Q(t)$ is passed as an inflow boundary condition into HydroMT-SFINCS / Delft3D `[RESEARCHED]`. The 2D hydrodynamic solver routes the water wave downstream over the 30m DEM grid across a 50km stretch, generating time-series NetCDF rasters of water depth, arrival time, and velocity `[INFERENCE]`.
5. **GEE NRT SAR Analysis**: In parallel, the GEE module fetches Sentinel-1 SAR GRD images for pre-flood and post-flood dates `[RESEARCHED]`. It applies Lee speckle filtering, computes backscatter differences in VV/VH polarizations, and generates an empirical observed flood extent mask `[RESEARCHED]`.
6. **Loss & Damage Assessment**: The Loss & Damage microservice performs spatial intersections of the maximum flood depth raster with WorldPop population density rasters and OSM building/infrastructure vectors `[INFERENCE]`. It quantifies flooded area ($\text{km}^2$), exposed population count, damaged road lengths ($\text{km}$), and land-use impact categories `[INFERENCE]`.
7. **Visualization & Vector Export**: GeoPandas and GDAL convert output raster boundaries into Shapefile (`.shp`) and Keyhole Markup Language (`.kml`) vector formats `[RESEARCHED]`. Results are pushed via WebSockets to the Next.js frontend, rendering smooth 3D WebGL animations of the flood wave and interactive loss charts `[INFERENCE]`.

## 13. AI/ML Justification

### Critical Technical Assessment
**Hydrodynamic fluid flow is governed by physical conservation laws (Navier-Stokes and Shallow Water Equations), NOT machine learning models `[KNOWN]`.** Using AI to fabricate or predict water flow routing directly is physically unsound and leads to hallucinated flood boundaries that violate conservation of mass `[INFERENCE]`.

However, lightweight AI/ML is strictly justified for two specific sub-tasks:

#### AI Component 1: Sentinel-1 SAR Flood Thresholding
* **Purpose**: Automated classification of flooded vs. non-flooded SAR backscatter pixels under complex terrain and rough water surface conditions `[RESEARCHED]`.
* **Model Type**: Multilayer Perceptron (MLP) / Random Forest Classifier integrated with Height Above Nearest Drainage (HAND) topographic index `[RESEARCHED]`.
* **Input**: Sentinel-1 VV backscatter, VH backscatter, VV/VH ratio, DEM slope, HAND elevation index `[RESEARCHED]`.
* **Output**: Binary flood classification mask (1 = Flooded, 0 = Non-flooded) `[RESEARCHED]`.
* **Data Required**: Historical Sentinel-1 SAR scenes over validated Indian flood events (e.g., Assam, Kerala, Odisha floods) `[RESEARCHED]`.
* **Why AI is Preferable**: Fixed global Otsu thresholding fails when wind creates rough water surfaces (high radar backscatter) or in mountain radar shadows `[RESEARCHED]`. ML incorporating HAND topography eliminates false positives on high-altitude slopes `[RESEARCHED]`.
* **Evaluation Metric**: Intersection over Union (IoU) and F1-Score against verified Copernicus Emergency Management Service (CEMS) flood vector maps `[RESEARCHED]`.
* **Failure Mode & Human Oversight**: In dense urban canyons, SAR layover produces false negatives. The dashboard provides a manual threshold slider allowing disaster analysts to override AI classification boundaries `[INFERENCE]`.

#### AI Component 2: Instant Surrogate Flood Predictor (Hackathon Demo Acceleration)
* **Purpose**: Provide real-time (instant < 1 second) predicted flood extents while heavy SPH/Delft3D simulations run in the background `[INFERENCE]`.
* **Model Type**: XGBoost Regressor / Convolutional Neural Operator (CNO) trained on pre-run Delft3D grid outputs `[INFERENCE]`.
* **Input**: Dam breach peak discharge $Q_\text{peak}$, reservoir storage volume $V$, river slope, downstream distance $X$ `[INFERENCE]`.
* **Output**: Instant estimated maximum flood depth $H_\text{max}(x, y)$ grid `[INFERENCE]`.
* **Data Required**: Offline synthetic database of 200+ Delft3D runs across representative Indian terrain geometries `[INFERENCE]`.
* **Why AI is Preferable**: Full Delft3D runs take 2–5 minutes; the surrogate ML model provides immediate UI feedback during parameter slider adjustments `[INFERENCE]`.
* **Failure Mode**: ML surrogates can underestimate unprecedented extreme surge peaks. The dashboard explicitly marks surrogate outputs as "Preliminary AI Estimate" until the physics-based Delft3D execution completes `[INFERENCE]`.

#### Where AI Should NOT Be Used
AI must **NEVER** replace the physics-based SPH or Delft3D hydrodynamics numerical solvers for generating final authoritative disaster relief maps `[INFERENCE]`.

## 14. Data Architecture & Offline/Low-Network Design

### Spatial Database Schema (PostGIS)

```sql
-- PostgreSQL / PostGIS Core Schema

CREATE EXTENSION IF NOT EXISTS postgis;

-- 1. Dams and River Obstacles Table
CREATE TABLE dams (
    dam_id SERIAL PRIMARY KEY,
    name VARCHAR(250) NOT NULL,
    river_name VARCHAR(250) NOT NULL,
    state VARCHAR(100),
    height_m NUMERIC(6,2),
    capacity_mcm NUMERIC(10,2),
    location GEOMETRY(Point, 4326),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 2. Hydrodynamic Simulation Runs Table
CREATE TABLE simulation_runs (
    sim_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    dam_id INT REFERENCES dams(dam_id),
    model_type VARCHAR(50) CHECK (model_type IN ('SPH', 'DELFT3D', 'HYBRID')),
    initial_water_level_m NUMERIC(6,2),
    breach_width_m NUMERIC(6,2),
    failure_duration_sec INT,
    status VARCHAR(50) DEFAULT 'PENDING',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 3. Inundation Output Vectors Table
CREATE TABLE inundation_extents (
    extent_id SERIAL PRIMARY KEY,
    sim_id UUID REFERENCES simulation_runs(sim_id) ON DELETE CASCADE,
    time_step_min INT,
    max_depth_m NUMERIC(5,2),
    geom GEOMETRY(MultiPolygon, 4326),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_inundation_geom ON inundation_extents USING GIST (geom);

-- 4. Loss & Damage Summary Table
CREATE TABLE loss_assessments (
    loss_id SERIAL PRIMARY KEY,
    sim_id UUID REFERENCES simulation_runs(sim_id) ON DELETE CASCADE,
    flooded_area_sqkm NUMERIC(10,2),
    exposed_population INT,
    damaged_roads_km NUMERIC(8,2),
    impacted_cropland_ha NUMERIC(10,2),
    estimated_damage_inr NUMERIC(14,2)
);
```

### Offline & Low-Network Optimization Strategy
1. **PMTiles Vector Caching**: Vector basemaps and administrative boundaries are packaged as PMTiles (single-file serverless vector tile archives) and cached locally in the browser via IndexedDB `[RESEARCHED]`. This allows the map GUI to render fully even when field Internet drops `[INFERENCE]`.
2. **Bandwidth Reduction via Compressed GeoJSON / Vector Tiles**: Raw hydrodynamic raster grids are converted server-side into simplified vector contours (`.pbf` vector tiles) before transmission, reducing payload size by up to 90% compared to heavy raw GeoTIFF rasters `[INFERENCE]`.
3. **Offline Export Packages**: Field teams can pre-download lightweight `.kml` or `.kmz` files (typically < 2 MB) onto mobile phones or handheld GPS devices running maps.me or QGIS for offline navigation in disaster zones `[INFERENCE]`.
