# SIH 2026 Solution Dossier: Web-Based Interactive 3D Ocean Data Visualization Platform

---

## 1. Executive Snapshot

### Summary
The Indian National Centre for Ocean Information Services (INCOIS), an autonomous organization under the Ministry of Earth Sciences (MoES), generates and archives vast volumes of 3D ocean model fields (e.g., MOM5, GODAS, ROMS, BGC) alongside real-time and delayed-mode in-situ observational profile data (Argo floats, underwater Gliders, CTD, moorings) across India's Exclusive Economic Zone (EEZ) and the broader Indian Ocean [PS]. Currently, oceanographers and operational forecasters must switch between legacy desktop GIS, 2D plan-view web servers, and offline scripts, creating a critical bottleneck in rapidly correlating model forecasts with direct observations during marine emergencies [PS]. This proposed solution delivers a platform-independent, web-native 3D interactive ocean visualization system that seamlessly co-renders 4D/3D volumetric numerical model fields and geospatial in-situ profiles in a single browser viewport [INFERENCE]. By combining WebGL/Cesium.js volumetric GPU raycasting, dynamic depth slicing, custom colorbar/isosurface extraction, and interactive profile chart inspection, the platform accelerates operational decision-making for disaster management, search-and-rescue, and fishery advisories while doubling as an engaging science communication tool for public outreach [INFERENCE].

## 2. Problem Deconstruction

The problem statement explicitly highlights existing operational gaps and outlines functional requirements for a web-based 3D ocean data visualization platform [PS].

### Explicit Problem Statement Requirements

1. **3D Volumetric Rendering [PS]:**
   * *Source Text:* "Interactive visualization of ocean model fields (temperature, salinity, current vectors) across the full water column, with support for depth-slice views, isosurface extraction, and time-step animation using WebGL / Three.js or Cesium.js." [PS]
   * *Interpretation:* The frontend must render 3D scalar fields (temperature, salinity) as volumetric textures or isosurfaces and vector fields (currents $u, v, w$) as directional streamlines/particles across multiple depth layers [INFERENCE].
   * *Implementation Implication:* Requires slicing 4D NetCDF files ($T, Z, Y, X$) into compressed WebGL-friendly 3D texture blocks or WebGPU volume buffers, alongside custom WebGL shaders for GPU raycasting and volumetric slicing [INFERENCE].

2. **Instrument Data Overlay [PS]:**
   * *Source Text:* "Co-display of Argo float, Glider profile, CTD and BGC data using geospatially accurate markers; users can click a float/glider to inspect a depth-vs-variable profile chart with timestamps." [PS]
   * *Interpretation:* In-situ point and trajectory profile datasets must be geospatially anchored over the 3D terrain/globe [INFERENCE]. Selecting an instrument marker triggers interactive popups displaying depth profiles ($Z$ vs $T/S/Chl$) and time-series plots [INFERENCE].
   * *Implementation Implication:* Ingest Argo trajectory index files and Glider NetCDF profiles into GeoJSON/CZML format; link map interaction events to Chart.js/Plotly.js rendering overlays [INFERENCE].

3. **Multi-format Data Ingestion [PS]:**
   * *Source Text:* "Automated parsers for NetCDF (via PyNIO / xarray backend) and delimited text formats, with a modular architecture that allows new variables or data sources to be added with minimal code change." [PS]
   * *Interpretation:* Backend service must auto-parse NetCDF files (CF-compliant) and ASCII/CSV text files from INCOIS LAS or FTP feeds, converting them into structured API responses or Zarr/COG/JSON formats [INFERENCE].
   * *Implementation Implication:* Build a Python FastAPI ETL pipeline using `xarray`, `netCDF4`, `dask`, and `pandas` [ASSUMPTION]. (Note: PyNIO is deprecated in modern scientific Python, so `xarray` + `netCDF4`/`h5netcdf` serves as the resilient backend driver) [RESEARCHED].

4. **Customizable Colorbar & Variable Controls [PS]:**
   * *Source Text:* "Dynamic colorbar editor (color palette, min/max range, log/linear scale), variable selector, layer opacity controls, and vertical exaggeration slider for intuitive depth perception." [PS]
   * *Interpretation:* User interface must provide real-time controls over shader lookup tables, data stretching, opacity, variable switching, and vertical scale adjustment ($Z$-scaling) to accommodate shallow coastal vs. deep ocean bathymetry [INFERENCE].
   * *Implementation Implication:* Map UI sliders directly to WebGL uniform variables (`u_min`, `u_max`, `u_opacity`, `u_zExaggeration`, `u_colormapTexture`) without requiring full scene re-renders [INFERENCE].

5. **Web-based, Scalable Architecture [PS]:**
   * *Source Text:* "Frontend built on modern JavaScript frameworks with a lightweight REST/OPeNDAP API backend, enabling deployment on INCOIS infrastructure without any client-side dependencies." [PS]
   * *Interpretation:* No desktop software, Java applets, or plugins required on the user device [INFERENCE]. Runs in standard WebGL2-enabled web browsers (Chrome, Firefox, Edge, Safari) [KNOWN].
   * *Implementation Implication:* React / Vite single-page application frontend communicating with an OPeNDAP/THREDDS server or FastAPI microservice over REST/WMS [INFERENCE].

6. **Extensible Design [PS]:**
   * *Source Text:* "Plugin-style module for future integration of additional sensors (e.g., CTDs, moorings, HF-radar, Acoustic Doppler Current Profiler (ADCP), etc.), new ocean model variables, and machine-learning derived products." [PS]
   * *Interpretation:* Architecture must enforce modular abstraction layers for data loaders, UI controls, and visualizers [INFERENCE].
   * *Implementation Implication:* Abstract Data Provider Interface pattern in JavaScript/TypeScript and adapter pattern in Python ETL pipeline [INFERENCE].

7. **Open Standards Compliance [PS]:**
   * *Source Text:* "The system will follow open standards (OGC WMS/WCS, CF Conventions for NetCDF), enabling interoperability with national and international ocean data portals." [PS]
   * *Interpretation:* Services must conform to Open Geospatial Consortium (OGC) specifications (WMS/WCS) and NetCDF Climate and Forecast (CF) Metadata Conventions (v1.8+) [RESEARCHED].
   * *Implementation Implication:* Serve standard GeoTIFF/WMS layers via GeoServer/THREDDS alongside custom 3D volume tiles [INFERENCE].

8. **Public Outreach & Science Communication [PS]:**
   * *Source Text:* "Beyond operational use, the platform will serve as a powerful science communication tool... educating school and college students about ocean dynamics, engaging the general public... and supporting policymakers." [PS]
   * *Interpretation:* Platform must feature dual UX modes: an "Operational Mode" with dense technical controls and a simplified "Public Outreach Mode" with guided 3D story maps and intuitive tooltips [INFERENCE].

## 5. Constraints & Environment Realities

1. **Client-Side Hardware Diversity [INFERENCE]:**
   * Operational forecasters may possess high-end workstations with discrete GPUs, whereas schools and public users operate on basic laptops, tablets, or integrated graphics [INFERENCE].
   * *Mitigation:* WebGL2 fallback modes, Level-of-Detail (LOD) volumetric texture sub-sampling, and adaptive frame-rate adjustment [INFERENCE].

2. **Network Bandwidth Constraints [INFERENCE]:**
   * Raw 3D ocean model outputs (e.g., $0.083^\circ \times 0.083^\circ \times 50 \text{ depth levels} \times 24 \text{ time steps}$) exceed several gigabytes per day [RESEARCHED]. Streaming uncompressed NetCDF directly to browser viewports will choke internet connections [INFERENCE].
   * *Mitigation:* Server-side data sub-sampling, Zarr chunking, and compressed WebGL 3D texture format generation ($256 \times 256 \times 50$ RGB alpha atlas) [INFERENCE].

3. **Geospatial & Vertical Scale Disparity [KNOWN]:**
   * The horizontal extent of India's EEZ spans thousands of kilometers (e.g., $60^\circ\text{E} - 95^\circ\text{E}$), while depth spans only 0 to 6,000 meters [KNOWN]. On a true-scale 3D globe, the entire water column is a paper-thin surface sheet [KNOWN].
   * *Mitigation:* Implement real-time GPU vertical exaggeration slider ($10\times$ to $200\times$) and local bathymetric sub-surface curtain rendering [INFERENCE].

4. **Heterogeneous Data Coordinates [KNOWN]:**
   * Ocean models use structured curvilinear grids or regular lat-lon grids with vertical depth/sigma levels [KNOWN]. Argo floats provide discrete vertical point profiles at irregular temporal intervals [KNOWN]. Gliders record continuous diagonal sawtooth path profiles [KNOWN].
   * *Mitigation:* Normalize coordinate metadata on the backend into WGS84 ($EPSG:4326$) horizontal coordinates and standard depth levels ($meters$), keeping raw profile points intact for hover inspection [INFERENCE].

5. **Deployment Environment [PS]:**
   * Platform must deploy seamlessly on INCOIS server infrastructure without requiring end-users to install desktop software, browser extensions, or administrative plugins [PS].

## 9. Candidate Solution Approaches

### Approach 1: Virtual Globe (Cesium.js) + WebGL2 Volume Raycasting Shader (Recommended)
* **Mechanism:** Use Cesium.js for the global 3D geospatial context, terrain bathymetry, and in-situ 3D point markers/trajectories [INFERENCE]. Integrate custom WebGL2 3D texture raycasting shaders bound to a sub-surface bounding box frame to perform volumetric scalar rendering, dynamic depth slicing, and isosurface rendering [INFERENCE].
* **Required Data:** Pre-sliced Zarr / 3D PNG texture atlas generated by Python FastAPI backend from NetCDF inputs [INFERENCE].
* **Architecture:** React + Cesium.js + Custom WebGL Shaders frontend; FastAPI + xarray + Zarr backend [INFERENCE].
* **Complexity:** Moderate-High (Custom GLSL raycasting shader logic required) [INFERENCE].
* **Explainability:** High (Direct physical scalar mapping and geospatial anchoring) [INFERENCE].
* **Cost:** Low (100% Open Source: CesiumJS, FastAPI, Zarr) [INFERENCE].
* **Scalability:** High (Tile-based and chunked volume streaming) [INFERENCE].
* **Hackathon Feasibility:** 9/10 (Can build working MVP in 36-48 hours with sample NetCDF) [INFERENCE].
* **Production Feasibility:** 9.5/10 (Scales to full INCOIS operational infrastructure) [INFERENCE].

### Approach 2: Server-Side VTK/PyVista Rendering with WebRTC/HLS Live Stream
* **Mechanism:** Perform heavy 3D volumetric rendering and isosurface extraction on a GPU server using Python VTK/PyVista/ParaView Server [INFERENCE]. Stream the rendered 3D scene frame-by-frame to the web client using WebRTC or WebSocket image frames [INFERENCE].
* **Required Data:** Direct NetCDF access on GPU server [INFERENCE].
* **Architecture:** Python PyVista / VTK server cluster + WebRTC stream + React control client [INFERENCE].
* **Complexity:** Very High (Heavy server GPU requirements, complex streaming latency management) [INFERENCE].
* **Explainability:** High [INFERENCE].
* **Cost:** High (Requires dedicated server-side GPU instances for concurrent web users) [INFERENCE].

* **Hackathon Feasibility:** 5/10 (High streaming latency and server configuration risk) [INFERENCE].

## 10. Recommended Approach & Why

### Selection: Approach 1 (Cesium.js + WebGL2 Custom 3D Volume Raycasting + Python xarray Backend)

**Why It Wins:**
1. **Geospatial & Volumetric Integration:** Cesium.js natively handles global WGS84 coordinates, 3D terrain/bathymetry, and camera navigation [INFERENCE]. Custom WebGL2 volume raycasting shaders embedded within Cesium Primitive stages provide true 3D volumetric scalar rendering ($T, S$) directly inside the sub-surface water column [INFERENCE].
2. **Zero Client Dependencies:** Operates natively in any WebGL2-compliant web browser without third-party plugins [PS].
3. **High Hackathon Feasibility:** Cesium.js handles globe camera navigation out of the box, allowing the student team to focus energy on GLSL volumetric shaders, xarray data chunking, and profile UI popups [INFERENCE].
4. **Outreach & Operational Flexibility:** Supports both dual-perspective rendering (dense operational slicing vs. public guided camera tours) [INFERENCE].

**Rejection Reasons for Alternatives:**
* *Approach 2 (Server-side VTK Streaming)* was rejected because server-side GPU rendering for hundreds of concurrent public users introduces high infrastructure costs, streaming latency, and server bottlenecks [INFERENCE].
* *Approach 3 (Three.js + Deck.gl Dual Canvas)* was rejected due to complex WebGL depth-buffer and camera synchronization issues across two distinct canvas contexts, which poses high delivery risk during a timed hackathon [INFERENCE].

### Data-Flow Narrative Step-by-Step

1. **Ingestion & Processing:** The backend ETL pipeline uses `xarray` and `netCDF4` to monitor ocean model output repositories (INCOIS LAS / Copernicus) and in-situ FTP servers (Ifremer Argo/Glider) [INFERENCE].
2. **Chunking & Formatting:** 3D model variable grids ($T, S, u, v, w$) are processed into multi-dimensional Zarr store arrays or packed into 3D binary byte buffers [INFERENCE]. In-situ profile points and trajectories are indexed into GeoJSON/CZML structures with depth attributes [INFERENCE].
3. **API Serving:** When a user selects a spatial bounding box, time step, and model variable, the frontend issues a REST request to the FastAPI service [INFERENCE].
4. **WebGL Volume Loading:** The frontend downloads the downsampled 3D scalar byte array, loads it into a WebGL2 `WebGLTexture3D`, and passes uniform parameters (`u_min`, `u_max`, `u_sliceDepth`, `u_zExaggeration`) to the GLSL volume raycasting shader [INFERENCE].
5. **Raymarching Render:** The custom WebGL shader casts rays from the camera through the 3D bounding volume, sampling texture points to compute color and opacity based on user-configured colormaps and isosurface thresholds [INFERENCE].
6. **In-situ Overlay & Interaction:** Argo and Glider markers are placed on the Cesium globe at precise WGS84 locations [INFERENCE]. Hovering or clicking an in-situ marker triggers an event that fetches profile array data and renders an overlay graph using Chart.js/Plotly.js [INFERENCE].

## 13. AI/ML Justification

### Proposed AI/ML Component: 3D Spatial Profile Gap-Infilling & Ocean Feature Extraction (Eddy Detection)

1. **What exact problem does AI solve?**
   * Ocean model outputs and in-situ profiles have spatial-temporal gaps (e.g., cloud cover in satellite SST, sparse Argo float spatial density) [INFERENCE]. AI algorithms (e.g., 3D Kriging neural networks or Convolutional Autoencoders) perform spatial gap-infilling and automatically extract 3D oceanic features such as mesoscale eddies and thermocline boundary layers [INFERENCE].
2. **What is the input?**
   * 3D gridded numerical model scalar fields ($T, S$) and sparse in-situ profile vectors [INFERENCE].
3. **What is the output?**
   * Infilled continuous 3D scalar arrays and 3D bounding geometry metadata marking mesoscale eddy centers and boundary contours [INFERENCE].
4. **Why can a simpler rule/system not solve it?**
   * Simple linear or bi-cubic interpolation smooths out non-linear physical dynamics like sharp fronts and eddy boundaries [INFERENCE].
5. **What data is required?**
   * Historical 3D MOM5/GODAS reanalysis fields (e.g., Copernicus `GLOBAL_MULTIYEAR_PHY_001_030`) and synchronized Argo profile datasets [PS].
6. **How will it be evaluated?**
   * Mean Squared Error (MSE) and structural similarity (SSIM) against cross-validated holdout Argo profile observations [INFERENCE].
7. **What happens when it is wrong?**
   * The system falls back to standard inverse-distance weighting (IDW) or raw physics model output [INFERENCE].
8. **Does it require training?** Yes [INFERENCE].
9. **Does it require fine-tuning?** Yes, on regional Indian Ocean high-resolution datasets [INFERENCE].
10. **Does it require RAG?** No [INFERENCE].
11. **Does it require computer vision?** Yes (3D CNNs for spatial volume pattern detection) [INFERENCE].
12. **Does it require speech processing?** No [INFERENCE].
13. **Does it require forecasting?** Optional (short-term eddy movement prediction) [INFERENCE].
14. **Is human oversight required?** Yes, INCOIS forecasters must visually verify AI-extracted eddy boundaries against direct observation profiles before issuing advisories [PS].

### Where AI Should NOT Be Used
* **Raw Render Pipeline:** AI should NOT be used to generate or synthesize the primary WebGL rendering shaders or raw physical data values [INFERENCE]. Forecasters require exact physical numerical values, not AI-hallucinated imagery [PS].

## 14. Data Architecture & Offline/Low-Network Design

### Data Schema (PostGIS & Zarr Structure)

#### In-Situ Observation Metadata Table (`insitu_platforms`)
* `platform_id` (VARCHAR, PK): e.g., `"ARGO_2901542"`, `"GLIDER_INCOIS_04"`
* `platform_type` (ENUM): `'ARGO'`, `'GLIDER'`, `'CTD'`, `'BGC'`, `'MOORING'`
* `last_latitude` (FLOAT), `last_longitude` (FLOAT)
* `trajectory_geom` (GEOMETRY(LineStringZ, 4326)): 3D spatial track
* `last_updated` (TIMESTAMP)

#### Profile Measurement Table (`insitu_profiles`)
* `profile_id` (UUID, PK)
* `platform_id` (FK -> `insitu_platforms`)
* `timestamp` (TIMESTAMP)
* `location` (GEOMETRY(PointZ, 4326))
* `depth_array` (FLOAT[]): Array of depth values ($m$)
* `temp_array` (FLOAT[]): Temperature values ($^\circ\text{C}$)
* `salinity_array` (FLOAT[]): Salinity values ($\text{PSU}$)
* `chlorophyll_array` (FLOAT[]): Chlorophyll values ($\text{mg/m}^3$)

### Offline & Low-Network Strategies

```
+-----------------------------------------------------------------------+
|                       LOW-NETWORK RESILIENCE                          |
|                                                                       |
|  +---------------------+    +-------------------+    +-------------+  |
|  | Progressive LOD     |    | Browser Cache     |    | Delta Sync  |  |
|  | Sub-sampling        |    | (IndexedDB Layer) |    | Engine      |  |
|  | (128x128 -> 256x256)|    | - Geometry/Tiles  |    | - Metadata  |  |
|  |                     |    | - Profiles        |    |   Only      |  |
|  +---------------------+    +-------------------+    +-------------+  |
+-----------------------------------------------------------------------+
```

1. **Progressive Level-of-Detail (LOD) Volume Sub-sampling:** Under constrained bandwidth, the backend serves low-resolution 3D grid volumes ($64 \times 64 \times 25$). As network throughput allows, high-resolution volume grids ($256 \times 256 \times 50$) stream progressively [INFERENCE].
2. **Local Caching (IndexedDB):** Client-side IndexedDB caches downloaded bathymetry tiles, in-situ platform metadata, and profile array JSONs [INFERENCE].
3. **Bandwidth Reduction via Byte Packing:** Floating-point scalar arrays ($T, S$) are normalized to 8-bit unsigned integers (`uint8`) mapped to min/max scalar ranges, cutting network payload size by 75% [INFERENCE].
4. **Offline UX Mode:** If network connection drops, the UI displays a warning banner, preserves the currently loaded 3D scene, and allows offline inspection of cached profiles and slices [INFERENCE].
