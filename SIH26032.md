## 1. Executive Snapshot

Indian agricultural procurement operates under vast seasonal volume spikes, where millions of farmers transport harvested grains to designated Procurement Centres (PPCs / Mandis) within narrow time windows [KNOWN]. Due to uncoordinated farmer arrivals, manual registration bottlenecks, and opaque queue management, farmers endure multi-day delays at procurement centres, leading to crop degradation, distress sales, high transit costs, and administrative chaos [KNOWN]. This problem dossier presents the comprehensive technical and operational blueprint for **Krishi-Queue (Smart Procurement & Real-Time Token Management System)**, designed specifically for the Ministry of Consumer Affairs, Food & Public Distribution (Department of Consumer Affairs) [PS]. Krishi-Queue combines dynamic capacity-aware slot allocation, real-time queue status tracking, automated multi-channel notifications (SMS/WhatsApp/IVR), and direct integration with Public Financial Management System (PFMS) and AgriStack frameworks to eliminate mandi bottlenecks, guarantee transparent queueing, and deliver end-to-end payment visibility [INFERENCE].

* **Operating Speed Constraints:** Weighbridge entry and quality checks must take under 2–3 minutes per vehicle to prevent physical tailbacks on public access roads [INFERENCE].

## 9. Candidate Solution Approaches

### Approach 1: Static Time-Slot Booking & SMS Gate Pass System
* **Mechanism:** Farmers register on a web/mobile portal, pick an available date, and receive a static SMS token with a date assignment. Mandi gatekeepers manually verify the token code against a daily printed sheet.
* **Required Data:** Farmer ID, land size, crop type, selected date, gate pass ID.
* **Architecture:** Simple Monolithic Web App (Node.js/Django) + MySQL + SMS Gateway.
* **Complexity:** Low.
* **Explainability:** High.
* **Cost:** Very Low.
* **Scalability:** High for basic web traffic, but poor for physical traffic management.
* **Hackathon Feasibility:** High (Can be built in 2 days).
* **Production Feasibility:** Low (Fails during mandi delays because static slots cannot adjust when weighbridges slow down).
* **Risks:** Unmanaged congestion inside the yard when processing lags behind scheduled arrivals [INFERENCE].

### Approach 2: Dynamic Capacity-Aware Queue & Automated Notification Platform (Selected Approach)
* **Mechanism:** Integrates dynamic slot booking with real-time stage-by-stage mandi queue tracking (Gate -> Weighbridge -> Quality Check -> Offloading -> J-Form). The system continuously computes live average processing time per vehicle. If queue length exceeds safety thresholds, it automatically triggers schedule adjustments, notifies upcoming farmers via SMS/WhatsApp/IVR to delay arrival, and provides interactive dynamic slot re-booking.
* **Required Data:** Farmer identity, land/crop quota, GPS/Mandi capacity parameters, real-time stage timestamp events, PFMS payment logs.
* **Architecture:** Microservices/Modular Monolith + React/PWA Frontend + Node.js/Python Backend + Redis Queue Engine + PostgreSQL + Multi-channel Gateway (SMS/WhatsApp/Bhashini Voice) + Sync Service.
* **Complexity:** Moderate-High.
* **Explainability:** High (Rule-based queue management + statistical wait-time estimation).
* **Cost:** Moderate.
* **Scalability:** Excellent (Horizontal scaling of API endpoints and queue processing).
* **Hackathon Feasibility:** High (Feasible within hackathon timeframe using mock integration wrappers).
* **Production Feasibility:** High (Resilient to real-world mandi operational disruptions).
* **Risks:** Requires basic training for mandi gate staff to update state transitions [INFERENCE].

### Approach 3: Fully Decentralized Peer-to-Peer USSD & WhatsApp Queue Bot
* **Mechanism:** Operates entirely through WhatsApp Bot and USSD shortcodes without a web/app UI. Queue priority is managed purely via chat/USSD interactions, with offline local mesh sync between gate keepers using local Bluetooth/Wi-Fi Direct.
* **Required Data:** Minimal text strings, phone numbers, numeric tokens.
* **Architecture:** Serverless Bot API + WhatsApp Business API + Offline Mesh DB sync.
* **Complexity:** High (Complex mesh sync, high WhatsApp message unit costs).
* **Explainability:** Moderate.
* **Cost:** High (WhatsApp messaging API charges at scale).
* **Scalability:** High digital access, low administrative control.
* **Hackathon Feasibility:** Moderate.
* **Production Feasibility:** Low (Lacks comprehensive administrative monitoring, auditability, and official reporting required by DoCA).
* **Risks:** High risk of message loss, lack of physical verification, high API cost [INFERENCE].

## 10. Recommended Approach & Why

The **Recommended Solution is Approach 2: Dynamic Capacity-Aware Queue & Automated Notification Platform (Krishi-Queue)**.

### Why Approach 2 Wins:
1. **Solves the Core Problem:** Unlike static slot systems (Approach 1) that cause massive physical gridlocks when weighbridge operations slow down, Approach 2 dynamically tracks mandi throughput and proactively halts or delays gate pass dispatch to prevent yard congestion [INFERENCE].
2. **Inclusive Multi-Channel Reach:** Combines an offline-first Progressive Web App (PWA) for officers and smart farmers with zero-data SMS/IVR voice channels powered by Bhashini AI for feature phone users [INFERENCE].
3. **End-to-End Transparency:** Tracks the full workflow from AgriStack land-verified slot booking to digital gate pass, moisture test, weighment slip, J-Form issuance, and PFMS Direct Benefit Transfer tracking [INFERENCE].
4. **Realistic Hackathon Scope:** The core event-driven queue state engine, dynamic scheduling algorithm, and multi-channel notification engine can be fully demonstrated in a hackathon setting using modular mock adapters for PFMS and AgriStack [INFERENCE].

### Why Alternatives Were Rejected:
* **Approach 1 Rejected:** Static scheduling cannot adapt to real-world delays (e.g., weighbridge mechanical failure, unexpected rain), resulting in massive tractor traffic jams outside mandis [INFERENCE].
* **Approach 3 Rejected:** Relying solely on chat/USSD lacks the formal administrative governance, state reporting dashboards, and audit-trail enforcement required by the Ministry of Consumer Affairs [INFERENCE].

### Detailed Data-Flow Narrative

1. **Farmer Registration & Slot Booking:**
   - The farmer accesses the system via PWA, CSC Kiosk, or IVR toll-free call [INFERENCE].
   - Enters Mobile Number + Aadhaar / AgriStack ID. System queries the AgriStack Mock API to verify land ownership and maximum permissible crop quota (e.g., 50 Quintals of Wheat) [INFERENCE].
   - System displays available Mandis within a 25 km radius, along with available date/time slots calculated based on daily mandi throughput limits [INFERENCE].
   - Farmer selects a slot. The system generates a **Digital Gate Pass** containing a unique QR Code and 6-digit numeric token ID, dispatched immediately via SMS/WhatsApp [INFERENCE].

2. **Mandi Gate Arrival & Queue Processing:**
   - On the scheduled date, the farmer arrives at the Mandi gate. The Gate Officer scans the QR Code or enters the 6-digit token on the offline-first PWA [INFERENCE].
   - System verifies the slot window. If valid, the vehicle status changes to `GATE_ENTERED`, assigning a sequential Queue Position (e.g., Position #14) [INFERENCE].
   - An automated SMS is sent to the farmer: *"Gate pass verified. Your queue position is #14. Estimated weighbridge call in 25 mins."* [INFERENCE]

3. **Weighbridge & Quality Inspection:**
   - The weighmaster scans the token, records Tare/Gross Weight, and submits moisture percentage [INFERENCE].
   - System updates status to `QUALITY_APPROVED` and assigns an Offloading Bay number [INFERENCE].
   - If quality fails, status updates to `REJECTED_WITH_REASON`, issuing an official digital dispute slip [INFERENCE].

4. **Procurement Receipt (J-Form) & PFMS Payment Trigger:**
   - Upon offloading, the system auto-calculates total net weight, applies official MSP rate, generates a digital **J-Form Sale Receipt**, and signs it digitally [INFERENCE].
   - Procurement details are pushed to the **PFMS Payment Gateway Service** [INFERENCE].
   - System streams real-time status updates (`PAYMENT_INITIATED` -> `PFMS_BANK_VERIFIED` -> `CREDITED`) directly to the farmer's app dashboard and via SMS [INFERENCE].

## 13. AI/ML Justification

### AI Component 1: Mandi Congestion & Processing Time Predictor
* **Purpose:** Dynamically predict expected wait times per vehicle and calculate maximum optimal slot allowances per hour based on historical mandi speed, crop volume, weather, and labor availability [INFERENCE].
* **Model Type:** XGBoost / Random Forest Regression [INFERENCE].
* **Input:** Mandi ID, time of day, active weighbridges count, vehicle type (Tractor vs Small Truck), total crop volume queued, current weather condition [INFERENCE].
* **Output:** Predicted processing time per vehicle (in minutes) and estimated wait time [INFERENCE].
* **Data Required:** Historical mandi log records of gate entry to offload completion times [INFERENCE].
* **Why AI is Preferable:** Static averages fail because offloading speed varies dynamically based on crop moisture, labor crew size, and vehicle type [INFERENCE].
* **Evaluation:** Mean Absolute Error (MAE) in minutes [INFERENCE].
* **Failure Mode:** If prediction fails, system defaults to a deterministic moving-average formula based on the last 5 offloaded vehicles [INFERENCE].
* **Human Oversight:** Mandi manager can manually override daily slot capacity if physical disruptions occur [INFERENCE].

### AI Component 2: Multilingual Voice & Speech Assistant (Bhashini API Integration)
* **Purpose:** Enable low-literacy farmers to register, check queue status, and receive updates in their local dialect via voice IVR [RESEARCHED].
* **Model Type:** Bhashini Neural Speech Recognition (ASR) & Text-to-Speech (TTS) models [RESEARCHED].
* **Input:** Audio stream from phone call / app voice button [INFERENCE].
* **Output:** Synthesized speech response in regional language (Hindi, Punjabi, Odia, etc.) [INFERENCE].
* **Data Required:** Pre-trained Bhashini Indian language speech corpora [RESEARCHED].
* **Why AI is Preferable:** Rule-based keypad IVR (DTMF) is confusing and difficult for non-literate farmers [INFERENCE].
* **Evaluation:** Word Error Rate (WER) and Task Completion Rate [INFERENCE].
* **Failure Mode:** Falls back to human CSC operator or simple DTMF keypad options ("Press 1 for Queue Status") [INFERENCE].
* **Human Oversight:** High-value transactions (e.g., slot cancellation) require explicit OTP confirmation [INFERENCE].

### Where AI Should NOT Be Used:
* **Slot Allocation & Priority Order:** AI MUST NOT be used to decide which farmer gets priority or slot eligibility. Queue ordering and eligibility MUST remain 100% deterministic, rule-based (First-Come, First-Served within booked windows), and transparent to prevent bias, corruption, or legal disputes [INFERENCE].

```sql
    centre_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    centre_name VARCHAR(100) NOT NULL,
    district VARCHAR(50) NOT NULL,
    weighbridge_count INT DEFAULT 2,
    max_hourly_capacity_qtl DECIMAL(8,2) NOT NULL,
    is_active BOOLEAN DEFAULT TRUE
);

-- Slot Bookings & Tokens
CREATE TABLE slot_bookings (
    booking_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    farmer_id UUID REFERENCES farmers(farmer_id),
    centre_id UUID REFERENCES procurement_centres(centre_id),
    token_number VARCHAR(20) UNIQUE NOT NULL,
    booking_date DATE NOT NULL,
    time_slot_start TIME NOT NULL,
    time_slot_end TIME NOT NULL,
    estimated_quantity_qtl DECIMAL(8,2) NOT NULL,
    status VARCHAR(20) DEFAULT 'BOOKED' -- BOOKED, CHECKED_IN, WEIGHED, COMPLETED, CANCELLED
);

-- Real-time Queue Events
CREATE TABLE queue_events (
    event_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    booking_id UUID REFERENCES slot_bookings(booking_id),
    stage VARCHAR(30) NOT NULL, -- GATE_ENTRY, WEIGHBRIDGE_TARE, QUALITY_CHECK, WEIGHBRIDGE_GROSS, JFORM_ISSUED
    recorded_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    recorded_by_user VARCHAR(50) NOT NULL
);

-- Procurement Receipts (J-Forms) & Payment
CREATE TABLE procurement_transactions (
    transaction_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    booking_id UUID REFERENCES slot_bookings(booking_id),
    net_weight_qtl DECIMAL(8,2) NOT NULL,
    moisture_percentage DECIMAL(4,2) NOT NULL,
    msp_rate_per_qtl DECIMAL(8,2) NOT NULL,
    total_amount DECIMAL(10,2) NOT NULL,
    jform_pdf_url VARCHAR(255),
    pfms_ref_number VARCHAR(50),
    payment_status VARCHAR(20) DEFAULT 'PENDING' -- PENDING, INITIATED, SUCCESS, FAILED
);
```

### Offline & Low-Network Synchronization
* **Local Storage:** The PWA uses `IndexedDB` via `Dexie.js` to store local scan logs, gate verification lists, and offline queue events [INFERENCE].
* **Synchronization Flow:** When mandi connection drops, the gate entry application queues state transition records locally. A background Service Worker monitors `navigator.onLine` and automatically syncs batch records to backend `/api/v1/queue/sync` upon reconnection [INFERENCE].
* **Conflict Handling:** Server-authoritative timestamping. If two officers log an entry offline, the server orders events based on cryptographically signed local device sequence counters [INFERENCE].
* **Bandwidth Reduction:** API payloads utilize lightweight JSON compression (gzip/brotli), and images (quality certificates) are compressed on-device before upload [INFERENCE].

## 15. Security, Privacy & Governance

* **Personal Identifiable Information (PII) Protection:** Farmer phone numbers are masked in public dashboards (`98****3210`). Bank details are stored as SHA-256 hashes with salt; unencrypted numbers are transmitted only to PFMS via secure TLS 1.3 channels [INFERENCE].
* **Location Data:** GPS coordinates of mandis and gate check-ins are verified to prevent fraudulent remote check-ins. No continuous tracking of farmers is performed [INFERENCE].
* **Authentication & Role-Based Access Control (RBAC):**
  * Farmers: OTP-based mobile authentication.
  * Mandi Officers: Multi-Factor Authentication (MFA) linked with government employee credentials.
* **Auditability & Non-Repudiation:** Every state transition (Gate entry, quality grade, weighment reading) is cryptographically signed with the officer's session key, creating an unalterable audit log [INFERENCE].
* **Regulatory Compliance:** Compliant with India's **Digital Personal Data Protection Act (DPDP Act) 2023** [KNOWN] and **CERT-In cybersecurity guidelines** [RESEARCHED]. Data resides exclusively on MeitY-empaneled cloud servers within India [KNOWN].
