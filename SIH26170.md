## 1. Executive Snapshot

In space payload engineering, a single failing microelectronic component can cause complete mission failure [KNOWN]. Traditional component screening relies on static datasheet pass/fail limits [PS]. However, marginal components with "latent defects"—which satisfy static specs but exhibit subtle lot-relative anomalies or accelerated parametric drift—frequently escape into flight hardware [PS]. This dossier presents an end-to-end blueprint for **AURA-Space** (*Anomalous Component Drift & Dynamic Outlier Detector*), a machine learning solution engineered for ISRO’s component screening labs [INFERENCE]. AURA-Space combines dynamic statistical outlier detection (Module A) with a predictive time-series drift model (Module B) and an SHAP-driven explainability interface to ensure zero defective components escape into space payloads [INFERENCE].

## 2. Problem Deconstruction

The ISRO problem statement requires migrating component screening from static datasheet limits to dynamic, predictive, and explainable AI-driven screening [PS]. The atomic requirements are extracted below:

### Background Context
- **Requirement B1:** Environmental Stress Screening (ESS) and Burn-In testing subject space-grade electronic components to elevated thermal stress (e.g., 125°C) over extended durations (e.g., up to 168 hours or 240 hours) per standards like MIL-STD-883 Method 1015 [PS, RESEARCHED].
- **Requirement B2:** Static parametric pass/fail limits fail to catch "latent defects"—components that fall within absolute limits but exhibit anomalous baseline offsets or time-dependent degradation [PS]. Escaped latent defects cause catastrophic payload failures [PS].

### Explicit Functional Modules
- **Requirement M-A (Module A - Dynamic Outlier Detection System):**
  - *Source Text:* "Static limits catch obvious failures. Participants need to develop a 'Dynamic' outlier detection system. If a lot has an average leakage current of 10µA, a part showing 45 µA is a massive anomaly, even if the absolute datasheet maximum limit is 50 µA." [PS]
  - *Interpretation:* The model must compute intra-lot dynamic baseline distributions and reject components whose parametric values (e.g., $I_{DDQ}$, leakage current, propagation delay) deviate statistically from their lot cohort, regardless of static upper specification limits (USL) [PS, INFERENCE].
- **Requirement M-B (Module B - Time-Series Drift Predictor):**
  - *Source Text:* "Build a predictive regression model that takes Value_0h and Value_24h as inputs and forecasts Value_168h. If the predicted 168h drift rate exceeds a calculated safety slope, the system flags the component for early rejection." [PS]
  - *Interpretation:* A supervised regression pipeline must ingest early burn-in measurements ($t=0\text{h}, t=24\text{h}$) to predict the component's state at $t=168\text{h}$. It must compute the forecasted trajectory slope $\frac{\Delta V}{\Delta t}$ and flag parts exceeding safety limits for early burn-in ejection, saving up to 144 hours of test chamber time [PS, INFERENCE].

### Core Evaluation Metrics
- **Metric E1 (Asymmetric Anomaly Detection Score):** Missing a defective part (False Negative) is catastrophic for space missions [PS]. The scoring function must penalize False Negatives (FN) exponentially more severely than False Positives (FP) [INFERENCE].
- **Metric E2 (Drift Prediction Accuracy):** Evaluated using Mean Absolute Error ($\text{MAE}$) between forecasted $\hat{V}_{168\text{h}}$ and hidden ground-truth $V_{168\text{h}}$ [PS].
- **Metric E3 (Explainability & QA Interpretability):** The system cannot be a black box [PS]. It must provide human-readable feature attribution, distribution plots, and threshold rationale to Quality Assurance (QA) inspectors before component rejection [PS, INFERENCE].

## 5. Constraints & Environment Realities

1. **Air-Gapped Test Environment:** Space qualification labs at ISRO operate under strict security guidelines with air-gapped Automated Test Equipment (ATE) networks [INFERENCE]. Cloud-dependent real-time APIs are unacceptable for core screening operations [INFERENCE].
2. **Data Availability & Format:** Parametric data from ATE systems is typically structured as Standard Test Data Format (STDF), CSV, or tabular DB exports [RESEARCHED]. Data availability per component is sparse in time ($t = 0\text{h}, 24\text{h}, 96\text{h}, 168\text{h}$) [PS].
3. **Imbalanced Defect Rates:** In high-reliability space-grade batches, natural defect rates are very low (<1% to 3%) [RESEARCHED]. Models must handle severe class imbalance without over-fitting or hallucinating anomalies [INFERENCE].
4. **Physical Burn-In Oven Constraints:** Thermal chambers maintain elevated temperatures (125°C) for days [PS, KNOWN]. Intermittent testing at $t=24\text{h}$ requires momentarily bringing components to room temperature or using automated in-situ sockets [RESEARCHED].
5. **Zero Tolerance for Black-Box Decisions:** Aerospace certification standards (e.g., IEEE/ECSS/MIL-STD) require clear audit trails [RESEARCHED]. A QA inspector must be able to legally and technically justify why an expensive space-grade component was scrapped [INFERENCE].

## 9. Candidate Solution Approaches

### Approach 1: Classical Statistical & Rule-Based DPAT System
- **Mechanism:** Implements parametric AEC-Q001 Dynamic Part Average Testing (DPAT). Calculates Lot Mean $\mu_{\text{lot}}$ and Standard Deviation $\sigma_{\text{lot}}$. Sets dynamic limit $\text{USL}_{\text{dynamic}} = \mu_{\text{lot}} + 3 \cdot \sigma_{\text{lot}}$. For Module B, uses simple linear extrapolation: $\hat{V}_{168\text{h}} = V_{0\text{h}} + \frac{168}{24} \cdot (V_{24\text{h}} - V_{0\text{h}})$.
- **Problem Fit:** Low to Moderate [INFERENCE].
- **Accuracy Potential:** Poor for non-linear drift and non-Gaussian parameter distributions [INFERENCE].
- **Complexity:** Very Low [INFERENCE].
- **Explainability:** Excellent (Pure mathematical rules) [INFERENCE].
- **Hackathon Feasibility:** 100% [INFERENCE].
- **Production Feasibility:** Inadequate for complex space-grade IC degradation mechanisms [INFERENCE].

### Approach 2: Deep Learning LSTM / Autoencoder Architecture
- **Mechanism:** Trains a Sequence-to-Sequence LSTM Autoencoder for Module A (reconstruction error thresholding for anomalies) and an LSTM Regressor for Module B to forecast $168\text{h}$ trajectory from sequence $[V_{0\text{h}}, V_{24\text{h}}]$.
- **Problem Fit:** Moderate [INFERENCE].
- **Accuracy Potential:** High with huge datasets, but overfits severely on small time-series samples (only 2 input time points: $0\text{h}$ and $24\text{h}$) [INFERENCE].
- **Complexity:** Very High [INFERENCE].
- **Explainability:** Very Poor (Deep neural network black box, difficult to explain to QA inspectors) [INFERENCE].
- **Hackathon Feasibility:** Moderate [INFERENCE].
- **Production Feasibility:** Low due to explainability barriers in aerospace certification [INFERENCE].

### Approach 3: Hybrid Statistical-ML Framework (Robust Dynamic Profiling + XGBoost Ensemble + SHAP)
- **Mechanism:**
  - *Module A:* Dual-stage outlier detection. Combines non-parametric Robust Z-Score / IQR bounds with an unsupervised Isolation Forest / Local Outlier Factor (LOF) trained on lot-normalized multi-parametric features [INFERENCE].
  - *Module B:* Feature-engineered XGBoost Regressor trained on baseline values, 24h delta, percentage drift rate, and lot variance features to forecast $\hat{V}_{168\text{h}}$ [INFERENCE]. Uses Cost-Sensitive Loss to penalize under-predicting drift [INFERENCE].
  - *Explainability:* SHAP TreeExplainer generates exact feature attribution waterfall charts and human-readable text justification for every flagged part [INFERENCE].
- **Problem Fit:** Excellent [INFERENCE].
- **Accuracy Potential:** Very High ($\text{MAE} < 0.05$ on normalized scale, low FN rate) [INFERENCE].
- **Complexity:** Moderate [INFERENCE].
- **Explainability:** Excellent (SHAP feature importance + dynamic statistical score breakdown) [INFERENCE].
- **Hackathon Feasibility:** High [INFERENCE].
- **Production Feasibility:** High (Lightweight, air-gapped capable, high precision) [INFERENCE].

## 10. Recommended Approach & Why

**Selected Approach:** **Approach 3: Hybrid Statistical-ML Framework (AURA-Space)** [INFERENCE].

### Why Alternatives Were Rejected:
1. **Approach 1 (Pure Rule-Based Linear DPAT) Rejected:** Linear extrapolation fails to capture physical IC degradation dynamics (e.g., exponential electromigration or logarithmic oxide trap saturation) [RESEARCHED]. It leads to excessive False Negatives on subtle non-linear drifters [INFERENCE].
2. **Approach 2 (Deep Learning / LSTM) Rejected:** LSTMs are over-parameterized for time series with only two initial observations ($t=0\text{h}, t=24\text{h}$) [INFERENCE]. Furthermore, deep learning reconstruction errors act as black boxes, failing the mandatory E3 Explainability requirement [PS, INFERENCE].

### Why Approach 3 Wins:
- **Mathematical Rigor:** Handles both Gaussian and skewed non-Gaussian parameter distributions using Median Absolute Deviation (MAD) and Isolation Forest [RESEARCHED, INFERENCE].
- **Asymmetric Risk Management:** Supports custom objective functions in XGBoost to penalize False Negatives (missing a defective flight part) 20x more heavily than False Positives [INFERENCE].
- **Full Inspector Interpretability:** Provides QA inspectors with an interactive dashboard displaying exact lot distribution curves, feature importance ranking, and compliance scores [PS, INFERENCE].

### Data-Flow Narrative
1. **Ingestion & Parsing:** Raw ATE test logs (containing component IDs, lot numbers, parameters, and time-stamped measurements) are uploaded to the system [INFERENCE].
2. **Dynamic Lot Profiling:** The Feature Engineering engine groups telemetry by Lot ID and computes robust population statistics ($\mu, \text{Median}, \sigma, \text{MAD}$) for each electrical parameter ($I_{DDQ}$, $I_{\text{leak}}$, $T_{pd}$) [INFERENCE].
3. **Module A (Outlier Screening):** Each component's $V_{0\text{h}}$ and $V_{24\text{h}}$ measurements are evaluated against dynamic lot bounds. Components exceeding the modified multi-sigma threshold (e.g., $I_{DDQ} = 45\,\mu\text{A}$ in a $10\,\mu\text{A}$ lot) are instantly flagged as dynamic outliers [PS, INFERENCE].
4. **Module B (Drift Prediction):** Features ($V_{0\text{h}}, V_{24\text{h}}, \Delta V_{24\text{h}}$, lot relative offsets) are passed into the trained XGBoost regressor [INFERENCE]. The model forecasts $\hat{V}_{168\text{h}}$ and computes the predicted trajectory slope $S = \frac{\hat{V}_{168\text{h}} - V_{0\text{h}}}{168}$ [PS, INFERENCE].
5. **Safety Slope Decision:** If $S > S_{\text{safety}}$, the component is flagged for early rejection at $t=24\text{h}$, halting further burn-in testing [PS, INFERENCE].
6. **Explainability & QA Sign-off:** The SHAP engine calculates exact feature contributions [INFERENCE]. The dashboard renders a rejection card showing why the part failed (e.g., *"Flagged via Module B: Predicted 168h $I_{DDQ} = 58\,\mu\text{A}$ exceeds safety limit of $50\,\mu\text{A}$ based on anomalous +350% 24h drift rate"*), allowing the QA inspector to confirm quarantine [PS, INFERENCE].

## 13. AI/ML Justification

### 1. Module A: Dynamic Outlier Detector (Isolation Forest & Robust Z-Score)
- **Purpose:** Detect lot-relative parametric anomalies that pass absolute static limits [PS].
- **Model Type:** Hybrid Unsupervised Isolation Forest + Robust Modified Z-Score ($\text{MAD}$) [INFERENCE].
- **Input:** $V_{0\text{h}}, V_{24\text{h}}$, Lot Mean, Lot Median, Lot MAD for parameters ($I_{DDQ}, I_{\text{leak}}, T_{pd}$) [PS, INFERENCE].
- **Output:** Anomaly Score $[-1, 1]$, Binary Outlier Flag (0 or 1), and Deviation Magnitude [INFERENCE].
- **Data Required:** Parametric test values across at least 20–30 components per lot [RESEARCHED].
- **Why AI/ML is Preferable:** Static rule limits cannot adapt to wafer-to-wafer manufacturing baseline shifts [RESEARCHED]. ML multidimensional outlier detection catches multi-parametric anomalies (e.g., $I_{DDQ}$ and $T_{pd}$ moving abnormally together) [RESEARCHED].
- **Evaluation:** Precision, Recall, and Anomaly Detection Score with asymmetric FN penalty [PS, INFERENCE].
- **Failure Mode:** False Positives (over-flagging benign lot variance).
- **Human Oversight:** Mandatory QA inspector review card with lot distribution overlay before quarantining parts [PS, INFERENCE].

### 2. Module B: Time-Series Drift Predictor (XGBoost Regressor)
- **Purpose:** Forecast $168\text{h}$ parametric values using early $0\text{h}$ and $24\text{h}$ measurements to enable early burn-in rejection [PS].
- **Model Type:** Gradient Boosted Decision Trees (XGBoost Regressor) [INFERENCE].
- **Input:** $V_{0\text{h}}, V_{24\text{h}}$, Delta ($\Delta V_{24\text{h}} = V_{24\text{h}} - V_{0\text{h}}$), Percentage Drift Rate, Lot Relative Rank [PS, INFERENCE].
- **Output:** Predicted Continuous Value $\hat{V}_{168\text{h}}$, Forecasted Safety Slope $S$, Early Rejection Flag [PS, INFERENCE].
- **Data Required:** Historical burn-in time-series records containing ground-truth $168\text{h}$ measurements [PS, INFERENCE].
- **Why AI/ML is Preferable:** Physical degradation during burn-in (such as hot-carrier injection or oxide breakdown) is non-linear [RESEARCHED]. ML captures non-linear drift trajectories far more accurately than linear extrapolation [INFERENCE].
- **Evaluation:** Mean Absolute Error ($\text{MAE}$) between predicted $\hat{V}_{168\text{h}}$ and actual $V_{168\text{h}}$ [PS].
- **Failure Mode:** Under-predicting drift rate (False Negative). Mitigated by training with an asymmetric Huber loss function that penalizes under-estimation [INFERENCE].
- **Human Oversight:** Inspector can override early rejection and allow the component to remain in burn-in for the full 168 hours if criticality requires physical verification [INFERENCE].

### Where AI Should NOT Be Used:
- **Absolute Datasheet Safety Ceiling:** Hard Upper Specification Limits (USL) and Lower Specification Limits (LSL) must remain deterministic IF-ELSE safety overrides [INFERENCE]. If a component exceeds the hard datasheet maximum (e.g., $I_{DDQ} > 50\,\mu\text{A}$), it must be immediately rejected by hardcoded logic without consulting ML models [PS, INFERENCE].

```sql
-- Production Component Lots
CREATE TABLE ComponentLots (
    lot_id VARCHAR(50) PRIMARY KEY,
    part_number VARCHAR(50) NOT NULL,
    manufacturer VARCHAR(50),
    screening_date DATE,

CREATE TABLE ComponentTelemetry (
    component_id VARCHAR(50) PRIMARY KEY,

    val_24h FLOAT NOT NULL,
    val_96h FLOAT,               -- Optional interim measurement
    val_168h_actual FLOAT,       -- Ground truth for evaluation
    FOREIGN KEY (lot_id) REFERENCES ComponentLots(lot_id)
);

-- Screening Results & AI Predictions Table
CREATE TABLE ScreeningResults (
    result_id INTEGER PRIMARY KEY AUTOINCREMENT,
    component_id VARCHAR(50) REFERENCES ComponentTelemetry(component_id),
    module_a_outlier_flag BOOLEAN,
    module_a_zscore FLOAT,
    predicted_val_168h FLOAT,
```
