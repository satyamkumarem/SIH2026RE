# SIH Problem Analysis & Solution Architecture Dossier

---

## 1. Executive Snapshot

### Summary
The elderly population in the North Eastern Region (NER) of India faces increasing rates of cognitive disorders such as dementia and Alzheimer's disease, compounded by severe geographical isolation, limited neurological care infrastructure, and significant linguistic diversity [PS, KNOWN]. Existing cognitive health platforms fail in this context because they require continuous high-speed cloud connectivity, rely on Western/urban motifs, and lack voice support for NER regional languages [INFERENCE]. This dossier outlines a local-first, AI-powered cognitive gaming and memory assistance platform named **"AASHA-NER" (Adaptive Auxiliary & System for Health Assistance in NER)** [ASSUMPTION]. Designed specifically for 4-6 student hackathon implementation, the platform combines on-device adaptive game difficulty using Item Response Theory (IRT) and Glicko-2 algorithms [RESEARCHED], voice-assisted interaction powered by the sovereign Digital India Bhashini AI stack [RESEARCHED], culturally familiar NER themes (e.g., Bihu motifs, Loktak lake flora, traditional weaving patterns) [RESEARCHED], local-first SQLite delta synchronization [RESEARCHED], and an integrated caregiver alert dashboard linked with primary healthcare workflows at Ayushman Arogya Mandirs and Tele-MANAS [RESEARCHED].

## 2. Problem Deconstruction

### Explicit Requirements & Source Text Extraction

The problem statement provided by MDoNER contains 8 explicit lettered requirements (a–h) and 7 core expected solution components [PS]:

#### Requirement `a` [PS]
* **Source Text:** *"Include interactive cognitive games and activities focused on: Memory improvement, Attention and concentration, Daily routine recall, Pattern and object recognition, Emotional and mental engagement."*
* **Interpretation:** The platform must provide at least five distinct mini-game/activity modules targeting these specific cognitive domains, designed specifically for elderly individuals experiencing mild-to-moderate cognitive decline [INFERENCE].
* **Implementation Implication:** Game mechanics must avoid complex multi-finger gestures or fast-twitch time limits. Instead, they should use simple tap, drag, and voice inputs mapped to standardized neuropsychological screening frameworks like HMSE (Hindi Mental State Examination) and MUDRA (Multilingual Dementia Research and Assessment) [RESEARCHED].

#### Requirement `b` [PS]
* **Source Text:** *"Use AI/ML algorithms to adapt difficulty levels based on patient performance and cognitive condition."*
* **Interpretation:** Static level progression is unacceptable. The platform must dynamically adjust task complexity (number of items, visual noise, prompt speed, recall delay) in real time based on player error rate, response latency, and historical performance trends [INFERENCE].
* **Implementation Implication:** An adaptive algorithm (such as 2-Parameter Logistic Item Response Theory or dynamic Glicko-2 rating) must run locally on the client device to recalculate difficulty parameters after every session without requiring cloud latency [RESEARCHED].

#### Requirement `c` [PS]
* **Source Text:** *"Support multilingual and voice-assisted interaction suitable for elderly users in NER."*
* **Interpretation:** Text-heavy interfaces fail with elderly dementia patients who may have reduced visual acuity or low literacy. Speech-to-Text (STT) and Text-to-Speech (TTS) must drive navigation and gameplay in major NER languages [INFERENCE].
* **Implementation Implication:** Integration with Bhashini APIs (or offline pipeline fallbacks) for Assamese, Bengali, Manipuri (Meitei), Bodo, and Indian English voice models [RESEARCHED].

#### Requirement `d` [PS]
* **Source Text:** *"Include culturally familiar themes, visuals, sounds, and regional language support for better engagement."*
* **Interpretation:** Generic Western/urban game assets (e.g., skyscrapers, Western musical instruments) induce anxiety or confusion. Graphics, audio, and narratives must incorporate North Eastern cultural elements [INFERENCE].
* **Implementation Implication:** Visual assets must feature regional themes such as Assam tea gardens, Majuli riverine motifs, Manipuri Pung Cholom rhythms, Meghalaya Living Root bridges, and traditional bamboo crafts [RESEARCHED]. Audio feedback should utilize authentic regional instruments (e.g., Pepa, Bahi/flute, Ektara) [RESEARCHED].

#### Requirement `e` [PS]
* **Source Text:** *"Provide reminders for: Medicines, Hydration, Daily activities, Medical appointments."*
* **Interpretation:** The app acts as a memory prosthetic for daily living activities (ADL). Reminders must be persistent, multi-modal (visual pop-ups, voice announcements in native language, physical vibration), and operable without internet access [INFERENCE].
* **Implementation Implication:** Local alarm scheduling using native Android system alarms (`AlarmManager` / Exact Alarms) with audio chime and localized speech synthesis [INFERENCE].

#### Requirement `f` [PS]
* **Source Text:** *"Enable caregivers and healthcare workers to monitor patient progress through dashboards and activity levels."*
* **Interpretation:** A dual-interface system is required: a simplified UI for elderly patients and an analytical dashboard for family caregivers, Community Health Officers (CHOs), and ASHA workers at Ayushman Arogya Mandirs [RESEARCHED].
* **Implementation Implication:** A secure caregiver web/mobile portal displaying key metrics: session frequency, domain-specific accuracy trends, task response times, adherence to medicine/hydration schedules, and behavioral anomaly flags [INFERENCE].

#### Requirement `g` [PS]
* **Source Text:** *"Work in low-connectivity environments with offline functionality support."*
* **Interpretation:** All core gameplay, adaptive logic, reminder scheduling, and local progress tracking must function 100% offline. Cloud communication should occur asynchronously via background delta synchronization when internet becomes available [INFERENCE].
* **Implementation Implication:** Local-first database architecture (SQLite via WatermelonDB or RxDB) with a client-side sync queue, optimistic local updates, and conflict-free delta sync protocols [RESEARCHED].

#### Requirement `h` [PS]
* **Source Text:** *"Be accessible through mobile/tablet devices with a simple and elderly-friendly interface."*
* **Interpretation:** Touch targets must be extra-large (minimum 48x48 dp, ideally 64x64 dp), visual contrast must meet WCAG AAA standards, typography must be high-legibility, and navigation depth must not exceed 2 levels [INFERENCE].
* **Implementation Implication:** Native Android/React Native/Flutter application optimized for low-cost Android tablets and smartphones (Android 8.0+, 2GB-4GB RAM) common in rural health settings [ASSUMPTION].

## 5. Constraints & Environment Realities

### Field Realities in North Eastern Region (NER)

1. **Geographical & Terrain Challenges [KNOWN]:**
   * NER comprises 8 states characterized by hilly terrain, dense forests, and riverine islands (e.g., Majuli). Travel to district hospitals takes 4–12 hours.
   * *System Constraint:* The solution must not depend on physical clinical visits for regular operation.

2. **Connectivity & Power Infrastructure [KNOWN]:**
   * Mobile network coverage in hill districts (e.g., Mon in Nagaland, Dima Hasao in Assam, East Khasi Hills in Meghalaya) fluctuates rapidly between 2G, 3G, and zero signal. Extended power outages (12–48 hours) are common during monsoon season.
   * *System Constraint:* The application must be 100% functional offline for up to 30 days. Data payloads during synchronization must be compressed to under 50 KB per sync cycle to transmit over weak 2G signals [INFERENCE].

3. **Linguistic Diversity & Literacy Levels [RESEARCHED]:**
   * Over 220 languages/dialects are spoken across NER. Primary official regional languages include Assamese, Bengali, Manipuri (Meitei), Bodo, Mizo, Khasi, Garo, and Kokborok [KNOWN]. Literacy among rural elderly (ages 60+) is low, with high rates of illiteracy or inability to read fine smartphone text [KNOWN].
   * *System Constraint:* Text-only UIs will fail. The platform must be voice-first, icon-driven, and support major official regional languages (Assamese, Bengali, Manipuri, Bodo) with clear audio prompts [INFERENCE].

4. **Device Availability & Hardware Limits [ASSUMPTION]:**
   * Rural households rely on budget Android smartphones or government-distributed tablets (e.g., under Ayushman Bharat / ASHA hardware schemes) with 2GB–4GB RAM, entry-level MediaTek/Snapdragon processors, and limited storage (32GB).
   * *System Constraint:* App binary size must stay under 40 MB. RAM usage must not exceed 150 MB. On-device AI processing must execute within < 50ms without overheating the device [INFERENCE].

5. **Physical & Cognitive Constraints of Dementia Patients [KNOWN]:**
   * Dementia patients suffer from spatial disorientation, short-term memory failure, fine-motor tremors, visual contrast decline, and age-related presbycusis (hearing loss).
   * *System Constraint:* No multi-touch gestures (pinching, swiping with 3 fingers). Taps must have a minimum target diameter of 15mm. Audio frequency response must be tuned for clear voice reproduction [INFERENCE].

## 8. Existing Solutions & Gap Analysis

### Evaluated Systems

#### 1. Global Cognitive Training Apps (CogniFit, Lumosity, Peak, BrainHQ) [RESEARCHED]
* **Description:** Commercial mobile/web apps providing brain training games designed for general cognitive fitness or mild cognitive decline [RESEARCHED].
* **Strengths:** Polished UX, large variety of games, scientifically structured difficulty scaling.
* **Weaknesses:** Require continuous cloud internet; subscription costs ($10–$15/month); English/Western centered; zero cultural familiarity for NER rural elderly; no voice interaction in regional Indian languages; no integrated medication/hydration reminder engine; no connection to local public healthcare systems [INFERENCE].
* **Relevance:** Benchmarks for game mechanics and cognitive domain targeting [INFERENCE].
* **Remaining Gap:** Completely unsuited for rural, low-literacy NER elderly [INFERENCE].
* **Confidence Tag:** [RESEARCHED]

#### 2. ICMR MUDRA Toolbox (Multilingual Dementia Research & Assessment) [RESEARCHED]
* **Description:** Neuropsychological assessment toolbox developed by ICMR consortium in 5 major Indian languages (Hindi, Bengali, Telugu, Kannada, Malayalam) for clinical diagnosis of dementia [RESEARCHED].
* **Strengths:** Culturally validated for Indian populations; accounts for literacy levels; accepted as clinical standard [RESEARCHED].
* **Weaknesses:** Diagnostic screening tool for trained clinicians, not a daily engaging therapeutic gaming system; does not offer offline mobile adaptive games or daily assistance reminders [INFERENCE].
* **Relevance:** Provides the psychometric foundation for gamified task design [INFERENCE].
* **Remaining Gap:** Needs translation into interactive, daily self-administered adaptive games with voice support in NER languages [INFERENCE].
* **Confidence Tag:** [RESEARCHED]

#### 3. Tele-MANAS & Ayushman Arogya Mandir (AAM) Workflows [RESEARCHED]
* **Description:** Government of India’s 24/7 tele-mental health service (14416) integrated with primary care Community Health Officers (CHOs) at AAMs [RESEARCHED].
* **Strengths:** Nationwide government infrastructure; supports 20+ regional languages; free 24/7 helpline; CHO/ASHA worker outreach [RESEARCHED].
* **Weaknesses:** Currently tele-counseling and primary clinical screening focused; lacks an interactive continuous daily digital cognitive therapy and memory assistance companion app for patients at home [INFERENCE].
* **Relevance:** The primary distribution, clinical referral, and monitoring backbone for production deployment [INFERENCE].
* **Remaining Gap:** Digital patient-side daily engagement tool that feeds longitudinal data into Tele-MANAS / AAM clinician workflows [INFERENCE].

### Approach 1: Pure Cloud-Native Web Platform with Generative AI / LLM Integration
* **Mechanism:** Next.js web application utilizing cloud LLM APIs (e.g., OpenAI / Claude) for dynamic dialogue, real-time cloud analytics, and server-side image generation for game levels.
* **Problem Fit:** Low. Fails in rural NER due to zero/intermittent connectivity [INFERENCE].
* **Complexity:** Medium (High backend complexity, low mobile client complexity).
* **Cost:** High (Continuous per-API call costs for LLMs and cloud hosting).
* **Offline Feasibility:** Zero (Application crashes without internet).
* **Verdict:** **REJECTED** — Violates Requirement `g` (offline support) and introduces unpredictable operating costs [INFERENCE].

### Approach 2: Monolithic Native App with Static Rule-Based Difficulty & Local Storage
* **Mechanism:** Standalone Flutter/React Native Android app with pre-programmed level transitions (e.g., Level 1 -> Level 2 on 80% score), local SQLite storage, hardcoded text prompts in English/Hindi, and zero backend synchronization.
* **Problem Fit:** Partial. Works offline, but fails on adaptive AI requirement, multilingual voice integration, and centralized caregiver/health worker monitoring [INFERENCE].
* **Complexity:** Low.
* **Cost:** Very Low.
* **Scalability:** Extremely limited (Isolated silos of data, no caregiver dashboard).
* **Verdict:** **REJECTED** — Fails Requirements `b` (AI/ML adaptive difficulty), `c` (voice multilingual), and `f` (caregiver dashboard) [INFERENCE].

### Approach 3 (RECOMMENDED): Hybrid Local-First Mobile App with On-Device IRT Adaptive Engine, Bhashini Voice Layer, and Asynchronous Delta Sync
* **Mechanism:**
  1. Client: React Native / Expo application running an embedded C++/JS **2-Parameter Item Response Theory (IRT) + Glicko-2 Adaptive Engine** locally on device [RESEARCHED].
  2. Database: Local-first SQLite engine (via **WatermelonDB**) enabling sub-10ms local reads/writes and 100% offline functionality [RESEARCHED].
  3. Voice & Localization: Native Bhashini API integration for online STT/TTS with bundled local compressed audio fallbacks for offline operation [RESEARCHED].
  4. Backend: Node.js / NestJS server with PostgreSQL + Prisma for asynchronous delta synchronization when connectivity is detected [RESEARCHED].
  5. Caregiver Portal: Lightweight Next.js web dashboard for family members and ASHA/CHO health workers [INFERENCE].
* **Problem Fit:** Excellent. Meets all requirements (a–h) while adhering to rural NER field constraints [INFERENCE].
* **Complexity:** Medium-High (Requires clean offline sync queue and state machine logic).
* **Cost:** Low (Open-source stack, Bhashini government sovereign AI, server needed only for lightweight sync).
* **Hackathon Feasibility:** High (MVP can build 3 core mini-games, local IRT engine, local SQLite database, Bhashini voice integration, and caregiver web dashboard within available build window) [INFERENCE].
* **Verdict:** **SELECTED** [INFERENCE].

## 10. Recommended Approach & Why

### Why Approach 3 Wins
Approach 3 uniquely reconciles the conflicting demands of **sophisticated AI adaptation** and **100% offline rural usability** [INFERENCE]. 

1. **Decoupled Intelligence:** By bringing the adaptive AI algorithm (IRT/Glicko-2) into the client-side JavaScript bundle, difficulty tuning happens instantaneously after every game session without network requests [RESEARCHED].
2. **Local-First Reliability:** The user experience is zero-latency because reads and writes happen against the embedded SQLite database [RESEARCHED]. Data loss is impossible even if the phone battery dies or the network drops mid-session [INFERENCE].
3. **Culturally & Linguistically Native:** Integrating Bhashini directly into the UI architecture ensures that elderly users who cannot read can navigate via simple voice prompts in Assamese, Bengali, Manipuri, or Bodo [RESEARCHED].
4. **Clinical Ecosystem Integration:** Asynchronous sync allows health workers at Ayushman Arogya Mandirs to download patient progress data during periodic home visits or when the patient enters a town with 4G coverage [RESEARCHED, INFERENCE].

### Detailed Data-Flow Narrative

1. **User Interaction & Offline Session Start:**
   * The elderly patient launches AASHA-NER on their Android device.
   * The app reads local patient profile and baseline theta score ($\theta$) from the on-device **WatermelonDB (SQLite)** in < 10ms [RESEARCHED].
   * The local UI announces the daily activity in the user's selected native language (e.g., Assamese) using cached audio files or local TTS synthesis [RESEARCHED].

2. **Gameplay & Adaptive Difficulty Adjustment:**
   * The patient plays a cognitive game (e.g., Memory Match with Bihu items).
   * Touch events, response times (ms), hints requested, and errors are captured locally by the **Game Session Logger** [INFERENCE].
   * Upon game completion, the **On-Device IRT Engine** executes locally:
     $$\theta_{new} = \theta_{old} + K \cdot (Score_{observed} - Score_{expected}(\theta_{old}, b_i))$$
     Where $b_i$ is the difficulty rating of item $i$. The updated ability parameter ($\theta_{new}$) immediately tunes the difficulty parameters for the next game session [RESEARCHED].

3. **Local Persistence & Reminder Scheduling:**
   * The session result, score, latency distribution, and updated ability score are stored in local SQLite tables (`GameSessions`, `CognitiveScores`) and appended to the `SyncQueue` table [RESEARCHED].
   * Meanwhile, the **Local Reminder Engine** uses Android `AlarmManager` to fire scheduled exact alarms for medication or hydration, displaying full-screen high-contrast modal prompts with local audio announcements even if the main app is closed [INFERENCE].

4. **Background Asynchronous Delta Synchronization:**
   * The **Connectivity Listener** continuously monitors network status using `NetInfo` [RESEARCHED].
   * When network connectivity (2G/3G/4G/Wi-Fi) is detected, a background sync worker pulls pending records from `SyncQueue` [RESEARCHED].
   * It sends a compressed JSON payload (Delta Sync) containing `last_pulled_at` timestamp and created/updated records to the Cloud Sync Gateway over TLS 1.3 [RESEARCHED].
   * The Cloud Sync Gateway validates the JWT token, applies field-level conflict resolution (Server-wins for caregiver overrides, Client-wins for game performance records), writes to PostgreSQL, and returns new server state (e.g., updated medication schedules set by the caregiver) [RESEARCHED, INFERENCE].
   * Upon receipt of HTTP 200 OK, the local `SyncQueue` records are marked as synced [RESEARCHED].

5. **Caregiver & Health Worker Dashboard View:**
   * Family caregivers or ASHA workers log into the Next.js web portal.
   * The portal fetches synchronized analytics from PostgreSQL and renders domain-specific cognitive trajectory charts (Memory, Attention, Executive Function), adherence rates, and alert flags [INFERENCE].
   * If a patient misses 3 consecutive medication reminders or exhibits a >20% decline in attention scores over 7 days, an automated SMS/WhatsApp notification is triggered to the caregiver [INFERENCE].

## 13. AI/ML Justification

### Module 1: On-Device Adaptive Difficulty Engine (Psychometric IRT + Glicko-2)

1. **What exact problem does AI solve?** Prevents cognitive fatigue/frustration (if game is too hard) or boredom/disengagement (if game is too easy) by dynamically adjusting game parameters to match the patient's real-time cognitive capacity [PS, INFERENCE].
2. **What is the input?** Game session telemetry: item ID, correct/incorrect status, completion time ($T_{obs}$ in ms), hints requested, current patient ability parameter ($\theta$).
3. **What is the output?** Updated patient ability score ($\theta_{new}$) and item parameter selection (grid dimension $N \times M$, target delay time $\tau$, visual distractor count $D$) for the next session.
4. **Why can a simpler rule/system not solve it?** Fixed rules (e.g., "if score > 80% go to Level 2") fail in dementia care because cognitive decline is non-linear and day-dependent (e.g., "sundowning" effects where cognitive function drops in late afternoon). IRT models the probability of a correct response as a continuous function of latent cognitive ability and item difficulty [RESEARCHED].
5. **What data is required?** Pre-calibrated item difficulty parameters ($b_i$) and discrimination parameters ($a_i$) for each game task, derived from neuropsychological standards (HMSE/MUDRA) [RESEARCHED].
6. **How will it be evaluated?** Target response success rate maintained within 65%–75% (the optimal flow state for cognitive rehabilitation without anxiety) [RESEARCHED].
7. **What happens when it is wrong?** If difficulty spikes, the patient fails a task; the algorithm detects consecutive errors ($N \ge 2$) and drops difficulty by $2\sigma$ immediately [INFERENCE].
8. **Does it require training?** No continuous deep learning training required. Uses standard psychometric parameter estimation formulas (Maximum Likelihood / Bayesian EAP) running locally [RESEARCHED].
9. **Fine-tuning?** No.
10. **RAG?** No.
11. **Computer Vision?** No.
12. **Speech Processing?** No.
13. **Forecasting?** Yes, forecasts expected probability of success $P(Y=1|\theta, b_i)$.
14. **Human Oversight?** Caregivers can view the estimated $\theta$ trajectory and manually cap maximum game difficulty if recommended by a physician [INFERENCE].

### Module 2: Multilingual Voice Interaction Engine (Bhashini API Integration)

1. **What exact problem does AI solve?** Enables illiterate or motor-impaired elderly users to navigate the app, receive spoken instructions, and respond to memory prompts using natural voice in regional languages [PS, RESEARCHED].
2. **What is the input?** Spoken audio input from patient mic (for STT); text strings for game prompts/reminders (for TTS).
3. **What is the output?** Recognized text intent / command (STT output); synthesized natural audio stream in native language (TTS output).
4. **Why can a simpler system not solve it?** Rule-based audio playback only works for pre-recorded fixed clips. Dynamic game prompts, localized reminder announcements, and voice-command recognition require acoustic deep learning models trained on Indian regional accents [RESEARCHED].
5. **What data is required?** Speech corpora for Assamese, Bengali, Manipuri, Bodo provided by Bhashini / AI4Bharat open datasets [RESEARCHED].
6. **How will it be evaluated?** Word Error Rate (WER) < 15% for primary regional languages under clear mic conditions [RESEARCHED].
7. **What happens when it is wrong?** The app displays large icon choices on screen alongside voice prompts and allows simple single-tap manual overrides [INFERENCE].
8. **Training?** Pre-trained models hosted on Bhashini infrastructure [RESEARCHED].
9. **Fine-tuning?** Not during hackathon.
10. **RAG?** No.
11. **Computer Vision?** No.
12. **Speech Processing?** Yes (STT / TTS).
13. **Forecasting?** No.
14. **Human Oversight?** Caregivers can select and verify the preferred dialect/accent in settings [INFERENCE].

### Module 3: Cognitive Trend Anomaly & Adherence Alert Engine

1. **What exact problem does AI solve?** Detects subtle, precipitous drops in cognitive performance or sudden non-adherence patterns that signal medical deterioration, infection (e.g., UTI-induced delirium common in dementia), or medication non-compliance [INFERENCE].
2. **What is the input?** 14-day rolling window of daily game scores, task latency distributions, and medication acknowledgment logs.
3. **What is the output?** Risk Anomaly Score (0–100) and automated alert flag ("Sudden Attention Score Drop", "3 Missed Hydration Reminders") sent to caregiver [INFERENCE].
4. **Why can a simpler system not solve it?** Simple thresholds trigger excessive false alarms due to daily variance. Anomaly detection uses rolling Z-score baselines combined with trend slope evaluation [INFERENCE].
5. **What data is required?** Historical patient interaction logs.
6. **How will it be evaluated?** False Positive Rate < 10% on simulated test trajectories [INFERENCE].
7. **What happens when it is wrong?** Triggers a soft notification to the caregiver ("Check in on grandma today") rather than a panic emergency call [INFERENCE].
8. **Training?** Unsupervised baseline statistical modeling (Z-score anomaly / Exponential Weighted Moving Average).
9. **Human Oversight?** Mandatory. Caregiver or CHO must review flag before taking clinical action [INFERENCE].

### Where AI Should NOT Be Used
* **Critical Reminder Scheduling:** Pill schedules, hydration alarms, and doctor appointments MUST use deterministic local system cron schedules (`AlarmManager`), NOT generative AI or predictive models [INFERENCE].
* **Core Game Rules & Scoring:** Correctness of memory matching or pattern recognition MUST be verified by deterministic exact logic, NOT probabilistic ML models [INFERENCE].

## 14. Data Architecture & Offline/Low-Network Design

### Database Schema (Local SQLite / WatermelonDB)

```sql
-- Patients Table
CREATE TABLE patients (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    age INTEGER NOT NULL,
    primary_language TEXT NOT NULL, -- 'as', 'bn', 'mn', 'br', 'en'
    dementia_stage TEXT NOT NULL,  -- 'EARLY', 'MODERATE', 'SEVERE'
    baseline_theta REAL DEFAULT 0.0,
    created_at INTEGER NOT NULL
);

-- GameSessions Table (Local Telemetry)
CREATE TABLE game_sessions (
    id TEXT PRIMARY KEY,
    patient_id TEXT NOT NULL,
    game_type TEXT NOT NULL,        -- 'MEMORY_MATCH', 'ATTENTION_TEA', 'ROUTINE_RECALL', 'PATTERN_WEAVE'
    start_time INTEGER NOT NULL,
    end_time INTEGER NOT NULL,
    score INTEGER NOT NULL,
    max_score INTEGER NOT NULL,
    avg_latency_ms INTEGER NOT NULL,
    hints_used INTEGER DEFAULT 0,
    theta_before REAL NOT NULL,
    theta_after REAL NOT NULL,
    synced_status INTEGER DEFAULT 0, -- 0 = Pending, 1 = Synced
    FOREIGN KEY(patient_id) REFERENCES patients(id)
);

-- CognitiveScores Table (Domain Trends)
CREATE TABLE cognitive_scores (
    id TEXT PRIMARY KEY,
    patient_id TEXT NOT NULL,
    domain TEXT NOT NULL,            -- 'MEMORY', 'ATTENTION', 'EXECUTIVE', 'RECALL'
    current_theta REAL NOT NULL,
    calculated_at INTEGER NOT NULL,
    synced_status INTEGER DEFAULT 0
);

-- Reminders Table
CREATE TABLE reminders (
    id TEXT PRIMARY KEY,
    patient_id TEXT NOT NULL,
    title TEXT NOT NULL,
    category TEXT NOT NULL,          -- 'MEDICINE', 'HYDRATION', 'ACTIVITY', 'APPOINTMENT'
    scheduled_time TEXT NOT NULL,    -- '08:00', '13:00', '20:00'
    audio_prompt_path TEXT,
    is_active INTEGER DEFAULT 1,
    synced_status INTEGER DEFAULT 0
);

-- ReminderLogs Table (Adherence Tracking)
CREATE TABLE reminder_logs (
    id TEXT PRIMARY KEY,
    reminder_id TEXT NOT NULL,
    triggered_at INTEGER NOT NULL,
    acknowledged_at INTEGER,         -- NULL if missed
    status TEXT NOT NULL,            -- 'TAKEN', 'MISSED', 'SNOOZED'
    synced_status INTEGER DEFAULT 0
);

-- SyncQueue Table (Delta Tracking)
CREATE TABLE sync_queue (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    table_name TEXT NOT NULL,
    record_id TEXT NOT NULL,
    action TEXT NOT NULL,            -- 'CREATE', 'UPDATE', 'DELETE'
    payload_json TEXT NOT NULL,
    created_at INTEGER NOT NULL
);
```

### Delta Synchronization Protocol

```
CLIENT (WatermelonDB Engine)                        CLOUD BACKEND (NestJS Sync Gateway)
  |                                                      |
  |--- 1. NetInfo detects online connectivity ----------->|
  |                                                      |
  |--- 2. Fetch unsynced records from `sync_queue` ------>|
  |                                                      |
  |--- 3. POST /api/v1/sync/push ----------------------->| (Payload: JSON Delta + last_pulled_at)
  |       Headers: Authorization, Device-HMAC            |
  |                                                      |--- 4. Validate JWT & HMAC
  |                                                      |--- 5. Apply Field Merge & Resolution
  |                                                      |--- 6. Write to PostgreSQL
  |<-- 7. HTTP 200 OK (Server Changes Delta) ------------|
  |                                                      |
  |--- 8. Apply Server Changes to Local SQLite --------->|
  |--- 9. Mark `sync_queue` items as synced (status=1) ->|
  |                                                      |
```

### Conflict Resolution Strategy
1. **Client-Wins for Game Telemetry:** The client local device is the absolute authority for game performance, reaction latency, and local theta scores. Server never overwrites client game logs [INFERENCE].
2. **Server/Caregiver-Wins for Schedules:** Caregivers modifying medication or doctor appointment schedules on the web portal take precedence over local schedule states [INFERENCE].
3. **Deterministic Timestamp Ordering (Last-Write-Wins):** For patient profile edits, the record with the higher ISO-8601 UTC timestamp prevails [RESEARCHED].
