## 1. Executive Snapshot

This research and implementation dossier presents an end-to-end software framework designed for the Defence Research and Development Organisation (DRDO) under the iDEX / Smart Vehicles challenge (Problem ID: SIH26053). Autonomous ground vehicles (UGVs) and defense mobile platforms operating in dynamic, unstructured tactical terrain require hyper-accurate spatial perception without incurring massive compute and latency overheads [PS, INFERENCE]. Standard 3D LiDAR point cloud processing (handling $10^5$–$10^6$ points per frame at 10–20 Hz) imposes extreme memory bandwidth bottlenecks, while traditional 2D occupancy grids strip crucial height profile information needed for detecting curbs, overhanging obstacles, and negative terrain [PS, KNOWN]. To resolve this trade-off, we specify an **Adaptive Variable-Resolution 2.5D LiDAR Mapping Pipeline** inspired by biological foveated vision [PS]. The architecture pairs a high-speed Sparse 3D Convolutional Neural Network (Sparse CNN / SpConv) for 3D semantic segmentation with a non-uniform 2.5D concentric ring grid engine ($5\text{ cm}$ cell resolution within a $10\text{ m}$ safety radius, relaxing smoothly to $50\text{ cm}$ cell resolution at $100\text{ m}$) [PS, ASSUMPTION]. This system preserves sub-centimeter obstacle detail in the immediate vehicle envelope while reducing memory footprint by over 70% and sustaining execution at $>20\text{ FPS}$ on edge-compute hardware [INFERENCE].

## 5. Constraints & Environment Realities

Defense UGVs operate in extreme operational environments [KNOWN]. Architectural design choices must reflect real field constraints rather than assuming idealized laboratory or cloud conditions [INFERENCE].

```
+-----------------------------------------------------------------------------------+
|                              FIELD ENVIRONMENT REALITIES                          |
+-----------------------+-----------------------+-----------------------------------+
| COMPUTATIONAL BOUND   | CONNECTIVITY AIR-GAP  | RUGGED MOBILITY                   |
| Embedded GPU (Orin)   | Zero Cloud / Internet | Sensor jitter & pitch/roll shocks |
| SWaP Bounded Thermal  | Pure Local Processing | High dust, rain, fog attenuation  |
+-----------------------+-----------------------+-----------------------------------+
```

1. **Hardware & Compute Constraints (SWaP)**: Tactical ground vehicles run on power-constrained edge platforms such as the NVIDIA Jetson AGX Orin (64GB) or Orin Nano (8GB/16GB) [KNOWN]. Cloud API offloading is impossible due to air-gapped security protocols and electronic warfare (EW) jamming risks [INFERENCE]. *All neural inference and grid mapping must execute 100% locally on onboard GPU hardware* [INFERENCE].
2. **Network & Connectivity Realities**: Tactical environments lack cellular or broadband connectivity [KNOWN]. Inter-node communication between perception modules and motion planners must occur via high-speed intra-process zero-copy IPC (Shared Memory ROS 2 / CycloneDDS) [INFERENCE].
3. **LiDAR Sensor Characteristics & Dust/Rain Noise**: Off-road terrain causes vehicle pitch/roll motion and sensor vibration [KNOWN]. Outdoor environments introduce backscatter noise from dust particles, rain, and ground spray [KNOWN]. The grid engine must integrate point cloud motion undistortion using IMU high-rate ego-motion data [INFERENCE].
4. **Distance Decay & Beam Divergence**: Mechanical and solid-state LiDAR sensors (e.g., Velodyne HDL-64E, Ouster OS1-128) suffer from beam sparsity at long range ($100\text{ m}$) [KNOWN]. Angular resolution creates sparse point distributions ($<2\text{ points/m}^2$ at $100\text{ m}$ vs $>500\text{ points/m}^2$ at $5\text{ m}$) [KNOWN]. *This physical phenomenon directly aligns with our variable-resolution strategy: spending $5\text{ cm}$ resolution at $100\text{ m}$ is physically wasteful due to point beam sparsity* [INFERENCE].

## 6. Research Questions

To ensure rigorous system engineering, the student team must investigate the following six core technical questions:

1. **Alignment Error Mitigation**: How do we continuously translate a multi-resolution concentric grid centered on a moving vehicle without introducing spatial aliasing or cell alignment jitter at ring boundaries ($10\text{ m}$ and $30\text{ m}$ transitions)? [INFERENCE]
2. **Model Optimization & Quantization**: Can a 3D Sparse Convolutional Network (SpConv / TorchSparse) achieve $>25\text{ FPS}$ on an NVIDIA Jetson AGX Orin using FP16 / INT8 TensorRT quantization without dropping mIoU below 65% on small dynamic obstacles (e.g., pedestrians at $25\text{ m}$)? [RESEARCHED, INFERENCE]
3. **Data Loss During 3D to 2.5D Projection**: When multiple 3D points with distinct elevation values land within a single $2.5\text{D}$ cell, what elevation metrics ($Z_{\max}, Z_{\min}, \Delta Z, \text{variance}$) must be preserved to guarantee that overhanging obstacles (bridges/branches) or negative obstacles (potholes/ditches) are not erased? [PS, INFERENCE]
4. **Dynamic vs Static Temporal Consistency**: How can the pipeline handle temporarily stopped dynamic objects (e.g., a car waiting at an intersection) to prevent them from being permanently baked into the static terrain layer? [INFERENCE]
5. **Memory Footprint Scaling**: What is the exact mathematical ratio of cell count and memory consumption between a uniform $5\text{ cm}$ grid over a $200\text{ m} \times 200\text{ m}$ bounding box ($1.6\times 10^7$ cells) versus a 3-tier concentric variable-resolution grid ($~4.8\times 10^5$ cells)? [INFERENCE]
6. **Robustness Under Sensor Drift**: How does high-frequency IMU integration prevent local map blurring when the vehicle undergoes aggressive braking or angular rotation? [INFERENCE]

## 10. Recommended Approach & Why

### Selection: Approach 2 — Sparse 3D CNN (SpConv / TorchSparse) + Concentric Multi-Ring Buffer Engine

We select **Approach 2** as the winning architecture for the DRDO challenge [PS, ASSUMPTION].

```
+-----------------------------------------------------------------------------------+
|                        WHY APPROACH 2 WINS THE EVALUATION                         |
+-----------------------------------------------------------------------------------+
|  1. Sparse 3D Convolutions exploit point cloud sparsity (95%+ empty space),       |
|     delivering <25ms latency on edge GPUs (NVIDIA Jetson AGX Orin).              |
|  2. Concentric Square Ring Buffers eliminate polar wedge area distortion          |
|     (A = dx * dy is constant within each ring zone).                              |
|  3. Multi-layer grid maps integrate directly with ROS 2 Nav2 and RViz2.           |
+-----------------------------------------------------------------------------------+
```

### Strategic Reasons for Selection

1. **Computational Efficiency via Sparsity**: Raw 3D point cloud space is $>95\%$ empty space [3.6]. Standard dense 3D convolutions waste trillions of FLOPs computing over empty air [3.6]. Submanifold Sparse Convolutions (SpConv v2 / TorchSparse v2) only execute matrix multiplications on non-empty voxels, achieving sub-25 ms inference per scan on edge GPUs [3.2, 3.4].
2. **Elimination of Polar Wedge Area Distortion**: Polar grids $(\rho, \theta)$ suffer from the "expanding cell area" problem where cell physical width grows linearly with distance ($\Delta s = \rho \cdot \Delta \theta$). At $\rho = 100\text{ m}$, a single polar wedge spans several meters wide, destroying spatial fidelity [INFERENCE]. Our **Concentric Multi-Ring Buffer Engine** maintains fixed square grid cells ($5\text{ cm}$ in Zone 1, $15\text{ cm}$ in Zone 2, $50\text{ cm}$ in Zone 3), ensuring consistent spatial geometry across all directions [INFERENCE].
3. **Zero Spatial Aliasing via Snapped Shift Buffers**: Moving the vehicle causes cell position jitter if grid anchors shift continuously [INFERENCE]. By snapping ring coordinate origins to integer multiples of each ring's cell size ($\Delta x_1 = k \cdot 0.05\text{ m}$, $\Delta x_3 = k \cdot 0.50\text{ m}$), we enable non-destructive circular buffer shifting without data copying or spatial aliasing [4.2, INFERENCE].

### Justification for Rejecting Alternatives

* **Why PointNet++ (Approach 1) was rejected**: PointNet++ relies on Furthest Point Sampling (FPS) and $k$-Nearest Neighbors ($k$-NN) search [RESEARCHED]. On large outdoor scans ($>100,000$ points), $k$-NN search creates severe GPU memory bandwidth bottlenecks, dropping frame rates below $10\text{ FPS}$ on embedded Jetson platforms [RESEARCHED, INFERENCE].
* **Why Range Image UNet (Approach 2D) was rejected**: Projecting 3D point clouds onto a 2D range image spherical canvas $(u,v)$ introduces severe spatial compression near the zenith and horizon, leading to boundary bleeding where distant dynamic vehicles blend into background ground terrain [RESEARCHED, INFERENCE].

### Step-by-Step Data-Flow Narrative

1. **Ingestion & Motion Undistortion**: The raw LiDAR driver publishes `sensor_msgs/msg/PointCloud2` at $10\text{--}20\text{ Hz}$ [INFERENCE]. A C++ motion undistortion kernel fetches high-frequency ($200\text{ Hz}$) IMU angular velocities $\vec{\omega}$ and linear accelerations $\vec{a}$, applying a per-point spherical linear interpolation (Slerp) to compensate for UGV motion distortion during beam scanning [4.9, INFERENCE].
2. **Voxelization & Sparse Neural Inference**: The undistorted point cloud is voxelized into a sparse coordinate tensor with a spatial resolution of $0.05\text{ m}$ [3.6, INFERENCE]. The sparse tensor is processed by a TensorRT-optimized **Sparse 3D UNet (SpConv v2)** [3.2, 3.10]. The deep neural network assigns a semantic category probability vector to every non-empty voxel, identifying:
   * *Class 0*: Drivable Ground Surface [PS]
   * *Class 1*: Non-Drivable Ground / Rough Terrain [PS]
   * *Class 2*: Static Obstacles (Walls, Buildings, Poles) [PS]
   * *Class 3*: Dynamic Pedestrians / VRUs [PS]
   * *Class 4*: Dynamic Vehicles [PS]
3. **Adaptive Concentric Grid Projection**: Classified 3D points $(x, y, z, c)$ are passed to the C++ Concentric Multi-Ring Engine [INFERENCE]. The engine computes the radial planar distance $r = \sqrt{x^2 + y^2}$ for each point [INFERENCE]:
   * If $r \le 10\text{ m}$, project into **Ring 1 Grid** (Resolution: $\Delta x = 0.05\text{ m}$, Grid Dimensions: $400 \times 400$ cells) [PS, ASSUMPTION].
   * If $10\text{ m} < r \le 30\text{ m}$, project into **Ring 2 Grid** (Resolution: $\Delta x = 0.15\text{ m}$, Grid Dimensions: $266 \times 266$ cells) [PS, ASSUMPTION].
   * If $30\text{ m} < r \le 100\text{ m}$, project into **Ring 3 Grid** (Resolution: $\Delta x = 0.50\text{ m}$, Grid Dimensions: $280 \times 280$ cells) [PS, ASSUMPTION].
4. **Layer Aggregation**: Within each target cell $(i, j)$ of the corresponding ring, the engine updates multi-layer attributes:
   * $Z_{\max} = \max(z_1, z_2, \dots, z_k)$
   * $Z_{\min} = \min(z_1, z_2, \dots, z_k)$
   * $Z_{\text{mean}} = \frac{1}{k} \sum z_k$
   * $\text{Roughness } \sigma_z^2 = \frac{1}{k} \sum (z_k - Z_{\text{mean}})^2$
   * $\text{Semantic Dominance } C^* = \arg\max_c (\sum \mathbf{1}(c_k = c))$
5. **Publishing & Telemetry Streaming**: The accumulated multi-ring data structure is formatted into a ROS 2 `/grid_map/variable_elevation` topic [4.8, INFERENCE]. Concurrently, the engine logs dynamic memory usage ($M_{\text{adaptive}}$) and compares it against a hypothetical uniform $5\text{ cm}$ grid over a $200\text{ m} \times 200\text{ m}$ area ($M_{\text{uniform}}$), transmitting telemetry to the visualization dashboard [PS, INFERENCE].

* **Where AI MUST NOT Be Used**: AI must **NOT** be used for projecting classified points into the 2.5D grid, computing ring cell coordinates, or calculating elevation $Z_{\max} / Z_{\min}$ statistics [INFERENCE]. Using neural network regression for spatial grid projection introduces unpredictable spatial distortion and violates deterministic defense safety guarantees [INFERENCE].

### Mathematical Memory Proof & Reduction Telemetry

To satisfy **REQ-4C** (*"demonstrating a significant reduction in memory usage compared to a uniform high-resolution 3D map"*), we formulate the exact mathematical memory footprint comparison [PS, INFERENCE]:

1. **Uniform High-Resolution Grid ($5\text{ cm}$ cell size across $100\text{ m}$ radius)**:
   * Bounding Box: $200\text{ m} \times 200\text{ m}$.
   * Grid Cells: $\left(\frac{200}{0.05}\right) \times \left(\frac{200}{0.05}\right) = 4,000 \times 4,000 = 16,000,000\text{ cells}$.
   * Memory per cell (32 bytes: $Z_{\max}, Z_{\min}, Z_{\text{mean}}, \sigma_z^2, \text{Class}, \text{Variance}$):
   * $M_{\text{uniform}} = 16,000,000 \times 32\text{ bytes} = 512,000,000\text{ bytes} \approx \mathbf{512\text{ MB}}$.
2. **Adaptive Variable-Resolution Concentric Grid**:
   * *Ring 1 ($0\text{--}10\text{ m}$, $5\text{ cm}$ cell)*: $20\text{ m} \times 20\text{ m} \to 400 \times 400 = 160,000\text{ cells}$.
   * *Ring 2 ($10\text{--}30\text{ m}$, $15\text{ cm}$ cell)*: $(60\text{ m} \times 60\text{ m}) - (20\text{ m} \times 20\text{ m}) \to (400 \times 400) - (133 \times 133) = 160,000 - 17,689 = 142,311\text{ cells}$.
   * *Ring 3 ($30\text{--}100\text{ m}$, $50\text{ cm}$ cell)*: $(200\text{ m} \times 200\text{ m}) - (60\text{ m} \times 60\text{ m}) \to (400 \times 400) - (120 \times 120) = 160,000 - 14,400 = 145,600\text{ cells}$.
   * Total Adaptive Cells: $160,000 + 142,311 + 145,600 = \mathbf{447,911\text{ cells}}$.
   * $M_{\text{adaptive}} = 447,911 \times 32\text{ bytes} \approx \mathbf{14.33\text{ MB}}$.
   * **Net Memory Footprint Reduction**: $\mathbf{97.2\%}$ memory reduction ($14.33\text{ MB}$ vs $512\text{ MB}$) [INFERENCE].

### Alignment & Spatial Aliasing Protection

When the vehicle translates by $(\Delta x, \Delta y)$, updating grid cell coordinates without spatial aliasing requires anchoring each ring to an integer grid snap function [INFERENCE]:

$$\text{Anchor}_k = \text{floor}\left( \frac{\mathbf{P}_{\text{UGV}}}{\text{CellSize}_k} \right) \times \text{CellSize}_k$$

This guarantees that as the vehicle moves, cells in Ring 1 ($5\text{ cm}$), Ring 2 ($15\text{ cm}$), and Ring 3 ($50\text{ cm}$) shift in discrete integer cell increments, eliminating cell interpolation artifacts during point cloud rasterization [INFERENCE].
