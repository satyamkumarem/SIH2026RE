# 1. Executive Snapshot

### Summary
Healthcare facilities generate substantial quantities of hazardous biomedical waste, where traditional manual handling introduces severe contamination risks, operational bottlenecks, and compliance violations [PS]. To address this critical challenge, this dossier defines a complete engineering strategy for designing and building an AI-powered, battery-electric autonomous mobile robot (AMR) system integrated with automated waste identification, multi-compartment segregation, and real-time cloud-based digital tracking [PS]. Built strictly in compliance with the Bio-Medical Waste Management Rules (2016) [RESEARCHED] and executed using Autodesk Fusion for the full product development lifecycle [PS], the proposed system bridges advanced mechanical product design, edge vision AI, autonomous indoor navigation, and digital chain-of-custody tracking. This document serves as an exhaustive blueprint enabling a 4–6 student hackathon team to execute the concept during the Smart India Hackathon (SIH) timeline, providing clear boundaries between the hackathon prototype and production deployment.

# 5. Constraints & Environment Realities

### Corridor & Architectural Constraints
* **Narrow Pathways & Pedestrians:** Hospital corridors vary from 1.5m to 2.5m in width, frequently occupied by IV poles, stretchers, medical carts, and walking patients [KNOWN]. The robot footprint must not exceed $600\text{ mm} \times 800\text{ mm}$ with zero-radius turning capability (differential or mecanum drive) [INFERENCE].
* **Ramps & Thresholds:** Facilities contain door saddles, elevator gap thresholds up to 15mm, and floor ramps with up to $8^\circ$ slope [KNOWN]. High-torque brushed/brushless DC gearmotors with rubber tires are essential [INFERENCE].

### Connectivity & Network Realities
* **Wi-Fi Dead Zones:** Radiology departments, basement storage areas, and shielded ICU bays block Wi-Fi signals [KNOWN]. The AMR must operate fully autonomously offline, queuing waste transaction records locally in SQLite and syncing when connection resumes [INFERENCE].

### Operational & Hygiene Constraints
* **Chemical Washdown:** System exterior must withstand daily wiping with Isopropyl Alcohol (70%) or Sodium Hypochlorite solutions [KNOWN]. CAD housing designed in Fusion must feature IP54 sealing and smooth, continuous filleted surfaces to eliminate dirt traps [INFERENCE].
* **Acoustic Noise Limits:** Hospital quiet zones (ICU, Neonatal) require ambient noise levels below 45 dB [KNOWN]. Motor drive gearboxes and sorting actuators must utilize helical gears or belt drives to operate quietly [INFERENCE].

### Grand Finale Rules Realities
* **Zero Pre-Designed Files Rule:** Teams importing pre-existing `.f3d`, `.step`, or `.igs` files will be disqualified [PS]. All CAD geometry must be generated on-site within Autodesk Fusion during the hackathon timeline [PS].
* **Strict Non-AI Rules for Submission Materials:** No AI-generated text, graphics, or synthesized presentations allowed in slide deck submissions [PS].

### Detailed Data Flow Narrative
1. **Initiation:** The healthcare worker calls the AMR via the Web Dashboard or scheduled route trigger [INFERENCE].
2. **Navigation:** ROS2 Nav2 computes a global trajectory using the pre-mapped hospital floorplan. LiDAR real-time scans update costmaps to dynamically dodge moving obstacles [KNOWN].
3. **Arrival & Presentation:** Upon reaching the ward station, the robot halts, flashes a soft green status ring, and displays "Present Waste Item" on its touchscreen [INFERENCE].
4. **AI Vision Classification:** The user holds the waste item in front of the intake optical chamber. The camera captures an image; YOLOv8 predicts the class (e.g., `plastic_syringe` -> `RED_BIN`, confidence `0.94`) [INFERENCE].
5. **Actuation & Segregation:** The onboard MCU actuates the internal rotating diverter funnel to align above the RED compartment and opens the RED bin sealing door. The user drops the item in [INFERENCE].
6. **Weight Logging & Verification:** The compartment's HX711 load cell measures the weight delta (e.g., +45 grams) and confirms successful deposit [INFERENCE].
7. **Cloud Synchronization:** The system packages `[Robot_ID, Ward_ID, Timestamp, Category: RED, Weight: 45g, AI_Confidence: 0.94]` into an MQTT payload and transmits it to the hospital cloud database [INFERENCE].

# 13. AI/ML Justification

### Component 1: Waste Classification Engine
* **Purpose:** Classify presented medical items into 4 regulatory waste categories (Yellow, Red, Blue, White) [PS].
* **Model Type:** YOLOv8-Nano / MobileNetV3-SSD quantized to INT8 [INFERENCE].
* **Input:** $640 \times 640$ RGB camera frame of the intake portal [INFERENCE].
* **Output:** Class label (`Yellow`, `Red`, `Blue`, `White`), bounding box, confidence score ($0.00 - 1.00$) [INFERENCE].
* **Data Required:** ~3,000 annotated images of medical waste items (syringes, gloves, IV bags, ampoules, cotton rolls) [INFERENCE].
* **Why AI is Preferable:** Physical properties of medical waste are highly variable (deformed plastics, crumpled cotton, liquid-filled vials). Rigid rule-based vision cannot handle this variance [INFERENCE].
* **Evaluation:** Mean Average Precision (mAP@0.5) $> 90\%$, inference latency $< 150\text{ ms}$ on edge hardware [INFERENCE].
* **Failure Mode & Human Oversight:** If confidence score $< 0.70$, the UI prompts: "Uncertain Item. Please select category manually on screen." Prevents missegregation [INFERENCE].

### Component 2: SLAM & Obstacle Avoidance
* **Purpose:** Construct 2D floor maps and execute real-time collision-free path navigation [KNOWN].
* **Model Type:** Cartographer SLAM + TEB Local Planner in ROS2 [KNOWN].
* **Input:** LiDAR 2D point cloud + wheel encoder odometry + IMU data [KNOWN].
* **Output:** Velocity commands (`cmd_vel`: $v_x, \omega_z$) to motor drivers [KNOWN].
* **Data Required:** Real-time distance range measurements [KNOWN].
* **Why AI/Algorithmic Navigation is Preferable:** Fixed line-following tracks are rigid, expensive to install, and easily blocked by hospital clutter [KNOWN].
* **Evaluation:** Zero collisions during operation; position accuracy within $\pm 3\text{ cm}$ [INFERENCE].
* **Failure Mode & Human Oversight:** If path is blocked for $> 10$ seconds, robot emits an audible chime, updates costmap, or requests operator intervention via notification [INFERENCE].

### WHERE AI SHOULD NOT BE USED
* **Compartment Door Safety Interlocks:** Door opening/closing must be governed by deterministic hardware micro-switches and state machines—NEVER by AI inference [INFERENCE].
* **Emergency Stop System:** Hardware E-Stop button cutting motor power directly MUST bypass all software/AI stacks entirely for ISO 13850 compliance [KNOWN].

# 14. Data Architecture & Offline/Low-Network Design

### Database Schema (Local SQLite & Cloud PostgreSQL)

```sql
-- Waste Collections Table
CREATE TABLE waste_transactions (
    transaction_id VARCHAR(36) PRIMARY KEY,
    robot_id VARCHAR(20) NOT NULL,
    ward_id VARCHAR(20) NOT NULL,
    category VARCHAR(10) CHECK (category IN ('YELLOW', 'RED', 'BLUE', 'WHITE')),

    robot_id VARCHAR(20) PRIMARY KEY,
    battery_percentage INTEGER NOT NULL,
    current_location VARCHAR(50),
    active_state VARCHAR(20), -- 'NAVIGATING', 'COLLECTING', 'CHARGING', 'ERROR'
    last_heartbeat TIMESTAMP WITH TIME ZONE
);
```

### Offline Synchronization Strategy
1. **Local Buffering:** When Wi-Fi connectivity drops, the onboard controller writes transaction JSON records directly to an encrypted local SQLite database on the Jetson/Raspberry Pi storage [INFERENCE].
