# AI-Powered Monitoring & Analysis of Bitcoin Transaction Traffic

## 1. Executive Snapshot

### Executive Summary
The National Technical Research Organisation (NTRO) requires an offline, AI-powered transaction traffic monitoring and analysis system capable of ingesting bulk Bitcoin P2P network metadata alongside blockchain ledger records [PS]. Criminal actors exploit Bitcoin's pseudonymous structure to conduct ransomware, darknet market operations, and money laundering [PS]. Existing tools focus almost exclusively on public on-chain ledger records, ignoring critical network-layer observations (IP addresses, ports, timing) [RESEARCHED]. The proposed solution, **CryptoWatch-NTRO**, is an air-gapped, cross-layer intelligence system that ingests bulk network and ledger data (CSV/JSON/XML), correlates P2P node IP observations with wallet transactions, constructs an integrated entity-transaction graph, applies a hybrid Graph-XGBoost machine learning engine to detect anomalous illicit flows, and delivers ranked, fully explainable investigative leads via an interactive link-analysis dashboard [INFERENCE].

## 2. Problem Deconstruction

### Explicit Requirements
1. **Bulk Metadata Ingestion & Parsing [PS]:** System must ingest and parse bulk metadata containing timestamp, source IP (`src_ip`), destination IP (`dst_ip`), source port (`src_port`), destination port (`dst_port`), transaction ID (`txid`), input wallet addresses (`input_addresses[]`), output wallet addresses (`output_addresses[]`), input amounts (`input_amounts[]`), output amounts (`output_amounts[]`), transaction fee, script type, and GeoIP country/ASN [PS]. Input formats must include CSV, JSON, and XML [PS].
2. **Cross-Layer Entity/Transaction Graph [PS]:** System must construct a unified entity/transaction graph linking IP addresses, P2P network nodes, wallet addresses, and transactions [PS].
3. **AI/ML Detection Use Case [PS]:** System must implement a functional AI/ML detection model (not solely static heuristic/if-else rules) to detect anomalies, money laundering, ransomware, or illicit patterns [PS].
4. **Ranked, Explainable Leads & Confidence Scores [PS]:** System must generate a prioritized alert list with numerical confidence scores and human-interpretable evidence explaining why each entity or transaction was flagged [PS].
5. **Interactive Visualization Dashboard [PS]:** System must present findings through a simple, responsive dashboard or link-analysis graph interface [PS].
6. **Offline Linux Deployment [PS]:** System must run completely offline on a Linux platform without requiring external cloud services or live internet connections during execution [PS].
7. **Offline GeoIP Database Integration [PS]:** System must integrate an open-source, locally downloadable GeoIP database (e.g., MaxMind GeoLite2 `.mmdb`) to map IP addresses to geographic locations and ASNs offline [PS].
8. **Working Prototype & Technical Write-up [PS]:** Team must deliver a functional code repository, a complete offline software prototype, and a technical write-up detailing model architecture, feature engineering, and explainability techniques [PS].

### Implicit & Derived Requirements
1. **Deterministic Address Clustering Heuristics [INFERENCE]:** To group raw Bitcoin wallet addresses into entity clusters prior to ML scoring, the system must implement multi-input heuristics (common-input ownership) and change-address detection algorithms [KNOWN].
2. **High-Throughput Offline Storage [INFERENCE]:** Bulk CSV/JSON/XML file parsing and network graph generation require an embedded column-oriented analytical database (e.g., DuckDB) and graph storage (e.g., KùzuDB or NetworkX/Networkit) to handle millions of records locally [INFERENCE].
3. **Local Explainable AI Framework [INFERENCE]:** Explainability must utilize local post-hoc interpretability models like SHAP (SHapley Additive exPlanations) or GNNExplainer without external API dependencies [KNOWN].

## 9. Candidate Solution Approaches

```
+---------------------------------------------------------------------------------------------------+
|                                  CANDIDATE ARCHITECTURE COMPARISON                                |
+------------------------------------+--------------------------------+-----------------------------+
| Approach 1: Heuristic & Static Rules| Approach 2: Deep Hetero-GNN     | Approach 3: Hybrid Engine   |
| - Fast execution                   | - End-to-end graph learning     | - High precision XGBoost    |
| - Zero ML training needed          | - Captures complex topology    | - Node2Vec/GraphSAGE embeds |
| - Lacks adaptability to new patterns| - High compute, hard to explain| - SHAP feature-level XAI    |
+------------------------------------+--------------------------------+-----------------------------+
```

### Approach 1: Heuristic & Rule-Based Deterministic Engine
* **Mechanism:** Relies on hardcoded threshold rules (e.g., transaction amount > 10 BTC, velocity < 60s, known mixers) combined with standard Bitcoin wallet clustering heuristics (Common Input Ownership) [INFERENCE].
* **Evaluation:** High speed and 100% explainable, but fails the explicit PS requirement: *"Implement AI/ML detection use case... with a working model - not just rules"* [PS]. Low adaptability to novel laundering schemes [INFERENCE].

### Approach 2: End-to-End Heterogeneous Graph Neural Network (Hetero-GNN)
* **Mechanism:** Constructs a multi-relational graph (Nodes: `IP`, `Wallet`, `TX`; Edges: `SENT_FROM`, `BROADCAST_BY`). Trains a PyTorch Geometric Hetero-GNN (RGCN or Graph Attention Network) end-to-end to classify nodes as licit vs. illicit [RESEARCHED].
* **Evaluation:** Captures complex multi-hop structural relationships effectively [3.4]. However, GNNs suffer from high computational overhead on CPU-only Linux systems, black-box explainability challenges (GNNExplainer outputs subgraphs that non-technical investigators find difficult to parse), and susceptibility to severe class imbalance [3.2].

### Approach 3: Hybrid Feature-Engineered XGBoost + GraphSAGE Embeddings + SHAP (RECOMMENDED)
* **Mechanism:** Combines structural graph analysis with gradient-boosted decision trees. Extracts structural topological features (PageRank, degree, ego-network density) and Node2Vec/GraphSAGE embeddings, passes them to an XGBoost classifier, and generates SHAP explanations for every prediction [INFERENCE].
* **Evaluation:** Delivers top-tier classification performance on tabular-graph hybrid financial data [3.9], operates efficiently on CPU-based offline workstations, provides mathematical feature importance scores via SHAP [RESEARCHED], and fulfills every explicit problem statement requirement [PS].

## 10. Recommended Approach & Why

### Selection: Hybrid Architecture (Approach 3)
The recommended approach is **Approach 3: Hybrid Feature-Engineered Engine (Graph Topological Features + Node Embeddings + XGBoost + SHAP Explainability)** [INFERENCE].

### Justification & Rejection of Alternatives
1. **Why Approach 1 was Rejected:** Approach 1 fails the explicit requirement: *"Implement AI/ML detection use case... with a working model - not just rules"* [PS]. Rule-based systems cannot generalize to dynamic money laundering techniques such as automated peel chains or variable-delay coin mixing [INFERENCE].
2. **Why Pure GNN (Approach 2) was Rejected:** Peer-reviewed benchmark studies on Bitcoin transaction fraud (such as Weber et al., 2019 [3.8] and Erasmus University AML benchmarks [3.9]) demonstrate that tree-based ensembles (XGBoost/Random Forest) consistently outperform pure Graph Convolutional Networks (GCNs) on Bitcoin financial crime datasets, achieving higher F1-scores while requiring a fraction of the compute resources [3.9]. Furthermore, GNNs present significant explainability barriers for non-technical law enforcement officers compared to SHAP-backed tree ensembles [3.2].
3. **Why Hybrid Wins:** Combining topological graph metrics (PageRank, clustering coefficient) and node embeddings with XGBoost provides superior precision, fast offline CPU execution, and mathematically rigorous SHAP explanations required by NTRO analysts [INFERENCE].

```
   ▼

   │  ├── Topological Feature Extractor (PageRank, Degree, Ego Density, Velocity)

   ▼

   │  ├── SHAP Interpreter (Calculates local feature contributions per alert)
   │  └── Natural Language Evidence Generator (Converts SHAP vectors into English rationale)
   ▼

   │  ├── Local Web Dashboard (Dash / Plotly / Cytoscape.js on http://localhost:8050)
   │  ├── Interactive Link-Analysis Graph Visualizer (Expandable Nodes, Zoom, Path Trace)
   │  └── Ranked Alert Desk & PDF/JSON Lead Export Engine

```

### Step-by-Step Data Flow Narrative
1. **Ingestion & Validation:** The user uploads or specifies a local directory path containing bulk CSV, JSON, or XML transaction metadata files via the offline dashboard [PS]. The ingestion pipeline uses `Polars` for fast multi-threaded parsing, validating all required fields (`timestamp`, `src_ip`, `dst_ip`, `txid`, `input_addresses`, `output_addresses`, `amounts`, `fee`, `script_type`) [INFERENCE].
2. **Offline GeoIP Enrichment:** Every IP address (`src_ip`, `dst_ip`) is queried against the bundled local MaxMind `GeoLite2-Country.mmdb` and `GeoLite2-ASN.mmdb` binary files, populating ISO country codes, coordinates, and Autonomous System Numbers without network calls [PS].
3. **Graph Construction & Address Clustering:** The system applies the Common Input Ownership heuristic: if Addresses $A$ and $B$ are spent together in Transaction $T$, they are merged into Entity Cluster $C_k$ [KNOWN]. Edges are created linking `IP` $\rightarrow$ `Transaction` (P2P broadcast) and `Wallet/Cluster` $\rightarrow$ `Transaction` (Ledger spend/receive) [INFERENCE].
4. **Feature Extraction:** For every transaction and cluster, the engine computes 32 structural, financial, and network features, including transaction velocity, output entropy, fan-in/fan-out ratio, fee-to-amount ratio, time-delta between network broadcast and ledger timestamp, and local Node2Vec graph embeddings [INFERENCE].
5. **AI/ML Inference:** The extracted feature vector is fed into the offline pre-trained XGBoost model [INFERENCE]. The model outputs an anomaly classification label (e.g., `Ransomware Pool`, `Peel Chain`, `Mixer/Tumbler`, `Benign`) and a continuous confidence score $S \in [0, 1]$ [INFERENCE].
6. **XAI Evidence Generation:** For any entity scored above the alert threshold ($S \ge 0.65$), the SHAP explainer computes exact Shapley values [RESEARCHED]. The Top-3 contributing features (e.g., `High Output Entropy (+0.32)`, `Rapid Peel Sequence (+0.25)`, `High-Risk ASN (+0.18)`) are extracted and formatted into human-readable evidence points [INFERENCE].
7. **Visualization:** Findings are displayed in the local dashboard, featuring a ranked lead table, confidence indicators, and an interactive Cytoscape.js link-analysis graph allowing investigators to expand node connections visually [PS].

## 13. AI/ML Justification

### Comprehensive AI Component Evaluation

```
+---------------------------------------------------------------------------------------------------+
|                                 AI/ML MODEL EVALUATION WORKFLOW                                   |
+---------------------------------------------------------------------------------------------------+

   [Input Features: 32 Matrix Columns]
   ├── Graph Topology (PageRank, In/Out Degree, Ego Density)
   ├── Transaction Attributes (Amounts, Fees, Output Entropy, Script Types)
   └── Network Attributes (IP Propagation Delay, Country Risk, ASN Category)
         │
         ▼
   [XGBoost Gradient Boosting Classifier] ──> [Supervised Classification Output]
         │                                    ├── Predicted Category (Licit / Ransomware / Mixer)
         │                                    └── Probabilistic Score (0.00 to 1.00)
         ▼
   [SHAP Explainer Engine] ──────────────────> [Local Feature Weight Attributions]
                                              └── Human-Readable Evidence Sentences
+---------------------------------------------------------------------------------------------------+
```

1. **What exact problem does AI solve?** Detects non-linear, multi-attribute illicit financial patterns (e.g., peel chains, ransomware payout splitting, obfuscated mixing flows) that static rule sets miss [INFERENCE].
2. **What is the input?** A 32-dimensional feature vector per transaction/cluster combining structural graph metrics, financial flow statistics, and network timing attributes [INFERENCE].
3. **What is the output?** An anomaly classification label (`Benign`, `Ransomware`, `Mixer`, `Peel Chain`, `High-Risk IP Hop`) and a confidence score between $0.00$ and $1.00$ [INFERENCE].
4. **Why can a simpler rule/system not solve it?** Criminal actors alter transaction amounts, split payments into variable fractions, and rotate IP addresses to evade fixed static thresholds [KNOWN]. ML models learn generalized structural patterns across thousands of historical transactions [RESEARCHED].
5. **What data is required?** Historical labelled Bitcoin transaction graph data (e.g., Elliptic Dataset [3.8]) combined with synthetic network metadata logs [PS].
6. **How will it be evaluated?** Precision, Recall, F1-Score, and Receiver Operating Characteristic - Area Under Curve (ROC-AUC) evaluated on an offline hold-out validation set [INFERENCE].
7. **What happens when it is wrong?** False positives or false negatives are presented with full SHAP evidence breakdowns, allowing human intelligence analysts to review and override automated ratings [INFERENCE].
8. **Does it require training?** Yes. Pre-trained offline using historical benchmark datasets; weights saved to disk as a `.json` model file [INFERENCE].
9. **Does it require fine-tuning?** No live fine-tuning needed during offline evaluation [INFERENCE].
10. **Does it require RAG?** No. Retrieval-Augmented Generation is unnecessary for structured numerical graph classification [INFERENCE].
11. **Does it require computer vision?** No [INFERENCE].
12. **Does it require speech processing?** No [INFERENCE].
13. **Does it require forecasting?** No [INFERENCE].
14. **Is human oversight required?** Yes. System functions as an "Investigative Copilot"—generating prioritized leads for human analyst validation [INFERENCE].

### Explicit Non-AI Components
Address clustering (Common Input Ownership heuristic) and GeoIP country resolution must **NOT** use AI [INFERENCE]. They must remain 100% deterministic algorithms to guarantee strict consistency [INFERENCE].
