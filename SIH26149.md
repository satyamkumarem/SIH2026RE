## 1. Executive Snapshot

This dossier presents the architecture and strategic blueprint for **AegisSanitize & Carve**, a unified, enterprise-grade forensic software platform designed for the National Technical Research Organisation (NTRO) [PS]. The platform resolves the critical operational fragmentation in digital forensics and IT asset decommissioning by integrating two diametrically opposed capabilities into a single, air-gapped application: (1) deterministic, standards-compliant drive/file data sanitization and (2) forensic-grade, metadata-independent file carving and reconstruction [PS]. Designed for air-gapped deployment in high-security environments, the solution guarantees tamper-proof audit trails for media sanitization according to NIST SP 800-88 Rev 2 and IEEE 2883-2022 standards [RESEARCHED], while employing signature, structure, and machine-learning-assisted entropy analysis to recover evidence from formatted, corrupted, or fragmented storage media [PS].

## 5. Constraints & Environment Realities

*   **Air-Gapped Deployment Constraint:** NTRO digital forensics labs and government security units operate strictly in air-gapped, high-security environments [RESEARCHED]. The solution **must not require internet connectivity**, cloud APIs, or external licensing servers [INFERENCE].
*   **Hardware Architecture Differences (HDD vs. SSD/NVMe):**
    *   *HDDs (Magnetic):* Data resides on magnetic platters; overwriting sector LBAs directly overwrites physical data [KNOWN]. Multi-pass zero/pattern overwrites (DoD 5220.22-M, NIST Clear) are effective [RESEARCHED].
    *   *SSDs / NVMe (Flash):* Flash Translation Layers (FTL), wear-leveling algorithms, and over-provisioned hidden blocks mean logical overwrites to LBA 100 do **not** guarantee physical erasure of the underlying NAND cell [RESEARCHED]. Overwriting SSDs via standard software causes cell wear and leaves data in hidden blocks [RESEARCHED]. Flash media requires native controller commands: NVMe Sanitize, ATA Secure Erase, or Cryptographic Erase (IEEE 2883-2022 / NIST Purge) [RESEARCHED].
*   **Operating System & Privilege Realities:** Accessing raw disk blocks (`\\.\PhysicalDriveX` on Windows, `/dev/sdX` or `/dev/nvmeXn1` on Linux) requires elevated administrative/root privileges [KNOWN]. Software must gracefully request OS privilege escalation at startup [INFERENCE].
*   **Performance & Scale Constraints:** Forensic drive images routinely exceed 1 TB to 4 TB in size [KNOWN]. Processing raw data byte-by-byte in Python is computationally infeasible; low-level pattern matching and raw block I/O must be implemented using compiled native C/C++ threads or memory-mapped files (`mmap`) [INFERENCE].

## 6. Research Questions

1.  **RQ1:** How does the solution securely sanitize SSD/NVMe storage without causing excessive drive wear or missing over-provisioned areas?
    *   *Verification Plan:* Test native NVMe Sanitize (`nvme sanitize /dev/nvme0n1 -a 2`) and ATA Secure Erase against logical zero-fill on SATA and NVMe drives; measure drive health (SMART) and verify zero data retrieval from over-provisioned blocks [RESEARCHED].
2.  **RQ2:** How can file carving accurately reassemble fragmented files when the file system table (MFT/FAT/Inode) is completely destroyed?
    *   *Verification Plan:* Benchmark bifragment gap-carving algorithms against heavily fragmented synthetic disk images (e.g., DFRWS forensic challenge datasets) [RESEARCHED].
3.  **RQ3:** How can sanitization audit reports be rendered cryptographically tamper-evident without relying on public cloud PKI or online Certificate Authorities?
    *   *Verification Plan:* Implement local Ed25519 asymmetric key pair generation during installation; embed digital signatures and pre/post SHA-256 hashes directly into generated PDF reports [INFERENCE].

## 9. Candidate Solution Approaches

### Approach 1: CLI-Wrapper Scripting Monolith
*   **Mechanism:** Python-based GUI wrapping external command-line utilities (`dd`, `hdparm`, `nvme-cli`, `foremost`, `scalpel`, `exiftool`) via subprocess execution [INFERENCE].
*   **Pros:** Rapid hackathon prototyping; leverages mature open-source tools [INFERENCE].
*   **Cons:** Fragile process management; poor cross-platform error handling; severe performance bottlenecks during multi-terabyte scans; difficult to implement custom fragment reassembly or unified confidence scoring [INFERENCE].
*   **Evaluation:** High hackathon speed, but low architectural quality, poor reliability, and unacceptable for NTRO production standards [INFERENCE].

### Approach 2: Pure User-Space Custom Native Engine (C++17)
*   **Mechanism:** Single high-performance C++17 monolithic desktop application incorporating custom direct disk I/O, raw byte scanning, custom file system parsers, and custom Qt GUI [INFERENCE].
*   **Pros:** Maximum execution speed; zero external runtime dependencies; complete control over raw block I/O and memory management [INFERENCE].
*   **Cons:** Extremely high implementation effort for a 4–6 student team; high risk of non-completion within hackathon constraints; complex GUI code in C++ [INFERENCE].
*   **Evaluation:** Excellent performance, but excessively high implementation risk for a student team [INFERENCE].

### Approach 3: Hybrid Native Micro-Core Architecture (Recommended)
*   **Mechanism:** PySide6 (Qt6) frontend driving a multi-threaded C++/Python backend engine [INFERENCE]. Low-level raw block I/O, signature scanning, and hardware ioctls are executed via high-performance C++ extensions / `ctypes` bindings, while high-level structure parsing, ML file classification, and PDF audit generation are handled in Python [INFERENCE].
*   **Pros:** Optimal balance between C++ raw execution speed and Python rapid development; clean modular separation between Eraser and Carver engines; robust cross-platform GUI [INFERENCE].
*   **Cons:** Requires careful memory management across C++/Python boundaries [INFERENCE].
*   **Evaluation:** Best approach for a 4–6 student hackathon team to achieve production-grade functionality within deadline constraints [INFERENCE].

## 10. Recommended Approach & Why

**Selected Approach:** **Approach 3 (Hybrid Native Micro-Core Architecture)** [INFERENCE].

### Justification:
1.  **Performance vs. Development Velocity:** Digital forensic operations require processing gigabytes of raw disk data per second. Pure Python approaches fail on throughput, while pure C++ approaches impose unacceptable GUI and development overhead [INFERENCE]. A hybrid core gives native execution speeds for block scanning while enabling rapid development of complex GUI and AI features [INFERENCE].
2.  **Modularity:** The three required modules (Drive Eraser, File/Folder Eraser, File Carver) can be developed in parallel by different team members as isolated backend classes before integration into the PySide6 UI [ASSUMPTION].
3.  **Standard Compliance:** Allows direct integration of standard OS system calls (`ioctl`, Win32 `DeviceIoControl`) for native NVMe/ATA sanitization while utilizing Python's rich cryptography (`cryptography` library) and reporting (`ReportLab`) tools for tamper-evident PDF output [INFERENCE].

### Rejection of Alternatives:
*   *Approach 1 (CLI Wrappers)* was rejected because it lacks the deep integration, custom fragment reassembly, and structural verification required for an enterprise NTRO submission [INFERENCE].
*   *Approach 2 (Pure C++ Monolith)* was rejected due to the unreasonable burden it places on a student team to build custom UI widgets, PDF engines, and ML classifiers from scratch in C++ within the build window [INFERENCE].

### Data-Flow Narrative:

1.  **Drive Sanitization Flow:**
    *   User selects target disk device (e.g., `/dev/sdb` or `\\.\PhysicalDrive1`) and desired standard (e.g., NIST SP 800-88 Purge / IEEE 2883-2022) [PS].
    *   System queries SMART data and device architecture (HDD vs. SSD/NVMe) via `smartctl` / Win32 API [RESEARCHED].
    *   Pre-sanitization SHA-256 hash of sample sectors is computed and logged [INFERENCE].
    *   If NVMe/SSD: System unmounts partitions, issues `NVMe Sanitize` / `ATA Secure Erase` command via OS ioctl, and waits for hardware controller completion signal [RESEARCHED].
    *   If HDD: Multi-threaded C++ engine performs single-pass zero or multi-pass pattern overwrites across all LBAs [RESEARCHED].
    *   Post-sanitization verification sweep checks sample sectors for residual data [PS].
    *   System generates an Ed25519-signed PDF Audit Certificate detailing drive serial number, operator ID, method, timestamps, and hashes [PS].

2.  **File Carving Flow:**
    *   User loads a raw forensic disk image (`.raw`, `.dd`) or mounts an unallocated drive partition [PS].
    *   The C++ Stream Engine uses memory-mapped files (`mmap`) to scan raw sectors at high throughput, matching magic-byte signatures (e.g., `FF D8 FF` for JPEG) [RESEARCHED].
    *   When a header is located, the Structure Parser validates internal format integrity (e.g., checking JPEG segment markers, PNG chunk CRC32 checksums, PDF xref tables) [RESEARCHED].
    *   If fragmentation is detected (footer missing or mismatched), the Fragment Reassembler executes bifragment gap analysis and entropy boundary matching to identify the remaining file clusters [RESEARCHED].
    *   The ML Classifier calculates byte-frequency distributions and Shannon entropy to assign a confidence score (0–100%) [PS].
    *   Recovered artifacts are saved to a isolated target folder with SHA-256 hashes, and displayed in the GUI Hex/Image viewer [PS].

## 13. AI/ML Justification

AI/ML is **strictly targeted** at problem domains where deterministic rule-based algorithms are insufficient: file classification and corrupted fragment confidence scoring [INFERENCE].

### 1. Component 1: File Fragment Classification & Entropy Classifier
*   **Purpose:** Differentiate between valid file payload data, compressed archives, encrypted blocks, and random garbage during carving when headers are missing [INFERENCE].
*   **Model Type:** LightGBM / Random Forest Classifier trained on byte-frequency histograms (256-bin byte distribution) and sliding-window Shannon entropy calculation [RESEARCHED].
*   **Input:** 4 KB block byte arrays extracted from unallocated space [INFERENCE].
*   **Output:** Predicted file category (e.g., `Text`, `JPEG`, `Exec`, `Encrypted/Compressed`, `Garbage`) + Probability Score [INFERENCE].
*   **Data Required:** Synthetic training dataset built from public corpora (Govdocs1, Wikipedia text, random JPEG/PNG samples, encrypted BLOBs) [RESEARCHED].
*   **Why AI is Preferable:** Pure rule-based checks fail on headerless data blocks; byte-frequency histograms exhibit distinct statistical clustering across file types [RESEARCHED].
*   **Evaluation Metric:** F1-Score on out-of-sample block test set (>92% target) [INFERENCE].
*   **Failure Mode Handling:** If classification probability is <60%, block is tagged as "Unclassified/Raw Sector" for manual investigator review [INFERENCE].
*   **Human Oversight:** Investigator can manually override classification in the UI [PS].

### 2. Component 2: Recovered Artifact Confidence Scoring Engine
*   **Purpose:** Calculate an overall valid confidence score (0–100%) for every carved file [PS].
*   **Model Type:** Hybrid Rule-Based + Gradient Boosted Decision Tree (GBDT) [INFERENCE].
*   **Input:** Structural parsing results (Header match flag, Footer match flag, Internal length field match, Image/Document decode success, Shannon entropy variance) [INFERENCE].
*   **Output:** Float Confidence Score (0.00 to 1.00) mapped to GUI badge (High / Medium / Low Integrity) [PS].
*   **Why AI is Preferable:** Weighted combination of multi-variable structural parameters cannot be accurately modeled with rigid static thresholds across diverse file types [INFERENCE].
*   **Failure Mode Handling:** Low-confidence files (<40%) are flagged with visual warnings to prevent investigator misinterpretation [INFERENCE].

### Where AI Should NOT Be Used:
*   **Data Sanitization Wiping:** Wiping routines **MUST NOT** use AI [INFERENCE]. Sanitization must remain 100% deterministic, executing exact byte overwrites or native hardware commands dictated by NIST/IEEE standards [RESEARCHED].

*   **Privilege Control & Access Boundaries:** Wiping low-level disk sectors requires root/administrator rights. The software isolates elevated disk I/O operations inside a separate background daemon process, maintaining least-privilege principles for the primary GUI frontend [INFERENCE].
