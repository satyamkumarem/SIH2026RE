## 1. Executive Snapshot

### Summary
Urban flooding in major Indian metropolises (e.g., Mumbai, Delhi, Chennai) has evolved into a recurring annual catastrophe [PS]. Traditional Numerical Weather Prediction (NWP) models quantify total atmospheric precipitation over broad geographical grids, but fail to predict street-level water accumulation because flooding is driven by micro-topography, surface imperviousness, and complex underground drainage network dynamics [PS]. This dossier presents a complete technical blueprint for a high-resolution, real-time Urban Flood Nowcasting System (0–3 hour lead time) [PS]. The solution couples Doppler Weather Radar (DWR) rainfall nowcasts with bare-earth Digital Elevation Models (DEM) and a directed graph representation of the underground stormwater drainage network [PS]. By computing surface runoff routing and hydraulic conduit capacity (including backflow and surcharge onto roads), the system delivers street-by-street water depth predictions (in centimeters) via an interactive web GIS dashboard and exposes a REST API for dynamic, flood-aware navigation routing for emergency services and citizens [PS].

To accurately predict street-level flood inundation depth (cm) 0 to 3 hours in advance by coupling high-resolution radar rainfall nowcasts with 2D terrain hydrology and graph-based dynamic hydraulic sewer/drain network routing, providing real-time GIS visualization and flood-safe routing APIs `[PS]`.

## 2. Problem Deconstruction

The explicit problem statement provided in the source JSON is deconstructed into atomic requirements below. No explicit requirements have been removed, weakened, or altered `[PS]`.

* **Req-1 (Domain Context & Core Problem)**: Urban flooding in major Indian metros (Mumbai, Delhi, Chennai) occurs because Numerical Weather Prediction (NWP) models only forecast atmospheric rain, not street inundation `[PS]`. Micro-topography, concrete imperviousness, and underground drainage constraints dictate hyper-local flooding `[PS]`.
  * *Interpretation*: System must bridge the gap between atmospheric rainfall rate ($mm/hr$) and street surface water depth ($cm$).
  * *Implementation Implication*: Requires hydrologic transformation (rainfall to surface runoff volume) coupled with hydraulic pipe/canal routing.

* **Req-2 (Lead Time & Spatial Granularity)**: Design a real-time Urban Flood Nowcasting System with a 0–3 hour forward-looking lead time at street-level resolution `[PS]`.
  * *Interpretation*: Simulations must execute faster than real-time (e.g., run a 3-hour projection in $<2$ minutes) at a spatial resolution fine enough to distinguish individual street segments ($\approx 10\text{–}30\text{ m}$).
  * *Implementation Implication*: Time-critical compute pipeline; full 2D hydrodynamic models (like SWMM or shallow water equations) must be optimized or accelerated via surrogate graph models.

* **Req-3 (Coupled System Framework)**: Move away from isolated weather models and build a coupled framework fusing real-time rainfall nowcasts, high-resolution DEMs, and a graph-based drainage network model `[PS]`.
  * *Interpretation*: The system architecture must integrate three distinct domains: atmospheric radar observations, surface terrain elevation, and sub-surface pipe hydraulic state.
  * *Implementation Implication*: Middleware must pass calculated runoff volume from surface DEM catchments into the node inlets of the sub-surface graph.

* **Req-4 (2D Surface Terrain Routing Pipeline)**: Develop a pipeline taking high-resolution radar nowcasts (from Doppler Weather Radars) and instantly routing water volume across a 2D surface terrain model `[PS]`.
  * *Interpretation*: Radar reflectivity ($Z\text{–}R$ relationship) or pre-processed DWR quantitative precipitation estimates (QPE) must be mapped onto 2D terrain cells to compute overland flow vectors.
  * *Implementation Implication*: Grid-based overland flow routing using Digital Terrain Models (e.g., FABDEM / Copernicus DEM or custom elevation rasters).

* **Req-5 (Graph-Based Hydraulic Sewer/Drain Network Model)**: Represent the city's stormwater drain network as a directed graph where nodes represent manholes/inlets and edges represent pipes/canals `[PS]`. The model must calculate hydraulic capacity and predict where blockages or overcapacity cause backflow onto streets `[PS]`.
  * *Interpretation*: Directed Graph $G = (V, E)$. Node $v_i \in V$ holds elevation, depth, head, and surface inflow; Edge $e_{ij} \in E$ holds diameter/cross-section, roughness, slope, and max discharge capacity ($Q_{max}$). Surcharge occurs when $Q_{in} > Q_{max}$ or downstream head $H_j > H_i$, triggering negative flow (backflow) spilling out of node $v_i$.
  * *Implementation Implication*: Hydraulic solver must support 1D Dynamic Wave routing (St. Venant equations) or full 1D/2D coupled engine (e.g., PySWMM / EPA-SWMM engine).

* **Req-6 (Dynamic Web-Based GIS Dashboard)**: Build a dynamic web GIS dashboard showing real-time, street-by-street flooding projections (water depth in centimeters) with a 0–3 hour forward window `[PS]`.
  * *Interpretation*: Frontend must render vector street lines and polygon inundation zones color-coded by predicted depth ($0\text{ cm}$, $10\text{ cm}$, $30\text{ cm}$, $>50\text{ cm}$) updated at intervals matching radar nowcast pulses.
  * *Implementation Implication*: WebGL/Mapbox GL JS or Leaflet UI fetching vector tiles or GeoJSON predictions from the backend time-series data store.

* **Req-7 (Navigation & Routing API Utility)**: Provide an API utility interfacing with navigation maps to suggest flood-safe alternative routes for emergency services, public transit, and commuters during heavy downpours `[PS]`.
  * *Interpretation*: Navigation endpoint taking origin/destination coordinates and returning a route geometry that dynamically penalizes or excludes road edges where predicted water depth exceeds vehicle safety thresholds (e.g., $>15\text{ cm}$ for cars, $>30\text{ cm}$ for buses/trucks).
  * *Implementation Implication*: Custom Open Source Routing Machine (OSRM) or Valhalla instance with dynamic edge weight adjustments based on nowcast inundation predictions.

## 5. Constraints & Environment Realities

* **Geographic & Topographic Realities**: Coastal Indian cities (e.g., Mumbai, Chennai) feature flat terrain, tidally influenced outfalls, and low elevation gradients ($<1\%$), meaning drainage discharge is heavily constrained during high tide events `[KNOWN]`. Inland metros like Delhi have critical low-lying underpasses susceptible to rapid flash pooling `[KNOWN]`.
* **Connectivity & Bandwidth Constraints**: Severe downpours in Indian metros frequently trigger cellular network congestion, towers running on backup batteries, and degraded packet loss `[KNOWN]`. Field mobile applications used by emergency responders must support offline caching and lightweight vector map tiles `[INFERENCE]`.
* **Underground Infrastructure Data Scarcity**: Complete 3D CAD/GIS datasets of municipal stormwater networks (pipe invert levels, slope, internal diameters, roughness) are missing, incomplete, or outdated in most Indian cities `[KNOWN]`.
* **Digital Literacy & User Interface**: Field emergency staff require clear visual color cues (Green = Safe, Yellow = Waterlogged $<15\text{ cm}$, Red = Impassable $>30\text{ cm}$) rather than complex hydraulic unit metrics `[INFERENCE]`.
* **Hardware & Compute Realities**: Municipal disaster control rooms run standard commodity cloud server instances or basic desktop workstations `[INFERENCE]`. Model execution cannot depend on massive supercomputer clusters for real-time nowcast cycles `[INFERENCE]`.

### Approach 1: Pure 2D Overland Hydrodynamic Surface Model (LISFLOOD-FP)
* **Mechanism**: Solves simplified 2D Shallow Water Equations (SWE) directly on a fine raster grid using rainfall as an spatial input array. Ignore underground pipe geometry and assume an empirical surface loss/infiltration rate.
* **Required Data**: High-resolution DEM ($5\text{--}10\text{m}$), land-cover surface roughness (Manning's $n$), radar precipitation grids.
* **Architecture**: Heavy GPU raster compute grid performing finite-difference surface water movement across elevation pixels.
* **Complexity**: High mathematical complexity (partial differential equations).
* **Cost**: High computational GPU cloud cost.
* **Explainability**: High physical explainability (mass conservation / momentum equations).
* **Scalability**: Poor for real-time nowcasts over large urban areas due to heavy raster compute requirements.
* **Hackathon Feasibility**: Low; setting up 2D SWE CUDA solvers within a hackathon timeframe is error-prone.
* **Production Feasibility**: Moderate; requires high-end dedicated GPU clusters.
* **Risks**: Misses underground sewer capacity, backflow from surcharged manholes, and pipe blockages `[INFERENCE]`.

### Approach 2: Full 1D/2D Coupled Hydrodynamic Model (EPA-SWMM Engine via PySWMM)
* **Mechanism**: Fuses 2D surface catchment runoff with a 1D Dynamic Wave sewer network model. Rainfall nowcast is converted to sub-catchment runoff (Green-Ampt infiltration), fed into graph nodes (manholes), and routed through directed pipe edges via St. Venant equations. Node surcharge spills over onto linked surface storage nodes representing street segments.
* **Required Data**: DEM elevation, OpenStreetMap road network, synthesized/municipal sewer graph (nodes, invert levels, edge cross-sections), radar rainfall inputs.
* **Architecture**: Python microservices orchestrated via FastAPI, executing native C-compiled EPA-SWMM binary solvers via `pyswmm` bindings in parallel across urban drainage sub-basins.
* **Complexity**: Moderate; standard open-source hydraulic engine wrapped in modern Python APIs.
* **Cost**: Low to Moderate (Standard CPU container clusters).
* **Explainability**: Very high; fully compliant with hydraulic engineering principles (St. Venant dynamic wave formulation).
* **Scalability**: High when sub-divided by river/drainage basin boundaries.
* **Hackathon Feasibility**: High; leveraging mature `pyswmm` and `swmm_api` libraries allows rapid model assembly.
* **Production Feasibility**: High; proven industry standard for urban drainage analysis worldwide.
* **Risks**: Execution latency if the network graph contains $>10,000$ nodes without sub-basin spatial partitioning `[RESEARCHED]`.

### Approach 3: Graph Neural Network (GNN) Surrogate Metamodel + Dynamic OSRM Routing
* **Mechanism**: Trains a Message Passing Graph Neural Network (PyTorch Geometric) on offline pre-simulated SWMM hydraulic runs. The GNN learns to instantly predict node surcharge and street segment water depths ($0\text{--}3\text{ hr}$) given rainfall nowcast spatial arrays.
* **Required Data**: Massive pre-computed dataset of SWMM simulation runs across thousands of storm scenarios for training.
* **Architecture**: Deep learning inference pipeline (PyTorch GPU) feeding predicted street inundation depths directly into a dynamic OSRM routing engine wrapper.
* **Complexity**: Very high; requires complex dataset generation, metamodel training, and transferability tuning.
* **Cost**: Low inference cost; high offline training cost.
* **Explainability**: Low (black-box neural network predictions); hydraulic engineers cannot easily verify mass conservation.
* **Scalability**: Extremely fast inference ($<1\text{ second}$).
* **Hackathon Feasibility**: Low/Moderate; generating enough training simulations and training a reliable GNN within hackathon constraints is extremely risky.
* **Production Feasibility**: High for instant real-time nowcasting if backed by continuous SWMM validation.
* **Risks**: Model hallucination or unphysical water depth predictions under extreme unobserved storm conditions `[INFERENCE]`.

## 10. Recommended Approach & Why

### Selection: Hybrid Architecture (Approach 2 Core with Approach 3 Light Surrogate Fallback)
The recommended approach for a 4–6 student hackathon team is **Approach 2 (Coupled Hydrologic Graph Engine via PySWMM)** as the primary deterministic physics engine, supplemented by a simplified spatial lookup matrix for real-time navigation routing.

### Justification
1. **Direct Alignment with PS**: Problem Statement SIH26085 explicitly demands representing the city's stormwater drain network as a "directed graph (nodes as manholes/inlets, edges as pipes/canals)" and calculating "hydraulic capacity and backflow onto streets" `[PS]`. Approach 2 implements this requirement natively.
2. **Standard Hydraulic Engineering Principles**: EPA-SWMM solves 1D Dynamic Wave equations, accurately capturing backwater effects, pipe surcharge, pressurized flow, and manhole overflow `[RESEARCHED]`.
3. **Execution Speed & Feasibility**: `pyswmm` provides C-level execution speed (running 3-hour nowcast hydrographs in $<10$ seconds for a typical municipal ward with $500\text{--}1,500$ nodes) `[RESEARCHED]`.
4. **Why Alternatives Were Rejected**:
   * *Approach 1 (Pure 2D Surface SWE)*: Rejected because it completely ignores the underground pipe network requirement `[PS]` and requires prohibitive GPU compute resources.
   * *Approach 3 (Full Pure GNN Surrogate)*: Rejected as the primary engine for the hackathon because training data generation requires thousands of verified SWMM runs. Without guaranteed training data accuracy, a pure GNN risks unphysical predictions (hallucinating water volume) `[INFERENCE]`.

### Detailed Data-Flow Narrative
1. **Radar Ingestion & Nowcast Vectorization**: Every 10 minutes, the Data Ingestion pipeline receives a radar reflectivity scan array. An advection-based optical flow model (Rainymotion) projects spatial precipitation vectors forward over a 0–3 hour horizon at 15-minute intervals `[RESEARCHED]`.
2. **Hydrologic Runoff Calculation**: For each 15-minute forecast slice, rain intensity ($mm/hr$) is superimposed on sub-catchment polygons derived from the 10m FABDEM terrain model `[RESEARCHED]`. Green-Ampt infiltration equations compute net surface runoff volume `[RESEARCHED]`.
3. **Directed Graph Hydraulic Inflow**: Surface runoff volumes are injected into corresponding inlet nodes (manholes) of the directed graph $G=(V,E)$ built via `PySWMM` `[RESEARCHED]`.
4. **Hydraulic Network Routing & Surcharge Calculation**: `PySWMM` executes 1D Dynamic Wave routing across all pipe edges. When conduit inflow exceeds $Q_{max}$ or downstream tailwater backs up, the solver calculates node surcharge volume. Overflow water volume ($m^3$) accumulates above the manhole rim into linked street surface storage basins, converting volume to water depth ($cm$) based on road surface cross-section geometry `[RESEARCHED]`.
5. **State Persistence & Spatial Map Mapping**: Street inundation depth predictions ($0\text{--}180\text{ minutes}$) are linked to OpenStreetMap road segment IDs (`osm_id`) and indexed into PostGIS and Redis `[ASSUMPTION]`.
6. **Dynamic Routing & Dashboard Render**:
   * *Dashboard*: Mapbox GL JS fetches GeoJSON vector tiles from FastAPI, styling road segments in real time (e.g., Green: $<5\text{cm}$, Yellow: $5\text{--}15\text{cm}$, Orange: $15\text{--}30\text{cm}$, Red: $>30\text{cm}$).
   * *Navigation API*: When an emergency vehicle requests a route from Point A to Point B, the FastAPI service queries Redis for predicted flooded road edges at the estimated time of arrival, temporarily increasing their travel cost in OSRM to generate a safe alternative route `[RESEARCHED]`.

## 13. AI/ML Justification

### 1. Optical Flow Precipitation Nowcaster (Rainymotion)
* **Purpose**: Generates 0–3 hour high-resolution precipitation nowcast grids from consecutive Doppler Weather Radar reflectivity scans `[RESEARCHED]`.
* **Model Type**: Computer Vision Optical Flow (Dense Farneback / Lucas-Kanade advection algorithm) `[RESEARCHED]`.
* **Input**: Past 3 consecutive radar reflectivity matrices ($Z$-grid array, e.g., $500 \times 500$ cells at 10-minute intervals).
* **Output**: Predicted reflectivity matrices for $t+15, t+30, \dots, t+180\text{ minutes}$.
* **Data Required**: Historical/live radar reflectivity images/arrays.
* **Why AI/Computer Vision is Preferable**: Pure numerical weather prediction (NWP) models take 1–3 hours to initialize and execute, making them useless for sub-3-hour rapid cloudburst nowcasts `[PS]`. Optical flow extrapolation runs in under 2 seconds `[RESEARCHED]`.
* **Evaluation Metric**: Critical Success Index (CSI), Structural Similarity Index (SSIM), Mean Absolute Error (MAE) against observed radar frames.
* **Failure Mode & Mitigation**: Rapid cell decay or unpredicted convective explosive growth (cloudburst onset). *Mitigation*: Fallback to persistence nowcast combined with AWS ground rain-gauge adjustment factors `[INFERENCE]`.
* **Human Oversight**: Meteorologist control room override interface to manually scale radar quantitative precipitation estimation (QPE) multipliers `[INFERENCE]`.

### 2. Explicit Non-AI / Physics-Based Decision
* **Underground Hydraulic Routing**: **AI/ML IS EXPLICITLY NOT USED HERE**. Solved deterministically using physical 1D St. Venant hydrodynamics via EPA-SWMM `[RESEARCHED]`.
  * *Reasoning*: Pure ML models (e.g., Regression trees or generic neural networks) cannot guarantee mass conservation (water volume in = water volume out + storage) and often produce unphysical backflow spikes when extrapolation boundaries are breached `[INFERENCE]`. Deterministic physics solvers provide 100% explainability for civil engineers and municipal authorities `[INFERENCE]`.

## 14. Data Architecture & Offline/Low-Network Design

### Database Schema (PostGIS)

```sql
-- Street Segments & Real-Time Inundation State
CREATE TABLE street_segments (
    osm_id BIGINT PRIMARY KEY,
    street_name VARCHAR(255),
    ward_id VARCHAR(50),
    geom GEOMETRY(LineString, 4326),
    surface_elevation_m FLOAT,
    max_safe_depth_cm FLOAT DEFAULT 15.0
);

-- Real-Time Inundation Prediction Time Series
CREATE TABLE street_inundation_predictions (
    prediction_id BIGSERIAL PRIMARY KEY,
    osm_id BIGINT REFERENCES street_segments(osm_id),
    forecast_timestamp TIMESTAMPTZ NOT NULL,
    lead_time_minutes INT CHECK (lead_time_minutes IN (0, 15, 30, 45, 60, 90, 120, 150, 180)),
    predicted_depth_cm FLOAT NOT NULL,
    risk_level VARCHAR(20) CHECK (risk_level IN ('SAFE', 'WATCH', 'WARNING', 'SEVERE')),
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

-- Drainage Graph Nodes (Manholes/Inlets)
CREATE TABLE drain_nodes (
    node_id VARCHAR(100) PRIMARY KEY,
    geom GEOMETRY(Point, 4326),
    rim_elevation_m FLOAT NOT NULL,
    invert_elevation_m FLOAT NOT NULL,
    max_depth_m FLOAT NOT NULL
);

-- Drainage Graph Edges (Conduits/Pipes)
CREATE TABLE drain_conduits (
    conduit_id VARCHAR(100) PRIMARY KEY,
    source_node VARCHAR(100) REFERENCES drain_nodes(node_id),
    target_node VARCHAR(100) REFERENCES drain_nodes(node_id),
    shape VARCHAR(50) DEFAULT 'CIRCULAR',
    geom GEOMETRY(LineString, 4326),
    diameter_m FLOAT NOT NULL,
    roughness_manning FLOAT DEFAULT 0.013
);

-- Geospatial Indexes
CREATE INDEX idx_street_geom ON street_segments USING GIST(geom);
CREATE INDEX idx_inundation_lookup ON street_inundation_predictions(osm_id, forecast_timestamp);
```

### Low-Network & Offline Synchronization Design
* **Vector Tile Caching**: The mobile navigation web client pre-downloads Mapbox Vector Tiles (MVT) for the target municipal boundary during high-bandwidth connectivity `[ASSUMPTION]`.
* **Lightweight Payload Protocol**: Instead of re-downloading entire geometries, the backend transmits *only* dynamic state updates over WebSockets/MQTT using Protocol Buffers or compact JSON arrays:
  `[[osm_id, predicted_depth_cm, risk_code], ...]`
  * *Payload Size*: $<15\text{ KB}$ for 5,000 street segments, enabling fast updates over degraded 2G/3G connections `[INFERENCE]`.
* **Local Offline Dynamic Routing**: The mobile app runs a lightweight local routing engine (or client-side A* algorithm on pre-loaded vector graphs), applying the cached depth array to recalculate routes when cellular signal drops `[INFERENCE]`.
