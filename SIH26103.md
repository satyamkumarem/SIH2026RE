## 1. Executive Snapshot

The Infrastructure & Project Monitoring Division (IPMD) under the Ministry of Statistics and Programme Implementation (MoSPI) monitors Central Sector Infrastructure Projects valued at ₹150 crore and above across 17 Central Ministries/Departments and 22 sectors [PS]. Historically monitored via the Online Computerised Monitoring System (OCMS) since 2006, the platform has been modernized into the PAIMANA (Project Assessment, Infrastructure Monitoring and Analytics for Nation-building) portal and its underlying PAIMANA-CRIP repository [PS, RESEARCHED]. As of April 2026, PAIMANA tracks 1,981 ongoing projects with an aggregate original cost of ~₹37.13 lakh crore, revised cost of ~₹42.78 lakh crore, and cumulative expenditure of ~₹20.36 lakh crore [PS]. Despite robust descriptive reporting, systematic time and cost overruns persist due to land acquisition, environmental clearances, utility shifting, and contractual delays [PS, RESEARCHED]. This dossier details an open-source, AI-powered Predictive Analytics, Early Warning, and Decision-Support System designed to transform PAIMANA from a descriptive portal into a predictive and prescriptive platform [PS]. The solution implements machine learning algorithms alongside econometric baselines, quantifies the explanatory power of existing Common Upload Form (CUF) fields versus exogenous variables, and provides explainable early warning risk scores and LLM-assisted project intelligence [PS, INFERENCE].

*   **Req-2.2 (Explicit) [PS]:** Aggregate financial baseline: Original cost ~₹37.13 lakh crore; Revised cost ~₹42.78 lakh crore; Cumulative expenditure ~₹20.36 lakh crore.

## 5. Constraints & Environment Realities

*   **Mandatory Open-Source Stack [PS]:** Proprietary software (e.g., SAP, Oracle, SAS, OpenAI API) is strictly prohibited by the problem statement [PS]. All components must use OSS licenses (Apache 2.0, MIT, BSD, GPL).
*   **Data Reporting Cadence [PS]:** Project updates on PAIMANA occur on a monthly reporting cycle [PS]. Models must operate on discrete monthly time-series snapshots rather than real-time sub-second streams [INFERENCE].
*   **Sectoral Diversity [PS, KNOWN]:** The platform tracks 22 distinct sectors (e.g., Road Transport vs Atomic Energy vs Telecommunications) [PS]. Cost structures and schedule dynamics differ fundamentally between a 50 km highway widening project and a nuclear power plant build [INFERENCE].
*   **Variable Data Completeness [PS, INFERENCE]:** Historical data across 2,000+ projects over 20 years contains missing fields, unaligned completion dates ("Zero Date" ambiguities), and qualitative text notes of varying depth [RESEARCHED, INFERENCE].
*   **G2G Deployment Security [KNOWN]:** Government hosting (NIC/GI Cloud - MeghRaj) mandates strict air-gapped deployment compatibility, zero external API dependency (e.g., self-hosted LLM), and compliance with CERT-In security guidelines [KNOWN, INFERENCE].
*   **Low-Bandwidth District Offices [KNOWN]:** Nodal officers in tier-3 cities or remote hill states operate under constrained network conditions, requiring lightweight dashboard payloads (<2MB initial load) and offline data entry capabilities [INFERENCE].

## 6. Research Questions

1.  **Statistical Baseline vs ML Superiority:** Do non-linear tree ensembles (LightGBM/XGBoost) or deep learning models achieve statistically significant lower RMSE/MAE in cost and time overrun prediction compared to classical Cox Proportional Hazards and ARIMA models?
2.  **CUF Feature Sufficiency:** What percentage of target variance ($R^2$) is explained strictly by Common Upload Form (CUF) parameters (financial expenditure velocity, physical progress %, milestone status) versus external exogenous indicators (Wholesale Price Index for cement/steel, district-level rainfall/monsoon severity, land acquisition litigation indices)?
3.  **Local LLM Performance on Administrative Text:** Can a 7B/8B open-source LLM quantized to 4-bit (INT4) running on standard server hardware accurately summarize unstructured monthly milestone delay notes without factual hallucination?
4.  **Early Warning Horizon:** How many months prior to actual financial or schedule failure can an automated early warning system detect high-risk status with a False Positive Rate (FPR) below 10%?
5.  **Explainability for Bureaucrats:** Does providing SHAP-based feature attribution increase policymaker trust and actionable intervention willingness compared to black-box risk scores?

## 9. Candidate Solution Approaches

### Approach 1: Classical Statistical & Econometric Forecasting
*   **Mechanism:** Fits parametric statistical models (ARIMA for monthly expenditure time-series, Cox Proportional Hazards for time-to-delay, Ordinary Least Squares / Ridge Regression for cost escalation).
*   **Required Data:** CUF financial expenditure history, milestone planned vs. actual dates.
*   **Architecture:** R / Python `statsmodels` pipeline executing batch periodic regression models.
*   **Pros:** High explainability, simple implementation, fast training, explicit confidence intervals.
*   **Cons:** Struggles with non-linear feature interactions, high-dimensional categorical delay reasons, and complex cross-sector dependencies.
*   **Hackathon Feasibility:** 10/10 | **Production Feasibility:** 6/10 (Too simplistic for policy decisions).

### Approach 2: ML-Centric Feature-Engineered Ensemble System (Recommended Core)
*   **Mechanism:** LightGBM / XGBoost Gradient Boosted Trees for cost/time overrun quantile regression and risk classification, paired with SHAP (SHapley Additive exPlanations) for driver analysis and a rule-based early warning engine.
*   **Required Data:** CUF fields + engineered features (financial burn rate velocity, physical vs. financial divergence, past contractor delay history) + exogenous macro indices (WPI).
*   **Architecture:** Python Scikit-Learn / LightGBM pipeline serving REST endpoints via FastAPI, visualized on a React dashboard.
*   **Pros:** Handles non-linear relationships, robust to missing data, superior prediction accuracy, fully explainable via SHAP, lightweight computation.
*   **Cons:** Requires structured tabular feature engineering; cannot directly process unstructured PDF document attachments without an added NLP layer.
*   **Hackathon Feasibility:** 9/10 | **Production Feasibility:** 9.5/10.

### Approach 3: Hybrid Multimodal AI Platform (ML + LLM RAG + Exogenous GIS Integration)
*   **Mechanism:** Combines Approach 2 (LightGBM + SHAP) for numeric/tabular predictions with a quantized open-source LLM (Llama-3.1-8B-Instruct / Qwen-2.5-7B) using Retrieval-Augmented Generation (RAG) over project text logs, plus PostGIS geospatial delay mapping.
*   **Required Data:** Full CUF database, monthly text progress notes, exogenous WPI/Rainfall data, GIS project shapefiles/coordinates.
*   **Architecture:** Microservices setup with PostgreSQL/pgvector, LightGBM inference container, Ollama/vLLM text inference engine, FastAPI backend, and React/Leaflet UI.
*   **Pros:** Fully satisfies ALL outcomes (a through i) of the problem statement, including the LLM Project Intelligence Assistant and exogenous variable analysis.
*   **Cons:** Higher architectural complexity, requires GPU acceleration for LLM inference during demonstration.
*   **Hackathon Feasibility:** 8.5/10 | **Production Feasibility:** 9/10.

## 10. Recommended Approach & Why

The recommended solution is **Approach 3 (Hybrid Multimodal AI Platform)** [INFERENCE].

### Justification
1.  **Direct Alignment with Explicit Deliverables:** The problem statement explicitly requires an LLM-enabled Project Intelligence Assistant (Outcome h), AI-powered Dashboard (Outcome g), CUF vs. non-CUF variable assessment (Technical Dimension c), and AI vs. Statistical comparison (Technical Dimension b) [PS]. Approach 1 lacks ML/LLM capabilities entirely, while Approach 2 misses the natural language intelligence assistant [INFERENCE].
2.  **Addressing Bureaucratic Needs:** Senior government stakeholders in MoSPI require actionable, explainable insights rather than opaque "black-box" scores [PS, INFERENCE]. Combining LightGBM's high numerical accuracy with SHAP explanations and an LLM that cites specific monthly progress notes provides complete auditability [INFERENCE].
3.  **Feasibility for a 4-6 Student Team:** The architecture cleanly splits into independent sub-modules: ML modeling, LLM/RAG pipeline, GIS backend, and React frontend, allowing 4-6 students to build concurrently [ASSUMPTION].

### Why Alternatives Were Rejected
*   **Pure Deep Learning (e.g., LSTM/Transformers for all tabular data):** Rejected due to high risk of overfitting on 1,981 monthly project snapshots, poor explainability for government auditors, and significantly higher computational overhead [INFERENCE].
*   **Proprietary API-based LLMs (e.g., OpenAI/Claude):** Explicitly violates the mandate to use 100% Open-Source Tools and Software [PS].

### Data Flow Narrative
1.  **Ingestion Phase:** Raw project records from monthly Flash Reports and CUF forms are ingested via `pdfplumber` and automated JSON parsers into PostgreSQL [INFERENCE]. Exogenous WPI commodity price data and regional rainfall indices are merged using state/district and month keys [INFERENCE].
2.  **Feature Engineering & Preprocessing:** The data engine computes derived metrics: Expenditure Velocity Ratio ($EVR = \frac{\text{Monthly Spend}}{\text{Planned Monthly Budget}}$), Financial-Physical Divergence Index ($FPDI = \text{Financial Progress \%} - \text{Physical Progress \%}$), and Slippage Velocity [INFERENCE].
3.  **Parallel Execution:**
    *   **ML Engine:** LightGBM models compute cost overrun (in ₹ Crores) and time overrun (in months), assigning a Composite Risk Index (0-100) [INFERENCE].
    *   **SHAP Explainer:** Generates local feature contribution values for every prediction, pinpointing the top 3 escalation drivers [INFERENCE].
    *   **Statistical Engine:** Runs baseline Cox Proportional Hazard and ARIMA models to dynamically output comparative benchmark metrics (RMSE, MAE) against the ML engine [INFERENCE].
    *   **LLM RAG Pipeline:** Monthly text delay notes are embedded using `bge-small-en-v1.5` into `pgvector`. Users can query the Llama-3.1 model for policy summaries [INFERENCE].
4.  **Presentation:** Results are pushed via FastAPI REST endpoints and WebSockets to the React frontend dashboard [INFERENCE].

## 13. AI/ML Justification

### 1. Cost & Time Overrun Prediction Engine
*   **Exact Problem Solved:** Predicts anticipated total cost escalation (in ₹ Crores) and schedule delay (in months) for any ongoing project [PS].
*   **Model Type:** Quantile Gradient Boosting Regressor (LightGBM) [INFERENCE].
*   **Input:** CUF fields (Original Cost, Current Revised Cost, Expenditure to date, Physical progress %, Original DOC, Elapsed Months) + Exogenous WPI indices [INFERENCE].
*   **Output:** Point estimate and 80% confidence interval for final cost and completion date [INFERENCE].
*   **Data Required:** Min. 500 historical project monthly snapshots [INFERENCE].
*   **Why AI Over Rules:** Project delays involve complex non-linear interactions between sector, financial velocity, physical progress divergence, and regional delays that static threshold rules cannot capture [INFERENCE].
*   **Evaluation Metric:** MAE (Mean Absolute Error) and RMSE (Root Mean Square Error) [INFERENCE].
*   **Failure Mode Handling:** Fallback to sector-average historical overrun percentage if project has <3 months of reporting history [INFERENCE].
*   **Human Oversight:** Model outputs marked as "Predictive Estimates"; official budget revisions require human committee approval [INFERENCE].

### 2. Cost Escalation Driver Analysis Engine
*   **Exact Problem Solved:** Identifies the precise root-cause factors contributing to a project's predicted risk [PS].
*   **Model Type:** TreeSHAP Causal Explainer [INFERENCE].

```sql
-- Core Schema Structure (PostgreSQL)

CREATE TABLE projects (
    project_id VARCHAR(50) PRIMARY KEY,
    project_name TEXT NOT NULL,
    ministry_name TEXT NOT NULL,
    sector_name TEXT NOT NULL,
    state_code VARCHAR(10),

    snapshot_id SERIAL PRIMARY KEY,
    project_id VARCHAR(50) REFERENCES projects(project_id),

    revised_cost_cr NUMERIC(12,2),
    expenditure_cum_cr NUMERIC(12,2),
    physical_progress_pct NUMERIC(5,2),
    anticipated_doc DATE,
    delay_reason_code VARCHAR(50), -- e.g., 'LAND_ACQUISITION', 'FOREST_CLEARANCE'
    unstructured_notes TEXT,
    data_source VARCHAR(20) DEFAULT 'CUF_API' -- 'CUF_API', 'MANUAL', 'SCRAPED'
);

CREATE TABLE predictions_history (
    pred_id SERIAL PRIMARY KEY,
    project_id VARCHAR(50) REFERENCES projects(project_id),
    model_version VARCHAR(20) NOT NULL,
    pred_month DATE NOT NULL,
    predicted_cost_cr NUMERIC(12,2),
    predicted_delay_months INT,
    composite_risk_score NUMERIC(5,2),
    top_driver_1 VARCHAR(100),
    top_driver_2 VARCHAR(100),
    cuf_only_explainability_pct NUMERIC(5,2)
);
```

### Low-Network & Offline Field Strategy
*   **Client-Side Caching:** The React UI utilizes `IndexedDB` via `Dexie.js` to store project metadata locally, enabling nodal officers in poor connectivity areas to view dashboard views offline [INFERENCE].
*   **Offline Data Entry & Sync Queue:** Field updates captured offline are saved in LocalStorage and automatically synced via Service Workers when connectivity is re-established, using optimistic locking (version timestamps) to handle conflicts [INFERENCE].
*   **Payload Optimization:** Gzip compression and JSON field stripping reduce API response payloads to <150KB per project query [INFERENCE].
