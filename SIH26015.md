## 1. Executive Snapshot

### Summary
The Department of Land Resources (DoLR), Ministry of Rural Development, oversees the Watershed Development Component of Pradhan Mantri Krishi Sinchayee Yojana (WDC-PMKSY 2.0) [KNOWN]. While millions of field-level geo-tagged photographs are collected via mobile applications like DRISHTI, they are currently treated primarily as static administrative proof rather than dynamic spatial intelligence [PS]. This dossier proposes **GeoSrishti-AI**, an integrated geospatial visualization and computer vision analytics platform designed to bridge ground-truth geo-coded imagery with 30m multi-spectral satellite observations (SRISHTI platform / Sentinel-2 / Landsat) [INFERENCE]. By combining spatial verification algorithms, automated land-use/cover change detection (NDVI, NDWI, SAVI), hydrological terrain analysis (DEM, slope, drainage density), and lightweight computer vision (YOLOv8 asset detection), the system transforms raw ground photos into verified, actionable watershed intelligence for planners, district officers, and national administrators [INFERENCE].

## 5. Constraints & Environment Realities

1. **Connectivity & Network Dead Zones**: Watershed intervention sites are located in remote rural, semi-arid, and hilly terrains where 4G/5G signal is frequently absent [KNOWN]. Mobile apps must store photo EXIF data and geospatial coordinates locally and sync lazily when connected [INFERENCE].
2. **Satellite Resolution Limits (30m Spatial Resolution)**: The problem statement explicitly anchors analysis to 30m spatial resolution satellite data (e.g., Landsat-8/9, Sentinel-2 resampled/downscaled, or ResourceSat-2 AWiFS) [PS]. Small watershed structures (e.g., a 5-meter wide check dam or farm pond) cannot be directly resolved in a single 30m pixel [INFERENCE]. The system must analyze local contextual signatures (e.g., surrounding NDWI wetness bloom, localized vegetation index uptick around the structure site) rather than expecting crisp pixel boundary detection of small concrete walls [INFERENCE].
3. **Device Constraints of Field Workers**: Field workers utilize low-to-mid tier Android smartphones (2GB-4GB RAM) [KNOWN]. Heavily complex AI inference or GIS rendering must be offloaded to cloud backends or executed via lightweight mobile quantized models (TensorFlow Lite / ONNX) [INFERENCE].
4. **Geographic Diversity**: India encompasses diverse hydro-geological zones (Deccan trap, Indo-Gangetic alluvium, Himalayan slopes, Rajasthan arid basins) [KNOWN]. Thematic map generation must accept regionally calibrated threshold parameters for soil and vegetation indices [INFERENCE].
5. **Data Standards Compliance**: Must comply with NDIS / NNRMS standards and ISRO Bhuvan spatial reference systems (EPSG:4326 / EPSG:3857) [RESEARCHED].

## 9. Candidate Solution Approaches

### Approach 1: Classical GIS Overlay & Rule-Based Heuristics (Traditional)
- **Mechanism**: Ingests geo-tagged photos into PostGIS. Generates standard buffer zones (e.g., 50m radius). Computes mean Sentinel-2 NDVI and NDWI within the buffer before and after the photo upload date using GDAL scripts.
- **Complexity**: Low.
- **Explainability**: 100% transparent math.
- **Cost**: Extremely low.
- **Limitations**: Fails to analyze the actual image contents (a photo of a rock could be uploaded at a check dam site and passed as valid).

### Approach 2: Deep Learning Image Vision + Cloud Satellite Processing (CV-Heavy)
- **Mechanism**: Uses a fine-tuned Vision Transformer (ViT) or YOLOv8 model trained on field assets to classify photos (Check Dam, Farm Pond, Gully Plug, Plantation, Terrace). Uses Google Earth Engine API to run cloud-based spatio-temporal change detection around verified GPS locations.
- **Complexity**: Medium-High.
- **Explainability**: High for vision (bounding boxes), Moderate for cloud ML models.
- **Cost**: Low to Moderate.
- **Limitations**: Dependent on GEE API rate limits during live presentation if cloud connection stutters.

### Approach 3: Hybrid Geo-AI Spatial Validation Engine (Recommended)
- **Mechanism**:
  1. **Ground Tier**: Lightweight YOLOv8 model detects asset types and condition flags in field photos.
  2. **Spatial Verification Tier**: PostGIS checks whether the photo's GPS coordinates and compass azimuth fall within a hydrologically valid zone (e.g., check dam within 30m of derived D8 stream network; farm pond within low-slope depression).
  3. **Satellite Analytics Tier**: Cloud-Optimized GeoTIFF (COG) pipeline computes 30m multi-spectral indices (NDVI, NDWI, SAVI, NDMI) across pre/post intervention dates.
  4. **Integrated Scoring**: Combines vision confidence + spatial validity score + satellite index delta into a single **Watershed Health & Verification Index (WHVI)**.
- **Complexity**: Moderate-High.
- **Explainability**: High (decomposed into visual score, spatial score, and spectral delta score).
- **Cost**: Low (open-source, self-hosted stack).
- **Hackathon Feasibility**: High (can run locally with pre-indexed COG tiles and FastAPI backend).
- **Production Feasibility**: High (scales horizontally via Docker/Kubernetes).

## 10. Recommended Approach & Why

### Selection
**Approach 3: Hybrid Geo-AI Spatial Validation Engine** is selected [INFERENCE].

### Justification
1. **Direct Problem Alignment**: The PS explicitly calls for *interpreting geo-coded images in relation to watershed characteristics and satellite-derived information* [PS]. Pure GIS overlay (Approach 1) ignores photo content, while pure CV (Approach 2) ignores terrain hydrology rules [INFERENCE].
2. **Robustness Against Fraud/Errors**: Field geo-tags can suffer from GPS drift or deliberate spoofing. By requiring the photo content (YOLOv8) to match the spatial hydrological location (D8 Stream Network) and satellite spectral response (NDWI/NDVI delta), the system ensures multi-tier validation [INFERENCE].
3. **Hackathon Demonstrability**: A student team can easily run YOLOv8 inference locally on sample photos, compute PostGIS spatial queries instantly, and render satellite change maps via GeoServer/Leaflet in real time without external API latency [INFERENCE].

### Why Alternatives Were Rejected
- **Approach 1 Rejected**: Does not perform true "interpretation of geo-coded images" as demanded by Requirement (b) [PS].
- **Approach 2 Rejected**: Over-relies on continuous cloud GEE API access, introducing external failure risks during hackathon judging and lacking strict hydrological spatial rules [INFERENCE].

### Step-by-Step Data Flow Narrative
1. **Photo Ingestion**: A field officer captures an asset photo using the app. The app attaches GPS metadata (latitude, longitude, elevation, timestamp, compass bearing) and pushes the JSON + JPEG payload to FastAPI backend [INFERENCE].
2. **AI Vision Classification**: The `Geo-Photo AI Service` runs YOLOv8 on the uploaded photo to identify structure type (e.g., `check_dam`, `farm_pond`, `plantation`) and structural state (`intact`, `silted`, `dry`, `overflowing`) with confidence scores [INFERENCE].
3. **Spatial Hydrological Validation**: The `Spatial Analysis Engine` queries PostGIS to cross-reference the photo coordinates with DEM-derived drainage layers. It computes:
   - Distance to nearest D8 stream line ($D_{stream}$)
   - Terrain slope angle ($\theta$)
   - Micro-watershed catchment ID [INFERENCE].
4. **Satellite Index Delta Extraction**: The `Satellite Index Pipeline` streams multi-temporal 30m Cloud-Optimized GeoTIFFs (Sentinel-2 / Landsat) for the watershed. It computes 50m-buffer zonal statistics before and after the photo timestamp:
   - $\Delta \text{NDVI} = \text{NDVI}_{\text{post}} - \text{NDVI}_{\text{pre}}$ (Vegetation growth)
   - $\Delta \text{NDWI} = \text{NDWI}_{\text{post}} - \text{NDWI}_{\text{pre}}$ (Surface water retention) [INFERENCE].
5. **Score Fusion & Visualization**: The backend calculates the **Watershed Health & Verification Index (WHVI)** and updates GeoServer. The web dashboard dynamically renders vector pins, satellite overlay layers, and interactive before/after swipe sliders [INFERENCE].

## 13. AI/ML Justification

### Component 1: Field Asset & Health Classifier (YOLOv8)
- **Purpose**: Automatically recognize physical watershed structures in field photos and detect damage or silting [INFERENCE].
- **Model Type**: Object Detection & Instance Segmentation (YOLOv8 medium/small) [INFERENCE].
- **Input**: Raw field photograph JPEG ($1024 \times 768$ or higher) [INFERENCE].
- **Output**: Bounding boxes, class labels (`check_dam`, `farm_pond`, `trench`, `gully_plug`, `afforestation`), confidence score, structural condition flag (`intact`, `silted`, `eroded`) [INFERENCE].
- **Data Required**: ~1,500 annotated field images across Indian watershed topographies [INFERENCE].
- **Why AI is Preferable**: Human manual audit of 1,000,000+ uploaded Drishti photos is impossible; simple color/edge algorithms fail under varying field lighting and vegetation camouflage [INFERENCE].
- **Evaluation**: Mean Average Precision (mAP@0.5) $> 85\%$ [INFERENCE].
- **Failure Mode**: Poor lighting or extreme close-up photos causing misclassification. System flags confidence $<0.60$ for human review [INFERENCE].
- **Human Oversight**: District Project Manager gets an "Unverified/Flagged" queue to approve low-confidence AI detections [INFERENCE].

### Component 2: Spatio-Temporal Anomaly Detector (Isolated Forest / Z-score Heuristic)
- **Purpose**: Flag fraudulent or mislocated photo uploads where claimed structure impact contradicts satellite spectral physics [INFERENCE].
- **Model Type**: Classical Anomaly Detection / Rule-Based Multi-Criteria Scoring [INFERENCE].
- **Input**: GPS location, photo azimuth, $\Delta\text{NDWI}$, $\Delta\text{NDVI}$, distance to DEM stream line [INFERENCE].
- **Output**: Anomaly Score ($0-100\%$) and Flag (`Location Mismatch`, `Implausible Spectral Response`) [INFERENCE].
- **Data Required**: Historical Sentinel-2 time series + PostGIS stream vectors [INFERENCE].
- **Why AI/ML is Preferable**: Captures non-linear relationships between slope, stream order, and satellite index change [INFERENCE].
- **Evaluation**: False Positive Rate $< 5\%$ on test benchmark [INFERENCE].
- **Failure Mode**: Seasonal drought causing low NDWI despite valid check dam presence. System incorporates rainfall data (TRMM/CHIRPS) to prevent false alerts [INFERENCE].
- **Human Oversight**: Mandatory manual review before rejecting any field worker submission [INFERENCE].

### Where AI Should NOT Be Used
- **Stream Network Delineation & Catchment Masking**: AI/Deep Learning should **NOT** be used for basic hydro-delineation. Classical, deterministic hydrologic models (D8 flow direction, Deterministic 8-neighbor flow accumulation on DEM via WhiteboxTools/GDAL) are 100% mathematically precise, fast, and physically consistent [INFERENCE].

## 14. Data Architecture & Offline/Low-Network Design

### Database Schema (PostgreSQL/PostGIS SQL Excerpt)
```sql
-- Micro-Watershed Boundaries
CREATE TABLE micro_watersheds (
    watershed_id VARCHAR(32) PRIMARY KEY,
    name VARCHAR(100),
    district VARCHAR(100),
    state VARCHAR(100),
    area_ha NUMERIC(10,2),
    geom GEOMETRY(MultiPolygon, 4326)
);

-- Geo-Coded Field Photos
CREATE TABLE geo_photos (
    photo_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    watershed_id VARCHAR(32) REFERENCES micro_watersheds(watershed_id),
    worker_id VARCHAR(50),
    captured_at TIMESTAMP WITH TIME ZONE,
    gps_lat NUMERIC(10,7),
    gps_lng NUMERIC(10,7),
    azimuth_deg NUMERIC(5,2),
    altitude_m NUMERIC(7,2),
    location GEOMETRY(Point, 4326),
    image_url TEXT,
    ai_asset_type VARCHAR(50),
    ai_confidence NUMERIC(4,3),
    ai_condition VARCHAR(50),
    is_spatially_valid BOOLEAN,
    whvi_score NUMERIC(5,2),
    sync_status VARCHAR(20) DEFAULT 'SYNCED'
);

-- Spatial Indexing
CREATE INDEX idx_geo_photos_loc ON geo_photos USING GIST(location);
CREATE INDEX idx_watershed_geom ON micro_watersheds USING GIST(geom);
```

### Offline & Synchronization Strategy
1. **PWA Local Storage**: Field app uses IndexedDB / SQLite (via Capacitors/PWA) to store offline map tiles (Vector PBFs for target micro-watershed) and pending photo submissions [INFERENCE].
2. **Compress-On-Capture**: High-res camera photos ($12\text{MP}+$) are locally downsampled to $1920 \times 1080$ JPEG ($80\%$ quality) with EXIF metadata preserved, reducing upload size from $\sim 5\text{MB}$ to $\sim 400\text{KB}$ [INFERENCE].
3. **Background Sync & Retry**: Web API client registers a Service Worker with Exponential Backoff retry strategy. When 2G/3G connectivity is restored, pending queue uploads automatically [INFERENCE].
4. **Conflict Resolution**: Last-Write-Wins (LWW) based on client timestamp, with cryptographic hash comparison to prevent duplicate photo uploads [INFERENCE].

## 15. Security, Privacy & Governance

1. **Personal & Location Data Protection**: Field worker identity and exact capture coordinates are stored with Role-Based Access Control (RBAC). Location coordinates are obfuscated/rounded on public-facing citizen views to protect field worker privacy [INFERENCE].
2. **Image Integrity & Anti-Spoofing**: EXIF timestamp and GPS tags are validated against device hardware sensors. Uploaded images undergo perceptual hashing (pHash) to detect duplicated/re-uploaded web photos [INFERENCE].
3. **Authentication & Authorization**: JWT-based OAuth2 authentication. Roles: `Field_Worker`, `PIA_Officer`, `SLNA_Admin`, `Public_Auditor` [INFERENCE].
4. **Data Ownership & Regulatory Compliance**: All spatial data and derived thematic maps belong to Department of Land Resources (DoLR), MoRD [PS]. Outputs produced during hackathon are strictly tagged as **Prototype Demonstrations** and require independent field validation prior to policy enforcement [INFERENCE].
