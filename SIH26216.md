## 9. Candidate Solution Approaches

### Approach 1: Microcontroller-Centric IoT Soundbox & Printer (ESP32-S3 + Modules)
*   **Mechanism**: ESP32-S3 microcontroller directly driving an SPI TFT touchscreen, PN532 NFC reader, UART thermal printer, and DFPlayer Mini / I2S DAC speaker [RESEARCHED].
*   **Required Data**: Pre-loaded audio MP3s, static QR codes, lightweight text data.
*   **Architecture**: Pure embedded C++ (FreeRTOS / ESP-IDF).
*   **Complexity**: Low.
*   **Cost**: Very Low (~₹3,500 – ₹5,000).
*   **Explainability**: High.
*   **Scalability**: Medium.
*   **Hackathon Feasibility**: Extremely High (easy to wire and code in 48 hours).
*   **Production Feasibility**: High for simple payment/printing tasks, but **Infeasible for Computer Vision AI** [INFERENCE].
*   **Risks**: Limited RAM/flash prevents on-device AI vision models or complex multi-sector GUIs [INFERENCE].

### Approach 2: SBC-Centric Edge AI Kiosk (Raspberry Pi 5 / Jetson Orin Nano + USB Peripherals)
*   **Mechanism**: Single-Board Computer (SBC) running Linux (Ubuntu/Raspberry Pi OS), handling OpenCV/YOLO edge vision, Python Pygame/Qt GUI, thermal printing via CUPS/USB, and WebSockets/MQTT networking [RESEARCHED].
*   **Required Data**: Retail object detection dataset (YOLOv8 nano models), regional audio streams, local database.
*   **Architecture**: Monolithic Linux Python/C++ application.
*   **Complexity**: Medium.
*   **Cost**: Medium (~₹12,000 – ₹16,000).
*   **Explainability**: High.
*   **Scalability**: High.
*   **Hackathon Feasibility**: High (rich Python software libraries).
*   **Production Feasibility**: High for smart kiosks, but high power consumption for battery-only standby [INFERENCE].
*   **Risks**: Software crash risks on Linux OS if power is abruptly cut without proper shutdown [INFERENCE].

### Approach 3: Hybrid Dual-Core Edge Architecture (SBC Linux + ESP32 MCU Co-Processor) — RECOMMENDED
*   **Mechanism**: A Raspberry Pi 5 / Jetson Orin Nano serves as the **High-Level Compute Engine** (running Vision AI, Multilingual Voice, sector GUIs, and local SQLite), connected via UART/USB to an **ESP32-S3 Real-Time I/O Controller** handling low-level hardware interrupts (NFC tap detection, thermal printer pulsing, battery management, and audio soundbox playback) [ASSUMPTION].
*   **Required Data**: Edge YOLOv8 vision models, regional audio assets, SQLite sector schemas, offline UPI cryptographic tokens.
*   **Architecture**: Dual-layer distributed edge architecture.
*   **Complexity**: Medium-High.
*   **Cost**: Medium (~₹10,500 – ₹14,000).
*   **Explainability**: High.
*   **Scalability**: Very High.
*   **Hackathon Feasibility**: High (division of labor: 2 students on ESP32 firmware, 2 on SBC Python/AI, 2 on Web/Backend & Enclosure).
*   **Production Feasibility**: Highest (combines real-time hardware safety with rich edge AI capability) [INFERENCE].
*   **Risks**: Inter-processor UART communication protocol bugs if frame headers are not strictly validated [INFERENCE].

## 10. Recommended Approach & Why

### Selection: Hybrid Dual-Core Edge Architecture (Approach 3)
We select **Approach 3: Hybrid Dual-Core Edge Architecture** as the optimal solution [ASSUMPTION].

### Why Alternatives Were Rejected
1.  **Approach 1 (ESP32-S3 Only)** was rejected because while it is extremely cheap, it cannot run real-time computer vision models (e.g., YOLOv8 visual checkout for retail) or complex multi-language voice models required to make a compelling SIH hardware innovation across all 4 tertiary sectors [INFERENCE].
2.  **Approach 2 (SBC Linux Only)** was rejected because direct Linux control of low-level pulse timing for thermal printers, NFC timing, and power management creates system instability during Linux OS load spikes or sudden power outages [INFERENCE].

### Why Approach 3 Wins
*   **Separation of Concerns**: The ESP32-S3 guarantees instant boot (<1 second) for payment alerts and NFC reading, while the SBC boots Linux in the background to handle heavy UI and Vision AI tasks [ASSUMPTION].
*   **Multi-Sector Versatility**: The same hardware unit runs 4 distinct software operational profiles:
    *   *Hospitality Mode*: Self-check-in, room key pass writer, receipt printer.
    *   *Financial Services Mode*: Micro-ATM token dispenser, offline payment audio box, biometric verification UI.
    *   *Entertainment Mode*: Rapid ticket scanner, thermal wristband printer, crowd entry gate trigger.
    *   *Retail Mode*: Vision AI object scanner for camera-based automatic cart checkout and tap-and-pay [INFERENCE].

### Data-Flow Narrative
1.  **User Interaction Initiated**: A user approaches the OmniServe-Edge terminal. The camera module detects user presence via lightweight motion detection.
2.  **Sector-Specific Input**:
    *   *Retail*: User places items under the camera. SBC runs YOLOv8-nano to visually identify items, updating the cart on the touch display in real time.
    *   *Hospitality*: Guest enters booking ID or scans a QR code; SBC verifies against local SQLite DB and commands ESP32-S3 to print room access card and print receipt.
    *   *Financial Services / Entertainment*: User selects micro-transaction or ticket printing; enters PIN or scans NFC pass.
3.  **Payment & Offline Transaction Processing**:
    *   User selects payment mode (NFC UPI Lite / Dynamic QR).
    *   For NFC: The user taps their phone/card against the PN532 module. The ESP32-S3 validates the offline HMAC token locally per RBI/NPCI guidelines [RESEARCHED].
    *   ESP32-S3 triggers the I2S audio amplifier, announcing: *"Payment of 150 Rupees Received Successfully"* in the configured regional language [RESEARCHED].
4.  **Physical Receipt Printing & Audit Logging**:
    *   ESP32-S3 sends ESC/POS raster commands over UART to the internal thermal printer, issuing a physical slip/token [ASSUMPTION].
    *   Transaction details are recorded with cryptographic timestamps in the local encrypted SQLite DB.
5.  **Background Cloud Sync**:
    *   When Wi-Fi/4G connection is detected, a background daemon syncs local ledger logs to the central FastAPI cloud server via HTTPS/WebSockets [INFERENCE].

## 13. AI/ML Justification

### 1. Visual Object Detection (Retail Self-Checkout Profile)
*   **Purpose**: Identify unpacked or packaged retail items placed on the kiosk scanner bed without requiring manual barcode alignment.
*   **Model Type**: YOLOv8-Nano quantized to INT8 precision.
*   **Input**: Live 1080p video stream from USB/MIPI camera (cropped ROI).
*   **Output**: Class label (e.g., "Bisk Farm Biscuit 100g") and confidence score (>0.85).
*   **Data Required**: 500 images per item class under varied lighting conditions.
*   **Why AI is Preferable**: Barcode scanning requires manual user orientation and fails when labels are torn or wrinkled; vision AI enables instant multi-item visual recognition [RESEARCHED].
*   **Evaluation Metric**: Mean Average Precision (mAP@0.5) and inference latency (<200ms).
*   **Failure Mode Handling**: If confidence is <0.80, prompt user on screen to scan standard 1D barcode or select item manually.
*   **Human Oversight**: Merchant store attendant override button on UI.

### 2. Regional Spoken Language Voice Guidance
*   **Purpose**: Provide spoken instructions and accept basic spoken voice commands in Hindi/English for low-literacy users across Hospitality and Micro-Banking.
*   **Model Type**: Offline Vosk / PocketSphinx STT keyword spotter + pre-rendered WAV TTS files.
*   **Input**: Audio stream from USB directional microphone.
*   **Output**: Command ID (e.g., `CMD_CHECKIN`, `CMD_PRINT_BALANCE`).
*   **Data Required**: Speech corpus of key sector command phrases.
*   **Why AI is Preferable**: Touchscreen menus alone alienate non-literate or elderly users in rural/Tier-3 settings [KNOWN].
*   **Evaluation Metric**: Word Error Rate (WER < 10% on key phrases).
*   **Failure Mode Handling**: Fallback to visual touch icons on screen if audio input is unclear after 2 attempts.
*   **Human Oversight**: Touchscreen active at all times.

### Explicit Exclusion: Where AI MUST NOT Be Used
*   **Payment Authorization & Cryptographic Validation**: AI models MUST NOT be used for payment validation, transaction approval, or financial ledger accounting [INFERENCE]. Payment transactions rely strictly on deterministic RSA/HMAC cryptographic signatures, official RBI/NPCI Lite protocols, and exact arithmetic rules [RESEARCHED].

## 14. Data Architecture & Offline/Low-Network Design

### Schema Design (SQLite Local Storage)

```sql
-- Sector Operational Profile Configuration
CREATE TABLE terminal_config (
    terminal_id TEXT PRIMARY KEY,
    sector_mode TEXT CHECK(sector_mode IN ('HOSPITALITY', 'FINANCIAL', 'ENTERTAINMENT', 'RETAIL')),
    merchant_name TEXT NOT NULL,
    default_language TEXT DEFAULT 'HI',
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Local Product / Service Catalog
CREATE TABLE catalog_items (
    item_id TEXT PRIMARY KEY,
    item_name TEXT NOT NULL,
    price_paisa INTEGER NOT NULL,
    vision_class_id INTEGER,
    barcode_sku TEXT
);

-- Offline Transaction Ledger (RBI 24-Hour Reconciliation Compliant)
CREATE TABLE offline_transactions (
    txn_id TEXT PRIMARY KEY,
    amount_paisa INTEGER NOT NULL,
    payment_mode TEXT CHECK(payment_mode IN ('UPI_LITE_NFC', 'DYNAMIC_QR', 'CASH_TOKEN')),
    status TEXT CHECK(status IN ('PENDING_SYNC', 'SYNCED', 'FAILED')),
    hmac_signature TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    synced_at TIMESTAMP
);
```

### Local Storage, Caching & Synchronization Strategy
*   **Local Ledger**: All payment confirmations, hotel check-ins, and ticket issuances are written immediately to the local encrypted SQLite database (`WAL` mode enabled for atomic writes) [ASSUMPTION].
*   **Sync Daemon**: A background Python daemon checks network interface status every 30 seconds [ASSUMPTION]. When network is restored, pending records from `offline_transactions` are posted in batches of 20 to the central cloud API [ASSUMPTION].
*   **Conflict Resolution**: Server timestamp authority rules apply [ASSUMPTION]. In the event of duplicate offline transaction IDs, the server verifies the unique cryptographic HMAC signature generated by the terminal's hardware key [RESEARCHED].
*   **Bandwidth Reduction**: Image data is NEVER transmitted over cellular sync [INFERENCE]. Only compact JSON payloads (<1 KB per transaction) are transmitted during sync cycles.

## 15. Security, Privacy & Governance

*   **Personal Data Protection (DPDP Act 2023 Compliance)**: The system processes video frames strictly in volatile RAM memory for real-time vision inference [RESEARCHED]. No raw customer facial images or camera feeds are saved to permanent disk storage, adhering to data minimization mandates [RESEARCHED].
*   **Location Data Security**: Terminal GPS/Cell Tower location tags are signed cryptographically with every transaction batch to prevent physical kiosk tampering or unauthorized relocation [INFERENCE].
*   **Authentication & Access Control**: Merchant administrative access requires a two-factor approach: physical admin NFC keycard tap + 6-digit PIN entry on the terminal hardware [ASSUMPTION].
*   **Hardware Encryption**: Sensitive API keys and offline cryptographic HMAC seeds are stored inside the ESP32-S3's eFuse flash memory with hardware read-protection enabled [RESEARCHED].
*   **Audit & Governance**: The terminal maintains an append-only cryptographic transaction log. Per RBI guidelines, offline transactions must reconcile within 24 hours of reconnecting [RESEARCHED].
