## 1. Executive Snapshot

### Summary
The Ministry of Earth Sciences (MoES) and National Centre for Polar and Ocean Research (NCPOR) operate two active, year-round research stations in Antarctica: **Maitri** (commissioned 1989 in Schirmacher Oasis) and **Bharati** (commissioned 2012 in Larsemann Hills, ~3,000 km apart) [KNOWN]. Remote management of these polar habitats is critically constrained by harsh weather, extreme isolation, strict fuel budgets, and severely limited satellite bandwidth (~4 MHz SATCOM links) [RESEARCHED]. This dossier proposes **PolarTwin**, an edge-native, hybrid cloud-edge Digital Twin framework designed specifically for Maitri and Bharati [INFERENCE]. PolarTwin combines an offline-autonomous Edge Twin Gateway at each station with an interactive 3D WebGL (Three.js/glTF) spatial visualizer at NCPOR Headquarters (Vasco da Gama, Goa) [ASSUMPTION]. Using protocol buffers (Protobuf) over compressed MQTT/HTTP store-and-forward sync, the framework unifies four core pillars: facility infrastructure, Combined Heat and Power (CHP) microgrid energy, seasonal ship/air cargo logistics, and external environmental feeds [INFERENCE]. A 4–6 student hackathon team can realistically deliver a functional WebGL 3D spatial twin, simulated IoT telemetry stream, offline sync engine, and predictive anomaly model within the SIH timeframe [ASSUMPTION].

## 5. Constraints & Environment Realities

1. **Satellite Connectivity & Bandwidth Limits**:
   - Stations rely on C-band / VSAT dedicated satellite channels (~4 MHz bandwidth) established via SAC/ISRO [RESEARCHED].
   - Round-trip latency ranges from 600ms to over 1200ms; solar blackouts and severe geomagnetic storms cause complete connection drops lasting hours or days [RESEARCHED].
   - *Constraint*: Raw streaming of high-frequency telemetry or live 3D mesh rendering over the network is impossible. All 3D models must be client-side cached; data sync must be compressed and delta-only [INFERENCE].

2. **Physical Infrastructure & Power**:
   - Bharati is powered by 3 CHP units (100 kVA each) running on Aviation Turbine Fuel (Jet A-1/ATF) with a ~300,000L fuel farm [RESEARCHED].
   - Maitri relies on diesel power units in Schirmacher Oasis [RESEARCHED].
   - *Constraint*: Power loss in winter (-40°C to -80°C wind chill) causes life-support failure within hours. Edge gateways must run on low-power, uninterruptible power circuits (UPS backed) [INFERENCE].

3. **Logistics & Resupply Window**:
   - Sea resupply occurs once per year (Dec–March navigation window) via chartered icebreakers [RESEARCHED]. Air resupply occurs via DROMLAN IL-76 flights landing on blue ice runways [RESEARCHED].
   - *Constraint*: Spare parts and hardware replacements take up to 12 months to arrive if missing from inventory [INFERENCE].

4. **Operating Personnel & On-Site Skill**:
   - Wintering crew (~24–40 staff per station) includes technical staff from contractors (OMRC) and scientists [RESEARCHED].
   - *Constraint*: UX must be simple, low-overhead, and functional without requiring deep software engineering expertise on-site [INFERENCE].

## 10. Recommended Approach & Why

### Selected Solution
**Approach 2: Edge-Native Hybrid Digital Twin with Lightweight Binary Delta Synchronization (PolarTwin)** [INFERENCE].

### Justification
1. **Satellite Autonomy**: Antarctic stations frequently experience multi-day satellite blackouts due to severe weather or solar storms [RESEARCHED]. Approach 2 deploys an Edge Twin Gateway on-site at Maitri and Bharati that stores all high-frequency IoT data locally in a time-series database (TimescaleDB / SQLite) and maintains the station's local operational twin independently of internet connectivity [INFERENCE].
2. **Bandwidth Efficiency**: Rather than streaming raw JSON strings over the limited 4 MHz C-band SATCOM link, the Edge Sync Gateway serializes state changes using Protocol Buffers (Protobuf) and Zstandard compression [INFERENCE]. Data updates are sent in small batch updates (every 30–60 seconds, ~2–5 KB payload size), reducing satellite bandwidth consumption by up to 90% [INFERENCE].
3. **Spatial Context & User Experience**: By using client-side WebGL (Three.js) loaded with low-polygon glTF 3D models of Maitri and Bharati, the 3D rendering happens locally in the user's browser [INFERENCE]. Telemetry updates dynamically alter 3D object properties (e.g., generator color changes to red during heat anomaly, thermal gradients mapped on pipe meshes), offering immediate visual diagnostics for both local engineers and HQ leadership in Goa [INFERENCE].

### Why Alternatives Were Rejected
- **Approach 1 (Cloud-Centric WebGL Twin)** was rejected because streaming continuous raw telemetry directly to the cloud relies on uninterrupted broadband, which does not exist in Antarctica [RESEARCHED]. Satellite link drops would leave local operators blind [INFERENCE].
- **Approach 3 (Minimalist 2D SCADA Dashboard)** was rejected because it fails to deliver a true *Digital Twin framework* as explicitly required by the problem statement [PS]. Textual/2D charts lack spatial awareness—making it difficult to locate physical assets (e.g., identifying which specific container module or HVAC duct is failing inside Bharati's 3-story complex) [INFERENCE].

### Data Flow Narrative

1. **Ingestion Step**: Physical sensors across Bharati (e.g., CHP generator thermocouples, fuel level transmitters, HVAC airflow sensors) broadcast readings via Modbus TCP / OPC UA to the local station **EMQX Edge MQTT Broker** [INFERENCE].
2. **Edge Processing & Local Storage**: The local station **Edge Gateway** ingests MQTT messages, validates sanity bounds, writes raw high-frequency records (1 Hz) into the local **SQLite / TimescaleDB**, and evaluates local safety rules [INFERENCE].
3. **Local Twin Rendering**: Local station engineers access the station PWA dashboard over LAN; Three.js renders the 3D model, binding local telemetry directly to 3D meshes without touching the internet [INFERENCE].
4. **Binary Compression & Sync**: The **Edge Sync Engine** aggregates 1-minute averaged telemetry, serializes it into **Protocol Buffer (Protobuf)** packets, compresses the payload using Zstandard, and queues it in a store-and-forward SQLite ring buffer [INFERENCE].
5. **Satellite Transmission**: When SATCOM connection is active, the queue flushes compressed packets over HTTPS/MQTT to the **NCPOR Central Cloud Server** in Goa [INFERENCE]. If the link drops, packets safely accumulate on the edge gateway for up to 30 days [INFERENCE].
6. **Central Twin Visualization**: The cloud server deserializes updates, updates the **PostgreSQL/TimescaleDB** master store, and pushes state deltas to HQ browser consoles via WebSockets, instantly updating the 3D Digital Twin model in Goa [INFERENCE].

## 13. AI/ML Justification

### AI Component 1: Anomaly Detection for CHP Power & HVAC Systems

1. **Purpose**: Detect subtle mechanical degradation (e.g., fuel injector clogging, coolant leaks, bearing wear) in Bharati's 3x 100 kVA CHP units before physical breakdown occurs [RESEARCHED].
2. **Model Type**: Isolation Forest / Autoencoder (Unsupervised Anomaly Detection) [INFERENCE].
3. **Input**: Exhaust gas temperature, oil pressure, vibration levels, kVA output load, fuel flow rate [RESEARCHED].
4. **Output**: Anomaly risk score (0.0 to 1.0) and identified contributing sensor features [INFERENCE].
5. **Data Required**: Historical 1-minute sensor telemetry from generator runs (or simulated baseline specs) [ASSUMPTION].
6. **Why AI is Preferable**: Fixed threshold rules miss complex multi-variable drift (e.g., normal temperature at high load is abnormal at low load) [INFERENCE].
7. **Evaluation**: Precision-Recall AUC on historical test datasets containing injected fault patterns [INFERENCE].
8. **Failure Mode**: False positives trigger unnecessary inspections; false negatives lead to equipment breakdown [INFERENCE].
9. **Human Oversight**: High-risk alerts prompt station engineers to conduct physical checks; **no automated shutdown is triggered by AI alone** [INFERENCE].

### AI Component 2: Fuel Consumption & Stock Depletion Forecaster

1. **Purpose**: Forecast Jet A-1 / ATF fuel reserve burn-down rates based on predicted winter ambient temperatures and station heat load [RESEARCHED].
2. **Model Type**: Ridge Regression / XGBoost Time-Series Forecaster [INFERENCE].
3. **Input**: Forecasted ambient temperature, wind chill index, station occupancy count, active CHP unit state [RESEARCHED].
4. **Output**: Predicted daily fuel consumption (liters/day) and estimated days until critical fuel threshold [INFERENCE].
5. **Data Required**: Weather forecast feeds, historical daily fuel usage logs [ASSUMPTION].
6. **Why AI is Preferable**: Fuel usage varies non-linearly with external blizzard conditions and thermal losses [INFERENCE].
7. **Evaluation**: Mean Absolute Error (MAE in liters/day) against actual fuel tank drop readings [INFERENCE].
8. **Failure Mode**: Underestimating fuel consumption could risk winter fuel depletion [INFERENCE].
9. **Human Oversight**: Logistics team uses predictions to plan annual ship cargo volumes; actual tank levels are verified manually via DIP stick / float sensors weekly [RESEARCHED].

### Explicit Non-AI Boundaries
- **Safety Interlocks & Emergency Tripping**: Circuit breaker trips, fire suppression release, and engine emergency stops MUST rely exclusively on hardcoded, deterministic PLC rules (IEC 61131-3) and physical hardware relays. **AI/ML shall NOT have direct write access to safety shutdown controls.** [INFERENCE]

    longitude DOUBLE PRECISION NOT NULL,
    elevation_m REAL,
    status VARCHAR(32) DEFAULT 'OPERATIONAL'
);

-- Assets (Digital Twin Components)
CREATE TABLE assets (
    asset_id VARCHAR(32) PRIMARY KEY, -- e.g., 'BHR-CHP-01', 'MTR-HVAC-02'
    station_id VARCHAR(16) REFERENCES stations(station_id),
    asset_name VARCHAR(64) NOT NULL,
    category VARCHAR(32) NOT NULL, -- 'ENERGY', 'INFRASTRUCTURE', 'LOGISTICS'
    mesh_node_name VARCHAR(64), -- Target 3D Object ID in glTF model

);

CREATE TABLE telemetry (
    time TIMESTAMPTZ NOT NULL,
    asset_id VARCHAR(32) REFERENCES assets(asset_id),
    metric_name VARCHAR(32) NOT NULL, -- 'temperature', 'power_kw', 'fuel_flow'
    val DOUBLE PRECISION NOT NULL,
    quality_code INT DEFAULT 1 -- 1=Good, 0=Degraded/Simulated
);

CREATE TABLE sync_queue (
    queue_id BIGSERIAL PRIMARY KEY,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    payload_protobuf BYTEA NOT NULL,
    retry_count INT DEFAULT 0,
    synced BOOLEAN DEFAULT FALSE
);

### Offline & Low-Network Synchronization Strategy

```
  Station Local Network (LAN)              SATCOM Uplink               NCPOR Cloud (Goa)
+-----------------------------+        +-------------------+        +---------------------+
| Local Sensors -> MQTT Broker|        |  4 MHz C-Band Link|        | Central Cloud Sync  |
|              |              |        |   High Latency    |        |       Receiver      |
|              v              |        |  Periodic Drops   |        +----------+----------+
|      Local Edge Gateway     |        +---------+---------+                   |
|  (SQLite Store-and-Forward) |                  |                             v
|              |              |  Protobuf Batch  |                   Central TimescaleDB
|    [Queue Pending Records]  +----------------->+                   & WebSocket Server
+-----------------------------+ (When Link Up)   +-----------------------------+
```

1. **Local Ring Buffer**: The edge gateway writes all high-frequency telemetry into SQLite. Disk storage is managed via a rolling ring buffer (retaining 30 days of raw data) [INFERENCE].
2. **Delta Encoding & Compression**: Telemetry records are grouped into 1-minute averaged bundles. Floating point values are delta-encoded (transmitting differences between consecutive readings) and serialized into binary Protobuf payloads [INFERENCE].
3. **Store-and-Forward Queue**: Packets enter the `sync_queue` table. A background daemon attempts transmission to the cloud endpoint [INFERENCE].
4. **Exponential Backoff & Chunking**: If the SATCOM link is down, packets accumulate safely. Upon reconnect, the engine sends historical chunks in chronological batches, capping bandwidth consumption to 15 kbps so essential station voice/data communications are not degraded [INFERENCE].
