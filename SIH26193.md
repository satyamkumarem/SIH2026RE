## 1. Executive Snapshot

This dossier presents a comprehensive technical, architectural, and strategic breakdown for Problem Statement **SIH26193** under the Smart India Hackathon (SIH) 2026. The objective is to design and implement an end-to-end, offline-first agricultural intelligence and post-harvest management ecosystem [INFERENCE]. India loses over ₹1.53 trillion (USD 18.5 billion) annually due to post-harvest handling, storage, and transport inefficiencies across 54 major crops [RESEARCHED]. This system bridges the gap between primary crop cultivation advisory and secondary micro-processing value addition [INFERENCE]. By combining computer-vision-based produce grading, real-time market price intelligence from Agmarknet/eNAM, and micro-processing advisory aligned with the Pradhan Mantri Formalisation of Micro Food Processing Enterprises (PMFME) scheme, the proposed platform empowers smallholder farmers and Farmer Producer Organizations (FPOs) to minimize perishability losses and maximize income realization [INFERENCE].

## 5. Constraints & Environment Realities

1. **Connectivity Realities:**
   * Rural India often faces intermittent 2G/3G networks or zero connectivity in farms/mandis [KNOWN].
   * *Architectural Constraint:* The mobile app MUST work offline for core functions (produce logging, offline CV quality scoring using local ONNX model, viewing saved advisories) and auto-sync when network is restored [INFERENCE].

2. **Device Hardware Constraints:**
   * Target users own low-end Android smartphones (2GB–4GB RAM, entry-level ARM processors, limited storage) [KNOWN].
   * *Architectural Constraint:* Mobile app payload must be under 35 MB; ML models must be quantized (TFLite/ONNX float16/int8 under 15 MB) [INFERENCE].

3. **Language & Digital Literacy:**
   * Over 70% of rural producers prefer regional languages (Hindi, Marathi, Telugu, Tamil, Kannada, Bengali, Punjabi, etc.) and voice interaction over dense textual UI [KNOWN].
   * *Architectural Constraint:* UI must be icon-driven with voice input/output support via Web Speech API or Bhashini integration [INFERENCE].

4. **Power & Field Operating Conditions:**
   * Frequent power outages in rural areas; high ambient sunlight and dust during field usage [KNOWN].
   * *Architectural Constraint:* High-contrast UI theme for outdoor sunlight legibility; low power consumption (dark mode default, minimal background GPS polling) [INFERENCE].

5. **Storage & Produce Shelf-Life Perishability:**
   * Perishable crops like tomatoes, onions, and green chilies rot within 3–7 days without cold storage [KNOWN].
   * *Architectural Constraint:* System algorithms must factor in harvest age and ambient temperature to prioritize immediate processing or local sale for fast-decaying batches [INFERENCE].

4. *Can computer vision models run locally on a budget Android phone to classify agricultural produce defects?*
   * **Verification:** Quantized MobileNetV3 or YOLOv8-nano models converted to TensorFlow Lite or ONNX Runtime format can perform inference in <150ms on budget Android devices without cloud connection [KNOWN].

## 10. Recommended Approach & Why

### Selected Architecture: Approach 3 — Hybrid Offline-First Agri-Processing Ecosystem

**Why Approach 3 Wins:**
1. **Field Reality Match:** Rural farmers routinely experience connection drops while standing in fields or mandis. Approach 3 performs crop disease diagnosis, produce quality grading, and processing ROI calculations directly on the smartphone without requiring an active internet connection [INFERENCE].
2. **Economic Feasibility:** Cloud-based computer vision APIs cost $0.001–$0.005 per image call. For millions of farmers, this creates an unsustainable cloud bill. Running quantized MobileNet/YOLO models on-device costs ₹0 in cloud fees [INFERENCE].
3. **End-to-End Value Chain:** Unlike generic apps that stop at crop production, this hybrid approach actively addresses food loss by giving farmers immediate decision matrix options: *"Sell raw at Mandi X for ₹18/kg OR process into Tomato Paste using local PMFME Unit Y for ₹42/kg net profit."* [INFERENCE]

### Why Alternatives Were Rejected
* **Approach 1 Rejected:** A simple web portal is generic, non-innovative, and ignores rural accessibility constraints. It would score poorly under SIH evaluation criteria [INFERENCE].
* **Approach 2 Rejected:** Monolithic cloud dependencies introduce single-point-of-failure risks during live hackathon demos (e.g., venue Wi-Fi failure) and cannot function in deep rural agricultural belts [INFERENCE].

### Data Flow Narrative (Step-by-Step)

1. **Harvest Logging & Quality Scan (Offline/Field):**
   * The farmer opens the app in the field, selects crop type (e.g., Tomato), and captures images of harvested produce batch.
   * The embedded **ONNX Runtime Edge AI** processes the image locally, outputting a quality breakdown (Grade A: 70%, Grade B: 20%, Defect/Rot: 10%).
   * The record is stored immediately in the phone's **local SQLite database** with a "PENDING_SYNC" flag.

2. **Network Reconnection & Delta Sync:**
   * When the mobile device detects network connectivity (Wi-Fi or cellular), the **Sync Engine** initiates a background HTTP POST with compressed JSON payload to the API Gateway.
   * The backend validates JWT token, updates **PostgreSQL**, stores image blobs in **Cloudflare R2/S3**, and returns a updated batch ID.

3. **Decision Matrix Calculation:**
   * The backend **Produce & Mandi Engine** fetches current day APMC Mandi rates from **Agmarknet API** (cached in Redis).
   * Concurrently, the **Micro-Processing Engine** evaluates local food processing opportunities (e.g., converting 500 kg Grade B tomatoes into 100 kg tomato paste).
   * The mobile app displays two explicit financial options to the farmer in regional voice/text:
     * *Option A:* Sell raw at Nearest Mandi (₹14/kg = ₹7,000 total income).
     * *Option B:* Send to local FPO PMFME Micro-Unit for processing into paste (Est. gross value ₹12,000 - ₹2,000 processing cost = ₹10,000 net income).

4. **Execution & Buyer Matchmaking:**
   * If Option B is chosen, the batch is listed on the **FPO B2B Sourcing Portal**. Local micro-processors view the verified quality grade and accept the sourcing request.

## 13. AI/ML Justification

To ensure AI is applied purposefully rather than speculatively, each AI component is strictly evaluated against 14 engineering criteria:

### Evaluation Matrix for AI Components

#### Component 1: On-Device Produce Quality & Defect Classifier
1. **Exact Problem Solved:** Eliminates subjective, manual visual inspection of harvested produce by automatically detecting defect percentages, surface decay, and maturity [INFERENCE].
2. **Input:** Camera image of harvested produce lot (e.g., tomatoes, potatoes, apples) [INFERENCE].
3. **Output:** Categorized breakdown: Quality Grade (Grade A / B / C), Ripeness Index (0–100%), Surface Rot Percentage [INFERENCE].
4. **Why Simpler Rule Cannot Solve:** Visual color variance, irregular shapes, and subtle fungal spots cannot be captured by manual threshold rules [INFERENCE].
5. **Data Required:** 3,000–5,000 annotated images of crops with labeled defect categories (Kaggle/Roboflow datasets) [RESEARCHED].
6. **Evaluation Metric:** Mean Average Precision (mAP@0.5) > 85%, Inference Time < 200ms on mobile CPU [INFERENCE].
7. **Failure Handling:** If confidence score < 60%, app flags item as "Manual Inspection Suggested" and allows farmer manual override [INFERENCE].
8. **Training Required:** Yes, custom lightweight convolutional neural network (MobileNetV3 backbone) [INFERENCE].
9. **Fine-Tuning Required:** Yes, transfer learning on Indian crop varieties [INFERENCE].
10. **RAG Required:** No [INFERENCE].
11. **Computer Vision Required:** Yes [INFERENCE].
12. **Speech Processing Required:** No [INFERENCE].
13. **Forecasting Required:** No [INFERENCE].
14. **Human Oversight Required:** Yes, farmer/trader can manually adjust final assigned grade before locking batch [INFERENCE].

#### Component 2: Multilingual Agromet & Processing Voice Advisor

## 14. Data Architecture & Offline/Low-Network Design

### Database Schema (PostgreSQL / SQLite Compatible)

```sql
-- 1. USERS & PROFILES
CREATE TABLE users (
    user_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    full_name VARCHAR(100) NOT NULL,
    phone_number VARCHAR(15) UNIQUE NOT NULL,
    user_role VARCHAR(20) CHECK (user_role IN ('FARMER', 'FPO_ADMIN', 'PROCESSOR', 'BUYER')),
    preferred_language VARCHAR(10) DEFAULT 'hi',
    district VARCHAR(50),
    state VARCHAR(50),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 2. PRODUCE BATCHES
CREATE TABLE produce_batches (
    batch_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    farmer_id UUID REFERENCES users(user_id),
    crop_name VARCHAR(50) NOT NULL,
    harvest_date DATE NOT NULL,
    quantity_kg NUMERIC(10, 2) NOT NULL,
    quality_grade VARCHAR(5) CHECK (quality_grade IN ('A', 'B', 'C', 'UNKNOWN')),
    defect_percentage NUMERIC(5, 2),
    image_url TEXT,
    status VARCHAR(20) DEFAULT 'AVAILABLE', -- AVAILABLE, PROCESSING, SOLD
    is_synced BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 3. MANDI PRICES (CACHE TABLE)
CREATE TABLE mandi_prices (
    price_id SERIAL PRIMARY KEY,
    state VARCHAR(50),
    district VARCHAR(50),
    mandi_name VARCHAR(100),
    commodity VARCHAR(50),
    modal_price NUMERIC(10, 2), -- Rs per Quintal
    price_date DATE NOT NULL,
    fetched_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 4. MICRO-PROCESSING RECIPES (LOOKUP TABLE)
CREATE TABLE processing_recipes (
    recipe_id SERIAL PRIMARY KEY,
    raw_crop VARCHAR(50) NOT NULL,
    processed_product VARCHAR(100) NOT NULL,
    conversion_ratio NUMERIC(4, 2), -- e.g., 5.0 kg raw tomato -> 1.0 kg paste
    estimated_cost_per_kg NUMERIC(8, 2),
    market_price_per_kg NUMERIC(8, 2),
    shelf_life_days INT NOT NULL,
    sop_steps JSONB NOT NULL
);
```

### Offline Synchronization Protocol
1. **Client Log Queue:** Every offline mutation (`INSERT`, `UPDATE`) in the Expo mobile app writes to a local SQLite table `sync_queue` with a monotonically increasing sequence ID, payload JSON, and timestamp [INFERENCE].
2. **Reconnection Trigger:** A background listener continuously monitors network state via `NetInfo` [INFERENCE]. Upon detecting active internet, it initiates a sync request [INFERENCE].
3. **Conflict Resolution Strategy:**
   * **Last-Write-Wins (LWW) with Server Timestamping:** For produce status updates [INFERENCE].
   * **Client-side Non-destructive Append:** Batch inventory records generated offline are appended to server tables using client-side UUIDs to prevent primary key collisions [INFERENCE].
4. **Bandwidth Optimization:**
   * Produce images captured offline are compressed locally (JPEG, 80% quality, max 1024x1024 resolution) before upload, reducing file size from ~4MB to <250KB [INFERENCE].
   * JSON sync payloads use delta transmission (sending only updated fields, not entire database rows) [INFERENCE].
