## 1. Executive Snapshot

This research dossier presents an end-to-end hardware-software architectural solution for Problem Statement **SIH26219**, an open student innovation track under AICTE's "Smart Automation" theme [PS]. Educational institutions, commercial campuses, and industrial facilities in India face up to 35% resource wastage in energy and water utilities due to unmonitored infrastructure, lack of localized edge intelligence, and delayed response to abnormal consumption patterns [RESEARCHED]. The proposed solution, **AURA-ResNode (Autonomous Utility & Resource Automation Node)**, combines low-cost embedded hardware controllers (ESP32-S3 with RS-485 Modbus RTU and non-invasive sensors) with edge-level rule fallback and a cloud-based multi-source AI analytics engine [INFERENCE]. By fusing real-time power/water telemetry, weather forecasts, ambient conditions, and historical tariff data, AURA-ResNode autonomously detects leaks, equipment inefficiencies, and rogue loads while executing automated load-shedding and optimization [INFERENCE].

## 5. Constraints & Environment Realities

1. **Connectivity Realities:** Indian institutional campuses and tier-2/3 industrial hubs frequently experience intermittent Wi-Fi and cellular dropouts [KNOWN]. The hardware node MUST store up to 72 hours of telemetry in local Flash/EEPROM SPIFFS and synchronize via MQTT QoS 1 when reconnected [INFERENCE].
2. **Power Grid Instability:** Frequent voltage fluctuations (160V–270V) and unexpected power outages occur in many regions [KNOWN]. Hardware nodes must incorporate optocoupler isolation, surge suppression (MOVs), and a backup lithium-ion battery (3.7V 2000mAh with TP4056 charger) [INFERENCE].
3. **Hardware Budget Constraints:** Hardware student teams in SIH operate under strict budget limits (typically under ₹5,000 per demo node) [INFERENCE]. Components must use readily available off-the-shelf microcontrollers (ESP32-S3) and non-invasive sensors rather than industrial-grade ₹50,000 PLCs [INFERENCE].
4. **Field Environment Conditions:** Water pump rooms and outdoor electrical distribution boxes are hot, humid, and dusty [KNOWN]. Enclosures must be 3D-printed IP65-rated ABS junction boxes with heat dissipation vents [INFERENCE].
5. **Language & User Literacy:** Ground maintenance staff may not speak fluent English or understand complex ML jargon [KNOWN]. Local hardware must feature color LED indicators (Green/Yellow/Red) and a bilingual (Hindi/English) dashboard toggle [INFERENCE].

## 9. Candidate Solution Approaches

### Approach 1: Cloud-Centric IoT System
- **Mechanism:** ESP32 nodes act as dumb data forwarders, sending raw sensor telemetry directly to AWS IoT Core / Firebase. All processing, rule matching, and relay switching decisions occur on the cloud server.
- **Problem Fit:** Basic monitoring fit, but fails during network disconnects.
- **Accuracy Potential:** Medium (depends on continuous connection).
- **Complexity:** Low.
- **Cost:** High recurring cloud costs for high-frequency MQTT payload ingestion.
- **Scalability:** High cloud scale, but bottlenecked by internet reliability.
- **Hackathon Feasibility:** High (easy to build).
- **Production Feasibility:** Poor (single point of failure: loss of internet disables critical water pump / load control).

### Approach 2: Edge-AI Hybrid Autonomous Node (AURA-ResNode - Proposed)
- **Mechanism:** ESP32-S3 node runs a local edge loop (TinyML anomaly detection + hard safety limits on SPIFFS). Telemetry is synced via MQTT to a lightweight FastAPI + LightGBM backend. Multi-source data (weather, tariffs, timetables) is integrated at the server level to update edge schedules dynamically.
- **Problem Fit:** Excellent fit for SIH hardware category and real-world deployment.
- **Accuracy Potential:** High (local edge filters noise; cloud AI performs multi-variable time-series forecasting).
- **Complexity:** Medium-High.
- **Cost:** Low (uses open-source stack and off-the-shelf ESP32 microcontrollers).
- **Scalability:** High (decentralized edge nodes function independently).
- **Hackathon Feasibility:** Very High (demonstrable physical hardware + live cloud dashboard).
- **Production Feasibility:** Excellent (fault-tolerant, affordable, scalable).

### Approach 3: Standalone Offline Microcontroller System
- **Mechanism:** Independent Arduino/ESP32 boards with local LCD displays and fixed threshold logic (e.g., relay trips if current > 15A). No cloud backend or multi-source data integration.
- **Problem Fit:** Poor (fails REQ-03, REQ-04, REQ-05 for AI and multi-source insights).
- **Complexity:** Very Low.
- **Cost:** Minimal.
- **Scalability:** Poor (isolated hardware silos with no remote visibility).
- **Hackathon Feasibility:** High to build, low winning potential in SIH.
- **Production Feasibility:** Unacceptable for modern smart campus automation.

## 10. Recommended Approach & Why

**Selected Approach:** **Approach 2 — Edge-AI Hybrid Autonomous Node (AURA-ResNode)** [INFERENCE].

### Why Alternatives Were Rejected:
- **Approach 1 (Cloud-Centric)** was rejected because internet outages in rural/semi-urban Indian campuses will leave water tanks overflowing or electrical lines unprotected [INFERENCE]. Cloud latency (>200ms) is also unacceptable for electrical overload tripping [INFERENCE].
- **Approach 3 (Standalone Offline)** was rejected because it completely ignores the problem statement's core requirements for Artificial Intelligence (`REQ-03`), multi-source data integration (`REQ-04`), and actionable web insights (`REQ-05`) [INFERENCE].

### Architectural Superiority of Approach 2:
1. **Zero-Downtime Guarantee:** The edge microcontroller autonomously manages switching and overload protection even if the internet fails for days [INFERENCE].
2. **Multi-Source Intelligence:** Cloud backend enriches local sensor data with external open APIs (Open-Meteo weather, DISCOM tariffs, CEA national baselines) to optimize power and water usage proactively [INFERENCE].
3. **SIH Hardware Winning Edge:** Demonstrates actual physical embedded hardware, edge computing, multi-sensor hardware integration, and modern cloud UX [INFERENCE].

### Step-by-Step Data Flow Narrative

1. **Physical Sensing:** The ESP32-S3 samples AC current via non-invasive SCT-013 sensors (sampling at 1 kHz via ADC) and polls RS-485 Modbus energy meters (Eastron SDM120/SDM630) every 1 second [INFERENCE]. Simultaneously, ultrasonic sensors (JSN-SR04T) monitor water overhead tank levels [INFERENCE].
2. **Local Edge Validation:** The embedded TinyML model running on core 0 of the ESP32-S3 evaluates current waveforms and voltage stability [INFERENCE]. If a severe power overload (>25A) or dry run pump condition is detected, core 0 trips the optocoupled relay board instantly (<20ms) without waiting for cloud instruction [INFERENCE].
3. **Telemetry Buffering & Ingestion:** Processed 5-second averaged telemetry is packed into lightweight JSON payloads and published via MQTT over TLS to the Mosquitto/EMQX broker [INFERENCE]. If Wi-Fi is lost, payloads are saved into SPIFFS Flash memory and bulk-synced upon reconnection [INFERENCE].
4. **Cloud Enrichment & Storage:** FastAPI ingests MQTT messages, caches current status in Redis for sub-second UI updates, and writes time-series records to TimescaleDB [INFERENCE]. An background worker queries Open-Meteo API for temperature forecasts and DISCOM tariff tables [RESEARCHED].
5. **AI Inference & Automated Scheduling:** The Cloud AI Engine (LightGBM) processes multi-source data (weather + tariff + historical consumption) to generate optimal water pump run times and HVAC setpoints [INFERENCE]. Control commands are published back via MQTT to the ESP32 node to trigger relay actions [INFERENCE].
6. **User Alerts & Visualization:** Next.js frontend renders real-time single-line power diagrams, resource waste heatmaps, and cost savings [INFERENCE]. Critical anomalies push instant alerts to technicians via WhatsApp/SMS [INFERENCE].

## 13. AI/ML Justification

### Component 1: Edge TinyML Power & Water Anomaly Detector

1. **What exact problem does AI solve?** Detects electrical motor bearing failures, unexpected phase current distortion, and micro-water leaks from high-frequency sensor noise [INFERENCE].
2. **Input:** 1 kHz sampled AC current waveform array (100 samples) and water flow pulse frequencies [INFERENCE].
3. **Output:** Anomaly Score (0.0 to 1.0) and classification label (`NORMAL`, `MOTOR_FAULT`, `LEAK_SUSPECTED`, `OVERLOAD`) [INFERENCE].
4. **Why can a simpler rule not solve it?** Fixed thresholds fail when baseline load changes (e.g., turning on a heavy lab instrument looks like an overload to a static rule, but has a smooth sinusoidal startup profile distinct from a short-circuit fault) [INFERENCE].
5. **Data Required:** 5,000 synthetic and recorded current/flow waveform frames across normal and abnormal operations [INFERENCE].
6. **Evaluation:** F1-Score on test set (>0.92) and latency on ESP32 (<50ms) [INFERENCE].
7. **What happens when it is wrong?** False Positive: Alert sent to maintenance without tripping main breaker [INFERENCE]. False Negative: Hard physical fuse/circuit breaker acts as fallback [INFERENCE].
8. **Training/Fine-tuning:** Trained on host PC using Scikit-Learn/Edge Impulse, exported as C++ library header [RESEARCHED].
9. **CV / Speech / Forecasting:** Neither [INFERENCE].

### Component 2: Cloud Multi-Source Resource & Tariff Optimizer

1. **What exact problem does AI solve?** Forecasts daily building energy consumption and plans optimal water pump cycles to avoid DISCOM peak-tariff hours while guaranteeing full water tanks before morning hours [INFERENCE].
2. **Input:** Historical 15-min energy telemetry, 24-hour Open-Meteo temperature forecast, day of week, and DISCOM tariff matrix [INFERENCE].
3. **Output:** Hourly predicted kWh demand profile and scheduled pump relay ON/OFF matrix for next 24 hours [INFERENCE].
4. **Why can a simpler rule not solve it?** Non-linear interactions between ambient temperature (HVAC load spikes), timetable changes, and multi-tier energy pricing require dynamic multi-variable optimization [INFERENCE].
5. **Data Required:** 6 months of historical hourly building consumption, weather logs, and tariff structures [INFERENCE].
6. **Evaluation:** Mean Absolute Percentage Error (MAPE < 8%) on energy demand forecasting [INFERENCE].
7. **What happens when it is wrong?** Water pump falls back to local tank float-switch threshold rules (turns ON when tank < 25%, turns OFF when tank > 95%) [INFERENCE].
8. **Training/Fine-tuning:** LightGBM regressor trained weekly on cloud server [INFERENCE].

### Explicit Identification: Where AI Should NOT Be Used
- **Safety Tripping & Emergency Cutoff:** Emergency electrical cutoff (>30A overload or voltage >280V) MUST NOT depend on AI/ML inference. It MUST execute on deterministic, hard-coded C++ interrupt service routines (ISRs) on the ESP32 [INFERENCE].

### Local Edge Storage & Offline Synchronization Strategy

```
+-------------------------------------------------------------------------+
|                       LOCAL HARDWARE EDGE BUFFER                        |
|                                                                         |
| [ Sensors ] ---> [ ESP32-S3 RAM ] ---> [ WiFi Available? ]              |
|                                                |                        |
|                        +-----------------------+-----------------------+|
|                        | YES                                   | NO     |
|                        v                                       v        |
|               [ Send MQTT Payload ]                 [ Write to SPIFFS  ]|
|               [  (QoS 1 Ack)      ]                 [ Flash Buffer Log ]|
|                        |                                       |        |
|                        +-----------------------+---------------+        |
|                                                | Reconnected?           |
|                                                v                        |
|                                     [ Read SPIFFS Flash ]               |
|                                     [ Burst MQTT Sync   ]               |
+-------------------------------------------------------------------------+
```

1. **Local Buffering:** Telemetry is written to a ring-buffer file in ESP32 Flash memory (SPIFFS/LittleFS) using a compact binary struct (24 bytes per record) [INFERENCE]. 8MB Flash holds up to 72 hours of 10-second interval readings [INFERENCE].
2. **Flash Wear Leveling:** LittleFS wear-leveling algorithms prevent localized flash memory degradation [KNOWN].
3. **Bandwidth Reduction:** Telemetry payload uses JSON key compression (`{"v": 230.1, "i": 4.2, "p": 0.92}`) or protocol buffers (Protobuf) to minimize cellular data consumption to <5MB/month per node [INFERENCE].

## 15. Security, Privacy & Governance

1. **Hardware & Communication Security:**
   - **mTLS Authentication:** ESP32 nodes authenticate to the MQTT broker using unique X.509 client certificates stored in encrypted flash [INFERENCE].
   - **Over-The-Air (OTA) Updates:** Firmware updates signed with RSA-2048 private keys to prevent malicious code injection [INFERENCE].
2. **Data Privacy & DPDP Act 2023 Compliance:**
   - The system processes facility operational data, avoiding collection of Personally Identifiable Information (PII) [INFERENCE].
   - User credentials for dashboard admins are hashed using `bcrypt` (work factor 12) [KNOWN].
3. **Safety & Regulatory Governance:**
   - Physical high-voltage relay connections must feature optocoupler isolation (PC817) and flyback diode protection (1N4007) to prevent voltage feedback to microcontrollers [KNOWN].
   - The system operates as an auxiliary optimization layer; main physical residual current circuit breakers (RCCBs) and miniature circuit breakers (MCBs) remain in place for primary electrical protection [INFERENCE].
