## 1. Executive Snapshot

### Summary
The Ministry of Railways requires a dynamic, data-driven Estimated Time of Arrival (ETA) forecasting system for coaching (passenger) trains across Indian Railways [PS]. Current ETA estimations rely primarily on static schedules, current delays, and fixed recovery times, failing to adapt to real-world variables like track congestion, signal halts, unscheduled stoppages, weather disruptions, and downstream delay propagation [PS]. This dossier presents an actionable architectural blueprint for a 4–6 student team competing in the Smart India Hackathon (SIH 2026) to design, build, and demonstrate a production-grade prototype [INFERENCE]. The proposed solution combines a Gradient Boosted Decision Tree (LightGBM/XGBoost) model for point-to-point delay estimation with a Spatio-Temporal Graph Network for section-level cascading delay propagation, exposed via high-throughput REST/WebSocket APIs to feed mobile applications, station display boards, and control room dashboards [INFERENCE].

## 6. Research Questions

1. *How does Indian Railways currently track train movement in real time?*
   * **Answer:** Via the Real-Time Train Information System (RTIS) developed by CRIS in collaboration with ISRO, using GSAT satellite transponders and GAGAN/NavIC GPS devices mounted on locomotives, pushing 30-second position updates to the Control Office Application (COA) [RESEARCHED].
2. *What open datasets exist for historical delay analysis on Indian Railways?*
   * **Answer:** Indian Railways schedule and station data are available on public portals like Kaggle ("Indian Railways Train Schedule & Delay Data") and data.gov.in, while live status is accessible via NTES web wrappers [RESEARCHED].
3. *What machine learning models work best for railway network delay prediction?*
   * **Answer:** Literature demonstrates that LightGBM/XGBoost excels at tabular station-to-station delay regression, while Graph Convolutional Networks (GCN) or LSTM-based Spatio-Temporal models capture cross-network delay cascading across shared track sections [RESEARCHED].
4. *How are signal aspects and speed restrictions logged in Indian Railways?*
   * **Answer:** Station Data Loggers capture signal movements and point switches, which are being progressively linked to division COA servers [RESEARCHED]. Temporary Speed Restrictions (TSRs) are issued via digital Caution Orders in COA [RESEARCHED].

## 9. Candidate Solution Approaches

### Approach 1: Heuristic & Rule-Based Sectional Delay Projection
* **Mechanism:** Computes live delay at current station and projects forward using historical mean sectional running times adjusted by static time-of-day multipliers [INFERENCE].
* **Pros:** Extremely simple, zero training required, instant execution, low compute cost [INFERENCE].
* **Cons:** Cannot adapt to complex non-linear delay factors such as downstream track congestion, weather, or train precedence [INFERENCE].
* **Hackathon Feasibility:** 100/100 | **Production Feasibility:** 30/100 [INFERENCE].

### Approach 2: Feature-Engineered Gradient Boosted Decision Trees (LightGBM / XGBoost)
* **Mechanism:** Formulates ETA prediction as a tabular regression problem. Features include current delay, section distance, day of week, hour of day, rolling average section speed, local weather (fog visibility), and downstream train density [INFERENCE].
* **Pros:** Highly accurate for point-to-point station arrivals, fast inference latency (<5ms per train), handles non-linear interactions, robust to missing features [INFERENCE].
* **Cons:** Evaluates each train semi-independently; does not explicitly model full network graph interactions [INFERENCE].
* **Hackathon Feasibility:** 90/100 | **Production Feasibility:** 85/100 [INFERENCE].

### Approach 3: Hybrid Spatio-Temporal Graph Neural Network (ST-GNN) + LightGBM Ensemble
* **Mechanism:** Represents the railway network as a directed graph $G = (V, E)$ where nodes $V$ are stations and edges $E$ are track sections [INFERENCE]. Uses a Graph Convolutional Network (GCN) combined with GRU/LSTM temporal units to capture network-wide spatial delay propagation across all active trains, combined with a LightGBM regressor for localized train-specific features [INFERENCE].
* **Pros:** State-of-the-art prediction accuracy; captures cascading delay effects (e.g., Train A delay causing Train B hold-up at a junction 50 km ahead) [INFERENCE].
* **Cons:** High computational complexity, longer training time, complex graph setup for hackathon timeline [INFERENCE].
* **Hackathon Feasibility:** 65/100 | **Production Feasibility:** 95/100 [INFERENCE].

### Detailed Data-Flow Narrative
1. **Ingestion:** Telemetry events (lat/long, speed, timestamp, current station status) arrive via RTIS stream or simulated telemetry producer into the Ingestion Service [INFERENCE].
2. **State Sync & Caching:** Ingestion Service updates current train position in Redis spatial cache and calculates actual arrival/departure time against master timetable [INFERENCE].
3. **Feature Generation:** Spatial engine queries PostGIS to identify the current block section, section length, downstream train count within 100 km, and weather visibility metrics from OpenMeteo [INFERENCE].
4. **ML Inference:** Feature vector is passed to the pre-trained LightGBM Regressor. The model predicts remaining sectional run times for all upcoming stations along the train's route [INFERENCE].
5. **Confidence Quantification:** LightGBM Quantile Loss outputs P10 (optimistic), P50 (expected), and P90 (pessimistic) arrival timestamps for each upcoming station [INFERENCE].
6. **Publishing:** Predicted ETAs are written to PostgreSQL and broadcast via WebSockets to connected Station Display boards and Control Room dashboards [INFERENCE].

## 13. AI/ML Justification

### AI Component 1: Sectional Run Time & Delay Regressor (LightGBM)
1. **Exact Problem Solved:** Predicts exact run-time (in seconds) for a train across upcoming track sections under dynamic network conditions [INFERENCE].
2. **Input:** Current delay (min), distance to target station (km), train priority class (1–5), historical median section speed, downstream train count (density), visibility/fog index [INFERENCE].
3. **Output:** Predicted section travel time (seconds) and P10/P50/P90 arrival timestamp windows [INFERENCE].
4. **Why Simpler Rule Fails:** Standard schedules use fixed recovery times. They cannot account for exponential delay buildup when multiple trains enter a congested section simultaneously [PS].
5. **Data Required:** Historical train movement logs (~500,000 station pass records), line distance schedules, weather logs [INFERENCE].
6. **Evaluation Metric:** Mean Absolute Error (MAE in minutes) and Mean Absolute Percentage Error (MAPE) against ground truth arrivals [INFERENCE].
7. **Failure Handling:** If model inference fails or features are corrupt, system gracefully falls back to static schedule + current delay extrapolation (NTES baseline) [INFERENCE].
8. **Training Required:** Yes, trained offline on historical movement logs [INFERENCE].
9. **Fine-tuning Required:** No [INFERENCE].
10. **RAG Required:** No [INFERENCE].
11. **Computer Vision:** No [INFERENCE].
12. **Speech Processing:** No [INFERENCE].
13. **Forecasting Required:** Yes, multi-step time-series forecasting [INFERENCE].
14. **Human Oversight:** Division train controllers can manually override ETA outputs during major network disruptions (e.g., accidents or line blockages) [INFERENCE].

### Where AI Should NOT Be Used
* **Timetable Lookup:** Exact scheduled arrival/departure times must be queried directly from static database tables, not generated by AI models [INFERENCE].
* **Distance Calculations:** Track distances between stations must be computed deterministically using GIS spatial math (`ST_Length` on track linestrings) [INFERENCE].

## 14. Data Architecture & Offline/Low-Network Design

### Database Schema (PostgreSQL/PostGIS)

```sql
-- Stations Table
CREATE TABLE stations (
    station_code VARCHAR(10) PRIMARY KEY,
    station_name VARCHAR(100) NOT NULL,
    division VARCHAR(50),
    zone VARCHAR(10),
    location GEOMETRY(Point, 4326) NOT NULL
);

-- Master Train Schedule
CREATE TABLE train_schedules (
    id SERIAL PRIMARY KEY,
    train_number VARCHAR(10) NOT NULL,
    station_code VARCHAR(10) REFERENCES stations(station_code),
    stop_sequence INT NOT NULL,
    scheduled_arrival TIME,
    scheduled_departure TIME,
    distance_from_source_km NUMERIC(6,2)
);

-- Live Telemetry Log
CREATE TABLE train_telemetry (
    id BIGSERIAL PRIMARY KEY,
    train_number VARCHAR(10) NOT NULL,
    timestamp TIMESTAMPTZ NOT NULL,
    current_lat NUMERIC(9,6),
    current_lon NUMERIC(9,6),
    speed_kmh NUMERIC(5,2),
    current_delay_mins INT,
    last_passed_station VARCHAR(10)
);

-- Predicted Dynamic ETAs
CREATE TABLE dynamic_etas (
    train_number VARCHAR(10) NOT NULL,
    station_code VARCHAR(10) NOT NULL,
    p10_eta TIMESTAMPTZ NOT NULL,
    p50_eta TIMESTAMPTZ NOT NULL,
    p90_eta TIMESTAMPTZ NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (train_number, station_code)
);
```

### Offline & Low-Network Optimization Strategy
* **Client Local Caching:** Station IPIS displays and mobile apps store full static timetable and station geo-data locally in IndexedDB / LocalStorage [INFERENCE].
* **Delta Sync Payloads:** Updates transmitted over WebSockets/MQTT carry only dynamic changes: `{"train": "12301", "stn": "NDLS", "p50": "14:25", "delay": 15}` (payload size <80 bytes) [INFERENCE].
* **Exponential Backoff & Offline Resilience:** Mobile passenger app caches the last known ETA and displays a visual indicator ("Updated 4 mins ago") if network connectivity is lost [INFERENCE].
