## 1. Executive Snapshot

### Summary
The **AI-Powered Criminal Network Analysis System** addresses a fundamental challenge faced by Indian Law Enforcement Agencies (LEAs) under the Ministry of Home Affairs (MHA) and National Crime Records Bureau (NCRB) [PS]. Modern criminal syndicates, human trafficking networks, illegal narcotics rings, and organized crime operations targeting women and vulnerable groups do not operate in isolated silos; they leverage distributed associates, financial intermediaries, burner phones, multi-jurisdictional locations, and coordinated event timelines [PS]. While vast quantities of data exist across First Information Reports (FIRs), Call Detail Records (CDRs), financial transactions, and surveillance reports, the data remains fragmented, unstructured, and siloed across state boundaries [PS]. This system ingests structured and unstructured multi-source criminal intelligence, utilizes Natural Language Processing (NLP) for Indian legal texts and entity extraction, constructs a unified Knowledge Graph, executes Graph Analytics (centrality and community detection) to identify key syndicates/influencers, and provides investigators with interactive spatial-temporal visual insights and actionable intelligence dossiers.

## 9. Candidate Solution Approaches

### Approach 1: Classical Rule-Based & Relational SQL Pipeline
* **Mechanism:** Import CDRs and structured database records into a PostgreSQL database. Execute SQL queries with `JOIN` operations and pre-defined threshold rules (e.g., "Find pairs with >10 calls in 3 days").
* **Pros:** Simple, fast setup; low memory footprint; no AI model training required; predictable output.
* **Cons:** Exponential performance degradation on multi-hop graph queries (e.g., 4-hop connection between suspect and kingpin); cannot process unstructured narrative text in FIRs without manual tagging.
* **Feasibility:** High for hackathon, but fails key problem requirements for AI NLP entity extraction and graph analytics.

### Approach 2: Deep Learning Graph Neural Network (GNN) + Pure LLM Pipeline
* **Mechanism:** Use Large Language Models (LLMs) for all entity and relationship extraction from FIR text, coupled with Graph Neural Networks (GNNs) for link prediction and node classification.
* **Pros:** Handles complex semantic relationships; state-of-the-art predictive capability for missing links.
* **Cons:** Very high computational requirement (GPUs needed); black-box explainability (unacceptable for court evidence); high risk of hallucination in relationship extraction; difficult to implement fully within a hackathon timeframe.
* **Feasibility:** Low for hackathon; high operational risk for legal deployment.

### Approach 3: Hybrid Knowledge Graph + Localized NLP Transformer + Deterministic Graph Analytics (RECOMMENDED)
* **Mechanism:**
  1. **Ingestion & NLP Layer:** Fast, lightweight Named Entity Recognition using spaCy / GLiNER fine-tuned on legal entities (Person, Vehicle, Location, Phone, Org) to convert unstructured FIR narrative text into structured entity-relation triples.
  2. **Storage Layer:** Native Property Graph Database (Neo4j or Memgraph) to store entities as nodes and interactions as directed weighted edges.
  3. **Entity Resolution Engine:** Deterministic + fuzzy matching (Jaro-Winkler + Soundex + strict phone/vehicle ID rules) to deduplicate entities across multi-source files.
  4. **Graph Analytics Engine:** Algorithmic network analysis (Betweenness Centrality for gatekeepers/kingpins, Louvain for community/gang detection, Co-location graph algorithms).
  5. **Presentation Layer:** Interactive Cytoscape.js web dashboard with timeline spatial filters and automated intelligence report generator.
* **Pros:** Highly explainable (algorithms are deterministic and mathematically auditable); moderate hardware requirements (runs smoothly on CPU/RAM); completely covers all PS requirements; highly feasible for a student team build.
* **Cons:** Requires clean entity extraction rules; graph schema design must be meticulously planned.
* **Feasibility:** Exceptional for both SIH Hackathon MVP and real-world LEA production deployment.

## 10. Recommended Approach & Why

### Selection
**Approach 3: Hybrid Knowledge Graph + Localized NLP Transformer + Deterministic Graph Analytics** is selected.

### Justification
1. **Mathematical & Legal Auditability:** In criminal justice, evidence submitted under the Bharatiya Sakshya Adhiniyam (BSA), 2023 must be deterministic and verifiable. Algorithmic centrality measures (Betweenness, Eigenvector) provide mathematically provable metrics for identifying network hubs, whereas pure black-box LLMs or GNNs cannot justify why an individual was flagged without risk of hallucination [INFERENCE].
2. **Multi-Source Synergy:** This approach seamlessly unifies unstructured text (FIR narratives), structured communication logs (CDRs), and tabular data (Bank transactions) into a single Neo4j/Memgraph property graph schema [INFERENCE].
3. **Hackathon Feasibility:** The architecture avoids heavy GPU dependencies during inference. spaCy/GLiNER models and Neo4j graph algorithms execute rapidly on standard developer hardware, allowing the 4-6 student team to demonstrate real-time graph rendering and interactive querying during the SIH finale [INFERENCE].
4. **Rejection of Alternatives:** Approach 1 was rejected because SQL relational databases cannot efficiently compute multi-hop graph traversals and cannot extract entities from unstructured FIR text. Approach 2 was rejected due to heavy GPU hardware requirements, black-box unexplainability in legal settings, and high implementation complexity within the hackathon timeline [INFERENCE].

### Data Flow Narrative
1. **Ingestion:** An investigator uploads an investigative file (a PDF of an FIR narrative, a CSV of a CDR call log, or a banking XLSX statement) via the React UI.
2. **Processing & Extraction:**
   * Structured files (CDRs/Bank logs) pass through specialized Pandas parsers that normalize column headers (A-Party, B-Party, Timestamps, Duration, Cell IDs) into standard JSON schema.
   * Unstructured text files (FIRs/Intelligence notes) are processed by Tika/OCR and fed into the fine-tuned spaCy/GLiNER NLP pipeline to extract entities (`Person`, `Location`, `Vehicle`, `Phone`, `Organization`) along with contextual relationship triples.
3. **Entity Resolution:** Extracted entities pass through the Entity Resolution Engine. If "Ramesh Kumar" (Phone: 9876543210) matches an existing node in the graph via phone number or fuzzy name + alias match, the engine links the incoming data to the existing `Person` node rather than creating a duplicate.
4. **Graph Persistence:** Resolved entities and relationships are written into the Neo4j/Memgraph Graph Database as nodes and directed edges with associated property metadata (timestamps, case IDs, source file hashes).
5. **Analytics Execution:** The backend triggers Graph Data Science (GDS) algorithms:
   * Betweenness & Eigenvector Centrality identifying potential network influencers.
   * Louvain Community Detection grouping connected clusters (syndicates/gangs).
   * Pattern algorithms flagging co-location or rapid communication spikes.
6. **Visualization & Insights:** The React frontend queries the backend via REST/WebSocket APIs, rendering the filtered sub-graph using Cytoscape.js and displaying temporal movement tracks on Leaflet.js. The investigator can click any node/edge to view supporting evidence or click "Generate Dossier" to export an auditable PDF report.

## 13. AI/ML Justification

### 1. NLP Named Entity Recognition (NER) Component
* **Purpose:** Automatically identify domain entities (`Person`, `Location`, `Vehicle`, `Phone Number`, `Organization`, `Law Section`) from unstructured narrative text in FIRs and intelligence notes.
* **Model Type:** Token classification model using spaCy / GLiNER (Generalist Lightweight NER transformer).
* **Input:** Unstructured legal narrative text (English / Hindi / Transliterated).
* **Output:** JSON array of extracted entities with character offsets and confidence scores.
* **Data Required:** Annotated sample of 200+ Indian police FIR sentences containing local names, locations, vehicle numbers, and statutory sections.
* **Why AI is Preferable:** Regular expressions (regex) fail on unstructured human narrative text, variable Indian name spellings, complex sentence syntax, and ambiguous context (e.g., distinguishing a victim's name from an accused's name).
* **Evaluation:** Precision, Recall, and F1-score on a held-out test set of FIR narratives.
* **Failure Mode:** Misclassification of entity type (e.g., labeling a location as a person's name).
* **Human Oversight:** The investigator UI highlights extracted entities in the text viewer, allowing the officer to manually correct, add, or un-tag entities before saving to the knowledge graph.

### 2. Graph Analytics & Key Influencer Identification Component
* **Purpose:** Calculate mathematical influence scores across the network to identify hidden kingpins, gatekeepers, and syndicate sub-groups.
* **Model / Algorithm Type:** Graph Algorithmic Centrality (Betweenness Centrality, Eigenvector Centrality) and Louvain Community Detection (Modularity Optimization).
* **Input:** Directed property graph (Nodes and Edges with weights).
* **Output:** Node centrality scores (0.0 to 1.0), community cluster assignments (Group IDs), and ranked influencer lists.
* **Data Required:** Graph topology constructed from merged case data.
* **Why AI/Graph Analytics is Preferable:** Manual visual inspection of a graph exceeding 30 nodes is impossible for humans to identify non-obvious bridge nodes connecting isolated sub-networks.
* **Evaluation:** Verification against ground-truth benchmark criminal graphs (e.g., synthetic syndicate test cases with known simulated leaders).
* **Failure Mode:** Over-estimating the importance of a peripheral node with high raw call volume (e.g., a customer care helpline or food delivery number).
* **Human Oversight:** Raw centrality scores are presented alongside contextual edge metadata (e.g., call duration, case severity), enabling the investigator to filter out benign high-degree nodes.

### Where AI Should NOT Be Used
* **Legal Case Verdicts or Guilt Determination:** The system must NEVER auto-generate conclusions of guilt or recommend arrests [INFERENCE].
* **Entity Deduplication Overrides:** High-confidence merging of two distinct individuals (e.g., merging two people with the same name) must NOT occur automatically without human confirmation if phone/Aadhaar/PAN IDs are absent [INFERENCE].

## 14. Data Architecture & Offline/Low-Network Design

### Graph Data Schema (Nodes & Edges)

```
[Person Node]
  - id: UUID
  - name: String
  - aliases: Array[String]
  - phone_numbers: Array[String]
  - aadhaar_hash: String
  - risk_score: Float

[Phone Node]
  - msisdn: String (Primary Key)
  - operator: String
  - imei_history: Array[String]

[Location Node]
  - id: UUID
  - address: String
  - latitude: Float
  - longitude: Float
  - cell_id: String

[Vehicle Node]
  - registration_no: String (Primary Key)
  - model: String
  - owner_name: String

[Event / FIR Node]
  - fir_number: String
  - police_station: String
  - date_registered: Date
  - bns_sections: Array[String]

-- RELATIONSHIPS (EDGES) --
(Person)-[:CO_ACCUSED_IN {case_id, role}]->(Event)
(Person)-[:USES_PHONE {since_date}]->(Phone)
(Phone)-[:CALLED {call_count, total_duration, last_timestamp}]->(Phone)
(Phone)-[:LOCATED_AT {timestamp}]->(Location)
(Person)-[:OWNS_VEHICLE]->(Vehicle)
(Person)-[:TRANSFERRED_FUNDS {amount, txn_id, timestamp}]->(Person)
```

### Offline & Synchronization Strategy
* **Local Caching:** The React frontend uses IndexedDB (via LocalForage) to store recently queried network sub-graphs and map tiles locally.
* **Bandwidth Reduction:** Network queries return optimized JSON payloads containing only delta node/edge updates rather than full graph re-downloads.
* **Air-Gapped / Local Deployment Mode:** The entire stack (FastAPI, Neo4j, spaCy, React build) can run locally inside a single Docker container environment on a standalone police station workstation without requiring internet access [INFERENCE].
