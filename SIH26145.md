## 1. Executive Snapshot

The National Technical Research Organisation (NTRO) requires a real-time cybersecurity intelligence pipeline capable of detecting, classifying, and scoring cyber threats from a strictly one-directional, read-only stream of IP traffic [PS]. Operating inside an isolated monitoring enclave fed by hardware data diodes or passive optical splitters, the system must process streaming network flows or packet captures with zero ability to actively probe, execute TCP handshakes, decrypt encrypted session payloads, or transmit mitigation feedback back into the source network [PS]. To meet this challenge, the proposed solution delivers a high-throughput, streaming hybrid analytics engine combining lightweight statistical entropy/periodicity estimators with specialized ML models (n-gram/entropy RF for DNS anomalies, JA3/JA4 + packet-length-time-sequence classifiers for TLS/QUIC, and streaming graph fan-out trackers) [INFERENCE]. The system outputs standardized JSON alert streams and populates an interactive, evidence-rich visualization dashboard to enable rapid SOC triage in critical infrastructure environments [INFERENCE].

## 2. Problem Deconstruction

### Explicit Requirements & Scope

#### Core Background & Environment Constraints
1. **Unidirectional Passive Ingest:** Traffic is mirrored into a monitoring enclave via passive optical taps or hardware data diodes in one direction only [PS]. The enclave has no physical or logical path back to the production network [PS].
2. **Zero Active Interaction:** The system cannot send network probes, complete TCP/TLS handshakes, or push automated firewall/mitigation rules back across the ingest link [PS].
3. **Passive Data Types:** Input consists purely of passively observed packet captures (PCAP), exported flow records (NetFlow v9, IPFIX, sFlow), and derived metadata [PS].
4. **Primary Output:** Labelled security alerts, confidence scores (0.00–1.00), and supporting evidence features displayed on a web dashboard and emitted as standardized structured records [PS].

#### Threat Categories to Detect
- **a. Volumetric / Protocol DDoS:** SYN floods, UDP reflection/amplification, and spoofed-source floods identified via flow-level rate spikes and source-IP Shannon entropy statistics [PS].
- **b. Botnet C2 Beaconing:** Periodicity, Fast Fourier Transform (FFT), and inter-arrival time (IAT) analysis on flows repeating at regular intervals to concentrated destination IP sets [PS].
- **c. DGA Domains & DNS Tunnelling:** Shannon entropy and n-gram analysis of DNS query names, query-length anomalies, and abnormal record-type usage (e.g., TXT, NULL, CNAME) [PS].
- **d. Malware Inside Encrypted Sessions:** Analysis of TLS/QUIC metadata alone (JA3/JA3S or JA4/JA4S fingerprints, Server Name Indication [SNI], Cipher Suites, Packet-Size & Timing Sequences [PSTS]) without payload decryption [PS].
- **e. Reconnaissance & Port Scanning:** High fan-out patterns from a single source host across multiple destination ports (vertical scan) or multiple destination hosts (horizontal scan) [PS].
- **f. Data Exfiltration:** Asymmetric flow-volume anomalies and abnormal outbound-to-inbound byte/packet ratios [PS].

#### Architectural Constraints
- **a. Read-Only Ingest:** The input pipeline must strictly treat network input as read-only. Systems requiring return paths or inline blocks are explicitly out of scope [PS].
- **b. No Payload Decryption:** Inspection of TLS/QUIC must rely exclusively on handshake metadata and flow side-channels, never on decrypted payload content [PS].
- **c. Streaming Processing:** Ingestion and threat detection must execute incrementally with bounded latency (< 2 seconds), rejecting batch-only offline reporting [PS].
- **d. Defined Throughput Target:** The solution must explicitly state and benchmark its sustained traffic handling capacity (e.g., Mbps or flows/sec) during evaluation [PS].
- **e. Standardized Alert Schema:** Output alerts must adhere to a rigid JSON structure containing timestamp, flow identifier (5-tuple), threat class, confidence score, and raw supporting evidence features [PS].

#### Problem Statement Ambiguities & Clarifications
1. **IP Data Simulation vs. Real Hardware Tap:** The PS explicitly mentions a "simulated IP data" source for prototype verification, while specifying real-world hardware data diodes as the target deployment environment [PS].
2. **5-Tuple Handling in Unidirectional Streams:** In asymmetric tap scenarios, return traffic might traverse a different link [KNOWN]. The system must account for single-direction flow records where return byte counts are zero or unobserved [INFERENCE].

## 5. Constraints & Environment Realities

1. **Hardware Data Diode Enforcement:** In production, physical isolation is enforced via fiber-optic TX-only transmitters on the production tap and RX-only receivers on the monitoring enclave [KNOWN]. The software ingest module must operate correctly even when Ethernet link autonegotiation and reverse ACK packets are physically absent [INFERENCE].
2. **Unidirectional Flow Asymmetry:** When traffic is passively mirrored at an egress gateway, return path packets might be missing or asymmetric [KNOWN]. ML features must avoid relying on symmetric two-way handshakes if only one direction is captured [INFERENCE].
3. **Air-Gapped Operation:** The NTRO enclave has no external internet connectivity [PS]. All threat intelligence feeds (e.g., GeoIP databases, known DGA domain lists, JA4 fingerprint registries) must be locally cached and updated out-of-band [INFERENCE].
4. **Encrypted Traffic Dominance:** Over 85-90% of modern web traffic uses TLS 1.3 or QUIC [KNOWN]. Features like SNI may be encrypted in TLS 1.3 (eSNI/ECH), making JA4 fingerprinting and Packet Size & Timing Sequences (PSTS) the primary signals [RESEARCHED].
5. **Real-Time Bounded Latency:** Ingest buffering must not introduce unbounded memory growth. Windowed sliding metrics must maintain a memory footprint of $O(K)$ relative to active flows [INFERENCE].

## 10. Recommended Approach & Why

The **Hybrid Feature-Engineered ML & Streaming Engine (Approach 3)** is the selected solution.

### Why Alternatives Were Rejected
- **Rejection of Approach 1 (Pure Rule-Based):** Classical NIDS rules fail against domain generation algorithms (DGAs) that dynamically change domain names, encrypted sessions where payloads cannot be inspected, and C2 channels using variable timing jitter [KNOWN]. Relying solely on static rules violates the explicit AI/ML requirement of SIH26145 [PS].
- **Rejection of Approach 2 (End-to-End Deep Learning):** Deep learning directly on raw packet byte streams requires massive GPU acceleration, scales poorly at multi-gigabit speeds, and acts as a "black box" [KNOWN]. NTRO SOC analysts require explicit, human-interpretable evidence features (e.g., entropy values, JA4 hashes, packet-size distributions) to validate alerts, which raw neural networks cannot provide natively [PS/INFERENCE].

### Why Approach 3 Wins
Approach 3 pairs lightweight, high-performance protocol metadata extraction (via Zeek / PyGo packet parsers) with specialized ML models (LightGBM / XGBoost) and fast streaming statistical algorithms (Shannon Entropy, FFT, HyperLogLog) [INFERENCE]. This design delivers sub-second alert generation, low CPU usage, and high accuracy, while natively exporting standardized JSON records containing exact supporting evidence [PS/INFERENCE].

### Detailed Data Flow Narrative
1. **Ingestion:** Raw mirrored network frames pass through the physical data diode into the enclave's dedicated RX network interface [PS]. An `AF_PACKET` ring buffer captures packets at line rate without sending any control frames [INFERENCE].
2. **Metadata Extraction:** Zeek / Suricata parses packet streams into structured JSON events containing 5-tuples, HTTP/DNS headers, and TLS handshakes (JA3/JA4) [RESEARCHED].
3. **Stream Buffering:** JSON metadata events are pushed into an in-memory Apache Kafka / Redpanda topic partitioned by source IP and destination IP [INFERENCE].
4. **Feature Engineering:** Stream processing workers consume flow windows to compute rolling statistical features (e.g., Shannon entropy, FFT periodicity, n-gram scores, byte ratios) [INFERENCE].
5. **Model Inference:** Pre-trained LightGBM and Isolation Forest classifiers evaluate the engineered feature vector for every completed flow window [INFERENCE].
6. **Alert Standardisation:** Detections exceeding defined confidence thresholds generate structured JSON alerts matching the schema required by Constraint (e) [PS].
7. **Storage & Dashboard:** Alerts are written to a ClickHouse time-series database and pushed via WebSockets to a React-based SOC dashboard for analyst visualization [INFERENCE].

### Detailed AI Model Breakdown

#### Threat Class A: Volumetric / Protocol DDoS
1. **Purpose:** Detect SYN floods, UDP reflection, and spoofed-source floods [PS].
2. **Model Type:** Streaming Statistical Entropy & Z-Score Thresholding (Non-ML/Statistical AI) [INFERENCE].
3. **Input:** Source IP distribution array, packet-per-second (PPS) rates over 1-second sliding windows [PS].
4. **Output:** DDoS probability, estimated attack volume (PPS/Mbps), spoofing indicator [PS].
5. **Data Required:** Synthetic traffic from `hping3` and `iperf3` [PS].
6. **Why AI/Statistical Engine:** Static thresholding fails under varying traffic baselines; entropy detects source address randomization instantly [KNOWN].
7. **Evaluation Metric:** Precision, Recall, Detection Latency (< 500ms) [INFERENCE].
8. **Failure Mode Handling:** Flash crowds (legitimate traffic spikes) maintain high source IP entropy, preventing false DDoS alerts [INFERENCE].
9. **Training Requirements:** No offline training required; uses online sliding window baselines [INFERENCE].
10. **Fine-Tuning:** Threshold adjustment via configuration YAML [INFERENCE].
11. **RAG Required:** No [INFERENCE].
12. **Computer Vision / Speech / Forecasting:** No [INFERENCE].
13. **Human Oversight:** High severity alert prompts SOC analyst to verify target IP [INFERENCE].

#### Threat Class B: Botnet C2 Beaconing
1. **Purpose:** Detect periodic command-and-control callbacks to malicious IPs [PS].
2. **Model Type:** Fast Fourier Transform (FFT) Periodicity Analysis + DBSCAN Clustering [INFERENCE].
3. **Input:** Inter-arrival time (IAT) series of flows grouped by `(SrcIP, DstIP, DstPort)` [PS].
4. **Output:** Beaconing score (0.00–1.00), estimated beacon interval (e.g., 60.0s ± 2%), jitter percentage [PS].
5. **Data Required:** Flow logs from sandboxed C2 emulators generating periodic connections [PS].
6. **Why AI/ML Engine:** Simple rules miss beaconing when attackers introduce 10-20% random timing jitter [KNOWN].
7. **Evaluation Metric:** Mean Absolute Error (MAE) on estimated beacon interval [INFERENCE].
8. **Failure Mode Handling:** Low-frequency legitimate telemetry (e.g., NTP sync) matched against known destination whitelist [INFERENCE].
9. **Training Requirements:** Unsupervised; fits online timing vectors [INFERENCE].
10. **Fine-Tuning:** Minimum flow count window size = 10 events [INFERENCE].
11. **RAG / Vision / Speech:** No [INFERENCE].
