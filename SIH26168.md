# SIH26168 Solution Research Dossier: AI-ML Based Intelligent Dead Reckoning System for Seamless Navigation

---

## 1. Executive Snapshot

### Summary
Modern navigation applications (e.g., Google Maps, MapmyIndia) heavily depend on Global Navigation Satellite System (GNSS) signals (GPS, NavIC, Galileo). When vehicles enter GNSS-denied environments—such as underground tunnels, multi-level parking garages, dense urban canyons, or forested highways—navigation apps freeze, jump erratically, or miscalculate turn distances [PS]. While high-end luxury vehicles feature factory-integrated wheel odometers and chassis Inertial Navigation Systems (INS), millions of commercial trucks, older automobiles, and two-wheelers in India rely exclusively on driver smartphones mounted on dashboards or mobile holders [PS]. Using consumer-grade smartphone Micro-Electro-Mechanical Systems (MEMS) Inertial Measurement Units (IMUs) for dead reckoning is severely constrained by sensor bias, engine vibrations, pothole shocks, and the absence of an OBD-II speed feed, leading to exponential quadratic drift [PS]. 

This project delivers a dual-architecture software solution: a 10Hz Android mobile application and a 200Hz C++ Edge Engine for Fiber Optic Gyroscope (FOG)/MEMS sensors [PS]. The system integrates:
1. An **Auto-Alignment & Calibration Engine** to resolve mounting orientation (pitch, roll, yaw) [PS].
2. A **1D-CNN + BiLSTM AI Speed & Vibration Filter** predicting forward velocity solely from IMU noise patterns [PS].
3. An **Error-State Unscented Kalman Filter (ES-UKF)** enforcing Non-Holonomic Constraints (NHC) [PS].
4. A **Hidden Markov Model (HMM) Map Matcher** over offline OpenStreetMap (OSM) vector data [PS].
5. An **Instantaneous GNSS Deficit Handler** executing state transitions within milliseconds [PS].

### Atomic Requirements Breakdown

#### Requirement A: In-Vehicle Alignment & Calibration Engine
* **Source Text:** *"An algorithmic module that automatically determines the phone’s pitch, roll, and yaw relative to the vehicle's driving direction, whether the phone is strictly dashboard-mounted or placed in mobile holder."* [PS]
* **Interpretation:** Sensor readings occur in the phone's local reference frame ($b$-frame), which is arbitrarily rotated relative to the vehicle frame ($v$-frame). The system must compute a dynamic Direction Cosine Matrix (DCM) or rotation quaternion ($q_b^v$) to project local sensor axes onto the longitudinal, lateral, and vertical axes of the vehicle [INFERENCE].
* **Implementation Implication:** Calculate gravity vector during stationary phases to establish pitch and roll; evaluate forward linear acceleration vectors during vehicle start/acceleration to resolve yaw misalignments [INFERENCE].
* **Confidence:** [PS]

#### Requirement B: AI Speed & Vibration Filter
* **Source Text:** *"A deep-learning or statistical signal-processing model running locally on the phone that filters out high-frequency road noise/potholes and directly estimates vehicle forward velocity from IMU signals."* [PS]
* **Interpretation:** Without an OBD-II wheel encoder feed, double-integrating noisy accelerometer signals causes quadratic position drift ($s = \frac{1}{2}at^2$) within seconds. The system must use an ML model to regress vehicle forward speed ($v_x$) directly from high-frequency IMU spectral signatures, while rejecting high-pass engine harmonics and impulse spikes (potholes/bumps) [INFERENCE].
* **Implementation Implication:** Train a lightweight 1D-CNN + BiLSTM network in PyTorch/TensorFlow, convert to ONNX Runtime / TFLite, and execute local inference on 1-second sliding IMU windows [INFERENCE].
* **Confidence:** [PS]

#### Requirement C: Advanced Map-Matching & Kinematic Constraints
* **Source Text:** *"A framework (e.g., AI-ML framework or Unscented Kalman Filter + Hidden Markov Map Matching) that binds the calculated position to known road networks and geometric paths during a dropout."* [PS]
* **Interpretation:** Raw dead-reckoning vectors drift over time. The fusion engine must enforce physical motion limits—Non-Holonomic Constraints (NHC) assuming zero lateral velocity ($v_y \approx 0$) and zero vertical velocity ($v_z \approx 0$) for non-sliding ground vehicles—and snap predicted coordinates to the surrounding road network using topological probabilities [INFERENCE].
* **Implementation Implication:** Construct an Error-State Unscented Kalman Filter (ES-UKF) integrated with a Viterbi-based Hidden Markov Model (HMM) matching engine executing against an offline spatial R-Tree index of OpenStreetMap (OSM) edges [INFERENCE].
* **Confidence:** [PS]

#### Requirement D: GNSS+INS Fusion Engine
* **Source Text:** *"An innovative AI based Sensor Fusion Algorithm that combines GNSS & IMU measurements and provides significant improvement in overall output by eliminating drift errors and providing accurate position and velocity."* [PS]
* **Interpretation:** During GNSS availability, the system must continuously estimate IMU gyroscope drift bias ($\mathbf{b}_g$), accelerometer bias ($\mathbf{b}_a$), and filter covariance matrices ($\mathbf{Q}, \mathbf{R}$) to maintain tight synchronization [INFERENCE].
* **Implementation Implication:** Deploy an adaptive neural network layer to dynamically adjust measurement noise covariance matrices ($\mathbf{R}_k$) based on real-time GNSS HDOP/PDOP and satellite lock status [INFERENCE].
* **Confidence:** [PS]

#### Requirement E: Seamless GNSS Deficit Handler
* **Source Text:** *"An instant seamless transition mechanism between GNSS aided INS and Dead reckoning modes within milliseconds of GNSS signal blackout and vice-versa."* [PS]
* **Interpretation:** Transitioning between satellite-aided tracking and pure inertial dead reckoning must happen without position jumps, UI freezes, or visual lag [INFERENCE].
* **Implementation Implication:** Maintain a continuous background shadow state vector. When GNSS carrier-to-noise ratio ($C/N_0$) drops below threshold ($< 25\text{ dB-Hz}$) or Dilution of Precision exceeds limits ($HDOP > 4.0$), instantly switch state propagation from measurement update mode to pure dead-reckoning mode within $<10\text{ ms}$ [INFERENCE].
* **Confidence:** [PS]

#### Requirement F: Universal Execution Architecture (Mobile & Edge Engine)
* **Source Text:** *"The Final solution and AI/ML models developed should not be constricted to smart phone IMU sensors data alone (Mobile application). These algorithms/models should also work with any other external IMU sensors data (Edge deployable software engine)... Position update rate of 10Hz with processing on smartphones... higher update rates on Edge deployable software engine using FOG based IMU sensors data (around 200Hz)."* [PS]
* **Interpretation:** The core estimation algorithms must be implemented in a decoupled, hardware-agnostic language (C++20 / Rust) compiled to native Android shared libraries (`.so` via JNI) for the mobile app, and directly to standalone binaries for embedded Linux edge targets receiving 200Hz FOG streams [INFERENCE].
* **Implementation Implication:** Core filter architecture built in clean C++20 with zero UI or OS dependencies; mobile app wraps C++ core using Flutter/JNI for 10Hz rendering; Linux edge daemon executes standalone at 200Hz [INFERENCE].
* **Confidence:** [PS]

#### Requirement G: Performance Benchmarks & Benchmark Dataset
* **Source Text:** *"The solution must restrict positional drift to less than 10% of the total distance travelled using smartphone IMUs sensors during GNSS signals blackout (e.g., <5m drift over 50m... OR <100m drift over 1km at 60kmph)... Dataset Details: IO-VNBD... Teams are required to include the preliminary AI models and the results of the position plot inferenced from the subset of IO-VNBD dataset as part of their proposals..."* [PS]
* **Interpretation:** Evaluation is quantitatively tied to the IO-VNBD benchmark dataset [1.1]. Models must achieve $<10\%$ drift across long outage windows (30s, 60s, 120s) [RESEARCHED].
* **Implementation Implication:** Train models on IO-VNBD smartphone sequences (Huawei P20 Pro, Moto G7 Power, Blackberry Priv sampled at 10Hz) and validate output trajectory trajectories against ground-truth ECU/GPS traces [2.3].

## 5. Constraints & Environment Realities

### Physical Mounting Variations
* Smartphones in real Indian road conditions are mounted on flexible air-vent clips, rigid dashboard suction cups, or loose phone holders [PS]. 
* **Reality:** Vibrations vary from high-frequency engine idle harmonics (20–50 Hz) to low-frequency chassis swaying (1–5 Hz) [RESEARCHED]. The auto-alignment system must continuously recalculate mounting angles rather than assuming a fixed static mounting orientation [INFERENCE].

### Vehicle & Road Disturbances
* Vehicles experience sudden braking, speed bumps, deep potholes, and unpaved roads [PS].
* **Reality:** Accelerometer vertical spikes from potholes can reach $\pm 3g$ [KNOWN]. Naive double integration converts these acceleration spikes into erroneous forward velocity leaps [INFERENCE]. The system requires an AI filter trained explicitly to isolate non-navigation impulse spikes from translational acceleration [PS].

### Hardware & Thermal Limitations (Smartphone)
* Mobile devices running continuous 100Hz IMU sampling, neural network inference, Kalman filtering, and vector map rendering suffer thermal throttling and battery drain [INFERENCE].
* **Reality:** Models must be quantized (INT8/FP16) and optimized via ONNX Runtime / Mobile GPU delegates to execute within $<15\text{ ms}$ per frame, consuming $<15\%$ CPU load at 10Hz [INFERENCE].

### High-Rate Embedded Edge Requirements (200Hz FOG Engine)
* Industrial tactical IMUs / Fiber Optic Gyroscopes (FOG) stream data at 200Hz to 1000Hz [PS].
* **Reality:** Python/Java runtimes introduce garbage collection pauses that drop frames at 200Hz [KNOWN]. The core fusion engine must be implemented in lock-free, zero-allocation C++20 [INFERENCE].

### Complete Offline Operation
* GNSS blackouts frequently co-occur with complete cellular network loss (e.g., deep tunnels, remote mountain gorges) [PS].
* **Reality:** The system must not rely on cloud map tile fetching or server-side routing APIs during outages [INFERENCE]. Maps must be stored locally as compact vector OpenStreetMap Protobuf (`.pbf`) or MBTiles databases [INFERENCE].

1. **Orientation Calibration:** How can the vehicle orientation frame be robustly estimated from smartphone IMU signals when the vehicle is turning or operating on banked roads? [INFERENCE]

3. **IO-VNBD Dataset Characteristics:** How do the phone IMU sampling characteristics (10Hz sampled in IO-VNBD) translate to high-rate real-time smartphone sensors (100Hz downsampled)? [2.3]

5. **Sensor Bias Estimation:** Can the Error-State UKF estimate MEMS gyro drift ($\sim 0.1^\circ/\text{s}$) fast enough during 30 seconds of clear GNSS visibility to prevent catastrophic yaw drift during a subsequent 2-minute tunnel outage? [RESEARCHED]

* **What it does:** Relies primarily on GNSS satellite signals; during outages, holds last known velocity or projects a straight line along the active route [PS].
* **Strengths:** Excellent global map coverage and live traffic routing [KNOWN].
* **Weaknesses:** Fails in tunnels, underpasses, and urban canyons; position marker freezes, jumps, or strays off-road [PS].
* **Relevance:** Demonstrates the explicit baseline problem to be solved [PS].
* **Remaining Gap:** Lack on-device inertial dead reckoning without OBD-II feeds [PS].
* **Source:** Problem Statement Background [PS]. Confidence: [PS].

#### 2. Factory Automotive Integrated Navigation Systems
* **What it does:** Fuses chassis IMU with physical CAN-bus / OBD-II wheel speed sensors to maintain accurate dead reckoning [PS].
* **Strengths:** Highly reliable and accurate due to direct physical wheel rotation measurements [PS].
* **Weaknesses:** Expensive option limited to luxury vehicles; cannot be retrofitted to older vehicles or 2-wheelers [PS].
* **Relevance:** Proves the necessity of speed inputs for INS, which our system must predict via AI [PS].
* **Remaining Gap:** Hardware-dependent; does not work on standalone smartphones [PS].
* **Source:** Problem Statement Background [PS]. Confidence: [PS].

#### 3. Standard Strapdown Inertial Navigation System (SINS)
* **What it does:** Performs double integration of accelerometer readings ($\int \int a \, dt^2$) to calculate position [PS].
* **Strengths:** Fully self-contained, independent of external signals [PS].
* **Weaknesses:** Low-cost MEMS IMUs introduce noise and bias errors that compound quadratically into hundreds of meters of drift within seconds [PS].
* **Relevance:** Standard mathematical baseline that requires AI filtering and kinematic constraints [PS].
* **Remaining Gap:** Cannot operate standalone on uncalibrated mobile devices [PS].
* **Source:** Problem Statement Description [PS]. Confidence: [PS].

#### 4. Academic Deep Learning Trajectory Estimators (e.g., R-WhONet, IONet)
* **What it does:** Uses end-to-end LSTM/GRU networks to predict 2D displacement vectors directly from IMU sequences [1.8, 2.8].

* **Weaknesses:** Black-box outputs often violate physical road geometry, predicting vehicle motion off-road or into buildings during out-of-distribution driving conditions [INFERENCE].
* **Relevance:** Serves as benchmark reference models [1.8].
* **Remaining Gap:** Lacks physical kinematic state bounds (NHC) and map matching integration [INFERENCE].
* **Source:** MDPI Applied Sciences / arXiv research papers on IO-VNBD [1.8, 2.8]. Confidence: [RESEARCHED].

### Approach A: Classical Strapdown INS + Extended Kalman Filter (EKF)
* **Mechanism:** Double integration of accelerometer signals with EKF state estimation, coupled with simple nearest-neighbor point snapping to road segments.
* **Required Data:** Raw IMU, GNSS fixes, OSM road vectors.
* **Complexity:** Low.
* **Explainability:** 100% mathematical physics equations.
* **Fatal Flaw:** Double integration of unconditioned MEMS accelerometer data accrues quadratic velocity and position drift within 5–10 seconds [PS]. Without speed pseudo-measurements, position errors exceed $30\%$ over 1 km [INFERENCE].
* **Verdict:** REJECTED. Fails the mandatory $<10\%$ drift benchmark requirement [PS].

### Approach B: Pure End-to-End Deep Recurrent Neural Network (LSTM / GRU)
* **Mechanism:** End-to-end deep learning model taking sequence windows of 10Hz/100Hz IMU readings and directly outputting absolute global latitude/longitude coordinates or relative $\Delta x, \Delta y$ displacements [1.8].
* **Required Data:** Massive labeled trajectory datasets across all terrain types.
* **Complexity:** High model complexity, simple code pipeline.
* **Explainability:** Zero (black box).
* **Fatal Flaw:** Model predictions easily stray off actual roads, crossing buildings or rivers when encountering unseen driving patterns or vehicle mounting angles [INFERENCE]. Lacks road graph constraints and fails to guarantee physical kinematic plausibility [INFERENCE].
* **Verdict:** REJECTED. Fails reliability and safety requirements [INFERENCE].

### Approach C (RECOMMENDED): Hybrid AI-Kinematic Architecture (1D-CNN Speed Estimator + ES-UKF + NHC + HMM Map Matcher)
* **Mechanism:** Decouples speed prediction from spatial trajectory state filtering:
  1. **In-Vehicle Alignment Engine:** Computes pitch, roll, yaw DCM transformation relative to vehicle chassis ($q_b^v$) [PS].
  2. **AI Speed & Vibration Net:** Uses a lightweight 1D-CNN + BiLSTM to predict forward scalar speed ($v_x$) directly from high-frequency vibration spectra, rejecting potholes/engine idle noise [PS].
  3. **Kinematic Filter (ES-UKF + NHC):** Feeds predicted $v_x$ as a pseudo-measurement into an Error-State Unscented Kalman Filter while enforcing Non-Holonomic Constraints ($v_y = 0, v_z = 0$) [PS].
  4. **HMM Map Matcher:** Applies Viterbi sequence search over OSM road graph topologies to snap predicted trajectories to valid road edges [PS].
* **Accuracy Potential:** $<5\%$ drift over 1 km outage ($<50\text{ m}$ drift), well within the $<100\text{ m}$ ($<10\%$) threshold [PS].
* **Explainability:** Fully explainable state filter and map-matching logic; neural network restricted strictly to velocity regression [INFERENCE].
* **Verdict:** SELECTED. Fulfills all explicit requirements [PS].

### Justification
1. **Solves the Speed Problem Without OBD-II:** Standard SINS double integration fails due to MEMS accelerometer noise. By utilizing a 1D-CNN trained on vehicle kinematic vibrations (e.g., IO-VNBD dataset), the system converts accelerometer variance and spectral signatures into forward speed $v_x$ with $<0.5\text{ m/s}$ error [4.2].
2. **Kinematic Safety Bounds via NHC:** Cars cannot move sideways ($v_y = 0$) or levitate ($v_z = 0$) under normal driving conditions [PS]. Enforcing NHC inside the ES-UKF measurement update step constrains multi-axis drift accumulation [INFERENCE].
3. **Topological Map Assurance:** HMM map-matching evaluates transition probabilities between adjacent road edges using Viterbi candidate scoring, ensuring that temporary sensor heading noise does not snap the vehicle onto parallel or opposite-direction lanes [INFERENCE].
4. **Universal Dual Execution:** Isolating the core filter in pure C++ allows seamless execution on Android smartphones at 10Hz and on industrial embedded edge nodes receiving 200Hz FOG IMU feeds [PS].

### Data-Flow Narrative

1. **Ingestion & Buffering:** Raw 3-axis accelerometer, gyroscope, magnetometer, and GNSS fix data are captured by the native C++ hardware layer at 100Hz on mobile devices (or 200Hz on Linux edge hardware) [PS].
2. **Auto-Calibration:** The alignment module evaluates initial static gravity vectors to derive pitch and roll angles, then evaluates longitudinal acceleration vectors upon initial motion to derive yaw alignment matrix $q_b^v$ [PS].
3. **Noise & Impulse Rejection:** High-frequency engine vibrations and sudden vertical pothole spikes are filtered through an adaptive digital bandpass filter [PS].
4. **AI Velocity Prediction:** Every $100\text{ ms}$, a 1-second sliding window of calibrated IMU data is passed to ONNX Runtime [INFERENCE]. The 1D-CNN + BiLSTM model outputs estimated forward speed $v_x$ [4.2].
5. **State Estimation (ES-UKF):** The 15-state Error-State Unscented Kalman Filter propagates position and velocity states at 100Hz/200Hz [INFERENCE]. 
   * **GNSS Active:** GNSS position and velocity updates calibrate IMU sensor biases ($\mathbf{b}_a, \mathbf{b}_g$) [INFERENCE].
   * **GNSS Outage Triggered:** The system detects signal drops within $<10\text{ ms}$ (e.g., HDOP $> 4.0$ or $C/N_0 < 25\text{ dB-Hz}$) and switches to dead reckoning mode, utilizing predicted AI speed $v_x$ and NHC zero-velocity constraints ($v_y=0, v_z=0$) [INFERENCE].
6. **HMM Map Matching:** The predicted ES-UKF coordinate queries the local spatial R-Tree index for nearby OSM road edges [INFERENCE]. The Viterbi algorithm computes transition probabilities to snap predicted trajectories to valid road geometries [INFERENCE].
7. **UI Rendering / Edge Output:** The snapped state is transmitted via JNI to the Flutter UI for 10Hz rendering, or output to serial/UDP streams at 200Hz on edge hardware [PS].

### Module 1: AI Forward Speed Estimator (1D-CNN + BiLSTM)
* **Purpose:** Predict vehicle forward speed $v_x$ directly from smartphone accelerometer/gyroscope vibration spectra without OBD-II connections [PS].
* **Model Type:** 1D Convolutional Neural Network (3 layers) fused with a Bidirectional LSTM (2 layers, 64 hidden units) [4.2].
* **Input:** 1-second sliding window of 3-axis accelerometer and 3-axis gyroscope data (100 samples @ 100Hz) [4.2].
* **Output:** Scalar forward speed $v_x$ (meters/second) [4.2].
* **Data Required:** Mandated IO-VNBD dataset (smartphone IMU logs synchronized with ECU wheel speed ground truth) [2.3].
* **Why AI is Preferable:** Classical double integration of MEMS accelerometer readings ($\int a \, dt$) accrues quadratic velocity drift within seconds [PS]. Frequency-domain heuristic filters fail because engine RPM and road texture vary non-linearly with vehicle dynamics [INFERENCE].
* **Evaluation Metric:** Mean Absolute Error (MAE) $<0.5\text{ m/s}$, Root Mean Square Error (RMSE) $<0.75\text{ m/s}$ against ECU speed ground truth [4.2].
* **Failure Mode Mitigation:** If the model outputs anomalous negative speeds or extreme speed spikes ($>180\text{ km/h}$), the state filter falls back to kinematic deceleration bounds ($a_{\text{max}} = 6\text{ m/s}^2$).
* **Human Oversight:** Real-time driver UI dashboard displays speed source indicator ("AI Inertial Speed" vs "GNSS Speed").

### Module 2: Road Disturbance & Pothole Classifier
* **Purpose:** Detect and isolate transient impulse shocks (potholes, speed bumps, sharp braking) to prevent filter state corruption [PS].
* **Model Type:** Lightweight 2-layer Convolutional Classifier / Decision Forest [INFERENCE].
* **Input:** High-frequency vertical accelerometer window ($a_z$) [INFERENCE].
* **Output:** Binary classification flag (`NORMAL_MOTION` vs `SURFACE_DISTURBANCE`) [INFERENCE].
* **Data Required:** IO-VNBD surface disturbance logs (bump, hard brake, wet road scenarios) [2.3].
* **Why AI is Preferable:** Simple fixed thresholding fails because high speeds over small expansion joints produce similar peak amplitudes to low speeds over deep potholes [INFERENCE]. AI learns multi-axis waveform shapes [INFERENCE].
* **Evaluation Metric:** Classification Accuracy $>95\%$, Precision $>92\%$ on disturbance windows [INFERENCE].
* **Failure Mode Mitigation:** During detected disturbance windows, zero out measurement updates to the vertical state vector for 500 ms [INFERENCE].

### Where AI Should NOT Be Used
1. **Raw Coordinate Extrapolation:** AI models MUST NOT directly regress absolute latitude and longitude coordinates [INFERENCE]. Direct spatial regression creates unpredictable off-road trajectories and ignores physical road geometries [INFERENCE].
2. **State Propagation Kinematics:** Standard strapdown physics equations ($\mathbf{p}_{k} = \mathbf{p}_{k-1} + \mathbf{v}_k \Delta t + \frac{1}{2} \mathbf{a}_k \Delta t^2$) MUST be governed by deterministic physical state equations inside the ES-UKF, not neural networks [INFERENCE].

### High-Frequency Circular Buffer Architecture
To support 100Hz smartphone IMU collection and 200Hz FOG edge streams without memory allocation overhead, the core C++ engine employs a thread-safe lock-free circular ring buffer (`boost::lockfree::spsc_queue` or custom atomics) [INFERENCE].

```
Raw IMU Producer Thread (100Hz / 200Hz)
       │
       ▼
+--------------------------------------------------------------+
| Thread-Safe Lock-Free Circular Ring Buffer (Capacity: 2048)  |
+--------------------------------------------------------------+
       │
       ├───────────────────────────────┐
       ▼                               ▼

[1s Sliding Window -> ONNX]     [Strapdown Integration & NHC Updates]
```

### Low-Network & Sync Strategy
* **Zero Network Dependency during Driving:** The map-matching engine queries the pre-downloaded local SQLite database directly on the device [PS].
* **Deferred Trajectory Sync:** When the vehicle regains network connectivity, high-level summary metrics (outage duration, drift distance, road segment IDs) are compressed using Protocol Buffers and synced to the cloud dashboard [INFERENCE].
