## 1. Executive Snapshot

### Summary
India's critical industrial and strategic sectors—including petroleum refining, petrochemicals, power grids, logistics, and defense—depend almost exclusively on foreign commercial mathematical optimization solvers such as IBM ILOG CPLEX, Gurobi, and FICO Xpress [PS, KNOWN]. These proprietary engines control high-stakes decisions like refinery crude blending, production scheduling, and supply chain allocation, creating foreign software lock-in, high recurring licensing costs, and national security vulnerabilities [PS, INFERENCE]. While open-source CPU solvers (such as COIN-OR CBC, HiGHS, and SCIP) exist, they lag on large-scale mixed-integer industrial models and lack native GPU acceleration for massive sparse linear algebra [PS, RESEARCHED]. This dossier details the architecture, technical roadmap, and implementation strategy for building an **Indigenous GPU-Accelerated Optimization Solver Core** from mathematical first principles [PS]. Built in modern C++20 and CUDA, the system combines a CPU-based multi-threaded Branch-and-Cut / Presolve framework with a GPU-accelerated linear algebra engine utilizing restarted Primal-Dual Hybrid Gradient (PDHG) and Interior Point Methods (IPM) [INFERENCE, RESEARCHED]. Designed to handle ill-conditioned, highly degenerate, and sparse industrial constraints from Mangalore Refinery and Petrochemicals Limited (MRPL) and benchmarked against MIPLIB 2017 and Netlib LP, this project establishes a sovereign foundation for Indian mathematical optimization software [PS, RESEARCHED].

2. **Air-Gapped Operational Environments**:
   - Refinery control rooms and defense installations operate in strictly air-gapped, offline networks without cloud access [PS, INFERENCE].

   - *Constraint*: Double-precision (`f64`) floating-point arithmetic is mandatory; critical basis factorizations require numerical pivoting and quadrupled precision (`f128` or double-double) fallback passes [INFERENCE, RESEARCHED].

4. **Sovereignty & Open Source Intellectual Property**:
   - Explicit mandate: "It shall not be built upon any existing open source solver library" [PS].
   - *Constraint*: Code audit strictly forbids pulling in SCIP, HiGHS, CBC, GLPK, or Cbc source code [PS]. Algorithmic techniques must be coded from textbook and academic literature primitives [PS, INFERENCE].

## 6. Research Questions

1. **GPU Acceleration Feasibility in Linear Programming**:
   - *Question*: Why have traditional Simplex methods struggled on GPUs, and why are first-order methods (like Restarted PDHG) or parallel interior-point matrix updates now winning on GPU architectures? [RESEARCHED]
   - *Findings*: Simplex relies on sequential basis changes (tableau updates), creating low arithmetic intensity unsuitable for massively parallel SIMD GPU architectures [RESEARCHED]. Restarted PDHG transforms LP into matrix-vector multiplications (`SpMV`), achieving up to 100x speedups on GPUs for large LPs [RESEARCHED].

2. **Presolve Impact on GPU Operations**:
   - *Question*: Does presolving remain critical when using ultra-fast GPU LP algorithms? [RESEARCHED]
   - *Findings*: Yes. Recent research shows presolving reduces matrix condition numbers and eliminates redundant rows, preventing GPU first-order methods from stalling on ill-conditioned bounds [RESEARCHED].

3. **GPU Role in Mixed-Integer Programming (MILP)**:
   - *Question*: Can the entire Branch-and-Bound tree fit onto a GPU, or is a hybrid CPU-GPU model superior? [RESEARCHED]
   - *Findings*: Branch-and-Bound tree management involves complex pointer manipulation and branch decisions best suited for CPU cores [RESEARCHED]. GPUs excel at root-node LP relaxations, parallel primal heuristics (Feasibility Pump, Probing), and large sub-MIP solutions [RESEARCHED].

4. **Numerical Stability Strategies for Refinery LPs**:
   - *Question*: How do CPLEX and Gurobi prevent numerical breakdown on ill-conditioned refinery models? [RESEARCHED]
   - *Findings*: Through aggressive Ruiz matrix equilibration, dual presolve, Markowitz tolerance pivoting in LU factorizations, and iterative refinement [RESEARCHED].

- **Mechanism**: Implement C++20 Revised Dual Simplex and Barrier Interior Point Method (IPM) using SuiteSparse/Eigen for sparse Cholesky CPU factorizations, integrated with a multi-threaded CPU Branch-and-Cut tree search [INFERENCE].
- **Data Requirements**: Standard MPS/LP files [PS].
- **Architecture**: Pure C++ multi-threaded architecture utilizing OpenMP/std::thread for parallel node evaluations [INFERENCE].
- **Evaluation**:
  - *Problem Fit*: Good for small-to-medium LPs and standard MILPs [INFERENCE].
  - *Accuracy Potential*: Very High (Simplex provides exact basic solutions) [RESEARCHED].
  - *Complexity*: Medium [INFERENCE].
  - *Explainability*: Excellent [INFERENCE].

- **Mechanism**: Implement a GPU-native LP solver using Primal-Dual Hybrid Gradient (PDHG) with restarted step sizes and diagonal matrix scaling, entirely executing on CUDA kernels (`cuSPARSE` / custom CUDA) [RESEARCHED].
- **Data Requirements**: Standard MPS/LP files converted to GPU CSR format [INFERENCE].
- **Architecture**: Monolithic CUDA engine where matrix-vector operations (`SpMV`) happen 100% on GPU memory [RESEARCHED].
- **Evaluation**:
  - *Problem Fit*: Outstanding for massive continuous LPs (million+ variables) [RESEARCHED].
  - *Accuracy Potential*: Moderate (first-order methods converge to $10^{-4} - 10^{-6}$ precision, requiring crossover for exact basic solution) [RESEARCHED].
  - *Complexity*: High (CUDA kernel tuning, matrix scaling) [INFERENCE].
  - *Explainability*: Moderate [INFERENCE].
  - *Cost*: Requires CUDA-capable NVIDIA GPUs [INFERENCE].
  - *Scalability*: Extremely High for LP [RESEARCHED].
  - *Hackathon Feasibility*: Moderate [INFERENCE].
  - *Production Feasibility*: Moderate (needs CPU crossover for MILP branching) [RESEARCHED].

## 10. Recommended Approach & Why

### Selection
**Approach 3: Heterogeneous Hybrid Solver Architecture** is selected [INFERENCE].

### Justification
1. **Why Approach 1 was rejected as standalone**: Pure CPU solvers cannot bridge the computational performance gap on million-variable continuous relaxations without hardware acceleration [PS, RESEARCHED]. Relying solely on CPU Simplex fails the requirement to explore GPU acceleration where measurable benefits exist [PS].
2. **Why Approach 2 was rejected as standalone**: Pure first-order GPU LP solvers struggle to deliver exact corner-point basic solutions needed for MILP node branching and cut generation without a simplex crossover mechanism [RESEARCHED]. Furthermore, Branch-and-Bound tree logic is inherently dynamic and inefficient when forced into pure GPU SIMD execution [RESEARCHED].
3. **Why Approach 3 Wins**: Approach 3 leverages the distinct strengths of both hardware architectures: GPUs handle massive parallel matrix-vector products (`SpMV`) in first-order LP algorithms and parallel primal heuristics, while CPUs manage complex pointer-heavy Branch-and-Bound trees, cutting plane generation, and exact simplex basis factorizations [RESEARCHED, INFERENCE]. This satisfies all requirements of SIH26119 while providing a scalable, sovereign solution [PS, INFERENCE].

### Detailed Data-Flow Narrative
1. **Ingestion**: The user passes an `.mps` or `.lp` file via CLI or Python bindings [PS, INFERENCE]. The C++ parser reads the file into an in-memory sparse matrix structure (`ProblemModel`) [INFERENCE].
2. **Presolve & Scaling**: The model passes through the presolver to eliminate redundant constraints, fix singleton variables, and propagate bounds [RESEARCHED]. The resulting reduced matrix is normalized using Ruiz equilibration scaling to ensure numerical stability [RESEARCHED].
3. **Problem Dispatch**:
   - For **Continuous LPs**: The scaled sparse matrix (CSC/CSR format) is copied to GPU device memory [RESEARCHED]. The GPU Restarted PDHG solver executes thousands of parallel primal-dual matrix-vector multiplications per second until primal/dual residuals reach tolerance ($10^{-6}$) [RESEARCHED]. If an exact basic solution is requested, the candidate solution is transferred to CPU Dual Simplex for rapid Crossover basis identification [RESEARCHED].
   - For **MILPs**: The CPU Branch-and-Cut manager initializes the root node [INFERENCE]. The LP relaxation is solved via GPU PDHG or CPU Simplex [RESEARCHED]. Generated cuts (Gomory fractional cuts, cover cuts) are added to tighten the relaxation [INFERENCE]. Simultaneously, GPU parallel primal heuristics run in background CUDA streams to quickly find valid integer feasible solutions [RESEARCHED]. Branching decisions (strong branching / pseudocost) spawn child nodes managed in a prioritized CPU queue [INFERENCE].
4. **Postsolve**: Optimal variable values and dual multipliers are un-scaled, mapped back through presolve reductions to original variable indices, and written to a `.sol` output file or returned to the API caller [INFERENCE].

## 13. AI/ML Justification

### Strategic AI Analysis
While classical mathematical optimization algorithms (Simplex, IPM, Branch-and-Bound) are deterministic and exact, Machine Learning (ML) can accelerate non-critical heuristic search decisions within the solver pipeline [RESEARCHED]. **Core numerical linear algebra decisions (such as basis inversions, presolve reductions, and feasibility proofs) must NOT use AI/ML** to preserve 100% mathematical rigor and guarantee solution validity [PS, INFERENCE].

| **Heuristic Selection Meta-Learner** | Select which primal heuristic (Feasibility Pump vs RINS vs Local Search) to run based on matrix structure [RESEARCHED]. | Decision Tree / Random Forest [INFERENCE]. | Matrix sparsity percentage, integer variable ratio, constraint type distribution [INFERENCE]. | Recommended heuristic execution policy [INFERENCE]. | Offline solver run logs on Netlib/MIPLIB [INFERENCE]. | Prevents wasting GPU/CPU compute on ineffective heuristics [INFERENCE]. | Time-to-first-feasible-solution [INFERENCE]. | Suboptimal heuristic chosen; Fallback: Run default Feasibility Pump [INFERENCE]. | None [INFERENCE]. |

### Where AI Should NOT Be Used
- **Presolve Matrix Reductions**: Rule-based logical reductions must be exact; ML predictions here risk introducing infeasibility or changing the optimal solution space [INFERENCE].
- **Basis Pivoting & Dual Simplex**: Simplex pivot selections must adhere strictly to Dantzig or Steepest Edge pricing rules to guarantee dual feasibility and termination [INFERENCE].
- **Optimality Gap & Certificate Verification**: Optimality proofs ($c^T x = b^T y$) must be calculated via exact double-precision floating-point linear algebra [INFERENCE].
