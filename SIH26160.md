## 1. Executive Snapshot

The National Technical Research Organisation (NTRO) requires an AI-driven protocol analysis platform capable of automatically evaluating Internet Protocol Security (IPsec) Virtual Private Network (VPN) deployments across diverse security configurations [PS]. While IPsec is foundational for securing communications across military, government, and enterprise infrastructures [PS], proper security relies on complex cryptographic configurations, key exchanges, operational modes, and traffic management [PS]. Misconfigurations or legacy algorithms introduce critical vulnerabilities that traditional packet analyzers (e.g., Wireshark) cannot flag without manual, specialized analysis [PS]. 

This project addresses this gap by creating an end-to-end framework consisting of an automated Docker-based VPN testbed generator [INFERENCE], a packet capture engine [PS], an intelligent protocol identification engine using rule-based parsing and ML traffic profiling [INFERENCE], an automated security compliance evaluator based on NIST SP 800-77 Rev. 1 [RESEARCHED], and an executive/technical dashboard [PS].

## 5. Constraints & Environment Realities

1.  **Air-Gapped / Isolated Operation [INFERENCE]:** Intelligence and defense environments like NTRO frequently operate in air-gapped classified networks [KNOWN]. The platform must execute entirely offline without external cloud API dependencies (e.g., OpenAI, external ML APIs) [INFERENCE].
2.  **ESP Encryption Boundaries [KNOWN]:** ESP encrypts the inner IP packet and payload [KNOWN]. Payload Inspection (DPI) is mathematically impossible without private keys [KNOWN]. Feature extraction must rely strictly on metadata (flow duration, packet size sequence, inter-arrival time, directional ratios) [RESEARCHED].
3.  **Missing IKE Handshakes in Live Streams [INFERENCE]:** In real-world passive interception, analysts often capture ongoing ESP traffic without having recorded the initial IKE key negotiation exchange [KNOWN]. The framework must handle both "Complete Handshake + ESP" and "ESP-Only" scenarios gracefully [INFERENCE].
4.  **Hardware & Compute Constraints during Hackathon [ASSUMPTION]:** Standard student laptops (8–16 GB RAM, x86_64 CPU, optional entry-level GPU) [ASSUMPTION]. AI models must be lightweight (e.g., Scikit-Learn ensembles, lightweight PyTorch 1D-CNN) to perform inference in sub-seconds [INFERENCE].
5.  **Operating System Dependencies [KNOWN]:** IPsec kernel transformation (`xfrm`) and strongSwan require Linux kernel support [KNOWN]. The testbed containerization must target Linux environments (Ubuntu/Debian containers) [INFERENCE].

3.  *Tunnel vs. Transport Mode Inference:* In the absence of IKE handshakes, can header size differences (e.g., 20-byte outer IP header vs. double IP header encapsulation) reliably distinguish Tunnel Mode from Transport Mode? [INFERENCE]
4.  *Cryptographic Scoring Baseline:* How do NIST SP 800-77 Rev. 1, NSA Commercial National Security Algorithm (CNSA) Suite 2.0, and CIS Benchmarks define numerical severity weights for legacy algorithms (e.g., 3DES, MD5, DH Group 2)? [RESEARCHED]

### Approach 1: Heuristic & Rule-Based Scripting Framework
*   **Mechanism:** Python script using `tshark` CLI to dump packet JSON. Static regex matching reads IKE proposals and compares ciphers against a CSV list of insecure algorithms [INFERENCE].
*   **Pros:** Fast to implement, low compute requirements, highly explainable [INFERENCE].
*   **Cons:** Fails on encrypted ESP payload identification (cannot predict VoIP vs. Video); cannot generalize to missing handshake scenarios; no confidence scoring [INFERENCE].
*   **Hackathon Feasibility:** High (1–2 days build) [INFERENCE].
*   **Production Feasibility:** Low (Inadequate for complex NTRO intelligence requirements) [INFERENCE].

### Approach 2: Pure End-to-End Deep Learning (Raw Packet Bytes to Image CNN)
*   **Mechanism:** Convert raw packet byte streams (first 1500 bytes of pcap flows) into 2D grayscale images and train a ResNet/2D-CNN model to predict cryptosuites and payload types simultaneously [RESEARCHED].
*   **Pros:** Requires minimal manual feature engineering [RESEARCHED].
*   **Cons:** High compute overhead, black-box model (no clear explainability for judges), prone to overfitting on source/destination IP/port artifacts rather than real traffic features [RESEARCHED].
*   **Hackathon Feasibility:** Medium (High risk of training failures and overfitting) [INFERENCE].
*   **Production Feasibility:** Medium [INFERENCE].

### Approach 3: Recommended Hybrid Architecture (Deterministic Dissection + Feature-Engineered ML + Automated Audit Matrix)
*   **Mechanism:** 
    1. *Deterministic Engine:* Uses `PyShark` / `Scapy` to parse unencrypted IKE (`UDP 500/4500`) fields (`Transform Payloads`, `DH Groups`, `PFS`, `IKE Version`) with 100% accuracy [KNOWN].
    2. *ML Feature Engine:* Extracts statistical flow features (Packet Size Histograms, Mean/Std Dev Inter-Arrival Time, Directional Byte Ratios, Flow Burstiness) from ESP flows. Evaluates a dual-stage ML model (Random Forest for Mode prediction, 1D-CNN + XGBoost for inner traffic classification) [RESEARCHED].
    3. *Audit Engine:* Cross-references extracted SA parameters against NIST SP 800-77 Rev. 1 compliance rules to generate quantitative security scores, threat matrices, and confidence levels [RESEARCHED].
*   **Pros:** Combines 100% accuracy on protocol parsing with state-of-the-art ML on encrypted ESP streams. Highly explainable, fast execution, low memory footprint [INFERENCE].
*   **Hackathon Feasibility:** High [INFERENCE].
*   **Production Feasibility:** Enterprise/Defense Grade [INFERENCE].

## 10. Recommended Approach & Why

**Selected Approach:** Approach 3 (Hybrid Architecture) [INFERENCE].

### Why Alternatives Were Rejected:
*   *Approach 1 (Heuristic Only) Rejected:* It completely fails Requirement (c)'s explicit mandate to "Predict Type of traffic inside ESP-IPsec" [PS]. Rule-based systems cannot classify encrypted payloads without statistical ML [RESEARCHED].
*   *Approach 2 (Pure Raw Byte Deep Learning) Rejected:* Raw byte CNNs suffer from "shortcut learning" where models memorize IP addresses, port numbers, or MAC addresses instead of learning true traffic dynamics [RESEARCHED]. Furthermore, black-box CNNs cannot explicitly state *why* a cipher suite failed compliance, violating the explainability requirements for defense analysts [INFERENCE].

### Strategic Winning Rationale:
The Hybrid Approach provides strict mathematical certainty where protocol headers exist (IKE dissection), while applying statistical AI models where payloads are encrypted (ESP analysis) [INFERENCE]. This directly fulfills every sub-requirement (a–e) in the NTRO problem statement [PS].

## 13. AI/ML Justification

### Component 1: Encrypted ESP Traffic Classifier

1.  **Exact Problem AI Solves:** Classifying the inner application protocol (VoIP, Video, Web, Email, ICMP) hidden inside encrypted ESP payloads where deep packet payload inspection is mathematically impossible [PS, KNOWN].
2.  **Input:** 29-element flow feature vector derived from packet size sequences, inter-arrival times, burst lengths, and byte counts [RESEARCHED].
3.  **Output:** Categorical probability distribution across application classes (e.g., VoIP: 94%, Video: 4%, Web: 2%) [INFERENCE].
4.  **Why Simpler Rule System Cannot Solve:** Payload contents are encrypted. Fixed port rules fail because IPsec ESP encapsulates everything into uniform IP Protocol 50 headers, stripping original L4 port information [KNOWN].
5.  **Data Required:** 10,000+ labeled flow samples across target applications collected via the Docker testbed [INFERENCE].
6.  **Evaluation Method:** F1-Score, Multi-class Accuracy, Confusion Matrix, Macro-Precision/Recall [INFERENCE].
7.  **What Happens When Wrong:** Model outputs low confidence score (<60%). Platform flags classification as "Uncertain / Requires Active Inspection" [INFERENCE].
8.  **Training Required:** Yes, offline training on synthetic testbed dataset [INFERENCE].
9.  **Fine-Tuning Required:** Optional for target network baselines [INFERENCE].
10. **RAG Required:** No [INFERENCE].
11. **Computer Vision Required:** No (1D sequential feature vector used instead of 2D images) [RESEARCHED].
12. **Speech Processing Required:** No [INFERENCE].
13. **Forecasting Required:** No [INFERENCE].
14. **Human Oversight:** Yes, analyst can override predicted labels on dashboard [INFERENCE].

### Component 2: Tunnel vs. Transport Mode ML Predictor (Missing Handshake Scenario)

1.  **Exact Problem AI Solves:** Inferring whether an active ESP stream uses Tunnel Mode or Transport Mode when initial IKE negotiation packets were not captured [PS, INFERENCE].
2.  **Input:** Sequence of ESP packet lengths, IP header length fields, and MTU padding distribution [INFERENCE].
3.  **Output:** Binary classification (Tunnel Mode vs. Transport Mode) + Confidence Score [INFERENCE].
4.  **Why Simpler Rule System Cannot Solve:** Packet sizes vary by payload. While Tunnel Mode adds an extra 20-byte outer IP header, payload variability can mask exact size differences without statistical flow aggregation [INFERENCE].
5.  **Data Required:** 2,000+ paired ESP flows captured in both Tunnel and Transport modes [INFERENCE].
6.  **Evaluation Method:** ROC-AUC Curve, Binary Accuracy [INFERENCE].
