## 1. Executive Snapshot

`DepthWizard` is an end-to-end geospatial artificial intelligence (GeoAI) pipeline and 3D visualization framework designed for the Indian Space Research Organisation (ISRO) [PS]. The platform resolves the domain gap in monocular height estimation by combining a pre-trained vision foundation model backbone with an adaptive scale-calibration module [INFERENCE]. It transforms single-view optical satellite images into high-precision Relative Digital Surface Models (rDSM) or absolute metric Digital Surface Models (DSM) [PS]. These elevation maps are projected onto 3D terrain meshes rendered in real time using a WebGL client (Three.js / CesiumJS) [INFERENCE], allowing field operators, urban planners, and defense personnel to navigate terrain, measure building/structural heights, and analyze terrain slopes from arbitrary aerial perspectives [PS].

## 2. Problem Deconstruction

The problem statement provided by ISRO contains explicit architectural, algorithmic, data format, and evaluation constraints [PS]. Below is the atomic extraction and interpretation of each explicit requirement:

*   **Requirement 1 (Core Pipeline) [PS]:** Develop an end-to-end software pipeline that transforms single-view optical RGB remote-sensing images into high-precision elevation maps.
    *   *Interpretation:* The input is a single optical image (no stereo pairs, multi-view passes, or LiDAR required during inference) [INFERENCE].
    *   *Implementation Implication:* The core ML component must infer dense depth maps from single 2D RGB arrays using learned spatial, contextual, and shadow priors [INFERENCE].
*   **Requirement 2a (Non-Georeferenced Mode) [PS]:** For non-georeferenced RGB imagery (e.g., PNG, JPG), produce a Relative Digital Surface Model (rDSM) without spatial metadata, where relative height values are used directly in the visualization stage.
    *   *Interpretation:* When coordinate metadata is missing, the system must gracefully fall back to normalized relative depth ($[0, 1]$ or $[0, 255]$) and render a geometrically plausible 3D terrain [INFERENCE].
*   **Requirement 2b (Georeferenced Mode) [PS]:** For georeferenced RGB imagery (e.g., GeoTIFF), produce an Absolute Digital Surface Model (DSM) with metric height values (meters above sea level / ellipsoid) using spatial coordinate metadata.
    *   *Interpretation:* The system must parse geospatial headers (EPSG projection, affine transform matrix, pixel scale) and output standardized geospatial rasters (GeoTIFF / COG) with absolute vertical metric values [INFERENCE].
*   **Requirement 3 (Monocular Backbone & Scale Calibration) [PS]:** Use a pre-trained monocular depth-estimation backbone to generate initial relative-depth maps. Convert relative depth to absolute height using scene-level statistics, low-resolution DEMs (e.g., SRTM 30m), semantic priors, or minimal Ground Control Points (GCPs).
    *   *Interpretation:* Foundation models predict depth up to an unknown scale and shift ($s \cdot d + t$) [KNOWN]. A scale calibration algorithm must solve for $(s, t)$ by co-registering the relative depth map with coarse public elevation baselines (SRTM 30m / Copernicus DEM 30m) or user-supplied sparse GCPs [INFERENCE].
*   **Requirement 4 (3D Visualization & Rendering Layer) [PS]:** Project the original optical image texture onto a generated 3D terrain mesh and integrate the result with a rendering engine (e.g., Three.js, Unity, or Babylon.js). Provide an interface supporting seamless first-person navigation and interactive analysis of structural heights and slopes from arbitrary aerial perspectives.
    *   *Interpretation:* The frontend must generate dynamic heightfields / 3D terrain geometry, texture-map the optical satellite image, provide flight/orbit controls, and include measurement tools for vertical clearance and slope calculation [INFERENCE].
*   **Requirement 5 (Input / Output Deliverables) [PS]:** Deliver a unified software suite accepting optical imagery in PNG, JPG, or TIFF format, outputting high-fidelity DSMs in standard geospatial formats, and providing interactive tools to validate estimated height values against reference datasets.
    *   *Interpretation:* Software must be deliverable as a deployable application (web/desktop) with complete source code, dataset evaluation tools, and validation metrics (RMSE, MAE, Correlation) [INFERENCE].
*   **Requirement 6 (Evaluation Criteria & Weights) [PS]:**
    *   *DSM Estimation Accuracy & Validation (50%):* Evaluated using Root Mean Square Error (RMSE), Mean Absolute Error (MAE), and Pearson Correlation ($r$) against LiDAR or reference data across urban, sparse, hilly, and forested landscapes.
    *   *Visualization & UX (50%):* Assessed on projection accuracy, visual fidelity, 3D flythrough navigability, UI intuitiveness, software stability, and successful standalone deployment.

## 5. Constraints & Environment Realities

*   **Geographic & Landscape Heterogeneity:** The model must operate consistently across diverse Indian terrains: dense urban concrete jungles (steep height discontinuities), sparse rural plains, steep hilly/mountainous terrain (Himalayan slopes), and dense forest canopies (where canopy surface vs. ground elevation differs) [PS].
*   **Geospatial Scale & Resolution Disparity:** High-resolution optical imagery typically ranges from $0.3\text{ m}$ to $1.0\text{ m}$ per pixel (Cartosat-2/3, WorldView), whereas freely available elevation baselines like SRTM or Copernicus DEM are at $30\text{ m}$ resolution [KNOWN]. The calibration module must bridge a $30\times$ to $100\times$ spatial resolution gap without blurring fine structural edges [INFERENCE].
*   **Hardware & Processing Constraints:** Hackathon and field deployment targets often lack multi-GPU clusters. Inference must run efficiently on consumer GPUs (e.g., NVIDIA RTX 3060 / RTX 4060 or Google Colab T4) within $\le 10$ seconds per $1024 \times 1024$ tile [ASSUMPTION].
*   **Network & Air-Gapped Operation:** Disaster response teams and military operators frequently operate in low-bandwidth or completely air-gapped environments. The 3D visualization and inference engine must support local, standalone offline deployment without requiring external map tile servers [PS].
*   **Monocular Illumination & Shadow Dependencies:** Single-view height estimation relies heavily on spatial contextual cues (building shadows, sun angle, perspective cues) [RESEARCHED]. Variable illumination and extreme sun angles can introduce artificial elevation distortion if unmitigated [INFERENCE].

## 6. Research Questions

1.  *Backbone Selection:* Does a fine-tuned monocular vision foundation model (e.g., Depth Anything v2 or Marigold) outperform remote-sensing-specific CNN/Transformer architectures (e.g., MAFENet) in zero-shot generalization across Indian terrain types?
2.  *Scale Recovery Precision:* Can a robust RANSAC-based affine linear regression ($z_{\text{metric}} = s \cdot d_{\text{relative}} + t$) co-registered with $30\text{ m}$ SRTM DEM achieve an RMSE below $3.0\text{ meters}$ in urban environments?
3.  *Edge Preservation:* How can structural building boundaries be preserved in the DSM when coarse DEMs ($30\text{ m}$) smooth out vertical architectural walls?
4.  *Client Rendering Performance:* What is the maximum heightmap resolution ($1024\times1024$ vs $2048\times2048$) that Three.js / CesiumJS can render at $\ge 60\text{ FPS}$ on a mid-range client machine during continuous first-person flythroughs?
5.  *Validation Calibration:* How do shadow-based height priors complement coarse DEM fitting when SRTM data is noisy or obscured by clouds/steep terrain?

## 9. Candidate Solution Approaches

### Approach 1: End-to-End Deep Learning Fine-Tuning (Full Supervised Model)
*   **Mechanism:** Train a custom encoder-decoder neural network (e.g., MAFENet or UNet++ with Swin Transformer backbone) directly mapping high-resolution satellite RGB patches to absolute metric DSMs using paired LiDAR training datasets [RESEARCHED].
*   **Evaluations:**
    *   *Problem Fit:* High fit for metric output; learns terrain-specific representations [INFERENCE].
    *   *Accuracy Potential:* High in trained geographies; moderate to poor on unseen terrain types due to overfitting [INFERENCE].
    *   *Data Requirements:* Massive paired high-res RGB + LiDAR DSM dataset (100+ GB) [INFERENCE].
    *   *Complexity:* High (requires deep network architecture development, loss function engineering) [INFERENCE].
    *   *Explainability:* Low (black-box neural network) [INFERENCE].
    *   *Cost & Scalability:* High training cost; requires dedicated GPU cluster (NVIDIA A100/H100) [INFERENCE].
    *   *Hackathon Feasibility:* **Low** (training from scratch within hackathon limits is high-risk and time-prohibitive) [INFERENCE].
    *   *Production Feasibility:* Moderate [INFERENCE].

### Approach 2: Two-Stage Hybrid Framework (Pre-Trained Foundation Backbone + Affine Scale Calibration & Local DEM Alignment + WebGL Engine)
*   **Mechanism:**
    1.  Pass single RGB image through a state-of-the-art pre-trained monocular vision backbone (e.g., Depth Anything v2 / Metric3D) to extract a dense, scale-agnostic relative depth map $d_{\text{rel}}$ [RESEARCHED].
    2.  For georeferenced images, pull low-resolution SRTM $30\text{ m}$ elevation data for the bounding box. Apply RANSAC-based robust linear regression ($z_{\text{abs}} = s \cdot d_{\text{rel}} + t$) to fit relative depth to the SRTM baseline while filtering out structural outliers [RESEARCHED].
    3.  For non-georeferenced images, use normalized relative height or user-supplied ground control points (GCPs) for metric scaling [PS].
    4.  Stream texture and height maps into a client-side WebGL engine (Three.js / CesiumJS) for real-time 3D rendering and measurement [PS].
*   **Evaluations:**
    *   *Problem Fit:* Perfect fit for all explicit requirements [INFERENCE].
    *   *Accuracy Potential:* High structural accuracy ($0.5-1.5\text{ m}$ relative) with coarse absolute anchor ($2-4\text{ m}$ absolute RMSE) [RESEARCHED].
    *   *Data Requirements:* Lightweight (pre-trained weights + open SRTM tiles) [INFERENCE].
    *   *Complexity:* Moderate (requires clean algorithmic formulation of affine calibration and WebGL rendering) [INFERENCE].
    *   *Explainability:* High (scale factor $s$ and translation $t$ are mathematically explicit and auditable) [INFERENCE].
    *   *Cost & Scalability:* Low cost; runs efficiently on consumer GPUs / CPUs [INFERENCE].
    *   *Hackathon Feasibility:* **Very High** (highly realistic to complete and demonstrate within limited dev time) [INFERENCE].
    *   *Production Feasibility:* High [INFERENCE].

### Approach 3: Shadow-Guided Geometric & Physics-Based Reconstruction Hybrid
*   **Mechanism:** Combine classical shadow-length geometry ($h = L \cdot \tan \theta_{\text{sun}}$) with classical monocular depth estimation. Extract building footprints via segmentation (Segment Anything Model / Mask R-CNN), measure shadow vectors based on solar azimuth and elevation metadata, compute exact absolute heights for structures, and interpolate ground terrain using SRTM [RESEARCHED].
*   **Evaluations:**
    *   *Problem Fit:* High for urban landscapes with clear shadows; poor for cloudy imagery, dense forests, or flat terrain [INFERENCE].
    *   *Accuracy Potential:* High for tall isolated buildings; fails on complex terrain or low sun angles [RESEARCHED].
    *   *Data Requirements:* Requires accurate solar elevation/azimuth metadata in imagery EXIF/headers [RESEARCHED].
    *   *Complexity:* Extremely high (shadow segmentation, directional filtering, sun angle math) [INFERENCE].
    *   *Explainability:* High (physics-based formulation) [INFERENCE].
    *   *Cost & Scalability:* Moderate [INFERENCE].
    *   *Hackathon Feasibility:* **Moderate-Low** (shadow extraction is highly prone to edge failures during live demos) [INFERENCE].
    *   *Production Feasibility:* Moderate [INFERENCE].

## 10. Recommended Approach & Why

The recommended choice is **Approach 2: Two-Stage Hybrid Framework (Pre-Trained Foundation Backbone + Adaptive Affine Calibration + WebGL Rendering Engine)** [INFERENCE].

### Why Alternatives Were Rejected:
*   *Rejection of Approach 1 (Full Supervised Fine-Tuning):* Model pre-training from scratch requires massive LiDAR-satellite paired datasets that cannot be reliably ingested, cleaned, and trained within a short hackathon window [INFERENCE]. Furthermore, end-to-end models overfit to specific sensor characteristics and fail when evaluated on unseen ISRO satellite bands [INFERENCE].
*   *Rejection of Approach 3 (Pure Shadow Geometry):* Shadow-based calculation fails in un-illuminated, overcast, forested, or mountainous regions where distinct shadow boundaries do not exist [RESEARCHED]. It also violates Requirement 2a/2b by being unable to handle images lacking solar metadata [INFERENCE].

### Why Approach 2 Wins:
1.  **Strict Compliance with PS:** Fulfills all explicit requirements—uses pre-trained monocular backbone, supports non-georeferenced (relative) and georeferenced (absolute via SRTM/GCP) workflows, and feeds directly into Three.js/Babylon.js 3D flythrough environments [PS].
2.  **Robustness & Zero-Shot Generalization:** Pre-trained foundation models (e.g., Depth Anything v2) contain massive structural priors, guaranteeing sharp building and ridge boundaries even without fine-tuning [RESEARCHED].
3.  **Mathematical Explainability:** The scale calibration step uses transparent linear regression ($s, t$) with RANSAC outlier rejection, enabling easy auditing, manual correction, and ground control point (GCP) override [INFERENCE].

### Data Flow Narrative

1.  **Ingestion:** User uploads a satellite image via the Web React UI [INFERENCE].
    *   If GeoTIFF: `rasterio` extracts spatial extent, coordinate reference system (CRS: e.g., EPSG:4326), pixel transformation matrix, and nodata values [INFERENCE].
    *   If PNG/JPG: Raw RGB pixel array is decoded into image tensors without spatial metadata [INFERENCE].
2.  **Inference:** The RGB tensor is passed through the pre-trained Monocular Depth Backbone (PyTorch runtime GPU backend) [INFERENCE]. The backbone outputs a floating-point relative depth array $d_{\text{rel}} \in [0, 1]$ matching image dimensions [INFERENCE].
3.  **Scale Calibration:**
    *   For GeoTIFF: The backend uses spatial coordinates to query the local SRTM 30m DEM baseline tile [INFERENCE]. The SRTM DEM is resampled to match the high-res optical image grid. RANSAC regression estimates scale ($s$) and shift ($t$), filtering out high-frequency structural outliers (buildings/trees not present in $30\text{ m}$ SRTM). Absolute metric surface elevation is derived: $Z_{\text{metric}} = s \cdot d_{\text{rel}} + t$ [INFERENCE].
    *   For PNG/JPG: Normalized relative values are scaled directly or calibrated using user-entered Ground Control Points (GCPs) [PS].
4.  **Export & Storage:** Output elevation raster is serialized into a 32-bit Float GeoTIFF (or COG) and stored in local cache/disk [INFERENCE].
5.  **3D Flythrough Rendering:**
    *   Backend transmits the optical RGB texture image and downsampled float elevation array (PNG/WebP packed depth or JSON array) to the Three.js client [INFERENCE].
    *   Custom WebGL vertex shaders displace terrain mesh geometry dynamically according to height values, while fragment shaders apply the optical satellite texture [INFERENCE].
    *   User navigates terrain via camera flythrough, clicking points to query absolute elevation, structural heights ($\Delta z$), and slope angles [PS].

## 13. AI/ML Justification

### 1. Monocular Depth Backbone (Depth Anything v2 / Metric3D)
*   **Purpose:** Extract fine-grained relative geometric and structural representations (building edges, street channels, hill ridges) from a single 2D optical RGB satellite image [PS].
*   **Model Type:** Vision Transformer (ViT-Encoder) + DPT Decoder [RESEARCHED].
*   **Input:** Single RGB image array $(H \times W \times 3)$ [PS].
*   **Output:** Continuous relative depth map $(H \times W \times 1)$, $d_{\text{rel}} \in [0, 1]$ [PS].
*   **Data Required:** Pre-trained weights (Depth Anything v2 Small/Base trained on 62M imagery) [RESEARCHED].
*   **Why AI is Preferable:** Classical geometric photogrammetry mathematically fails on a single 2D image because stereoscopic parallax requires at least two distinct viewing angles [KNOWN]. AI leverages learned visual priors (shadow gradients, texture compression, perspective cues) [RESEARCHED].
*   **Evaluation:** Evaluated on relative structural consistency using Scale-Invariant Error (SILog) and Pearson Correlation ($r$) against reference ground truth [PS].
*   **Failure Mode:** Flat uniform regions (e.g., calm water bodies, desert sand dunes, snow fields) lack texture, causing depth artifacts or false height variations [INFERENCE].
*   **Human Oversight:** User interface includes mask toggles to zero out water/flat surfaces using NDWI thresholds or manual region overrides [INFERENCE].

### 2. Affine Scale & Shift Calibration Head
*   **Purpose:** Map scale-agnostic relative depth outputs to absolute metric elevation values ($Z_{\text{metric}}$ in meters) [PS].
*   **Model Type:** RANSAC Robust Linear Regression ($z_{\text{abs}} = s \cdot d_{\text{rel}} + t$) [RESEARCHED].
*   **Input:** Relative depth array $d_{\text{rel}}$ and co-registered coarse DEM raster $Z_{\text{coarse}}$ (SRTM 30m) [PS].
*   **Output:** Metric scale factor $s$ (float) and offset/translation factor $t$ (float) [INFERENCE].
*   **Data Required:** SRTM 30m / Copernicus DEM 30m tile covering the image bounding box [PS].
*   **Why AI/Rule Hybrid is Preferable:** Pure deep learning metric predictors fail when transferred across different satellite sensors (varying camera focal lengths and orbital altitudes) [RESEARCHED]. Explicit mathematical fitting to a physical DEM anchor guarantees metric stability [INFERENCE].
*   **Evaluation:** Metric Root Mean Square Error (RMSE) and Mean Absolute Error (MAE) in meters against LiDAR evaluation data [PS].
*   **Failure Mode:** Extreme cloud cover in the optical image corrupts structural correlation with SRTM [INFERENCE].
*   **Human Oversight:** Manual GCP input option allows users to click 3+ known elevation points (e.g., ground level, building top) to manually calculate or refine $(s, t)$ [PS].

### Explicit Non-AI Component Identification
*   **Terrain Mesh Generation & Texturing:** Solved strictly using deterministic WebGL shaders and GPU buffer calculations (no generative AI used) [INFERENCE].
*   **Slope Calculation:** Computed deterministically using Sobel spatial gradient filters ($\text{Slope} = \arctan\sqrt{(\partial z / \partial x)^2 + (\partial z / \partial y)^2}$) [KNOWN].
