## 1. Executive Snapshot

### Executive Summary
Infrastructure mega-projects in the upstream and midstream oil & gas sector (such as pipeline laydown, refinery expansion, and wellhead surface facility construction) rely on micro-level Work Breakdown Structures (WBS L5/L6) to track execution across multidisciplinary engineering streams [PS]. However, field execution progress reported by site supervisors via site diaries, free-text WhatsApp/daily progress reports (DPRs), and discipline spreadsheets lacks standardization and is disconnected from Primavera P6 / MS Project activity IDs [PS]. This disconnect creates multi-week reporting latency, corrupts baseline schedules with late/inaccurate actuals, and destroys historical execution knowledge [PS]. 

To solve this, we propose **"ProjectBridge AI"**—an intelligent data capture, semantic linking, and real-time schedule update layer [INFERENCE]. ProjectBridge AI ingests heterogeneous discipline inputs (PDFs, spreadsheets, voice logs, scanned notes) [PS], utilizes a hybrid NLP pipeline (fine-tuned sentence transformers + rule-based heuristics + LLM disambiguation) [INFERENCE] to fuzzy-match field activity descriptions with L5/L6 schedule nodes with confidence scoring [PS], automatically propagates actual start/end dates into Primavera/PMIS schedules with an audit log [PS], and populates an institutional execution memory repository to optimize future project estimation [PS].

## 2. Problem Deconstruction

### Explicit Requirements
The problem statement explicitly specifies the following core requirements:

1. **Heterogeneous Input Ingestion [PS]**: Ingest diverse field progress formats including free-text daily progress reports (DPRs), discipline-wise spreadsheets (civil, piping, electrical, instrumentation), scanned site diaries, and native Primavera P6 / MS Project exports (`.xer`, `.xml`, `.xlsx`) [PS].
2. **Conversational/Voice Field Entry ("Time Agent") [PS]**: Provide a low-friction LLM-based conversational or voice interface allowing field supervisors across disciplines to record activity actual start/end times without navigating rigid forms [PS].
3. **Fuzzy-Matching & Semantic Linking Engine [PS]**: Automatically map discipline-specific field terminology (e.g., "spool erected", "hydrotesting done for segment 3") to planned L5/L6 activity IDs (e.g., "Erect Line 24”-XX-001"), resolving vocabulary mismatches, multi-discipline overlap, and granularity variations [PS].
4. **Unmatched / New Activity Exception Handling [PS]**: Flag unmatched field activities or scope additions for planner review with justification tags instead of silently dropping or misallocating them [PS].
5. **Near Real-Time Schedule Update & Audit Trail [PS]**: Automatically update actual start date, actual finish date, and percent complete in Primavera P6/MS Project/PMIS with an assigned confidence score, timestamp, user credit, and full change-history audit trail [PS].
6. **Structured Execution Memory & Analytics Foundation [PS]**: Convert daily progress updates into a queryable institutional memory repository containing historical durations, discipline productivity metrics, recurring bottlenecks, and delay causes to feed predictive analytics and future project planning [PS].
7. **Prototype Scope Constraint [PS]**: A working prototype demonstrating ingestion of 2–3 varied formats (e.g., free-text DPR and discipline spreadsheet), extraction, and schedule-linking logic is expected for SIH; production-grade OCR/ASR hardware pipelines are not mandatory [PS].

### Implicit & Derived Requirements
1. **Multi-Discipline Terminology Ontology [INFERENCE]**: The system must maintain specialized domain dictionaries (Civil, Mechanical, Piping, Electrical, Instrumentation, HSE) to disambiguate jargon (e.g., "tie-in", "holiday testing", "cable pulling", "grouting") [INFERENCE].
2. **Offline-First Data Capture for Remote Oilfields [INFERENCE]**: Oil India field locations (e.g., Assam/Arunachal exploration blocks) often experience intermittent 2G/3G connectivity; mobile/web capture interfaces must support local SQLite/IndexedDB storage with background sync [INFERENCE].
3. **Bidirectional Primavera P6 / PMIS Integration [INFERENCE]**: Must read schedule baselines (via `.xer` parsing or Primavera REST API) and export back modified schedule updates or delta XML/XER files without corrupting baseline logic links or float calculations [INFERENCE].

## 6. Research Questions

1. **How do Primavera P6 `.xer` and `.xml` files represent activity hierarchical structures (L1-L6) and actual dates?**
   - *Investigation*: `.xer` is a tab-delimited text format using relational tables (e.g., `TASK` for activities, `PROJWBS` for WBS hierarchy, `TASKPRED` for logic links) [1.3, 1.4]. Actual start/finish dates are stored in `act_start_date` and `act_end_date` columns in the `TASK` table [1.3].
2. **What semantic similarity algorithms yield the highest accuracy when matching noisy field updates to standardized WBS text?**
   - *Investigation*: Combining sentence transformers (e.g., `sentence-transformers/all-MiniLM-L6-v2`) with cosine similarity and domain-specific lexicon expansion (e.g., "spool" -> "piping spool", "hydrotest" -> "pressure testing") achieves >88% top-1 accuracy on domain benchmarks [3.1, 3.2].
3. **What is the standard EPC schedule hierarchy from L1 to L6 in Oil & Gas infrastructure?**
   - *Investigation*: L1 = Executive Milestone Plan; L2 = Management Master Schedule; L3 = Project Control Schedule; L4 = Execution Work Package Schedule; L5 = Detailed Field Task Schedule (e.g., "Weld Pipe Joint #42"); L6 = Sub-task/Crew Level Steps [2.6, 2.8].

## 10. Recommended Approach & Why

### Selection: Hybrid Multi-Tier Engine (Approach 3)
We select **Approach 3: The Hybrid Multi-Tier Engine** as the primary solution architecture. Real-world EPC field updates contain both structured technical codes (e.g., "Tag #V-101", "Line #24-P-01") and highly informal, discipline-specific language (e.g., "civil team finished pouring base slab near compressor"). 

A single approach cannot handle both:
1. **Tier 1 (Deterministic Filter)**: Executes exact string matching on Activity IDs, Tag Numbers, or Line Numbers. If an exact match is found, confidence = `1.0`.
2. **Tier 2 (Vector Semantic Search)**: If Tier 1 fails, the system converts field text into dense vector embeddings using `sentence-transformers/all-MiniLM-L6-v2` and calculates Cosine Similarity against all L5/L6 activity descriptions within the relevant WBS discipline branch.
3. **Tier 3 (LLM Disambiguation Agent)**: If Tier 2 returns multiple candidates with close similarity scores (e.g., 0.72 vs 0.70), an LLM Agent (Llama-3/GPT-4o-mini) receives the prompt with surrounding WBS context, discipline constraints, and precedent activities to select the exact match and provide reasoning.

### Why Alternatives Were Rejected
- **Approach 1 (Rule-Based Only)** was rejected because field supervisors use hundreds of colloquial variations that cannot be captured by static regex. It fails the fundamental objective of reducing reporting friction [PS].
- **Approach 2 (Pure LLM RAG)** was rejected because passing thousands of WBS L5/L6 activities directly into an LLM context window causes hallucination of non-existent Activity IDs, violates strict schedule logic, and incurs unnecessary latency and API cost.

### Data-Flow Narrative
1. **Ingestion**: A field supervisor submits a voice note via the mobile PWA ("Started hydrotesting on Line 24 in Sector B at 8 AM, expecting completion by 4 PM"). Simultaneously, a contractor uploads a daily civil progress spreadsheet (`.xlsx`).
2. **Extraction**: Speech is transcribed via Whisper ASR into text. The Spacy NLP Extraction module parses the raw text into structured JSON: `{discipline: "Piping", activity_hint: "hydrotesting Line 24 Sector B", actual_start: "2026-09-05 08:00", actual_end: "2026-09-05 16:00"}`.
3. **Matching**:
   - The JSON hint is passed to Tier 1. No exact Activity ID match exists.
   - Passed to Tier 2. The phrase is converted into a 384-dimensional vector embedding. Cosine similarity is calculated against all "Piping" discipline activities in the active P6 baseline. Top candidates:
     - `ACT-PIP-104` ("Hydrostatic Testing of Line 24-P-01 Sector B") -> Similarity: `0.87`.
     - `ACT-PIP-105` ("Pneumatic Testing of Line 24-P-02 Sector B") -> Similarity: `0.64`.
   - Confidence threshold (0.80) is satisfied by `ACT-PIP-104`.
4. **Update & Audit Logging**:
   - Actual Start Date (`2026-09-05 08:00`) and Actual Finish Date (`2026-09-05 16:00`) are staged for update.
   - An immutable audit log entry is written: `{Activity_ID: "ACT-PIP-104", Match_Score: 0.87, Source: "Voice_Note_042", User: "Supervisor_Das", Timestamp: "2026-09-05 16:05:00"}`.
5. **Schedule Export**: The updated actuals are merged into the target Primavera P6 `.xer` / `.xml` output file or pushed to the PMIS API.
6. **Institutional Memory Population**: The executed duration (8 hours) and activity details are vectorized and indexed in PostgreSQL `pgvector` for future estimation queries [PS].

## 13. AI/ML Justification

### AI Component Breakdown

#### 1. Entity Extraction & Structured Parser Agent
- **Purpose**: Parses unstructured free-text daily progress reports and voice transcriptions into structured JSON events.
- **Model Type**: Fine-tuned SpaCy NER + Light LLM Prompting (Llama-3/GPT-4o-mini).
- **Input**: Raw text/transcriptions (e.g., "Civil team completed pour of 40m3 concrete for pump house foundation today").
- **Output**: JSON payload: `{discipline: "Civil", action: "concrete pour", quantity: "40m3", location: "pump house foundation"}`.
- **Data Required**: 200+ annotated EPC field sentences.
- **Why AI**: Fixed regular expressions fail on diverse phrasing, grammatical errors, and sentence structures.
- **Evaluation**: Precision, Recall, F1-Score on entity tagging.
- **Failure Mode**: Extracts incorrect quantity or misses location.
- **Human Oversight**: Extracted JSON displayed on planner confirmation UI prior to schedule committing.

#### 2. Hybrid Semantic WBS Matcher & Disambiguation Agent
- **Purpose**: Maps extracted field events to planned Primavera L5/L6 Activity IDs.
- **Model Type**: Bi-Encoder Sentence Transformer (`all-MiniLM-L6-v2`) + LLM Cross-Encoder.
- **Input**: Field activity description + Candidate L5/L6 WBS descriptions.
- **Output**: Matched Activity ID + Confidence Score (0.0 to 1.0) + Explanation.
- **Data Required**: Historical WBS task catalogs and past match logs.
- **Why AI**: Field language ("spool erected") never matches exact Primavera plan terminology ("Erect Line 24”-XX-001") [PS].
- **Evaluation**: Top-1 and Top-3 Categorical Accuracy on synthetic testing set.
- **Failure Mode**: Mismatches activity to wrong WBS branch (e.g., Piping Sector A instead of Sector B).
- **Human Oversight**: Any match with confidence score < 0.80 is routed to human planner review queue [PS].

#### 3. Institutional Memory RAG Query Engine
- **Purpose**: Enables natural language querying over past project performance, productivity rates, and delay root causes [PS].
- **Model Type**: Vector RAG (Retrieval-Augmented Generation) using `pgvector` + LLM synthesis.
- **Input**: User natural language query (e.g., "What was our average daily piping crew productivity during monsoon in Assam?").
- **Output**: Context-backed synthesized answer with source project references [PS].
- **Data Required**: Historical project progress logs, weather records, and final as-built completion reports.
- **Why AI**: Keyword search cannot aggregate unstructured historical performance data or extract contextual insights [3.1].
- **Evaluation**: Context Relevance and Answer Faithfulness (RAGAS framework).
- **Failure Mode**: Hallucinates historical productivity numbers.
- **Human Oversight**: Answers cite exact historical project document IDs for manual verification [PS].

### Where AI Should NOT Be Used
- **Schedule Logic & Critical Path Calculation**: AI must NEVER calculate CPM float, early start/finish dates, or critical path shifts. These MUST be computed deterministically by Primavera P6 / MS Project scheduling engines [1.1, 4.1].
- **Earned Value Management (EVM) Financials**: SPI, CPI, Planned Value (PV), and Earned Value (EV) calculations must be strictly formulaic (e.g., $EV = \% \text{Complete} \times \text{BAC}$) to preserve financial auditing standards [3.4].

## 14. Data Architecture & Offline/Low-Network Design

### Relational & Vector Database Schema

```sql
-- 1. Projects Table
CREATE TABLE projects (
    project_id VARCHAR(50) PRIMARY KEY,
    project_name VARCHAR(255) NOT NULL,
    baseline_file_name VARCHAR(255),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 2. WBS L5/L6 Activities Table
CREATE TABLE wbs_activities (
    activity_id VARCHAR(50) PRIMARY KEY,
    project_id VARCHAR(50) REFERENCES projects(project_id),
    wbs_path VARCHAR(500) NOT NULL, -- e.g. "Main / Piping / Sector B / Welding"
    discipline VARCHAR(50) NOT NULL, -- "Civil", "Piping", "Electrical", "HSE"
    activity_name VARCHAR(500) NOT NULL,
    planned_start TIMESTAMP,
    planned_finish TIMESTAMP,
    planned_duration_hrs NUMERIC(10, 2),
    embedding vector(384) -- pgvector dense embedding index
);

-- 3. Field Progress Logs Table
CREATE TABLE field_progress_logs (
    log_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id VARCHAR(50) REFERENCES projects(project_id),
    source_type VARCHAR(50), -- "VOICE", "DPR_PDF", "EXCEL", "CHAT"
    raw_input_text TEXT NOT NULL,
    extracted_discipline VARCHAR(50),
    matched_activity_id VARCHAR(50) REFERENCES wbs_activities(activity_id),
    actual_start TIMESTAMP,
    actual_finish TIMESTAMP,
    percent_complete NUMERIC(5, 2),
    confidence_score NUMERIC(3, 2),
    status VARCHAR(50) DEFAULT 'PENDING_REVIEW', -- 'AUTO_APPROVED', 'MANUAL_APPROVED', 'REJECTED'
    logged_by VARCHAR(100) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 4. Audit Trail Table
CREATE TABLE schedule_audit_trail (
    audit_id SERIAL PRIMARY KEY,
    log_id UUID REFERENCES field_progress_logs(log_id),
    activity_id VARCHAR(50) NOT NULL,
    previous_status VARCHAR(50),
    new_status VARCHAR(50),
    updated_by VARCHAR(100) NOT NULL,
    confidence_at_update NUMERIC(3, 2),
    change_reason TEXT,
    timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### Offline & Low-Network Synchronization Strategy
1. **Local Progressive Web App (PWA) Cache**: Built using `IndexedDB` and LocalStorage. Field supervisors can record voice updates, fill progress tables, and attach photos without cell coverage.
2. **Background Sync Engine**: Utilizes Service Worker Background Sync API. When the mobile device detects network restoration (4G/3G/Wi-Fi), queued field logs are pushed as batch JSON requests to the FastAPI backend.
3. **Conflict Handling & Deduplication**:
   - Updates are stamped with UTC timestamps and client-side UUIDs.
   - If two updates are received for the same activity on the same date, the system retains both in the audit log, flagging a conflict for planner review rather than overwriting data.
4. **Bandwidth Optimization**: Audio recorded on mobile devices is compressed using Ogg Opus encoding (reducing raw WAV audio size by ~85%) before queuing for upload.

## 15. Security, Privacy & Governance

### Critical Governance Vectors
1. **Personal & Location Data Protection**: Field reports contain supervisor names and optional GPS coordinates. All PII and location metadata are encrypted at rest using AES-256 and in transit using TLS 1.3.
2. **Access Control & RBAC**:
   - **Field Supervisor**: Read access to assigned WBS branches; write access to log actual progress logs.
   - **Planning Engineer / Scheduler**: Full approval authority for low-confidence matches, schedule commits, and `.xer` exports.
   - **Project Manager**: Read-only access to executive dashboards and institutional memory queries.
3. **Immutability of Audit Trails**: Progress updates committed to Primavera P6 / PMIS generate an unalterable, append-only log entry recording raw source text, extracted fields, AI confidence score, user credit, and timestamp [PS].
4. **AI Reliability & Misuse Prevention**: To prevent site supervisors from fraudulently logging progress, the system requires photographic evidence attachments for progress updates exceeding 30% in a single day.
5. **Data Ownership**: All captured datasets, baseline models, and institutional knowledge repositories remain the exclusive intellectual property of Oil India Limited [PS].
