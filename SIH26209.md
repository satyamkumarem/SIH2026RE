Because the problem statement is open-ended under the AICTE MIC Student Innovation Software stream [PS], winning teams must avoid generic toy models and deliver a high-impact, mathematically sound, software-driven mission planning, telemetry monitoring, and orbital conjunction analysis system [INFERENCE]. ## 5. Constraints & Environment Realities

1. **Hardware & Graphics Constraints:** 3D rendering in WebGL/CesiumJS can cause high GPU and CPU utilization on standard student laptops. The system must support fallbacks to 2D Leaflet/OpenLayers canvas rendering [INFERENCE].
2. **Network Bandwidth in Field / Hackathon Venues:** Hackathon environments often suffer from congested Wi-Fi. Large 3D Earth tile downloads and satellite catalog payloads must be cached locally using IndexedDB and Service Workers [INFERENCE].
3. **Data Access Restrictions:** Real-time military or classified space situational awareness feeds (e.g., high-precision TOLD/CPF files) are restricted. The system must rely on public NORAD Two-Line Element (TLE) sets from CelesTrak [KNOWN].
4. **Computational Limits for Orbit Propagation:** Propagating thousands of space objects simultaneously in the browser main thread will freeze the UI. Orbit calculations must run in Web Workers or offloaded to a multi-threaded Python backend [INFERENCE].
5. **No Access to Operational Spacecraft:** Student teams cannot connect to live active satellites during a hackathon. Telemetry must be generated via a high-fidelity simulator that streams realistic CCSDS-structured frames [ASSUMPTION].

## 9. Candidate Solution Approaches

### Approach 1: Lightweight Client-Only Web-GIS (Three.js + SGP4 JS)
* **Mechanism:** Runs SGP4 orbital propagation entirely inside the browser using JavaScript libraries (`satellite.js`) and Three.js / CesiumJS for rendering.
* **Problem Fit:** High frontend interactivity, zero backend deployment overhead.
* **Accuracy Potential:** Moderate (SGP4 analytical model accuracy ~1 km at epoch) [KNOWN].
* **Data Requirements:** Direct CORS fetch of CelesTrak TLE text files.
* **Complexity:** Low.
* **Explainability:** High (Standard Keplerian mechanics).
* **Cost:** Zero server costs (hosted on GitHub Pages or Vercel).
* **Scalability:** Limited by client browser CPU/GPU performance (max ~100 satellites before UI lag).
* **Hackathon Feasibility:** Very High (Build time 1–2 days).
* **Production Feasibility:** Low (Cannot perform backend batch processing, ML anomaly detection, or long-term historical data storage).

### Approach 2: Native Desktop Flight Dynamics Suite (Python / PySide6 + Orekit / C++)
* **Mechanism:** Desktop application written in Python using Qt/PySide6, leveraging `Orekit` (Java/Python wrapper) for high-precision orbit determination and numerical propagation (dopri853 integrator).
* **Problem Fit:** High computational accuracy for aerospace simulation.
* **Accuracy Potential:** Extremely High (Includes atmospheric drag models, solar radiation pressure, geopotential J2-J4).
* **Data Requirements:** Local TLE databases, Earth Orientation Parameters (EOP) files.
* **Complexity:** Very High (Requires JVM integration, complex build steps, native installers).
* **Explainability:** High.
* **Cost:** Low hosting, but high setup friction.
* **Scalability:** Single workstation scope.
* **Hackathon Feasibility:** Medium-Low (Integration hurdles with JVM/Python in 36 hours).
* **Production Feasibility:** High for individual flight dynamics engineers, Low for multi-user mission operations.

### Approach 3: Hybrid Web-GIS + Distributed Microservice Engine (FastAPI + SGP4/Orekit + CesiumJS + Isolation Forest ML) [RECOMMENDED]
* **Mechanism:** A decoupled architecture with a modern web frontend (React + CesiumJS) for 3D visualization, backed by a fast Python FastAPI backend. The backend handles background TLE sync, multi-threaded orbit propagation, conjunction screening, and WebSocket-based telemetry streaming with an Isolation Forest ML model for anomaly detection.
* **Problem Fit:** Perfect balance between rigorous backend aerospace physics and an accessible, interactive web interface.
* **Accuracy Potential:** High (SGP4 propagation + automated vector proximity checks).
* **Data Requirements:** CelesTrak REST APIs, NASA GIBS WMTS tiles, synthetic WebSocket telemetry generator.
* **Complexity:** Medium-High.
* **Explainability:** High (Deterministic physics for orbits, interpretable ML feature importance for telemetry).
* **Cost:** Low (Free tier cloud hosting on Render/Vercel or local Docker orchestration).
* **Scalability:** High (Backend can scale horizontally to handle 10,000+ space objects).
* **Hackathon Feasibility:** High for a 4–6 student team with frontend/backend split.
* **Production Feasibility:** High (Matches modern cloud-native aerospace ground software architecture).

## 10. Recommended Approach & Why

**Selected Approach:** **Approach 3 (Hybrid Web-GIS + Python FastAPI Engine + CesiumJS)** [ASSUMPTION].

### Trade-Off Analysis & Rejection Justification
* **Why Approach 1 was rejected:** While client-only JavaScript propagation is easy to set up, it lacks backend processing power. Running space debris conjunction checks (comparing $N \times N$ orbital positions) in the browser thread crashes the page [INFERENCE]. Additionally, it cannot host background telemetry parsing or ML models.
* **Why Approach 2 was rejected:** Building a native C++/Java desktop application introduces severe build and distribution friction during judging. Judges must be able to view and interact with the system via a web browser without installing specialized Java/C++ runtime environments [INFERENCE].
* **Why Approach 3 Wins:**
  1. **Separation of Concerns:** The backend handles computational physics (SGP4), database caching, and ML inference, while the frontend focuses entirely on fluid 60 FPS 3D spatial rendering [INFERENCE].
  2. **Demonstrable Engineering Depth:** Integrates real REST APIs (CelesTrak), WebSockets (telemetry), ML algorithms (Isolation Forest), and 3D Web-GIS (CesiumJS) [INFERENCE].
  3. **Hackathon Work Division:** A 4–6 student team can cleanly divide work into Frontend/3D Globe, Backend API/Orbital Physics, Telemetry/ML Anomaly Engine, and UI/UX Strategy [INFERENCE].

### Data-Flow Step-by-Step Narrative

1. **Orbit Data Ingestion:** The FastAPI backend executes an asynchronous background task that fetches active satellite Two-Line Element (TLE) sets from CelesTrak REST endpoints [RESEARCHED]. TLEs are parsed and cached in SQLite/Redis [ASSUMPTION].
2. **Propagator Execution:** When a frontend user requests a 3D orbit view, the backend passes TLE parameters into the `sgp4` module to calculate Cartesian position ($\mathbf{r}$) and velocity ($\mathbf{v}$) vectors in the TEME (True Equator Mean Equinox) coordinate frame, converting them to WGS84 Geodetic coordinates (Lat, Lon, Alt) [KNOWN].
3. **3D Globe Rendering:** Position streams are transmitted via JSON/REST or WebSockets to the React application, where CesiumJS updates the satellite position, orbit polyline, and ground track in real time [INFERENCE].
4. **Conjunction Screening:** The backend conjunction worker iterates through active satellite positions against cataloged space debris objects. If the Euclidean distance falls below a safety threshold (e.g., $d < 10\text{ km}$), a Conjunction Warning Alert is published [INFERENCE].
5. **Telemetry Processing:** A simulated telemetry microservice streams spacecraft subsystem parameters (Battery Voltage, Solar Panel Current, Magnetometer readings, Structure Temperature) over WebSockets at 1 Hz [ASSUMPTION].
6. **ML Anomaly Detection:** Incoming telemetry vectors pass through a pre-trained scikit-learn Isolation Forest model. If anomalous multivariate sensor patterns are detected, the system flags the telemetry frame with an alert severity score and highlights the metric on the live dashboard [INFERENCE].

### AI Component Details

* **Purpose:** Detect unexpected, out-of-nominal behavior in satellite telemetry streams (e.g., sudden battery drain coupled with anomalous thermal spikes) [INFERENCE].
* **Model Type:** Unsupervised Isolation Forest (`sklearn.ensemble.IsolationForest`) [ASSUMPTION].
* **Input:** Multi-variate numerical telemetry vector: `[bus_voltage, bus_current, battery_temp, payload_temp, gyro_x, gyro_y, gyro_z, reaction_wheel_rpm]` [ASSUMPTION].
* **Output:** Anomaly Score $[-1.0, 1.0]$ where values $< -0.1$ indicate abnormal system state, along with feature contribution weights [ASSUMPTION].
* **Data Required:** 1,000 historical synthetic telemetry frames under nominal orbital operations (sunlit vs. eclipse phases) [ASSUMPTION].
* **Why AI is Preferable:** Simple static thresholds fail when a parameter is technically within absolute safety bounds but abnormal for a specific orbital phase (e.g., solar panel current dropping to zero during sunlit orbit phase) [INFERENCE].
* **Evaluation Metric:** Anomaly Precision/Recall on synthetically injected fault datasets (e.g., simulated short circuits, reaction wheel friction spikes) [INFERENCE].
* **Failure Mode:** False positive flags during transient maneuvers.
* **Human Oversight:** High. ML flags are presented as visual telemetry warnings requiring operator confirmation; the system never executes autonomous telecommands [INFERENCE].

### Explicit Non-AI Boundary
**AI MUST NOT be used for orbital propagation or trajectory prediction.** Trajectory propagation relies strictly on deterministic Newtonian dynamics, Keplerian gravity models, and validated SGP4 analytical physics (`python-sgp4`) [KNOWN]. Replacing physical orbital mechanics with neural network regression introduces dangerous drift, lack of explainability, and catastrophic position errors [INFERENCE].

## 14. Data Architecture & Offline/Low-Network Design

### Database Schema (SQLite / JSON Schema)

```sql
-- Cached Satellite Two-Line Element Table
CREATE TABLE satellites (
    norad_id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    tle_line1 TEXT NOT NULL,
    tle_line2 TEXT NOT NULL,
    epoch_datetime TIMESTAMP NOT NULL,
    category TEXT DEFAULT 'ACTIVE',
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Ground Station Table
CREATE TABLE ground_stations (
    station_id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    latitude REAL NOT NULL,
    longitude REAL NOT NULL,
    altitude_m REAL DEFAULT 0.0,
    min_elevation_deg REAL DEFAULT 10.0
);

-- Telemetry Frame Log Table
CREATE TABLE telemetry_logs (
    log_id INTEGER PRIMARY KEY AUTOINCREMENT,
    norad_id INTEGER NOT NULL,
    timestamp TIMESTAMP NOT NULL,
    bus_voltage REAL,
    battery_temp REAL,
    anomaly_score REAL,
    is_anomaly BOOLEAN DEFAULT 0,
    FOREIGN KEY(norad_id) REFERENCES satellites(norad_id)
);
```

### Offline & Low-Network Strategies
1. **Local Browser Caching:** Frontend assets, standard 2D vector tile overlays, and public TLE files are cached using Service Workers and IndexedDB (`Dexie.js`) [ASSUMPTION].
2. **Client-Side SGP4 Fallback:** If the backend connection drops during field operations, the React client switches to executing `satellite.js` in a local Web Worker using previously cached TLEs [INFERENCE].
3. **Bandwidth Reduction:** Satellite state vectors ($\mathbf{r}, \mathbf{v}$) are calculated locally in 10-second increments rather than streaming high-frequency raw coordinate arrays from the server [INFERENCE].
4. **Synchronization Strategy:** On connection restoration, the client background sync worker updates local TLE stores with delta updates from the FastAPI backend [INFERENCE].
