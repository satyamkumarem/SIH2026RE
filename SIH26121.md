## 1. Executive Snapshot

### Summary
Oil India Limited (OIL) operates an Enterprise Real-Time Monitoring and Analysis Center (eRTMAC) at its Field Headquarters in Duliajan, Assam [RESEARCHED][1.1], streaming high-frequency drilling telemetry from active rigs. However, critical historical drilling insights—such as previous stuck pipe incidents, lost circulation zones, cementing practices, and formation-specific hazards—are trapped in thousands of unstructured PDF Well Completion Reports (WCRs), Daily Drilling Reports (DDRs), and unindexed databases [PS]. The proposed **eRTMAC-NWIS (Nearby Wells Intelligence System)** bridges this gap by creating an AI-powered geospatial knowledge and decision-support platform. NWIS ingests unstructured offset well documents using multi-modal OCR/NLP, indexes geological and drilling events into a PostGIS spatial-geological database and vector store, correlates historical hazards with active well telemetry by True Vertical Depth (TVD) and formation horizons, and delivers real-time proactive risk alerts to drillers and command center engineers 15–30 minutes before hazardous incidents occur [INFERENCE].

## 5. Constraints & Environment Realities

1. **Geographic & Geological Context:**
   * Operations are heavily concentrated in Upper Assam (Duliajan, Moran, Digboi, Hubrijan) characterized by highly complex, faulted, multi-layered deltaic sandstone-shale sequences (Tipam, Barail, Girujan formations) [RESEARCHED][1.1]. Tectonic stresses and depleted reservoir pressures cause frequent differential sticking and severe lost circulation [INFERENCE].
2. **Network Connectivity & Bandwidth at Rig Sites:**
   * Active drilling rigs in remote Assam locations connect to eRTMAC FHQ via satellite VSAT links with variable latency (600ms–1200ms) and constrained upload bandwidth (256 kbps – 1 Mbps) [INFERENCE]. The system **must not** rely on heavy cloud processing for real-time field alerts; local edge caching and lightweight data payloads (MQTT/Protobuf) are mandatory [ASSUMPTION].
3. **Hardware & Field Operating Constraints:**
   * Field supervisors use ruggedized Zone-2 hazardous-area certified tablets or basic laptop terminals running Windows/Linux on site [INFERENCE]. The frontend web app must maintain low GPU/CPU utilization and support touch interaction.
4. **Unstructured Heritage Document Quality:**
   * Historical Well Completion Reports (WCRs) dating back 20–40 years in OIL's archives consist of multi-generation scanned, skewed, low-DPI PDF documents with handwritten notes, faded ink, and complex multi-column tables [INFERENCE]. Direct text extraction fails; robust OCR preprocessing (deskew, binarization, denoising) is required [INFERENCE].
5. **Data Privacy & Enterprise Security:**
   * Upstream E&P subsurface data (well coordinates, seismic horizon tops, reservoir pressures) is strictly proprietary national asset data protected by India's Information Technology Act and Oil India internal security policies [KNOWN]. All models and data stores must run on-premise or within OIL's secure private cloud [ASSUMPTION].

## 9. Candidate Solution Approaches

### Approach 1: Conventional GIS Map + Keyword Search + Static Rule-Based Thresholds
* **Mechanism:** PostGIS spatial database storing well coordinates. ElasticSearch cluster indexing plain-text OCR outputs from PDFs. Rule engine triggering alerts when active TVD matches offset hazard depth ±10m and current SPP/Torque exceeds a static fixed threshold.
* **Data Requirements:** Structured CSV inputs of well locations, pre-processed TXT files from OCR, standard WITSML telemetry feed.
* **Architecture:** Traditional 3-tier monolith (Django + PostgreSQL/PostGIS + ElasticSearch + Vue.js).
* **Complexity:** Low.
* **Cost:** Very Low (100% open-source stack).
* **Explainability:** 100% deterministic (clear rule triggers).
* **Scalability:** High for basic search, low for complex multi-parametric pattern detection.
* **Hackathon Feasibility:** 95/100 (Easy to build in 3 weeks).
* **Production Feasibility:** 40/100 (Fails on complex scanned PDFs, produces excessive false alarms from static thresholds, lacks semantic context).
* **Risks:** High false-positive alarm rate on telemetry; unable to parse handwriting or unstructured tabular data in heritage reports.

### Approach 2: LLM-Only RAG System with Conversational Map Interface
* **Mechanism:** Large Language Model (e.g., Llama-3 / GPT-4) integrated with a vector database (Qdrant). All PDF documents are chunked into embeddings. Frontend features a chatbot interface with an embedded Mapbox widget where users ask natural language questions ("What happened in offset well NH-12 at 2,400m?").
* **Data Requirements:** Embedded PDF document chunks, vector representations.
* **Architecture:** FastAPI + LangChain/LlamaIndex + Qdrant + React.
* **Complexity:** Medium.
* **Cost:** High (requires heavy GPU inference infrastructure or LLM API usage).
* **Explainability:** Low/Medium (Risk of LLM hallucination during critical drilling advice).
* **Scalability:** Medium (High latency for vector similarity search + LLM generation).
* **Hackathon Feasibility:** 80/100.
* **Production Feasibility:** 30/100 (Unacceptable latency for real-time 1-second drilling stream monitoring; dangerous potential for hallucinating mud weights or casing depths).
* **Risks:** Severe hallucination risk; cannot process real-time 1-Hz time-series sensor anomalies efficiently; lack of physical engineering constraints.

### Approach 3: Hybrid Spatial-Geological Knowledge Graph + Multi-Modal Document Intelligence + Physics-Informed ML Anomaly Engine (RECOMMENDED)
* **Mechanism:** Integrated multi-tier architecture:
  1. *Document Intelligence Tier:* Multi-modal OCR (`Unstructured` + `LayoutLMv3`) extracting structured JSON tables and text chunks, generating spatial-geological entity links in a PostgreSQL/PostGIS schema and `pgvector` store.
  2. *Geospatial & Depth Correlation Tier:* PostGIS radius engine calculating TVDSS horizon deltas and structural dip offsets.
  3. *Physics-Informed ML Anomaly Engine:* XGBoost + Isolation Forest models combining offset historical event priors with live eRTMAC WITSML telemetry (d-exponent, hydraulics, torque-and-drag deviations) to output real-time hazard probabilities.
  4. *RAG & Advisory Engine:* LlamaIndex RAG pipeline delivering grounded, citation-backed historical mitigation advisories when an anomaly is detected.
* **Data Requirements:** Scanned PDFs (WCR/DDR), WITSML time-series feeds, directional surveys, stratigraphic formation tables.
* **Architecture:** Microservices/Decoupled architecture: FastAPI backend, PostGIS DB + `pgvector`, XGBoost ML worker, Next.js / Leaflet frontend.
* **Complexity:** High (Multi-disciplinary engineering).
* **Cost:** Moderate (Optimized for hybrid open-source CPU/GPU execution).
* **Explainability:** High (Hazard score is backed by specific sensor trend deviations AND explicit historical offset document citations).
* **Scalability:** Very High (Time-series ML runs in milliseconds; vector RAG is invoked only upon query/alert).
* **Hackathon Feasibility:** 85/100 (Feasible with clear MVP boundary).
* **Production Feasibility:** 90/100 (Fully aligned with enterprise oilfield operational realities).
* **Risks:** Model pre-training requires representative drilling data; mitigation handled via synthetic WITSML stream generator.

## 10. Recommended Approach & Why

### Selection
**Approach 3 (Hybrid Spatial-Geological Knowledge Graph + Multi-Modal Document Intelligence + Physics-Informed ML Anomaly Engine)** is selected as the winning architecture.

### Justification & Rejection Analysis

* **Why Approach 1 was rejected:** While easy to build, rule-based static thresholding is notorious in drilling operations for generating "alarm fatigue" [RESEARCHED][3.1]. Drilling parameters change drastically across different formations and hole sizes; a static torque threshold of 15,000 ft-lbs may be normal in an 8.5-inch lateral but indicative of catastrophic mechanical sticking in a 12.25-inch hole [INFERENCE]. Furthermore, basic keyword search cannot extract complex tabular data (e.g., mud weight vs depth records) from scanned heritage PDFs [INFERENCE].
* **Why Approach 2 was rejected:** A pure LLM/RAG system is fundamentally incapable of real-time time-series anomaly detection on 1-Hz WITSML streams [INFERENCE]. Asking an LLM to process thousands of continuous sensor data points causes immense latency, extreme token costs, and high hallucination risk [INFERENCE]. In drilling operations, hallucinating a recommended mud weight or fracture gradient can lead to catastrophic well control incidents (blowouts) [KNOWN].
* **Why Approach 3 Wins:** Approach 3 decouples the problem into domain-appropriate engines:
  1. **Deterministic Physics & GIS** handle spatial queries and depth calculations without error [INFERENCE].
  2. **Multi-Modal AI & NLP** convert unstructured legacy PDFs into reliable structured records with vector embeddings [INFERENCE].
  3. **Gradient Boosting & ML Anomaly Detection** evaluate high-frequency sensor streams in milliseconds [RESEARCHED][3.6].
  4. **RAG Language Models** act strictly as an information retrieval and advisory summarizer, constrained to produce verifiable citations from historical WCR/DDR documents [INFERENCE].

### End-to-End Data Flow Narrative

1. **Document Ingestion Workflow:** Scanned PDF Well Completion Reports (WCRs) and Daily Drilling Reports (DDRs) are uploaded into the ingestion pipeline. `Unstructured.io` isolates document blocks (headers, narrative text, tables). Scanned images are passed to `Tesseract OCR` / `LayoutLMv3` for text and tabular extraction. Extracted JSON entities (casing sizes, mud weights, NPT event descriptions, bit records) are written into PostgreSQL relational tables. Unstructured narrative sections ("Lessons Learned", "Operational Comments") are chunked, vectorized using `text-embedding-3-small` (or local `bge-large-en`), and stored in `pgvector` with metadata (Well ID, MD, TVD, Formation).
2. **Geospatial & Trajectory Indexing:** Wellhead coordinates (Latitude/Longitude) and directional survey points (MD, Inclination, Azimuth) are processed through a Minimum Curvature algorithm to generate 3D borehole LineStrings stored as PostGIS `ST_GeometryZ` objects. Stratigraphic markers are indexed by TVDSS (True Vertical Depth Sub-Sea).
3. **Real-Time Stream Processing & Geo-Fencing:** During active drilling, eRTMAC transmits 1-second WITSML data (Active TVD, Bit Depth, ROP, WOB, RPM, Torque, SPP, Flow Out, Pit Volume). The **Geo-Fencing Engine** continuously queries PostGIS for offset wells within a user-defined radius (e.g., 2 km). It compares active bit TVD against historical hazard depth zones in those offset wells.
4. **Predictive Anomaly Scoring:** Simultaneously, the **Physics-Informed ML Engine** evaluates continuous 60-second sliding windows of WITSML parameters. It calculates rate-of-change metrics (e.g., torque drift, differential pressure, mechanical specific energy - MSE) and passes them to the XGBoost anomaly classifier.
5. **Alert & Advisory Generation:** When active TVD is within 30 meters of a known offset hazard zone AND/OR the ML model detects precursor anomaly signatures (probability > 0.75), an alert is triggered. The **RAG Engine** immediately queries `pgvector` for the exact historical mitigation procedures used in that offset well for that specific hazard.
6. **Dashboard Delivery:** The FastAPI backend pushes a JSON payload via WebSocket to the Next.js dashboard. The map highlights the active rig and target offset well in pulsing red, displays the side-by-side lithology/drilling log, fires an visual alert banner, and presents the RAG-generated advisory with direct links to view the original PDF source document page [INFERENCE].

## 13. AI/ML Justification

### 1. Document Extraction Engine (Multi-Modal OCR & Layout Analysis)
* **Purpose:** Extract structured operational parameters (casing design, mud weight, NPT event logs) from scanned PDF Well Completion Reports [PS].
* **Model Type:** `LayoutLMv3` + `Tesseract OCR` + `Table Transformer`.
* **Input:** Raw PDF document pages (images/scans).
* **Output:** Structured JSON objects containing key-value pairs (e.g., `{"casing_size": "9.625 in", "depth": "2450 m", "event": "Mud Loss 15 bbl/hr"}`).
* **Data Required:** 20–50 sample WCR/DDR PDF documents for template fine-tuning.
* **Why AI:** Traditional regex/python script parsing fails completely on scanned, skewed, or multi-column PDF layouts with handwritten notes [INFERENCE].
* **Evaluation Metrics:** Field-level Precision, Recall, and Table Extraction Accuracy (> 90%).
* **Failure Mode & Mitigation:** If OCR fails or confidence score < 0.70, flag document page for manual human review in dashboard.
* **Human Oversight:** Drilling Data Analyst reviews and verifies extracted entities in the staging interface before committing to primary DB.

### 2. RAG Lessons-Learned Knowledge Base
* **Purpose:** Provide instant semantic retrieval and summarized answers regarding historical drilling challenges and proven engineering mitigations [PS].
* **Model Type:** Local quantized LLM (`Llama-3-8B-Instruct` via Ollama) paired with `pgvector` dense embeddings (`bge-large-en`).
* **Input:** Natural language query from engineer (e.g., "How was stuck pipe resolved in Barail formation in offset wells?").
* **Output:** Synthesized advice paragraph with explicit citations (e.g., "[Source: Well NH-12 WCR, Page 14]").
* **Data Required:** Vectorized text chunks from parsed WCR/DDR narrative sections.
* **Why AI:** Keyword search fails to capture semantic meaning (e.g., missing "lost circulation" when searching for "mud loss") [INFERENCE].
* **Evaluation Metrics:** Retrieval Accuracy (MRR - Mean Reciprocal Rank) and Faithfulness Score (zero hallucinated facts).
* **Failure Mode & Mitigation:** If vector search similarity score < 0.65, display message: "No relevant historical offset experience found in database."
* **Human Oversight:** Answers explicitly display source PDF page thumbnails; engineer must verify advice before executing field decisions.

### 3. Predictive Hazard Anomaly Engine
* **Purpose:** Identify early precursor signatures of impending mud loss or stuck pipe incidents 15–30 minutes before conventional threshold alarms [PS][RESEARCHED][3.1].
* **Model Type:** Gradient Boosted Decision Trees (`XGBoost`) + Isolation Forest Anomaly Detector.
* **Input:** Sliding 60-second window of live WITSML telemetry (ROP, WOB, RPM, Torque, SPP, Flow Out, Pit Volume, MSE, d-exponent).
* **Output:** Probability score (0.0 to 1.0) for 5 hazard categories (Stuck Pipe, Mud Loss, Kick, Torque Spike, Cement Failure).
* **Data Required:** Historical WITSML time-series logs labeled with event start times.
* **Why AI:** Human operators watching 20+ continuous sensor curves cannot spot multi-variable subtle cross-parameter trends (e.g., simultaneous slight torque drift + minor connection gas increase + d-exponent flattening) [RESEARCHED][3.4].
* **Evaluation Metrics:** ROC-AUC score (> 0.88), False Positive Rate (< 10%), Lead Time (> 15 minutes).
* **Failure Mode & Mitigation:** If sensor feed is noisy or missing, model degrades gracefully to spatial depth-buffering offset rules.
* **Human Oversight:** Alerts are presented as "Probability Advisories" to the eRTMAC Command Engineer, who validates telemetry before calling the rig floor.

### Explicit Non-AI Directives (Where AI MUST NOT be used)
1. **3D Spatial Distance Calculations:** Must use exact PostGIS spherical geometry equations (`ST_3DDistance`), NOT spatial ML approximations [INFERENCE].
2. **True Vertical Depth (TVD) Conversions:** Directional survey trajectory processing MUST use the deterministic industry-standard Minimum Curvature Method algorithms [KNOWN].
3. **Hydrostatic Pressure & ECD Calculations:** Mud pressure calculations MUST use exact physics formulas ($HP = 0.052 \times MW \times TVD$), NOT neural network estimation [KNOWN].

## 14. Data Architecture & Offline/Low-Network Design

### Database Schema (PostgreSQL + PostGIS)

```sql
-- 1. Wells Master Table
CREATE TABLE wells (
    well_id VARCHAR(50) PRIMARY KEY,
    well_name VARCHAR(100) NOT NULL,
    field_name VARCHAR(100) NOT NULL, -- e.g., 'Duliajan', 'Moran'
    operator VARCHAR(100) DEFAULT 'Oil India Limited',
    wellhead_location GEOMETRY(Point, 4326) NOT NULL, -- WGS84 Lat/Lon
    spud_date DATE,
    completion_date DATE,
    total_depth_md NUMERIC(8,2), -- Measured Depth in meters
    total_depth_tvd NUMERIC(8,2), -- True Vertical Depth in meters
    status VARCHAR(30) -- 'Active Drilling', 'Completed', 'Abandoned'
);

-- 2. Well Trajectories (3D Borehole Survey)
CREATE TABLE well_trajectories (
    trajectory_id SERIAL PRIMARY KEY,
    well_id VARCHAR(50) REFERENCES wells(well_id) ON DELETE CASCADE,
    md NUMERIC(8,2) NOT NULL,
    inclination NUMERIC(5,2) NOT NULL,
    azimuth NUMERIC(5,2) NOT NULL,
    tvd NUMERIC(8,2) NOT NULL,
    tvdss NUMERIC(8,2) NOT NULL, -- TVD Sub-Sea
    geom_3d GEOMETRY(PointZ, 4326) -- 3D Spatial point
);

-- 3. Geological Formations Reference
CREATE TABLE geological_formations (
    formation_id SERIAL PRIMARY KEY,
    formation_name VARCHAR(100) NOT NULL, -- e.g., 'Tipam Sandstone', 'Barail'
    typical_top_tvdss NUMERIC(8,2),
    typical_bottom_tvdss NUMERIC(8,2),
    primary_lithology VARCHAR(100),
    known_hazards TEXT
);

-- 4. Historical Operational Events (NPT / Hazards)
CREATE TABLE operational_events (
    event_id SERIAL PRIMARY KEY,
    well_id VARCHAR(50) REFERENCES wells(well_id),
    event_type VARCHAR(50) NOT NULL, -- 'Stuck Pipe', 'Mud Loss', 'Kick', 'Cement Failure'
    depth_md NUMERIC(8,2) NOT NULL,
    depth_tvd NUMERIC(8,2) NOT NULL,
    formation_name VARCHAR(100),
    severity VARCHAR(20), -- 'Minor', 'Moderate', 'Severe', 'Catastrophic'
    npt_hours NUMERIC(6,2),
    description TEXT,
    mitigation_applied TEXT,
    source_document_id VARCHAR(100),
    source_page_number INT
);

-- 5. Vector Embeddings (Lessons Learned RAG Store)
CREATE TABLE document_embeddings (
    chunk_id SERIAL PRIMARY KEY,
    well_id VARCHAR(50) REFERENCES wells(well_id),
    document_name VARCHAR(200),
    page_number INT,
    chunk_text TEXT,
    embedding vector(1536) -- OpenAI / BGE embedding dimensions
);

-- Spatial and Vector Indexes
CREATE INDEX idx_wells_spatial ON wells USING GIST(wellhead_location);
CREATE INDEX idx_trajectories_spatial ON well_trajectories USING GIST(geom_3d);
CREATE INDEX idx_vector_search ON document_embeddings USING hnsw (embedding vector_cosine_ops);
```

### Offline & Low-Network Edge Synchronization Strategy
* **Rig-Site Local Caching:** Field laptops/tablets run a Progressive Web App (PWA) with `IndexedDB` caching [INFERENCE]. When connected, the rig client downloads offset well geospatial metadata and hazard logs within a 5 km radius of the active rig location.
* **Payload Compression:** Live WITSML stream data between rig site and eRTMAC hub is serialized using Protocol Buffers (Protobuf) over WebSockets/MQTT, reducing telemetry bandwidth consumption by up to 80% compared to verbose XML WITSML [INFERENCE].
* **Delta Synchronization:** If satellite VSAT drops, the field client logs telemetry locally in SQLite/IndexedDB. Upon reconnection, a background service pushes lightweight delta logs to eRTMAC, prioritizing real-time hazard alerts over historical batch sync [INFERENCE].
