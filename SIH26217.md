# Smart India Hackathon (SIH) Solution Research Dossier

## 1. Executive Snapshot

### Summary
The proposed solution, **Aegis-Grid Hardware & Energy Management Unit**, is an integrated, edge-AI-assisted hardware and software microgrid controller designed to maximize renewable energy generation and optimize power distribution [INFERENCE]. Addressing the critical problem of efficiency losses in localized renewable energy installations (e.g., solar PV and micro-wind turbines), Aegis-Grid combines a **Dual-Axis Active Solar Tracker** [RESEARCHED], an **Adaptive Perturb & Observe Maximum Power Point Tracking (MPPT) Charger** [RESEARCHED], an intelligent **Battery Management System (BMS)** [KNOWN], and automated **Priority-Based Load Shedding** [INFERENCE]. Operating on a dual-core ESP32 microcontroller with industrial Modbus RTU / RS-485 communications [RESEARCHED] and local SQLite / SPIFFS telemetry buffering [KNOWN], the system ensures zero data loss during grid/network disconnects. An lightweight Edge-AI model running locally provides short-term solar generation forecasting and real-time electrical fault/anomaly detection [INFERENCE], while a central web dashboard gives administrators microsecond-level monitoring and control [INFERENCE].

## 5. Constraints & Environment Realities

1. **Connectivity Realities:** Rural microgrid sites in India frequently suffer from intermittent or non-existent cellular/Wi-Fi coverage [KNOWN]. The hardware must function completely autonomously without requiring active internet connections for primary control decisions [INFERENCE].
2. **Thermal & Weather Exposure:** Solar hardware deployed outdoors experiences ambient temperatures ranging from 0°C to 48°C and humidity up to 95% [KNOWN]. Hardware components must be housed in IP65-rated enclosures, and temperature compensation must be built into battery charging voltage thresholds [INFERENCE].
3. **Power Self-Consumption:** A microgrid controller that consumes excessive idle power defeats its own purpose [INFERENCE]. The overall hardware controller standby power must remain below 1.5 Watts [ASSUMPTION].
4. **Dust & Soiling in Indian Conditions:** Dust accumulation on solar panels in dusty regions reduces power yield by 15-25% [RESEARCHED]. The system should include dust detection heuristics based on expected vs. actual current output [INFERENCE].
5. **Component Availability & Cost for Student Hackathons:** Complex custom ASICs or high-end FPGA-based microcontrollers are infeasible for a student hackathon [INFERENCE]. Hardware components must rely on readily accessible off-the-shelf modules (ESP32, INA219, ACS712, SP3485 RS-485 transceiver, relay modules) [ASSUMPTION].

## 9. Candidate Solution Approaches

### Approach 1: Basic Embedded Microcontroller with Static Logic (Threshold Rules)
* **Mechanism:** ESP32 running simple C++ code reading 4 LDRs for tracking, basic Perturb & Observe MPPT, and hardcoded battery voltage cut-offs [INFERENCE].
* **Required Data:** LDR voltage values, INA219 panel/battery voltage and current [INFERENCE].
* **Architecture:** Monolithic Arduino framework loop executing on ESP32 [INFERENCE].
* **Complexity:** Low [INFERENCE].
* **Cost:** Very Low (~₹2,500 / $30) [INFERENCE].
* **Explainability:** 100% rule-based deterministic logic [INFERENCE].
* **Scalability:** Poor; non-modular code and no standard industrial bus [INFERENCE].
* **Hackathon Feasibility:** Very High (3-4 days build) [INFERENCE].
* **Production Feasibility:** Low (Lacks fault tolerance, filtering, and industrial communications) [INFERENCE].
* **Risks:** LDR jitter under cloudy weather causes continuous servo hunt, rapidly draining battery power [RESEARCHED].

### Approach 2: Cloud-Centric IoT Microgrid Controller with Cloud Machine Learning
* **Mechanism:** ESP32 acts solely as a telemetry dump node over Wi-Fi/GSM to AWS IoT Core / ThingSpeak. All processing, tracking offsets, load shedding decisions, and ML forecasting occur in the cloud [INFERENCE].
* **Required Data:** High-frequency cloud telemetry stream [INFERENCE].
* **Architecture:** Lightweight edge publisher + Cloud Serverless (AWS Lambda, DynamoDB, SageMaker) [INFERENCE].
* **Complexity:** High [INFERENCE].
* **Cost:** Medium (Ongoing cloud subscription & cellular data costs) [INFERENCE].
* **Explainability:** Medium (Cloud ML predictions dictate relay switching) [INFERENCE].
* **Scalability:** High cloud scale, but completely fragile at the edge [INFERENCE].
* **Hackathon Feasibility:** Medium [INFERENCE].
* **Production Feasibility:** Poor for off-grid rural sites due to network fragility [INFERENCE].
* **Risks:** Total microgrid loss of control during internet outages [INFERENCE].

### Approach 3: Edge-AI Microgrid Management Unit with Hybrid MPPT, Dual-Axis Tracking, Modbus Telematics & Offline Buffering (Recommended)
* **Mechanism:** Dual-core ESP32 executing FreeRTOS [RESEARCHED]. Core 0 manages high-frequency power switching (MPPT PWM, BMS safety, LDR digital filtering) [INFERENCE]. Core 1 manages Modbus RTU / RS-485 telematics, local SQLite/SPIFFS data logging, and lightweight edge-AI inferencing (TensorFlow Lite for Microcontrollers) [RESEARCHED].
* **Required Data:** Real-time sensor readings + local historical buffer [INFERENCE].
* **Architecture:** Modular Edge Hardware + Industrial Bus + Web Local Dashboard + Cloud Sync Engine [INFERENCE].
* **Complexity:** Medium-High [INFERENCE].
* **Cost:** Low (~₹4,500 / $55) [INFERENCE].
* **Explainability:** High (Control loops are deterministic; AI is used for health prediction/yield forecast only) [INFERENCE].
* **Scalability:** Excellent via Modbus multi-drop architecture [RESEARCHED].
* **Hackathon Feasibility:** High (Achievable with standard modular prototype boards) [INFERENCE].
* **Production Feasibility:** High (Robust, offline-first, industrial protocol support) [INFERENCE].
* **Risks:** Complex firmware synchronization between FreeRTOS tasks [INFERENCE].

## 10. Recommended Approach & Why

### Selected Solution
**Approach 3: Edge-AI Microgrid Management Unit with Hybrid MPPT, Dual-Axis Tracking, Modbus Telematics & Offline Buffering** [INFERENCE].

### Justification & Rejection of Alternatives
* **Why Approach 1 Was Rejected:** Basic threshold logic suffers from severe sensor jitter under passing clouds, causing "servo hunting" which wastes harvested energy [RESEARCHED]. Furthermore, it lacks telemetry, industrial expandability, and battery health protections [INFERENCE].
* **Why Approach 2 Was Rejected:** Cloud-dependent microgrid control is fundamentally flawed for rural/off-grid deployment where internet access is erratic or non-existent [KNOWN]. A lost TCP connection must never result in an unmanaged battery overcharge or unexpected microgrid shutdown [INFERENCE].
* **Why Approach 3 Wins:**
  1. **Autonomous Operation:** Critical safety trips (over-voltage, short circuit, battery deep discharge) and MPPT control run locally on ESP32 Core 0 at millisecond rates [INFERENCE].
  2. **Energy Harvest Maximization:** Combining dual-axis active sun tracking (capturing ~35% more radiation) with dynamic MPPT yield optimization extracts peak power across all solar angles [RESEARCHED].
  3. **Industrial Interoperability:** Integrating Modbus RTU over RS-485 allows the prototype to interface directly with commercial energy meters and PLCs used in enterprise microgrids [RESEARCHED].
  4. **TinyML Diagnostics:** Edge-AI running locally alerts on panel degradation, soiling, and thermal anomalies without cloud processing latency [INFERENCE].

### Data-Flow Narrative
1. **Sensors Acquisition:** At 100 Hz frequency, ESP32 Core 0 reads 4 LDR analog voltages, INA219 I2C bus values (PV Voltage, PV Current, Battery Voltage, Battery Current), and DS18B20 temperature [INFERENCE].
2. **Signal Filtering:** LDR voltage values are passed through a software Kalman filter to eliminate high-frequency atmospheric noise and cloud flicker [RESEARCHED].
3. **Active Tracking Execution:** Core 0 calculates differential light error ($E_{azimuth} = LDR_{left} - LDR_{right}$, $E_{elevation} = LDR_{top} - LDR_{bottom}$). If $|E| > \text{deadband threshold}$, servo motors step panel orientation toward peak intensity [RESEARCHED].
4. **MPPT Calculation:** Core 0 calculates instantaneous PV power ($P = V \times I$). The Perturb & Observe algorithm adjusts DC-DC buck PWM duty cycle by $\Delta D$. If $\Delta P > 0$, direction of duty cycle adjustment is maintained; if $\Delta P < 0$, direction is reversed [RESEARCHED].
5. **BMS & Load Shedding:** Core 0 checks battery voltage against low-voltage cut-off (LVCO). If battery SoC drops below 30%, Relay Channel 2 (Non-Critical Load) trips immediately while Relay Channel 1 (Critical Load) remains online [INFERENCE].
6. **Inter-Core Telemetry Sync:** Processed metrics are written into a shared FreeRTOS queue and read by Core 1 [INFERENCE].
7. **Storage & Edge-AI:** Core 1 appends telemetry to local SPIFFS flash memory ring buffer [RESEARCHED]. Every 15 minutes, Core 1 executes the TFLite Micro model to generate next-hour yield forecast and check for V-I curve anomalies [INFERENCE].
8. **Upstream Telemetry:** If Wi-Fi/GSM connection is alive, Core 1 transmits buffered JSON telemetry payloads via MQTT to central broker; if disconnected, data remains safely buffered locally [RESEARCHED].

## 13. AI/ML Justification

### Component 1: Edge-AI PV Health & Anomaly Detector
1. **What exact problem does AI solve?** Detects gradual degradation, soiling (dust cover), and partial shading faults by identifying deviations from theoretical $I-V$ characteristic power curves [INFERENCE].
2. **What is the input?** Real-time PV Voltage, PV Current, Surface Temperature, and Ambient LDR Light Intensity [INFERENCE].
3. **What is the output?** Health Anomaly Score ($0.0 - 1.0$) and status classification (`NORMAL`, `DIRTY_PANEL`, `ELECTRICAL_FAULT`) [INFERENCE].
4. **Why can a simpler rule/system not solve it?** Simple fixed thresholds fail because solar panel output varies non-linearly with temperature and solar irradiance; static rules produce excessive false alarms [RESEARCHED].
5. **What data is required?** Historical $V, I, T, \text{Irradiance}$ logs collected across clean and soiled panel conditions [INFERENCE].
6. **How will it be evaluated?** Classification accuracy, Precision, Recall, and confusion matrix on test dataset [INFERENCE].
7. **What happens when it is wrong?** Generates a minor warning flag on dashboard; does NOT interrupt main microgrid power flow [INFERENCE].
8. **Does it require training?** Yes, trained offline on host PC using Python (Scikit-Learn/TensorFlow) [INFERENCE].
9. **Does it require fine-tuning?** Optional post-deployment calibration [INFERENCE].
10. **Does it require RAG?** No [INFERENCE].
11. **Does it require computer vision?** No [INFERENCE].
12. **Does it require speech processing?** No [INFERENCE].
13. **Does it require forecasting?** No, real-time diagnostic classification [INFERENCE].
14. **Is human oversight required?** Yes, technician verifies panel condition prior to manual cleaning [INFERENCE].

### Component 2: Short-Term Generation Yield Forecaster
1. **What exact problem does AI solve?** Forecasts expected solar energy generation for the next 1-3 hours to optimize load shedding schedules in advance [INFERENCE].
2. **What is the input?** Past 6 hours of rolling hourly average irradiance, temperature, and power output [INFERENCE].
3. **What is the output?** Predicted Power Output ($\text{Watts}$) for hour $t+1, t+2, t+3$ [INFERENCE].
4. **Why can a simpler rule/system not solve it?** Solar irradiance fluctuations due to moving cloud fronts exhibit complex time-series non-linear patterns that moving averages miss [RESEARCHED].
5. **What data is required?** Hourly weather and generation time-series datasets (e.g. Kaggle / NREL NSRDB) [RESEARCHED].
6. **How will it be evaluated?** Mean Absolute Error (MAE) and Root Mean Square Error (RMSE) in Watts [INFERENCE].
7. **What happens when it is wrong?** Microgrid falls back to instant SoC battery threshold rules for load shedding [INFERENCE].
8. **Does it require training?** Yes, pre-trained Quantized LSTM / MLP neural network [INFERENCE].
9. **Does it require fine-tuning?** No [INFERENCE].
10. **Does it require RAG?** No [INFERENCE].
11. **Does it require computer vision?** No [INFERENCE].
12. **Does it require speech processing?** No [INFERENCE].
13. **Does it require forecasting?** Yes, time-series forecasting [INFERENCE].
14. **Is human oversight required?** No, automated advisory for load scheduler [INFERENCE].

### Local Storage Schema (SPIFFS / Flash Ring Buffer)

```sql
-- Local Telemetry Table Structure (Stored in SPIFFS Flash Memory)
CREATE TABLE microgrid_telemetry (
    timestamp INTEGER PRIMARY KEY, -- UNIX Timestamp (seconds)
    pv_voltage REAL NOT NULL,      -- Solar Panel Voltage (Volts)
    pv_current REAL NOT NULL,      -- Solar Panel Current (Amperes)
    bat_voltage REAL NOT NULL,     -- Battery Bank Voltage (Volts)
    bat_current REAL NOT NULL,     -- Battery Charge/Discharge Current (A)
    bat_soc INTEGER NOT NULL,      -- Battery State of Charge (%)
    temp_c REAL NOT NULL,          -- Ambient / Cell Temperature (Celsius)
    azimuth_angle INTEGER NOT NULL,-- Servo Motor Azimuth Position (Degrees)
    tilt_angle INTEGER NOT NULL,   -- Servo Motor Tilt Position (Degrees)
    load1_state INTEGER NOT NULL,  -- Critical Load Relay (1=ON, 0=OFF)
    load2_state INTEGER NOT NULL,  -- Non-Critical Load Relay (1=ON, 0=OFF)
    synced_flag INTEGER DEFAULT 0  -- Cloud Sync Status (0=Pending, 1=Synced)
);
```

### Caching, Synchronization & Retry Strategy
* **Circular Ring Buffer Management:** Flash memory writes are allocated to a 1MB SPIFFS ring buffer partition supporting up to 86,400 record entries (24 hours at 1 Hz, or 5 days at 5-minute sampling intervals) [INFERENCE]. Older synced records are automatically overwritten if flash capacity reaches 90% [INFERENCE].
* **Network Availability Check:** ESP32 Core 1 executes a background ping / MQTT heartbeat task every 30 seconds [INFERENCE].
* **Batch Synchronization:** Upon Wi-Fi connection establishment, Core 1 queries un-synced records (`WHERE synced_flag = 0`), bundles them into JSON arrays of 50 records per MQTT packet, and transmits to MQTT broker [INFERENCE].
* **Exponential Backoff:** If MQTT publishing fails or socket times out, retry delay doubles ($2s \rightarrow 4s \rightarrow 8s \rightarrow \dots \rightarrow \text{max } 300s$) to conserve system power and prevent network flooding [RESEARCHED].
* **Bandwidth Optimization:** Data payloads use short JSON key names (`{"t":1725530000,"pv_v":18.4,"pv_c":2.1,"soc":85}`) or binary CBOR encoding, reducing transmission payload size by up to 60% [RESEARCHED].

### Offline UX Strategy
* **Local Access via SoftAP Mode:** When no external network exists, the ESP32 hosts its own local Wi-Fi Access Point (`Aegis-Grid-AP`) [RESEARCHED]. Technicians connect using a mobile browser to `http://192.168.4.1` to view real-time gauges, download CSV logs directly from flash, and manually trigger panel positioning [RESEARCHED].
